# Security rules

## MANDATORY for any changes in the orchestrator

Security mechanisms must not unnecessarily limit the orchestrator’s functionality or degrade the user experience. When choosing between different approaches, priority is given to preserving existing capabilities, usability, and predictable behavior. Restrictions are introduced only when required by significant risks or mandatory requirements, and then only as the least restrictive solution that provides the necessary level of protection. **This is a first-class requirement, not a soft preference — do not silently trade functionality away for isolation.**

Every agent, check, scanner, and tool process must receive its environment through `build_child_env(SecurityConfig)`: strict isolation means `allowed_environment` plus `extra_environment`, while advanced mode means the parent environment minus names loaded from `.worc/.env`, with assignments applied last. Orchestrator-owned `git`/`gh` must instead use `build_git_env`/`build_helper_git_env` at either mode value — the allowlist, then a **whitelist** over the `GIT_*`/`GH_*`/`GITHUB_*` namespace (only `GIT_CONFIG_GLOBAL` and the two token names pass, so a retargeting variable a future release invents is closed by default), then the named scrub, then the unconditional hardening pins. Do not reconstruct either environment at a call site, and do not add a name to that whitelist without saying in the comment why it cannot move where a call goes.
