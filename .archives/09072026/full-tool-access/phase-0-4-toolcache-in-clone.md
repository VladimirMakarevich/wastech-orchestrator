# Фаза 0.4 — кэши тулчейнов внутрь клона

Status: **implemented 2026-08-18** (AC0.4.1–AC0.4.6 зелёные, включая живую пробу) Date: 2026-08-13 Owner: Vladimir Makarevich Требования: Т0.4 из [requirements-step-0.md](requirements-step-0.md) `schema_version`: без изменения Зависимости: [0.2](phase-0-2-extra-environment.md) — фаза стоит на её механизме

Фаза, ради которой Шаг 0 может закрыть часть Шага 2. `dotnet build`, `cargo build` и `npm ci` падают не потому, что утилита запрещена, а потому что им нужен `~/.nuget/packages`, `~/.cargo`, `~/.npm` — запись за пределами клона, которую песочница не даёт. Если через `extra_environment` перенаправить кэши **внутрь** клона, необходимость в записи наружу для них исчезает: клон писабелен для `workspace-write` узла, а `git clean` оркестратор не запускает (ни одного вызова в `src/`), так что кэш переживает задачи.

```yaml
security:
  extra_environment:
    NUGET_PACKAGES: "/Users/u/repos/target/.toolcache/nuget"
    CARGO_HOME: "/Users/u/repos/target/.toolcache/cargo"
    npm_config_cache: "/Users/u/repos/target/.toolcache/npm"
    GOMODCACHE: "/Users/u/repos/target/.toolcache/go"
```

## Что делаем

**1. Валидатор: служебные пути неперекрываемы, проверка в два уровня.** Значение `extra_environment` не может пересекаться ни в одну сторону с `.git`, `.worc`, `tasks/`, exchange, env-файлом, `denied_read_paths` и любым путём `InternalDenyPolicy` ([`runtime_layout.py:126`](../../../src/wastech_orchestrator/runtime_layout.py)) — приватным и контрольным home, `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, замороженными бандлами. Нельзя ни указать родителя защищённого каталога, ни каталог внутри него.

**Решение владельца 2026-08-13 — уровни разнесены:** лексическое сравнение (без обращения к диску) живёт в `_validate_security` ([`validation.py:326`](../../../src/wastech_orchestrator/config/validation.py)) и даёт одинаковый вердикт на любой машине; канонизация — резолв symlink/junction/reparse, регистр Windows, drive-letter и UNC-алиасы — живёт в `worc preflight`, потому что обязана трогать файловую систему. В первоначальном черновике канонизация стояла в валидаторе, и это противоречило разделению, принятому в [0.1](phase-0-1-allowed-environment.md): вердикт по конфигу зависел бы от того, есть ли на этой машине ссылка.

**1a. Что считается путём.** Значение разбирается по `:` и `;` на любом host с сохранением Windows drive prefix, и путём считается абсолютный или `~`-относительный **элемент**. Unsplitted значение остаётся collision-кандидатом для одиночного foreign-platform пути, но не становится ignore-правилом, если это список. Значения без путей (`"1"`, `"C.UTF-8"`) не проверяются и не резолвятся.

**1b. Поправки, найденные при реализации.** Четыре, и первая меняет объём пункта 1.

1. **Лексический уровень не может покрыть host-resolved roots.** Provider homes и явный `--env-file` проверяются в preflight/task-start с точными labels. `denied_read_paths` не сводится к фиксированному префиксу: concrete assigned path сопоставляется реальным glob matcher'ом, поэтому leading `**` работает, а `conf/*.yaml` не запрещает весь `conf/`.
2. **Host `os.pathsep` не выбирает семантику.** Оба разделителя разбираются всегда, Windows drive colon не рвётся; whole value сохраняется только для collision detection одиночного foreign-platform пути.
3. **Прецедент был указан не тот.** Идемпотентную правку `.git/info/exclude` уже делает `GitManager.ensure_runtime_excludes` — именно она пишет в clone-local exclude, тогда как `append_runtime_excludes` правит **трекаемый** `.gitignore` (это установочный путь). Реализация повторяет первую: новая модульная `ensure_path_excluded(repo_root, target)` рядом с `_git_path_ignored`, потому что звать её нужно из preflight, у которого нет собранного `GitManager`.
4. **Относительный `repo.local_path` оставляет лексический уровень инертным.** Config-производные пути тогда относительные и ни с одним абсолютным значением не сравниваются. Это не дефект: резолвить их пришлось бы относительно рабочего каталога процесса, то есть снова получить host-зависимый вердикт. `worc install` пишет разрешённый git-root, поэтому случай возникает только на плейсхолдере шипнутого шаблона (`./workspace/repo`), а preflight резолвит обе стороны и так.

**2. Игнорирование кэша — обязанность оркестратора.** Если путь-значение указывает внутрь `repo.local_path`, оркестратор идемпотентно дописывает его в **`.git/info/exclude`** целевого репо и проверяет результат через `git check-ignore -q`; preflight ставит `ok = False` только если после этого путь всё ещё не игнорируется. Клона нет на диске — шаг пропускается.

**Решение владельца 2026-08-13**, вместо черновикового «оператор обязан добавить в `.gitignore`». Причины три. `.gitignore` — файл целевого репо, и агент с `workspace-write` может его переписать, а `.git/info/exclude` лежит внутри `.git`, куда агенту запрещено писать и песочницей, и write-guard'ом. Tracked-файл чужого репо не трогается — ни diff, ни шума в PR. И обе части уже написаны: `_git_path_ignored` ([`git_manager.py:182`](../../../src/wastech_orchestrator/git_manager.py)) — готовая обёртка над `check-ignore`, а `append_runtime_excludes` ([`git_manager.py:210`](../../../src/wastech_orchestrator/git_manager.py)) — работающий прецедент того, как оркестратор сам идемпотентно чинит ignore-правила при установке.

Отклонён вариант «исключать кэш pathspec'ом при стейджинге», как для `.worc/` (`RUNTIME_EXCLUDED_DIRS`): он прячет файлы от коммита, но не от `git status`, поэтому детект дрейфа рабочего дерева всё равно их увидит, и исключение пришлось бы не забыть в каждом месте стейджинга — включая прямой `git add -A` ([`git_manager.py:1727`](../../../src/wastech_orchestrator/git_manager.py)).

**3. Путь наружу клона — WARN только в strict mode.** Там опечатка или переехавший клон дают путь, куда песочница писать не даст, и сборка падает с ошибкой прав. Advanced mode разрешает outside-clone writes и не печатает ложное предупреждение.

**3a. Поправка при реализации: в тексте предупреждения «Шага 2» нет.** [coding-style.md](../../../.agents/rules/coding-style.md) прямо запрещает бэклоговые идентификаторы в операторских строках — читателю без этого документа «Шаг 2» ничего не говорит, а документ переживёт не всякий мерж. Смысл требования сохранён целиком: строка объясняет **причину** («узел под песочницей может писать только внутрь клона, поэтому сборка упадёт по правам, и это будет похоже на сломанный тулчейн»), а тест проверяет её, а не ярлык.

**3b. Поправка при реализации: строки preflight не печатают значений.** Первый вариант печатал задетый элемент пути, и это уронило тест Фазы 0.2, который пиннит Т0.2.8 («печатаются только имена»). Правило безопасности сильнее удобства: значение и так лежит у оператора в конфиге, а вторая поверхность для секрета, попавшего туда вопреки гайду, не нужна. Поэтому и preflight, и валидатор называют **переменную** и **задетый служебный путь** (он оркестраторный и единственное, чего оператор не выведет сам), но не значение. Побочная выгода — сообщения стали короче и точнее.

**4. Гайд: рецепт и его границы.** Что перенаправить и куда; `.toolcache/` — рекомендуемое имя (соглашение гайда, код на имя не завязан); путь **не** под `.worc` (каталог целиком в deny-наборе — `control_home` и `private_home` оба указывают туда); на `read-only` узле это не заработает и не должно. Плюс фраза про рост: кэш внутри клона не чистится ничем, retention `.worc/runs` на него не распространяется, автоочистки нет намеренно — удалять чужой кэш опаснее, чем занять диск.

**5. Найдено финальным ревью фаз 0.1–0.4 и исправлено.** Четыре пункта, все — в этой фазе.

1. **Ложный FAIL на эквивалентных написаниях пути.** «Внутри клона?» решалось по резолвнутым путям, а дописывание правила — по сырым строкам, поэтому символическая ссылка в корне клона (на macOS достаточно чего угодно под `/tmp`, который ведёт в `/private/tmp`) давала `assigned-paths: FAIL` на полностью годном конфиге, да ещё с неверной причиной («трекаемый путь или negation-правило»). Обе стороны теперь резолвятся, и функции согласованы по построению.
2. **`..` обходил лексический уровень.** `<клон>/.toolcache/../.worc/x` не имеет общего компонентного префикса с `<клон>/.worc` и проходил валидацию; ловил его только канонизирующий уровень — то есть host-зависимый вердикт там, где требование просит host-независимый. Лексический уровень теперь сворачивает `..` текстово (для symlink'ов это заведомо «неправильно», и именно поэтому правильно здесь: уровень не имеет права спрашивать диск, а канонизирующая половина резолвит по-настоящему).
3. **Гарантия держалась только на preflight.** Ущерб, от которого фаза защищает, наступает на прогоне, а у соседней задачи — игнора `.worc/` — per-run хук есть с самого начала (`_prepare_branch`). Оператор, поправивший путь кэша после preflight, оставался незащищённым. Добавлен `GitManager.ensure_assigned_cache_excludes()` рядом с `ensure_runtime_excludes()`; остаточный неудачный случай там — предупреждение, не отказ задачи (падать из-за ignore-правила чужого репозитория значило бы выдумать новое терминальное состояние).
4. **`worc preflight` больше не «read-only».** Команда так себя объявляла в трёх местах (help, докстринг, корневой README), а фаза заставила её писать в `.git/info/exclude`. Формулировки исправлены: «задачу не запускает», и отдельно назван единственный записываемый файл — untracked, поэтому ни диффа, ни шума в PR.

## Тесты

- Отказы валидатора (лексический уровень): значение внутрь `.worc`, `.git`, `tasks/`, exchange, env-файла, `CODEX_HOME`, `CLAUDE_CONFIG_DIR`; и симметрично — значение-родитель любого из них.
- Значение-список: `PYTHONPATH="/repo/.worc:/x"` отвергается по своему первому элементу.
- Не-путевые значения (`"1"`, `"C.UTF-8"`) проходят валидацию, и ни одного обращения к диску по ним не делается.
- Канонизация (уровень preflight): symlink на защищённый каталог, регистровый вариант на Windows, drive-letter и UNC-алиасы одного пути.
- Preflight и `.git/info/exclude`: правило дописывается, повторный запуск ничего не дублирует, после записи `check-ignore` отвечает «игнорируется»; искусственно сломанный случай — FAIL; клон отсутствует — шаг пропущен и это видно в выводе.
- Путь вне клона → WARN в strict mode, без backlog-identifiers; в advanced mode — ни WARN, ни FAIL.

## Живая проба (часть DoD)

`dotnet build` или `npm ci` внутри турна агента (`workspace-write` узел) с кэшем в `<клон>/.toolcache/`: команда отрабатывает, а `git status` после неё чист. Это единственная проба во всём Шаге 0, которая доказывает исходную потребность целиком — «поправил → собрал → увидел ошибку, не выходя из узла», — поэтому её результат (и время сборки) стоит записать в отчёт о прогоне.

**Выполнена 2026-08-18 на macOS, обе половины доказаны.** Проба разбита на две, потому что профиль Codex `workspace-write` выключает сеть, — значит `npm ci` внутри песочницы не смог бы скачать пакеты по причине, к этой фазе не относящейся.

1. **Половина песочницы — без модели и без денег,** через `codex sandbox` (тот же механизм, которым пользуется isolation smoke). Запись в `<клон>/.toolcache/npm` — **разрешена**; запись в `$HOME/.npm`, то есть в дефолтный кэш npm, — **запрещена** с `PermissionError: Operation not permitted`. Это ровно исходный симптом и ровно его снятие, показанные рядом. Заодно замерено, что `$TMPDIR` и `/tmp` писабельны, а `$HOME`, `$HOME/.cache` и `$HOME/.dotnet` — нет.
2. **Половина тулчейна — настоящие сборки.** Окружение построено продуктовым `build_child_env` по реальному конфигу с `npm_config_cache` внутрь клона: `npm ci` — код 0 за 0.7 с, кэш материализовался в клоне, `git status` после сборки **пуст** (правило `/.toolcache/npm`, которое `worc preflight` сам дописал в `.git/info/exclude`, держит). Отдельно проверен .NET: `dotnet restore` с `NUGET_PACKAGES` внутрь клона положил туда `newtonsoft.json` (24 файла), `dotnet build --no-restore` прошёл за 3.4 с.

Не доказано одно: обе половины **в одном платном турне агента**. Это тот же пробел, что записан за AC0.2.7, и он не про кэши.

**Что проба попутно показала и что попало в гайд:** исключение идёт **по назначенным значениям**, по правилу на путь. Кэш, перенаправленный как-то иначе (флагом командной строки, `.npmrc`, переменной, которой нет в `extra_environment`), правила не получает и в `git status` виден. Отдельная строка в гайде просит назначать каждый кэш, который реально перенаправляется.

**Отрицательный результат, который стоит записать:** попытка тем же `codex sandbox` проверить, держатся ли `deny`-правила сгенерированного профиля (`.worc`, `.git`), **несостоятельна** — контрольный тест показал, что inline-профиль через `-c permissions.worc={…} -P worc` в этом вызове не применялся, и работала только база `:workspace`. Поэтому никаких выводов о write-guard из этой пробы не сделано; ими занимается канарейка продукта, а не эта фаза.

## Риск и откат

Риск не в записи, а в diff: незаигноренный кэш ломает задачу на гейте, который к кэшу отношения не имеет, и причина будет выглядеть как «агент нагенерил мусор». Его снимает пункт (2) — и снимает сильнее черновика, потому что правило в `.git/info/exclude` агент снять не может, а `.gitignore` мог бы. Второй, менее очевидный: кэш в клоне переживает задачи, то есть между задачами остаётся состояние, которое агент прошлой задачи мог испортить, — это принимается осознанно, ровно за то же, за что кэш и заводится. Откат — убрать перенаправление из `extra_environment`; тулчейны вернутся к своим путям в `$HOME` и снова упрутся в песочницу, то есть в исходную задачу Шага 2.

## Поправка follow-ups 2026-08-20

Path-list разбирается по `:` и `;` на любом host с сохранением Windows drive prefix; несоставное значение остаётся collision-кандидатом, но целая строка списка никогда не пишется в `.git/info/exclude`. `denied_read_paths` проверяется реальным glob-match'ем: ведущий `**` не теряется, а `conf/*.yaml` не расширяется до всего `conf/`. Helper git получает caller `SecurityConfig`. Host-aware preflight и task-start gate различают env-file и provider home в сообщении и повторяют canonical collision check после правки конфига. Outside-clone WARN существует только при strict isolation; advanced mode разрешает этот путь. Успешный task-start repair и его warning-only failure покрыты package-log тестами. Остаточный пробел записан явно: protected set assigned-path gate знает `<clone>/.git`, но пока не резолвит отдельный actual gitdir/common-dir linked worktree; этот случай не считается доказанным ни Windows/UNC-тестами, ни обычным клоном.

## Что эта фаза закрывает в Шаге 2

После неё Шаг 2 (`security.extra_writable_paths`) нужен только для того, что перенаправить **нельзя**: утилита с зашитым путём или кэш, который оператор не хочет держать в клоне. Проверить это стоит явно — списком того, что после Фазы 0.4 всё ещё не работает, — и этот список становится входом в решение «открывать ли Шаг 2».

**Список по состоянию на 2026-08-18.** Разделён по тому, чем подтверждён каждый пункт.

_Закрыто этой фазой (проверено живьём):_ кэш npm (`npm_config_cache`) и пакеты NuGet (`NUGET_PACKAGES`) — обе сборки прошли с кэшем в клоне, диффа не оставили.

_Закрыто без Шага 2 и без этой фазы (замерено):_ временные каталоги. `$TMPDIR` и `/tmp` писабельны под `workspace-write`, поэтому утилита, которой нужен только скрэтч, ни в чём не нуждается.

_Ожидается закрытым тем же рецептом, но живьём не проверено:_ остальные тулчейны со документированной переменной перенаправления — `CARGO_HOME`, `RUSTUP_HOME`, `GOMODCACHE`/`GOCACHE`, `PIP_CACHE_DIR`, `GRADLE_USER_HOME`, `DOTNET_CLI_HOME`, `npm_config_prefix`. Механизм тот же, что у проверенных двух; отдельная проба каждому не делалась.

_Остаётся за Шагом 2:_

1. **Общий кэш на несколько клонов.** Рецепт принципиально даёт кэш **на клон**: у двух клонов одного репозитория будут две копии, то есть двойной диск и повторное скачивание. Выразить «один кэш на всех» нельзя, и это не обходится ничем, кроме записи наружу.
2. **Утилита с зашитым путём и без переменной.** Категория, которую предполагает само требование; конкретного примера в этой пробе не нашлось, поэтому пункт остаётся открытым, а не подтверждённым.
3. **Оператор, который не хочет держать кэш в клоне** — по политике или потому, что клон живёт на медленном/сетевом диске. Это не техническое ограничение, а отказ от рецепта, и он тоже ведёт в Шаг 2.

Вывод для решения «открывать ли Шаг 2»: исходная потребность, из которой Шаг 2 вырос («сборка не идёт, потому что кэшу негде лежать»), закрыта. Остаток — про экономию диска и про редкие утилиты, то есть повод куда слабее исходного.
