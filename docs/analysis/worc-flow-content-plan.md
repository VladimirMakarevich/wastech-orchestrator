# Wastime Journey — worc flow: проработанный план и роли

> Рабочий документ. Развивает исходный инвестигейт [worc-flow-content.md](worc-flow-content.md) и адаптирует его под реальную задачу: не «сделать книгу с нуля», а **шаг за шагом дорабатывать уже существующую зрелую историю** [\_wastime_journey.md](../../../wastime-app-content/mobile/roadmap%20%28raw%20and%20working%20data%29/_wastime_journey.md) — улучшать, убирать лишнее, добавлять недостающее, выкристаллизовывать каждую главу, а затем собрать всё в единую книгу внутри приложения.
>
> Документ грунтован на исходном коде оркестратора (движок flow, роли-эвалуаторы, память, политики) — все утверждения про «что можно сделать конфигом, а что требует кода» проверены по коду и помечены ссылками на файлы.

---

## 0. Главный вывод (TL;DR)

**MVP этого флоу не требует ни одной строчки изменений в оркестраторе.** Всё делается операторской конфигурацией в репозитории контента (`wastime-app-content`):

- новый `task_type` = просто новый YAML-файл в `<repo>/.worc/flows/` (`registry.py` резолвит флоу по имени файла, dispatch-таблицы нет);
- весь граф узлов (`agent` / `evaluator` / `publish`), рёбра, циклы доработки, бюджеты — данные в YAML;
- все роли (аналитик, архитектор, автор, критик, валидатор, редактор, сборщик) — это markdown-промпты, а узлы передают результат друг другу через переменную `{<node_id>_path}`;
- детерминированный гейт качества (лимиты символов, число абзацев, запрет AI-паттернов) на старте делается скриптом в репозитории контента, который запускается штатным чекером `command_profile` — **без нативного чекера в оркестраторе**;
- деливери — правка существующих `.md`-глав «на месте» (`output_policy: code_change`), публикация — PR на главу (`publishing: documentation_pull_request`) или локальный коммит (`local_artifact` / `none`).

Изменения в оркестраторе (нативный чекер ограничений, тюнинг циклов, курирование Story Bible через память) — это **необязательный V2**, который повышает переносимость и качество, но не блокирует старт. Список — в §8.

Это сознательно минималистичный путь: начать можно уже сейчас, на одной пилотной главе.

## 1. Переосмысление задачи: чем реальность отличается от исходного инвестигейта

Исходный [worc-flow-content.md](worc-flow-content.md) описывает классическую фабрику «превратить приложение в историю с нуля»: смыслы → структура → черновик → критика → сборка. Это хорошая рамка, но реальная задача другая, и роли надо сдвинуть.

**1.1. Это не greenfield, а редакторская доработка.** Контент уже существует и он зрелый: 18 Parts + Bonus-части, у большинства статус `RU ready`, есть готовые тексты (см. [01_introduction_towatime_app_ru.md](../../../wastime-app-content/mobile/roadmap%20%28raw%20and%20working%20data%29/01_introduction_towatime_app_ru.md)). Значит «Автор глав» из инвестигейта превращается в **Редактора-переработчика**: его глаголы — _улучшить, сократить лишнее, добавить недостающее, разбить перегруженную страницу, выровнять ритм_ — а не «написать сцену с нуля».

**1.2. Story Bible уже написан.** Файл [\_wastime_journey.md](../../../wastime-app-content/mobile/roadmap%20%28raw%20and%20working%20data%29/_wastime_journey.md) — это фактически готовая «библия проекта»: цель, тон повествования, три типа голоса, структура контента, ограничения, карта переходов между частями, требования к качеству, запреты. «Нарративный архитектор» из инвестигейта не строит структуру заново — он **поддерживает и применяет** этот документ. Он же — авторитетный источник правил для всех остальных ролей (см. §7).

**1.3. Континуитет между главами уже формализован.** В \_wastime_journey.md есть таблица переходов основного маршрута и Bonus-частей («после X логично перейти к Y, потому что…»). Роль «континуитет» не изобретает связи — она **проверяет, что доработанная глава по-прежнему стыкуется с соседями** по этой карте.

**1.4. Жёсткие механические ограничения — это детерминированный гейт, а не работа для LLM.** В спецификации есть буквальные лимиты, которые нельзя доверять «на глаз» модели:

- целевой объём мобильной страницы `####` = 500–800 символов, максимум 800 (для EN-версии, см. 1.6);
- максимум 3 абзаца на страницу; максимум 1 Title на страницу;
- **строгий запрет AI-паттернов** вида «не X, а Y» («не абстрактная продуктивность, а момент…», «не для суда, а для…») и любых явных LLM-клише.

Это проверяется скриптом (счётчик символов/абзацев, regex на паттерны), а не эвалуатором-моделью. Модель ставится туда, где нужен вкус (сторителлинг, честность, эмоциональная дуга), а не арифметика.

**1.5. Три голоса держатся раздельно по блокам.** Спецификация требует не смешивать в одной странице практико-смысловой, нейтрально-философский и авторско-рефлексивный голоса без необходимости, а разносить их по разным `###`/`####`. При этом **заголовки не должны называть категорию голоса** («Философия», «Как это», «Комментарии автора» запрещены как заголовки). Это отдельное правило и для редактора (соблюдать), и для критика (ловить протечку голосов и «служебные» заголовки).

**1.6. Два языка — две стадии с разными ограничениями.** Рабочий язык смысловой разработки — русский; финальный язык приложения — английский, и EN должна быть **адаптацией, а не переводом**. Важный нюанс: **лимит 500–800 символов относится к EN мобильной странице, а не к RU рабочему файлу** — RU-страницы в готовых главах заметно длиннее (это семантическая разработка). Отсюда:

- **RU-доработка** гейтится структурой/нарративом/голосами/запретом AI-паттернов; жёсткий лимит символов НЕ применяется;
- **EN-адаптация** — отдельная поздняя стадия: адаптирует готовый RU-блок и применяет лимиты 500–800 символов, ≤3 абзаца, ≤1 Title;
- запрет AI-паттернов действует на обоих языках.

**1.7. Есть конечный технический контракт.** В самом конце RU→EN→лимиты идёт подготовка данных для `roadmap_module_contents.json` (`IModuleContent`: pages → data[] с типами text/title). Это финальная сборочная стадия, отдельная от смысловой доработки.

Вывод: роли из инвестигейта остаются осмысленными, но их надо **пересобрать под редактуру существующего + разнести по стадиям (RU → EN → JSON)** и **вынести арифметику из LLM в детерминированный гейт**.

## 2. Как это ложится на движок worc

Что бесплатно (только YAML + промпты), а что потребовало бы кода — проверено по исходникам.

| Возможность | Статус | Где в коде |
| --- | --- | --- |
| Новый `task_type` (новый флоу) | ✅ конфиг, кода не надо | `core/flow/registry.py` — резолв по имени файла в `.worc/flows/`, dispatch-таблицы нет |
| Граф узлов `agent`/`evaluator`/`publish`, рёбра, циклы, бюджеты | ✅ конфиг | `packaged/flows/implementation.yaml` как образец |
| Роли-промпты (markdown) + цепочка узлов `{<node_id>_path}` | ✅ конфиг | `core/flow/prompts.py` (`ALLOWED_PROMPT_VARS`), автопеременная на выход каждого агента |
| Пер-узловые `provider`/`model`/`reasoning`/`network_access`/`when`/`session_scope` | ✅ конфиг | `core/flow/schema.py`, применяется в `engine.py` |
| Роли эвалуаторов (`critic`, `verifier`, любой свой стринг) | ✅ конфиг (свой стринг → дефолтное поведение эвалуатора) | `core/flow/contracts.py:EvaluatorRole`, парс `snapshot.py` |
| `output_policy: code_change` (правка файлов на месте, диф = деливери) | ✅ конфиг | `core/flow/output_policy.py` |
| `publishing: documentation_pull_request` / `local_artifact` / `none` | ✅ конфиг | `core/flow/contracts.py:PublishingPolicy`, `nodes/publish.py` |
| Детерминированный гейт лимитов через `command_profile` + скрипт в репо | ✅ конфиг (скрипт живёт в репо контента) | `nodes/checks.py` (`command_profile` гоняет `checks.command_sets`) |
| Память как хранилище повторяющихся правил между главами (per-repo, durable) | ✅ есть | `memory/` (per-repo, `apply_delta`, промоушен по рекуррентности) |
| Пер-узловое отключение стадии в конкретной задаче (`nodes.<id>.enabled:false`) | ✅ конфиг (санкционированное исключение) | движок |
| **Нативный** детерминированный чекер (`prose_constraints`) | ⛔ нужен код | `_CHECKER_KINDS` (`snapshot.py`), `Literal` (`schema.py`), ветка в `nodes/checks.py` |
| Деливери-путь книги ≠ `docs/research/<id>/{report.md,sources.json}` | ⛔ нужен код при `repository_document` | пути захардкожены в `output_policy.py` → **обходим через `code_change`** |
| Новый `when`-факт (например `config.adapt_en`) | ⛔ нужен код | реестр из 2 фактов в `orchestrator._engine_facts` → **обходим отдельным флоу / `enabled:false`** |
| Новый вид узла / политика публикации / уровень сети / переменная промпта | ⛔ нужен код | закрытые enum'ы |

Из таблицы прямо следует форма MVP: `output_policy: code_change`, `publishing: documentation_pull_request` (или `none`), без `network_policy` (книге веб не нужен), гейт лимитов — скриптом через `command_profile`.

## 3. Архитектура: три флоу вместо одной фабрики

Пользователь работает **по одной главе**, потом собирает книгу. Это естественно раскладывается на отдельные флоу — каждый запускается своей задачей и переиспользуется много раз.

### A. `content_chapter` — доработка одной RU-главы (рабочая лошадка)

Запускается по одной задаче на главу; прогоняется столько раз, сколько есть глав, и повторно — когда глава возвращается на доработку. Именно здесь идёт «улучшить / убрать лишнее / добавить недостающее / выкристаллизовать».

Форма графа копирует проверенную топологию `implementation.yaml` (стадия → детерминированный гейт → эвалуатор с циклом доработки → фикс → публикация):

```
context (agent, read-only)
      ↓                       ← читает главу, её соседей по карте переходов, Story Bible; пишет бриф
revise (agent, workspace-write, editing_lineage)
      ↓                       ← редактирует .md главы на месте по брифу
constraints (checks: command_profile)   ──fail──▶ fix
      ↓ pass
product_accuracy (evaluator: verifier, blocking)  ──rework──▶ fix
      ↓ accept
story_critic (evaluator: critic, blocking)        ──rework──▶ fix
      ↓ accept
style (agent, workspace-write, reasoning: medium)
      ↓
publish (documentation_pull_request | none)
fix (agent, workspace-write) ──▶ constraints  (все циклы возвращаются на детерминированный гейт)
```

Порядок неслучаен: сначала дешёвый детерминированный гейт (арифметика/паттерны), потом дорогие LLM-эвалуаторы (сначала фактическая точность к продукту, затем сторителлинг), в конце — стилевая полировка. Все циклы доработки замыкаются обратно на `constraints`, как `fixing → testing` в implementation-флоу, чтобы фикс не сломал лимиты.

Слой супервизора (константный над флоу, не узел) пишет итоговое резюме по главе и наблюдает шаги; через дельту памяти он копит повторяющиеся уроки («в философских блоках проскальзывает маркетинг», «часто перегружены страницы во второй половине глав») — см. §7.

### B. `content_book` — сборка единой книги (запускается один раз в конце)

Когда критическая масса глав в статусе `Approved`, отдельная задача собирает их в цельный маршрут.

```
assemble (agent, workspace-write)   ← склеивает одобренные главы, единый голос, TOC, вступление/заключение, сглаживает переходы по карте
      ↓
book_critic (evaluator: critic, blocking)  ──rework──▶ book_fix ──▶ assemble
      ↓ accept                              ← сквозная дуга, повторы между главами, единый голос, континуитет
constraints (checks: command_profile)      ── глобально: ни одна страница не превышает лимиты
      ↓ pass
publish
```

### C. `content_translate` — EN-адаптация (позже, отдельная стадия)

Отдельный флоу (а не ветка в A), потому что: другой набор ограничений (жёсткий лимит 500–800 символов), другой характер работы (адаптация, не редактура), и он запускается только когда RU-блок помечен `RU ready`. Разнесение по флоу заодно снимает потребность в новом `when`-факте `config.adapt_en` (который потребовал бы кода).

```
adapt_en (agent, workspace-write)   ← адаптирует RU-блок в EN production-файл (формат Pages EN)
      ↓
constraints_en (checks: command_profile)  ── лимиты 500–800 симв., ≤3 абзаца, ≤1 Title  ──fail──▶ fix_en
      ↓ pass
en_critic (evaluator: critic)  ── адаптация ли это (не буквальный перевод), сохранён ли смысл и тон, нет AI-паттернов
      ↓ accept
publish
```

(Финальная сборка `roadmap_module_contents.json` из EN — это узкий детерминированный шаг; его можно сделать таким же скриптом через `command_profile` или отдельной маленькой задачей. Вне MVP.)

## 4. Роли, адаптированные под задачу

Ниже — итоговый состав. Для каждой роли: назначение, вход → выход, тип узла worc, ключевые запреты, скелет промпта. Роли из инвестигейта, которые в реальности избыточны, схлопнуты (см. примечания).

| Роль | Узел worc | Вход | Выход | Блокирующая? |
| --- | --- | --- | --- | --- |
| **Контекст-разведчик** (континуитет + аналитик + читатель) | `agent` read-only | глава, соседи по карте, Story Bible | бриф главы `{context_path}` | — |
| **Редактор-переработчик** (бывш. «Автор») | `agent` workspace-write | бриф, глава, Story Bible, память | отредактированный `.md` | — |
| **Гейт ограничений** | `checks: command_profile` | рабочее дерево | pass/fail | да (детерминир.) |
| **Валидатор продукта** | `evaluator: verifier` | диф, справочник функций | findings | да |
| **Критик истории** (+ devil's advocate) | `evaluator: critic` | диф, Story Bible | findings | да |
| **Стиль-редактор** | `agent` workspace-write | диф | полированный `.md` | — |
| **Фиксер** | `agent` workspace-write | findings `{review_path}` | правки | — |
| **Сборщик книги** | `agent` (флоу B) | одобренные главы | единый файл книги | — |
| **Продюсер** | супервизор-слой (не узел) | все шаги | резюме + дельта памяти | — |

Примечания к схлопыванию относительно инвестигейта:

- **«Аналитик продукта и смыслов» и «Агент аудитории» слиты в «Контекст-разведчика».** Смыслы уже описаны в Story Bible и главах; отдельный проход по «извлечению смыслов из кнопок» дублировал бы существующий документ. Разведчику остаётся собрать _контекст этой конкретной главы_: что она должна сделать в маршруте, что стыкуется с соседями, что лишнее/недостающее, план блоков по голосам.
- **«Нарративный архитектор» не отдельный узел флоу A**, а владелец Story Bible (§7). На уровне книги его работу делает `book_critic` + `assemble` во флоу B.
- **«Финальный редактор/Сборщик» = флоу B**, а не узел в каждой главе.

### 4.1. Контекст-разведчик (`context`)

Назначение: до любой правки понять роль главы в общем маршруте и наметить работу. Заменяет три «понимающих» агента инвестигейта одним дешёвым read-only проходом.

Вход: `{task_path}` (в задаче названы файл главы и её соседи), Story Bible по `{repo}`-относительному пути, файлы соседних Parts. Выход: короткий бриф в файл — что глава должна оставить у читателя (Purpose/Emotional point), чем стыкуется с предыдущей/следующей по карте переходов, что убрать, чего не хватает, план блоков по трём голосам. Downstream-узлы читают его как `{context_path}`.

Скелет промпта:

```
Ты — контекст-разведчик Wastime Journey. Не редактируй тексты; подготовь бриф для доработки одной главы.
Прочитай главу (см. {task_path}), её Purpose и Emotional point, и — по карте переходов из Story Bible — предыдущую и следующую части.
Story Bible (цель, тон, три голоса, ограничения, карта переходов, запреты): {repo}/mobile/roadmap (raw and working data)/_wastime_journey.md — это авторитетный источник правил.
Верни бриф: (1) что глава должна оставить у читателя; (2) как она стыкуется с соседями и нет ли разрыва; (3) что лишнее/повторяющееся убрать; (4) чего не хватает для полноты мысли; (5) план блоков по трём голосам (практико-смысловой / нейтрально-философский / авторско-рефлексивный) с раздельными ###.
Только анализ. Верни типизированный результат по схеме вывода.
```

### 4.2. Редактор-переработчик (`revise`)

Назначение: ядро флоу. Улучшает существующий текст, убирает лишнее, добавляет недостающее, разбивает перегруженные страницы, разносит голоса по блокам, выкристаллизовывает главу — сохраняя авторский голос и смысл продукта.

Узел: `agent`, `workspace-write`, `session_scope: editing_lineage` (правит на месте, держит контекст правки).

Запреты (в промпт): не переписывать с нуля живой готовый текст; не превращать в рекламу; не перечислять функции списком; не объяснять мораль в лоб; не смешивать три голоса в одной странице; **не использовать паттерн «не X, а Y» и другие явные AI/LLM-клише**; не выносить в заголовки служебные ярлыки голосов.

Скелет:

```
Ты — редактор Wastime Journey. Доработай ОДНУ главу прямо в её файле: улучши, убери лишнее, добавь недостающее, выкристаллизуй.
Бриф доработки: {context_path}. Story Bible (тон, три голоса, ограничения, запреты): {repo}/mobile/roadmap (raw and working data)/_wastime_journey.md.
Правила: одна основная мысль на страницу ####; если мыслей две — делай две страницы; три голоса держи в раздельных ###; заголовки живые, без служебных ярлыков («Философия», «Как это», «Комментарии автора»).
Сохраняй авторский голос, честность и смысл продукта. Это правка живого текста, а не написание с нуля — не выбрасывай работающее.
{?memory_path}Повторяющиеся уроки по этой книге (советуйся, но проверяй по тексту): {memory_path}.{/memory_path}
ЗАПРЕЩЕНО: реклама и «это приложение меняет жизнь»; перечисление функций списком; мораль в лоб; смешение голосов на одной странице; паттерн «не …, а …» и любые явные AI-клише.
Верни типизированный результат по схеме вывода.
```

### 4.3. Гейт ограничений (`constraints`, checks: command_profile)

Назначение: детерминированно поймать нарушения арифметики и паттернов, которые нельзя доверять модели. Это `checks`-узел с чекером `command_profile`, который гоняет `checks.command_sets` — то есть скрипт, лежащий в репозитории контента. Что проверяет — см. §6.

Для RU-флоу (A): ≤1 Title на страницу; структура `##`/`###`/`####` корректна; **regex-скан на AI-паттерны** («не … , а …» и список клише); отсутствие служебных ярлыков в заголовках. Жёсткий лимит символов на RU НЕ применяется. Для EN-флоу (C): дополнительно 500–800 символов на `####` (максимум 800), ≤3 абзаца.

### 4.4. Валидатор продукта (`product_accuracy`, evaluator: verifier)

Назначение: сверить текст с реальными функциями приложения — не исказил ли, не пообещал ли лишнего. Оценивает **только соответствие продукту**, не красоту (запрет из инвестигейта сохранён).

Вход: `{diff_path}` (что изменилось) + справочник функций (`advanced-mobile-app-functions.ru`, `roadmap_outline_en.md`) по `{repo}`-пути. Контракт вывода фиксирован движком (`_FINDINGS_SCHEMA`): массив `findings` с `severity`/`path`/`what`/`fix`. Роль-промпт обязан просить именно этот формат.

Скелет:

```
Ты — валидатор продуктовой точности Wastime Journey. Оцени ТОЛЬКО соответствие текста реальным функциям приложения, не язык и не красоту.
Изменения: {diff_path}. Справочник функций: {repo}/mobile/roadmap (raw and working data)/advanced-mobile-app-functions.ru (и roadmap_outline_en.md).
Ищи: искажение функций; выдуманные возможности; слишком сильные/ложные обещания; места, где история оторвалась от продукта; где продукт описан слишком прямолинейно.
Верни findings по схеме вывода: severity blocking/critical/high — то, что обязательно исправить; medium/low — совет. Для каждого finding задай path, what, fix. Нет замечаний — верни пустой массив findings, не прозу.
```

### 4.5. Критик истории (`story_critic`, evaluator: critic)

Назначение: ломать слабые места сторителлинга. Ловит: где скучно/рекламно/абстрактно; потерян ли герой и дуга; протекли ли голоса; служебные заголовки; оборвана ли связь с соседней главой; хочется ли читать дальше; **AI-клише, которые проскочили мимо regex** (смысловые, не только «не X, а Y»).

Запрет (из инвестигейта): не переписывать текст целиком; каждое замечание — к конкретному месту (`path`/`what`/`fix`).

Скелет:

```
Ты — строгий литературный критик Wastime Journey и адвокат дьявола. Найди слабые места, но не переписывай текст.
Изменения: {diff_path}. Story Bible (тон, три голоса, требования к качеству, запреты): {repo}/mobile/roadmap (raw and working data)/_wastime_journey.md.
Критерии: есть ли история, а не описание; жива ли эмоциональная дуга; не сползает ли в рекламу/пафос; разделены ли голоса; живые ли заголовки (без служебных ярлыков); держится ли связь с соседней главой; хочется ли читать дальше; нет ли смысловых AI-клише.
Верни findings по схеме вывода: blocking/critical/high — обязательно к правке; medium/low — совет. Каждое замечание с path/what/fix. Чисто — пустой массив findings.
```

### 4.6. Стиль-редактор (`style`)

Назначение: полировка языка без смены смысла и сюжета — ритм, тон, переходы, устранение повторов. Как узел `documentation` в implementation-флоу: `workspace-write`, `reasoning: medium` (полировка не требует высокого reasoning, экономит время хвоста).

Запрет: не менять сюжет; не добавлять функции; не менять смысл продукта; не ломать лимиты и разделение голосов.

### 4.7. Фиксер (`fix`)

Применяет замечания эвалуаторов/гейта из `{review_path}` в рабочем дереве. `lineage_affinity: revise` — держит контекст исходной правки. Все рёбра `rework`/`fail` ведут сюда, а он возвращает на `constraints`.

### 4.8. Продюсер = супервизорный слой

Не узел графа (в worc супервизор — константный слой над флоу). Пишет резюме по главе на закрытии задачи и наблюдает шаги. Через дельту памяти копит повторяющиеся уроки книги (см. §7). `emit_follow_ups` — код-ориентированная опция — для контент-флоу **не включаем**.

## 5. Итерации, волны и статусы главы

Инвестигейт предлагает волны — оставляем идею, но привязываем к реальному циклу worc: каждая глава = задача во флоу A, статусы главы ведём в рабочем индексе \_wastime_journey.md.

Жизненный цикл одной главы (расширяет `Draft → Reviewed → Rewritten → Validated → Edited → Approved` из инвестигейта и мэппится на узлы):

```
RU draft
   → (флоу A: context → revise)                Rewritten
   → (constraints pass)                          Constrained
   → (product_accuracy accept)                   Validated
   → (story_critic accept)                        Reviewed
   → (style)                                      Edited
   → человек принимает PR                         RU ready   ← ставим в индексе \_wastime_journey.md
   → (позже, флоу C)                              EN adapted
   → (JSON-сборка)                                Shipped
```

Порядок запуска (волнами, но реализованными как последовательность задач, а не одновременный залп):

1. **Пилот.** Одна глава через весь флоу A (§9). Цель — проверить, что стиль/смысл/структура держатся и роли не дублируют друг друга.
2. **Основной маршрут.** Крупные Parts по одной задаче на главу; каждая — свой PR, свой ревью человеком.
3. **Bonus-части** тем же флоу (они короче и слабее по статусу — многие `RU draft`).
4. **Сборка книги** (флоу B), когда основной маршрут в `RU ready`.
5. **EN-адаптация** (флоу C) по готовым RU-блокам.
6. **JSON-сборка** для приложения.

Правило владельца (из инвестигейта, сохраняем): **не начинать с полной книги — сначала одна пилотная глава.**

## 6. Детерминированный гейт качества (что и как проверять)

Ключевое решение: арифметику и паттерны проверяет **скрипт**, не модель.

**Что проверять:**

- RU (флоу A): ≤1 Title на страницу; валидная иерархия `##`→`###`→`####`; `Purpose`/`Emotional point` присутствуют и не являются пользовательскими страницами; **regex-скан AI-паттернов**: `не\s+…\s*,\s*а\s+…` и список явных клише; заголовки не содержат служебных ярлыков (`Что это`, `Философия`, `Как это`, `Использование`, `Комментарии автора`).
- EN (флоу C): всё выше + длина `####` в диапазоне 500–800 символов (жёсткий максимум 800); ≤3 абзаца на страницу.

**Как (MVP, без кода в оркестраторе):** маленький скрипт (`scripts/check_journey.py` в репо контента), который парсит изменённые `.md`, считает символы/абзацы/Title, гоняет regex и выходит с ненулевым кодом при нарушении. Он регистрируется как `checks.command_sets` и запускается штатным чекером `command_profile` — это ровно тот механизм, которым implementation-флоу гоняет линт/тесты. Ноль изменений в оркестраторе.

**Как (V2, с кодом):** нативный чекер `prose_constraints` в оркестраторе — см. §8.1. Плюсы: переносимость между репозиториями, структурированные findings, единообразие с `citation`/`dependency_scan`. Это апгрейд, не блокер.

## 7. Story Bible и память: два разных канала

Тонкость, важная для качества (проверено по коду памяти).

**Story Bible — это закоммиченный файл в репозитории**, а не запись в подсистеме памяти. \_wastime_journey.md уже играет эту роль. Роли ссылаются на него по `{repo}`-относительному пути прямо в промпте (как `synthesis.md` в deep_research ссылается на свои файлы). Причина: пакет памяти `{memory_path}` **капается по объёму и ранжируется** (движок отбрасывает низкоранговые записи, чтобы влезть в лимит), а закоммиченный файл читается целиком и авторитетно. Для «канона, который всегда должен быть под рукой» нужен файл, а не память.

**Подсистема памяти — для повторяющихся уроков между главами.** Она per-repo и durable (переживает задачи; промоушен в long-term по рекуррентности через `apply_delta`). Сюда естественно ложатся advisory-уроки, которые критик/валидатор находят снова и снова: «в философских блоках сползает в маркетинг», «во второй половине глав перегружены страницы», «повторяется метафора X». Супервизор пишет их дельтой на закрытии задачи; на следующих главах они подмешиваются в пакет `{memory_path}` редактора и критиков (после фикса F31 эвалуаторы тоже получают пакет памяти).

Итог: **канон → файл; накопленные наблюдения → память.** Не путать каналы.

## 8. Улучшения оркестратора для качества (приоритизировано)

MVP работает без них. Ниже — что реально повышает качество/удобство, от самого ценного к необязательному. Когда владелец решит строить — завести строками в [follow_ups.md](../backlog/follow_ups.md).

### 8.1. Нативный чекер `prose_constraints` (средний приоритет, нужен код)

Сейчас гейт лимитов — скрипт в репо контента через `command_profile`. Нативный чекер даёт переносимость и структурированные findings. Объём: добавить имя в `_CHECKER_KINDS` (`snapshot.py`) и `Literal` (`schema.py`); модуль `core/flow/checkers/prose_constraints.py`; ветку в `nodes/checks.py`. Конфигурировать лимиты (мин/макс символов, макс абзацев, regex-набор) через параметры чекера. **Строить только если появится второй репозиторий-книга** — иначе скрипт-через-`command_profile` достаточен (принцип YAGNI).

### 8.2. Калибровка блокирующих циклов доработки (высокий приоритет, только конфиг)

Прямой перенос урока **F42** (в follow_ups.md): один блокирующий эвалуатор способен уйти в 7 циклов rework и сожрать время. Для контента риск тот же (сторителлинг субъективен). Меры — **только конфигом флоу**:

- поставить `max_rework_per_stage` на `story_critic` (например 2–3);
- держать `product_accuracy` (фактическая точность) блокирующим, а стилистику — в **отдельном НЕблокирующем** эвалуаторе, чтобы вкусовые придирки не блокировали публикацию (findings уходят в advisory);
- в промптах критиков просить **батчить все замечания одного прохода в один вердикт** и явно разделять blocking-обязательное vs advisory-совет.

### 8.3. Курирование Story Bible / стиля через `worc memory` (низкий приоритет, только использование)

Высший тир доверия памяти — `human-curated` (оператор написал/одобрил), он durable и ранжируется выше всех. Владелец может через `worc memory` закрепить несколько ключевых правил стиля как human-curated уроки — они будут подмешиваться во все главы поверх файла-канона. Кода не требует, только дисциплина использования.

### 8.4. Что НЕ нужно (сознательные отказы)

- **Гибкий деливери-путь для `repository_document`** — не нужен: `code_change` правит главы на месте, диф и есть деливери. `repository_document` с его захардкоженными `docs/research/<id>/{report.md,sources.json}` для книги не подходит и не требуется.
- **Новый `when`-факт `config.adapt_en`** — не нужен: EN — отдельный флоу C; на выключение стадий есть санкционированный `nodes.<id>.enabled:false`.
- **Новый вид узла** — не нужен: хватает `agent`/`evaluator`/`checks`/`publish`.

## 9. MVP-план запуска

1. **В репо контента** создать `.worc/flows/content_chapter.yaml` (скелет — §10) и каталог `.worc/flows/content_chapter/*.md` с промптами семи ролей (§4).
2. Написать `scripts/check_journey.py` (§6) и прописать его в `checks.command_sets`.
3. Убедиться, что \_wastime_journey.md доступен ролям по `{repo}`-пути (канон) и есть справочник функций для валидатора.
4. **Пилот на одной главе.** Кандидат: Bonus-часть в статусе `RU draft` (например Part 3 «Home Page…») — низкий риск, видно, добавляет ли флоу ценность на слабом черновике; либо Part 1 (готовая) — видно, не портит ли флоу зрелый текст. Рекомендация: начать со слабого черновика (флоу должен _улучшать_, и на черновике это нагляднее).
5. Прогнать, прочитать PR/диф, оценить: держатся ли смысл, голос, структура; не дублируют ли роли друг друга; адекватны ли findings критиков.
6. По результату подкрутить **промпты и `max_rework_per_stage`** (не код). Затем масштабировать на маршрут.
7. Позже — флоу B (сборка) и C (EN).

Замечание про анализ прогонов: в оркестраторе есть скилл `/analyze-task-run` — после пилота он разберёт логи/диф/аудит и подскажет, какую роль/узел/бюджет крутить.

## 10. Скелет `content_chapter.yaml` (для репо контента)

Иллюстративный минимум (пути ролей и `command_sets` — под факт. структуру репо):

```yaml
flow:
  name: content_chapter
  task_type: content_chapter
  permission_ceiling: workspace-write
  output_policy: code_change # правим главы на месте, диф = деливери
  publishing: documentation_pull_request # PR на главу; для локальной работы → none

  defaults:
    evaluator:
      { session_scope: fresh_disposable, permission_profile: read-only }

  nodes:
    - id: context
      kind: agent
      role_file: content_chapter/context.md
      session_scope: fresh_disposable
      permission_profile: read-only
    - id: revise
      kind: agent
      role_file: content_chapter/revise.md
      session_scope: editing_lineage
      permission_profile: workspace-write
    - id: constraints
      kind: checks
      checker: command_profile # гоняет scripts/check_journey.py через checks.command_sets
    - id: product_accuracy
      kind: evaluator
      role: verifier
      role_file: content_chapter/product_accuracy.md
      blocking: true
      max_rework_per_stage: 2
    - id: story_critic
      kind: evaluator
      role: critic
      role_file: content_chapter/story_critic.md
      blocking: true
      max_rework_per_stage: 3 # F42: держим потолок
    - id: style
      kind: agent
      role_file: content_chapter/style.md
      session_scope: editing_lineage
      lineage_affinity: revise
      permission_profile: workspace-write
      reasoning: medium
    - id: fixing
      kind: agent
      role_file: content_chapter/fixing.md
      session_scope: editing_lineage
      lineage_affinity: revise
      permission_profile: workspace-write
    - id: publish
      kind: publish
      policy: documentation_pull_request

  edges:
    - { from: context, to: revise }
    - { from: revise, to: constraints }
    - { from: constraints, to: product_accuracy, outcome: pass }
    - { from: constraints, to: fixing, outcome: fail, loop: constraint_fix }
    - { from: product_accuracy, to: story_critic, outcome: accept }
    - {
        from: product_accuracy,
        to: fixing,
        outcome: rework,
        loop: accuracy_fix,
      }
    - { from: story_critic, to: style, outcome: accept }
    - { from: story_critic, to: fixing, outcome: rework, loop: critic_fix }
    - { from: fixing, to: constraints }
    - { from: style, to: publish }

  budgets:
    global_fix_iterations: 20
    constraint_fix: 8
    accuracy_fix: 6
    critic_fix: 6

  supervisor:
    role_file: content_chapter/supervisor.md
    finalize_role_file: content_chapter/summary.md
    # emit_follow_ups НЕ включаем — это код-ориентированная опция
```

Каталог промптов рядом с YAML: `.worc/flows/content_chapter/{context,revise,product_accuracy,story_critic,style,fixing,supervisor,summary}.md`.

## 11. Открытые вопросы (решения за владельцем)

1. **Пилотная глава:** слабый Bonus-черновик (нагляднее эффект «улучшения») или готовый Part 1 (проверка «не портит ли зрелый текст»)? Рекомендация — слабый черновик.
2. **Публикация:** PR на каждую главу (`documentation_pull_request`, ревьюишь диф в GitHub) или локальные коммиты (`none`/`local_artifact`, без PR)? Для одиночной работы, возможно, локально проще.
3. **Отдельный справочник функций для валидатора** — использовать существующий `advanced-mobile-app-functions.ru` или собрать компактный канон функций специально под валидацию?
4. **Насколько агрессивна редактура готовых глав?** Порог «не трогать работающее» vs «выкристаллизовывать» — задать в промпте `revise` явно (консервативный для `RU ready`, смелее для `RU draft`). Можно параметризовать через два варианта задачи.
5. **Строить ли нативный чекер `prose_constraints` (§8.1) сразу** или жить на скрипте через `command_profile`? Рекомендация — скрипт, пока книга одна.
