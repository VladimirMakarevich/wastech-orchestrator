Ниже — практиная агентная структура для создания **мини-книги по мотивам мобильного приложения**: не просто описание функций, а storytelling вокруг смыслов, пользовательского пути и трансформации.

## Главный принцип

Не делай “много агентов, которые все пишут”. Это быстро превращается в хаос.

Лучше сделать систему, где агенты разделены на роли:

**одни извлекают смыслы → другие строят историю → третьи пишут → четвертые критикуют → пятые улучшают → главный агент собирает финальную версию.**

---

# 1. Базовая структура агентов

## Агент 1: Продюсер / Оркестратор

Это главный агент. Он не пишет всю книгу сам, а управляет процессом.

**Задача:**
держать цель, структуру, дедлайны, качество и передавать задачи другим агентам.

**Что он делает:**

* принимает исходные материалы по приложению;
* формулирует творческий бриф;
* решает, какие агенты подключаются;
* собирает их результаты;
* принимает или отклоняет версии;
* следит, чтобы книга не стала “презентацией функций”.

**Главная инструкция агенту:**

```text
Ты — продюсер и главный редактор проекта мини-книги по мотивам мобильного приложения. 
Твоя задача — управлять командой агентов, превращая функции, пользовательские сценарии и смыслы приложения в цельную storytelling-книгу.

Ты не должен сразу писать финальный текст. Сначала организуй процесс:
1. извлеки суть продукта;
2. определи аудиторию;
3. найди главный конфликт и трансформацию;
4. создай нарративную структуру;
5. делегируй написание;
6. запусти валидацию;
7. собери финальную версию.
```

---

## Агент 2: Аналитик продукта и смыслов

Это агент, который разбирает приложение не как набор кнопок, а как систему смыслов.

**Задача:**
понять, что приложение “обещает” человеку на глубинном уровне.

Например:

* не “трекер привычек”, а “инструмент возвращения контроля над жизнью”;
* не “финансовое приложение”, а “история взросления через отношение к деньгам”;
* не “приложение для сна”, а “путь героя от хаоса к восстановлению”.

**Что он должен извлечь:**

* основные функции;
* какую боль решает каждая функция;
* эмоциональный смысл функции;
* какой момент трансформации она создает;
* какие метафоры можно использовать.

**Формат результата:**

| Функция приложения | Пользовательская боль   | Глубинный смысл    | Возможная сцена в книге          |
| ------------------ | ----------------------- | ------------------ | -------------------------------- |
| Напоминания        | Человек забывает важное | Возврат контроля   | Герой впервые не срывается       |
| Статистика         | Нет ощущения прогресса  | Видимое взросление | Герой видит, что путь был не зря |

**Промпт:**

```text
Ты — аналитик продукта и смыслов. 
Разбери мобильное приложение как систему человеческих потребностей, эмоций и трансформаций.

Не описывай функции технически. Для каждой функции определи:
1. какую боль пользователя она решает;
2. какую эмоцию вызывает;
3. какой глубинный смысл несет;
4. какую сцену или поворот в storytelling она может породить;
5. как эта функция может стать метафорой в мини-книге.
```

---

## Агент 3: Агент аудитории / Читатель

Этот агент защищает интересы будущего читателя.

**Задача:**
понять, для кого книга, зачем ее читать и что человек должен почувствовать после прочтения.

Он отвечает на вопросы:

* кто читатель?
* что его беспокоит?
* почему ему неинтересно читать “про приложение”?
* какая история его зацепит?
* какой стиль будет близок: вдохновляющий, кинематографичный, интимный, деловой, философский?

**Промпт:**

```text
Ты — агент читателя. 
Твоя задача — защищать интересы аудитории.

Посмотри на идею мини-книги глазами человека, который не знает приложение. 
Определи:
1. почему ему может быть интересно читать эту книгу;
2. какие темы его зацепят;
3. что будет скучным или рекламным;
4. какой эмоциональный путь он должен пройти;
5. какие вопросы должны возникнуть у него после каждой главы.
```

---

## Агент 4: Нарративный архитектор

Это один из ключевых агентов.

**Задача:**
превратить смыслы приложения в сюжетную структуру.

Он решает:

* кто герой;
* в чем конфликт;
* какая трансформация происходит;
* какие главы нужны;
* как функции приложения вплетаются в историю;
* где кульминация;
* чем заканчивается книга.

## Возможная модель мини-книги

Лучше всего подойдет структура:

**Проблема → Потеря контроля → Встреча с инструментом → Малые победы → Сопротивление → Перелом → Новая идентичность**

Пример:

1. Мир до приложения
2. Боль героя
3. Первый контакт с новым способом жить
4. Маленькие изменения
5. Срыв или конфликт
6. Понимание главного смысла
7. Новая версия героя

**Промпт:**

```text
Ты — нарративный архитектор. 
На основе анализа приложения создай storytelling-структуру мини-книги.

Тебе нужно определить:
1. главного героя или тип героя;
2. его исходную боль;
3. главный внутренний конфликт;
4. трансформацию героя;
5. структуру глав;
6. где и как функции приложения появляются в истории;
7. финальный эмоциональный эффект книги.

Важно: книга не должна быть рекламной брошюрой. Приложение должно ощущаться как часть пути героя, а не как объект продажи.
```

---

## Агент 5: Автор глав

Это агент, который пишет текст.

Но он должен начинать работу **только после** того, как есть:

* продуктовый анализ;
* портрет читателя;
* нарративная структура;
* стиль;
* план глав.

**Задача:**
писать сцены, главы, переходы, эмоциональные моменты.

**Промпт:**

```text
Ты — автор storytelling-мини-книги. 
Пиши живо, образно и понятно.

Твоя задача — превратить план главы в литературный текст. 
Не объясняй приложение напрямую, а показывай его смысл через действия, эмоции, выборы и изменения героя.

Каждая глава должна содержать:
1. сцену или ситуацию;
2. внутренний конфликт;
3. связь с одной из функций или идей приложения;
4. эмоциональный поворот;
5. короткий вывод или ощущение движения вперед.
```

---

## Агент 6: Критик / Devil’s Advocate

Очень важный агент. Он не пишет, а ломает слабые места.

**Задача:**
найти, где текст скучный, рекламный, неясный, слишком абстрактный или не связан с приложением.

Он проверяет:

* есть ли история, а не просто описание;
* понятен ли герой;
* не слишком ли много “маркетинга”;
* есть ли эмоциональная динамика;
* не потеряны ли функции приложения;
* есть ли смысл читать дальше.

**Промпт:**

```text
Ты — строгий литературный критик и стратег продукта. 
Твоя задача — найти слабые места в тексте мини-книги.

Оцени текст по критериям:
1. есть ли storytelling;
2. есть ли эмоциональная трансформация;
3. не выглядит ли текст как реклама;
4. понятна ли связь с приложением;
5. есть ли конфликт;
6. есть ли сцены, а не только объяснения;
7. хочется ли читать следующую главу.

Дай конкретные замечания и предложи, что улучшить.
```

---

## Агент 7: Валидатор смыслов

Этот агент проверяет, не исказила ли книга суть приложения.

**Задача:**
сравнить текст с исходной идеей приложения.

Он отвечает:

* правильно ли переданы функции?
* не придумали ли лишнего?
* не потеряны ли ключевые смыслы?
* нет ли противоречий?
* не обещает ли книга того, чего приложение не делает?

**Промпт:**

```text
Ты — валидатор смыслов и продуктовой точности. 
Проверь, соответствует ли текст мини-книги исходной идее мобильного приложения.

Тебе нужно найти:
1. искажения функций;
2. потерянные смыслы;
3. слишком сильные или ложные обещания;
4. места, где история оторвалась от продукта;
5. места, где продукт описан слишком прямолинейно.

Верни список проблем и предложи исправления.
```

---

## Агент 8: Редактор стиля

Этот агент делает текст красивым, цельным и читаемым.

**Задача:**
не менять смысл, а улучшать язык.

Он отвечает за:

* ритм;
* тон;
* эмоциональность;
* ясность;
* стиль;
* переходы;
* отсутствие повторов.

**Промпт:**

```text
Ты — литературный редактор. 
Твоя задача — улучшить стиль текста, не меняя смысл.

Сделай текст:
1. более живым;
2. более образным;
3. менее рекламным;
4. более цельным;
5. более легким для чтения.

Сохрани основную структуру, но улучши ритм, переходы и формулировки.
```

---

## Агент 9: Финальный редактор / Сборщик книги

Он собирает все в финальный продукт.

**Задача:**
сделать мини-книгу цельной.

Он проверяет:

* последовательность глав;
* единый голос;
* логические переходы;
* финальное название;
* оглавление;
* вступление;
* заключение;
* послесловие;
* CTA, если нужен.

**Промпт:**

```text
Ты — финальный редактор мини-книги. 
Собери все главы в цельную книгу.

Проверь:
1. есть ли единая история;
2. не повторяются ли идеи;
3. логично ли развивается герой;
4. есть ли эмоциональная кульминация;
5. все ли главы связаны между собой;
6. соответствует ли книга исходному брифу;
7. готова ли она для публикации или презентации.
```

# 3. Минимальная версия команды

Не обязательно запускать сразу 9 агентов. Для начала хватит 5.

## Минимальный набор

1. **Продюсер / Оркестратор**
   Управляет процессом.

2. **Аналитик смыслов**
   Извлекает идеи из приложения.

3. **Нарративный архитектор**
   Создает структуру истории.

4. **Автор**
   Пишет главы.

5. **Критик + Валидатор**
   Проверяет качество, смысл и связь с приложением.

Это уже даст нормальный цикл:

```text
смысл → структура → текст → критика → улучшение
```

---

# 4. Какие артефакты должны создавать агенты

Чтобы процесс не развалился, каждый агент должен отдавать не “размышления”, а конкретный артефакт.

## Главные артефакты

### 1. Product Meaning Map

Карта смыслов приложения.

```text
Функция → боль пользователя → эмоциональный смысл → storytelling-возможность
```

### 2. Reader Persona

Портрет читателя.

```text
Кто читатель?
Чего он хочет?
Чего боится?
Почему ему нужна эта история?
Какой тон ему близок?
```

### 3. Story Bible

Главный документ книги.

```text
Название:
Главная идея:
Герой:
Конфликт:
Трансформация:
Тон:
Метафоры:
Структура глав:
Что нельзя делать:
```

### 4. Chapter Briefs

Задания на главы.

```text
Глава:
Цель главы:
Сцена:
Конфликт:
Смысл приложения:
Эмоция:
Финальный поворот:
```

### 5. Validation Report

Отчет проверки.

```text
Что работает:
Что слабо:
Что рекламно:
Что непонятно:
Что не соответствует приложению:
Что нужно переписать:
```

### 6. Final Manuscript

Финальная мини-книга.

---

# 5. Как должна выглядеть глава

Для storytelling по мотивам приложения я бы использовал такую структуру главы:

```text
1. Сцена
2. Проблема героя
3. Внутреннее напряжение
4. Появление нового действия, привычки или инструмента
5. Маленькая трансформация
6. Связь с функцией приложения
7. Эмоциональный вывод
```

Важно: функция приложения не должна выглядеть как “теперь нажмите кнопку”. Она должна быть частью истории.

Плохо:

```text
В приложении есть функция напоминаний, которая помогает пользователю не забывать задачи.
```

Лучше:

```text
Впервые за долгое время утро не рассыпалось на случайности. Телефон мягко напомнил ему не о задаче — о выборе, который он обещал себе вчера.
```

---

# 6. Цикл улучшения контента

Каждую главу стоит прогонять через такой цикл:

```text
Автор пишет главу
        ↓
Критик находит слабые места
        ↓
Валидатор проверяет связь с приложением
        ↓
Автор переписывает
        ↓
Редактор стиля полирует
        ↓
Продюсер принимает или отправляет на доработку
```

Для каждой главы можно ставить статус:

```text
Draft → Reviewed → Rewritten → Validated → Edited → Approved
```

# 7. Правила для агентов

Вот важные правила, которые нужно дать всей системе.

## Общие правила

```text
1. Не превращать книгу в рекламу приложения.
2. Не перечислять функции без истории.
3. Каждая функция должна быть связана с человеческой болью.
4. Каждая глава должна двигать героя вперед.
5. Текст должен показывать, а не объяснять.
6. Книга должна иметь эмоциональную дугу.
7. Любое улучшение должно сохранять исходный смысл продукта.
```

# 9. Самая сильная схема запуска

Я бы запускал агентов не одновременно, а волнами.

## Волна 1: Понимание

```text
Аналитик смыслов + Агент аудитории
```

Цель: понять, о чем книга на самом деле.

## Волна 2: Архитектура

```text
Нарративный архитектор + Продюсер
```

Цель: создать структуру книги.

## Волна 3: Производство

```text
Автор глав
```

Цель: написать черновик.

## Волна 4: Проверка

```text
Критик + Валидатор
```

Цель: найти слабые места.

## Волна 5: Улучшение

```text
Автор + Редактор стиля
```

Цель: переписать и улучшить.

## Волна 6: Сборка

```text
Финальный редактор + Продюсер
```

Цель: получить готовую мини-книгу.

# 10. Главный системный промпт для всей команды

Можно использовать такой общий промпт как основу:

```text
Мы создаем storytelling-мини-книгу по мотивам мобильного приложения.

Цель книги — не описать функции приложения, а раскрыть его смысл через человеческую историю, конфликт, эмоциональную трансформацию и путь героя.

Каждый агент работает в своей роли и возвращает конкретный результат. 
Агенты не должны дублировать друг друга.

Главные принципы:
1. Сначала смысл, потом текст.
2. Сначала структура, потом главы.
3. Сначала история, потом продукт.
4. Функции приложения должны быть встроены в путь героя.
5. Текст должен быть эмоциональным, но точным.
6. Любая версия проходит критику, валидацию и редактуру.
```

# 11. Рекомендуемая структура мини-книги

Для первой версии я бы сделал 7 глав.

```text
Название: пока рабочее

Глава 1. Мир, который перестал слушаться
Герой сталкивается с хаосом, усталостью, потерей контроля или другой ключевой болью.

Глава 2. Маленький сбой, который стал сигналом
Появляется событие, показывающее, что старый способ жить больше не работает.

Глава 3. Первый новый ритуал
Герой пробует новый подход. Здесь мягко появляется первая функция приложения.

Глава 4. Сопротивление
Герой срывается, сомневается или возвращается к старому поведению.

Глава 5. Данные, которые стали зеркалом
Статистика, прогресс, визуализация или другая функция помогает герою увидеть себя иначе.

Глава 6. Не приложение изменило жизнь
Герой понимает, что инструмент не спасает сам по себе, а помогает ему делать выбор.

Глава 7. Новая версия себя
Финальная трансформация. Приложение становится не главным героем, а тихим спутником новой жизни.
```

# 12. Как я бы настроил MVP-процесс

Для первого запуска не усложняй. Сделай так:

```text
Шаг 1. Загрузи описание приложения, функции, скриншоты, целевую аудиторию.
Шаг 2. Агент смыслов делает карту: функция → боль → смысл → сцена.
Шаг 3. Нарративный архитектор делает Story Bible.
Шаг 4. Продюсер утверждает одну концепцию.
Шаг 5. Автор пишет 1 главу, а не всю книгу.
Шаг 6. Критик и валидатор проверяют эту главу.
Шаг 7. Редактор улучшает.
Шаг 8. Если глава работает — масштабируешь процесс на всю книгу.
```

Не начинай сразу с полной книги. Сначала сделай **одну пилотную главу**. Она покажет, работает ли стиль, смысл и структура.

# 13. Самая важная настройка

У каждого агента должен быть не только промпт, но и **запреты**.

Например:

## Автору запретить:

```text
Не писать рекламные абзацы.
Не перечислять функции списком.
Не объяснять мораль напрямую.
Не использовать слишком общие фразы вроде “это приложение меняет жизнь”.
```

## Критику запретить:

```text
Не переписывать текст полностью.
Не давать абстрактную критику.
Каждое замечание должно быть связано с конкретным местом текста.
```

## Валидатору запретить:

```text
Не оценивать красоту текста.
Оценивать только соответствие приложению, функциям и смыслам.
```

## Редактору запретить:

```text
Не менять сюжет.
Не добавлять новые функции.
Не менять смысл приложения.
```

# 14. Итоговая рекомендация

Я бы собрал систему так:

```text
1. Producer Agent
2. Product Meaning Agent
3. Reader Persona Agent
4. Story Architect Agent
5. Chapter Writer Agent
6. Critic Agent
7. Product Validator Agent
8. Style Editor Agent
9. Final Assembly Agent
```

Но запускал бы сначала только 5:

```text
Producer
Product Meaning Agent
Story Architect
Writer
Critic/Validator
```

Главная логика:

```text
Не “агенты пишут книгу”.
А “агенты строят смысловую машину, которая превращает приложение в историю”.
```

Именно это даст тебе не просто текст про приложение, а мини-книгу, где приложение становится частью человеческого пути.
