# Находки по worc (реальное тестирование на wastech-mdlint)

Журнал находок и предложений по улучшению оркестратора `worc`, обнаруженных в ходе реального прогона на проекте `wastech-mdlint`. Спутник [TEST-CHECKLIST.md](TEST-CHECKLIST.md).

Формат находки: **что** нужно изменить · **почему** · **рычаг** (какой код/ключ править) · **статус**.

---

## Установка / дефолты конфига

### F1. `skills.dynamic` должен по умолчанию быть `false` при установке

- **Что:** `worc install` сейчас пишет в `config.yaml` блок `skills: { dynamic: true, strict: false }`. Дефолт должен быть `dynamic: false`.
- **Почему:** динамический слой добавляет once-per-task supervisor-turn (предложение `node → skills`) даже когда репо-скиллов нет или они не нужны; это лишняя стоимость/шум по умолчанию. Безопаснее fail-quiet: оператор осознанно включает `dynamic: true`, когда действительно хочет авто-предложение скиллов.
- **Рычаг:** `install/config_writer.py` (дефолт блока `skills` в `build_config_mapping`); при необходимости — дефолт dataclass в `config/schema.py`. Сверить с `packaged/config.example.yaml`.
- **Статус:** OPEN (обнаружено 2026-07-02 на установке).

### F2. `supervisor.model` и `supervisor.reasoning` должны всегда заполняться при установке

- **Что:** `worc install` пишет `supervisor: { role_file: ..., model: null, reasoning: null }`. Оба поля должны заполняться конкретными значениями, а не `null`.
- **Почему:** `null` означает «унаследовать от глобального primary», но это неявно и непрозрачно для оператора — он не видит, какой моделью/усилием работает надзорный слой (а супервизор пишет summary, follow-ups, memory-delta и per-step advisory — цена реальная). Явные значения (например, модель primary-провайдера + его reasoning, либо осознанный дефолт) делают поведение видимым и управляемым из коробки.
- **Рычаг:** `install/config_writer.py` (блок `supervisor` — резолвить конкретные `model`/`reasoning` вместо `null`). Сверить с `packaged/config.example.yaml` и разделом supervisor в `docs/configuration.md`.
- **Статус:** OPEN (обнаружено 2026-07-02 на установке).

### F3. `telegram.trace` отсутствует в конфиге, который пишет `worc install`

- **Что:** `worc install` пишет блок `telegram` с ключами `enabled`, `bot_token_env`, `chat_id_env`, `ask_timeout_s`, но БЕЗ `trace`. Ключ приходится добавлять вручную (`telegram.trace: false`). Install должен писать `trace` (дефолт `false`) как часть блока.
- **Почему:** `telegram.trace` — реальный, задокументированный конфиг-ключ (live step-trace, config schema v21, см. чеклист §14). Его отсутствие в доставляемом конфиге означает, что оператор не знает о фиче и не может её включить, не заглядывая в исходники/`config.example.yaml`. Доставляемый конфиг должен быть полным self-документирующим срезом всех knob'ов блока.
- **Рычаг:** `install/config_writer.py` (блок `telegram` в `build_config_mapping` — добавить `trace: false`). Сверить с `packaged/config.example.yaml` (там ключ, вероятно, есть) — рассинхрон между example и тем, что реально пишет writer.
- **Статус:** OPEN (обнаружено 2026-07-02; пользователь добавил ключ вручную).

## CLI (`worc list`)

### F4. `worc list --format ids` игнорирует секционные флаги (`--pending` / `--recent` / `--all`) — источник только `state.db`

- **Что:** `worc list --pending --format ids` печатает пустой stdout, хотя `worc list --pending` (table) показывает все 10 задач в очереди. Причина подтверждена по коду: в `cmd_list` путь `--format ids` вызывает `_list_ids(store, scope)`, который читает **только** `store.all_tasks()` (state.db) и полностью игнорирует и флаг `--pending`, и pending-файлы на диске (докстринг: «DB-derived»). Свежие pending-задачи ещё не имеют строк в `state.db` → пустой вывод. То же и для `--format ids --scope status`.
- **Почему проблема:** (1) рассинхрон источников — table читает диск+БД и показывает задачи, `ids` читает только БД и не показывает; (2) нет машиночитаемого способа получить id'шники именно очереди `pending` (для скриптинга поверх `--pending`); (3) флаги молча не композируются — `--pending --format ids` тихо теряет `--pending`, без ошибки/предупреждения. Чеклист §3 подразумевает, что `--pending` = очередь pending, а `--format ids` = только id, — их комбинация должна давать id очереди.
- **Рычаг:** `cli.py:cmd_list` (≈ `fmt = "ids" if args.scope else args.format` → `return _list_ids(store, args.scope)`) и `cli.py:_list_ids`. Когда задан секционный флаг (`--pending`/`--recent`/`--all`) вместе с `--format ids`, брать id из того же источника, что и table (`_list_sections` / `scan_pending_sorted`), а не только из БД. Как минимум — задокументировать, что `--format ids` DB-only и не композируется с секционными флагами.
- **Статус:** OPEN (подтверждено чтением кода 2026-07-02). Связано с чеклистом §3.

## Валидация задач (gate)

### F5. Injection-скан отклоняет бэктики в display-поле `title`; консоль не показывает `detail`

- **Что:** задача с заголовком `title: "Add a \`lint\` command as an alias for \`scan\`"`была отклонена гейтом с`reason=injection_suspected`и уехала в`.worc/tasks/rejected/`, до запуска пайплайна. Причина (по коду): `security/injection.py`сканирует **все** front-matter значения на`INJECTION_SUBSTRINGS = (";", "\`", "|", "$(", "\n", "\r")`— включая`title`. Бэктик в заголовке (естественный markdown для кода) → `title: argv-shaped token`→ reject. Плюс: человекочитаемый`detail`(«title: argv-shaped token») пишется в`.worc/logs/<id>/validation_report.json`, но в stdout `worc run`виден только`reason=injection_suspected`— без поля и причины.`worc status <id>`при этом отвечает «no task found» (строки в`state.db`нет — см. F4), хотя`completed.jsonl`фиксирует`validation_reason`.
- **Почему проблема:** (1) заголовки задач естественно содержат `\`code\``/`;`/`|`— автор получает тихий reject в карантин на, по сути, косметике; при этом docstring самого модуля отмечает, что`title`— free-text, «cannot designate a path», а контент доходит до провайдеров только как пути (structural guarantee), т.е. бэктик в title безвреден для argv; (2) на консоли оператор видит непрозрачный`injection_suspected` без указания поля/причины — надо лезть в JSON-артефакт.
- **Рычаг:** (a) `security/injection.py:scan_value` — рассмотреть исключение provably-non-argv display-полей (`title`, `contacts`) из подстрочного argv-скана (оставив reject для полей, которые могли бы попасть в argv/путь), ЛИБО явно задокументировать «front-matter значения — только простой текст (без `\`` `;` `|` `$(`)»; (b) surface `finding.detail`в консольной строке reject (не только`reason`).
- **Обходной путь (нам):** держать заголовки задач простым текстом без бэктиков. Проверено: из 10 задач только smoke имела бэктики; 9 задач P0 чистые.
- **Статус:** OPEN (обнаружено 2026-07-02 на первом прогоне smoke; исправлено в задаче убиранием бэктиков).

### F6. Задача, отклонённая на валидации, «занимает» свой id в ledger — повторная подача того же id блокируется, а `rerun`/`status` её не видят

- **Что:** после reject'а на gate (attempt 1 — F5) повторная подача исправленной задачи с тем же id `lint-command-alias` отклонена с `reason=duplicate_task_id`. Причина (по коду `validation_gate.py`): дубль проверяется против tasks-table **или** ledger (`_ledger_has_task_id`), а attempt 1 записал строку в `completed.jsonl` (`final_status=failed`, `validation_reason=injection_suspected`), но строку в tasks-table НЕ создал (reject до claim). Итог: id «занят» в ledger, но `worc status <id>` → «no task found», а `worc rerun` (через `plan_rerun` требует tasks-row/ветку) восстановить не может.
- **Почему проблема:** штатный цикл «зареджектили на валидации → поправил → подал снова под тем же id» сломан. Валидационный reject (задача даже не запускалась) навсегда резервирует id через ledger, но recovery-путь (`rerun`, который bypass'ит duplicate через recovery-флаг) неприменим — нет tasks-row. Асимметрия: ledger достаточно, чтобы **заблокировать** подачу, но недостаточно, чтобы `rerun`/`status` **увидели** задачу. Выход — только смена id или ручная правка audit-ledger (нежелательно).
- **Рычаг:** `task/validation_gate.py` (duplicate-check + `_ledger_has_task_id`) и `cmd_rerun`/`plan_rerun`. Варианты: (a) не считать дублем id, чей единственный ledger-след — gate-reject (никогда не был claimed, нет tasks-row); (b) научить `rerun` восстанавливать задачу, известную только по ledger/pending-файлу; (c) дать команду очистить одну ledger-запись. Примыкает к F4 (status/ids — DB-only).
- **Обходной путь (нам):** переименовал id `lint-command-alias` → `lint-cmd-alias`.
- **Статус:** OPEN (обнаружено 2026-07-02 при re-submit после фикса F5).

### F7. Supervisor **finalize** (структурный turn) падает при `reasoning: xhigh` → теряются summary + follow_ups + memory_delta

- **Что:** finalize-turn супервизора (`stages/supervisor/run-000000`, sentinel id 0) завершился `status=failed exit=1`, `failure_subtype=error_max_structured_output_retries` («the provider completed without satisfying the task»). Провайдер (opus) при `reasoning=xhigh` не смог выдать валидный structured-output под схему `{summary, follow_ups}` за N ретраев. При этом ВСЕ observe-turn'ы супервизора (free-text, без схемы, тоже xhigh) прошли `exit=0` — падает только turn со схемой. Каскад: `summary.json` деградировал в детерминированный fallback («No provider-authored summary was available»), PR #1 получил file-list вместо нормального тела; follow_ups не собраны; **память осталась пустой** — `short_term/recent.jsonl` = `{"task_id":"lint-cmd-alias"}`, `long_term/` и `entities/` пусты, audit-row с пустым `rationale` (memory_delta едет тем же упавшим turn'ом, AC-W1).
- **Почему проблема:** контраст observe (без схемы, ✓) vs finalize (со схемой, ✗) при одинаковом xhigh изолирует причину: тяжёлый thinking-бюджет xhigh конкурирует со structured-output эмиссией/усечением JSON → provider отдаёт прозу/обрезанный JSON → max retries → fail. На КАЖДОЙ задаче при xhigh это будет стоить summary + follow_ups + всю запись памяти (главный value-add супервизора и memory-подсистемы).
- **Рычаг:** (a) немедленный, наш — `config.yaml supervisor.reasoning: xhigh → high` (или `medium`); структурному summary max-reasoning не нужен (target-only). (b) worc-side robustness — finalize structured-turn должен быть устойчив к высокому reasoning: например, извлекать structured-output игнорируя `thinking`-блоки, ретраить с понижением reasoning, либо кэпать reasoning для схемных turn'ов. Код: `core/supervisor.py` (finalize turn + `_FINALIZE_SCHEMA`), путь извлечения structured-output в `providers/claude.py` / `_adapter_base.py`, классификация `error_max_structured_output_retries`.
- **Связь:** подтверждает важность **F2** (supervisor model/reasoning при install) — дефолт не должен быть хрупким. Также: `error_max_structured_output_retries` как термінал у advisory-супервизора не валит задачу (правильно, degrade gracefully), но тихо жрёт value.
- **Статус:** **VERIFIED FIXED** (2026-07-02, прогон 2 `p0-01-workspace-decisions`, через `/analyze-task-run`). Обходной фикс `supervisor.reasoning: high` подтверждён: finalize-turn (`stages/supervisor/run-000000`) отработал `status=succeeded exit=0 failure_subtype=null`, `structured_output` содержит все три ключа `{summary, follow_ups, memory_delta}`. `summary.json` — реальный авторский текст + непустой evidence-gated `follow_ups`; память записана (`short_term`/`entities`/`audit` непусты). Worc-side robustness-часть (рычаг b: устойчивость схемного turn'а к высокому reasoning) **остаётся OPEN** — исправлен только конфиг, не код.

- **Статус:** OPEN (обнаружено 2026-07-02, прогон 2, через `/analyze-task-run`). Примыкает к F7 (тот же finalize write-seam) и §23 AC-SF3.

### F10. Структурный finalize сплющивает whole-task summary в абзац-простыню; в `summary.md`/теле PR нет заголовка

- **Что:** `summary.md` (= тело PR #2) открывается ОДНИМ плоским абзацем на 827 символов **без единого переноса строки** и **без заголовка документа**, под которым висят `## Technical debt / follow-ups` и `## Pipeline nodes skipped` (подзаголовки без родительского H1 — структура «вверх ногами»). Для контраста: free-text observe-turn'ы супервизора (напр. `run-000012`) выдают богатый многосекционный markdown (`### …`, `**bold**`, абзацы, множество `\n`). Именно это выглядит «криво».
- **Почему так (по коду):** при включённых memory + `emit_follow_ups` (наш конфиг) finalize-turn идёт под СТРУКТУРНОЙ схемой `_finalize_schema`, где `summary` объявлен как `{"type":"string","minLength":1}` — **без `description`/guidance по структуре**. Модель под structured-output кладёт весь синтез в один плоский JSON-string (0 `\n`). Free-text-ветка finalize (AC-S4, когда ни memory, ни follow_ups не включены) дала бы многострочный markdown, как observe-turn'ы, — но мы на структурной ветке. Плюс билдер `core/supervisor.py:finalize()` (≈ строка 414: `body = summary_text.rstrip("\n") + "\n"`) НЕ префиксит заголовок `# {task_title}` → документ безголовый. Flow-промпт `.worc/flows/implementation/summary.md` при этом просит «write for a reviewer … PR body» с секциями — но schema-string это желание гасит.
- **Почему проблема:** тело PR — это то, что читает человек-ревьюер. Простыня без структуры/заголовка ухудшает review-опыт. Это оборотная сторона фичи `emit_follow_ups`/memory: выигрывая машиночитаемые `follow_ups`+`memory_delta`, теряем читаемость summary-прозы. ### F15. 🔴 ROOT CAUSE публиш-фейлов (p0-02, p0-03): `staged_pathspec` добавляет `:(exclude)tasks_dir/`, и `git add` падает (exit 1), когда `tasks/` gitignored И изменение трогает файлы в КОРНЕ репо

### F18. 🔴 CRITICAL, второй publish-баг в `commit_code`: `git add -- <paths>` падает `exit 128 "pathspec did not match any files"`, когда набор изменений содержит УЖЕ-ЗАСТЕЙДЖЕННОЕ удаление отсутствующего в рабочем дереве файла (агент сам сделал `git rm`/`git mv`)

- **Что:** p0-05 релоцирует CLI-энтрипоинт (`src/cli.ts` → `packages/cli/src/…`). Агент-implementation сам застейджил удаление: `git status` показывает `D  src/cli.ts` (заглавная D в ПЕРВОЙ колонке = staged deletion; `git diff --cached` подтверждает `D src/cli.ts`), а файла в рабочем дереве нет. worc `commit_code` → `_commit` → `git add -- <changed_code_paths>` включает `src/cli.ts`. Git падает: `fatal: pathspec 'src/cli.ts' did not match any files` (**exit 128**) → `GitCommandError` → publish fail → `manual_action_required`. Полностью-застейдженное-и-отсутствующее удаление нечего «добавлять» → `git add` по литеральному pathspec фатально не матчит, а `git add` all-or-nothing → падает ВЕСЬ commit (не только эта строка).
- **Изолированное доказательство (reproducible на замороженном дереве p0-05):** `git add -n -- src/cli.ts` → **exit 128** `did not match any files`; `git add -A -n -- src/cli.ts` → **тоже exit 128** (`-A` НЕ спасает для явного pathspec отсутствующего staged-deleted пути); контроль — тот же набор БЕЗ `src/cli.ts` (`git add -n -- packages/cli/src/ README.md …`) → **exit 0**, стейджится чисто. Проверка `git check-ignore` по всем 41 changed-path'ам — **пусто** (ни один не gitignored), т.е. это НЕ F15. И с `:(exclude)tasks/`, и без него — падение идентично (F15-фикс не при чём).
- **Почему это НЕ F15 и почему p0-04 прошёл, а p0-05 нет:** F15 — про magic-pathspec `:(exclude)tasks/` на корневых путях (исправлено, валидировано p0-04). F18 — про литеральный pathspec staged-deleted пути. p0-04 делал `git mv` с ДЕТЕКТИРУЕМЫМ git'ом rename (`R src/… -> packages/core/…`) → `changed_code_paths` даёт НОВЫЙ путь (существует) → add ок. p0-05: `src/cli.ts` показан как чистое **удаление** (`D`, git НЕ счёл это rename'ом — новый `packages/cli/src/index.ts` untracked, слишком разный) → `changed_code_paths` даёт СТАРЫЙ отсутствующий путь → add падает. Итог: `commit_code` хрупок к любой agent-side манипуляции индексом (`git rm`/`git mv`/`git add`), когда путь оказывается полностью-застейдженным-и-отсутствующим.
- **Рычаг:** `git_manager._commit` / `staged_pathspec` / `changed_code_paths` — НЕ передавать в `git add` пути, которые уже полностью в индексе и отсутствуют в рабочем дереве (staged deletion): они и так войдут в коммит из индекса.
