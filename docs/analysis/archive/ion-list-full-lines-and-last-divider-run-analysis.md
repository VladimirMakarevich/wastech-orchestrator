### 1. Cross-provider fallback переносит `model` узла на чужого провайдера → claude 404 — КРИТИЧНО (это и есть причина падения)

- Категория: infra / orchestrator-core. Серьёзность: критическая. Уверенность: высокая.
- Доказательства: `stages/review/run-000028/2-claude/events.jsonl` — `api_error_status:404`, `error:"model_not_found"`, `result:"There's an issue with the selected model (gpt-5.5). It may not exist or you may not have access to it."`. `stages/review/run-000028/1-codex/request.json` → `"model": "gpt-5.5"`. `provider_attempts` (node_run_id=28): codex/attempt 1 → `unsupported_version`; claude/attempt 2 → `process_crashed`. В исходниках: `routing/router.py:371–378` (`_build_request` на повторной попытке меняет только `attempt` и `diff_path`, не трогает `model`/`reasoning`); `providers/codex.py:158–160` и `providers/claude.py:250–252` оба берут `model = request.model or config.model` без оглядки на то, какой провайдер сейчас исполняет узел.
- Корневая причина: `AgentRunRequest` несёт провайдер-агностичные переопределения `model`/`reasoning`, заданные на узле один раз (`core/flow/nodes/evaluator.py:177–179`: `model=node.model, reasoning=node.reasoning`). При fallback codex→claude роутер переиспользует тот же request, поэтому codex-овский `gpt-5.5` ушёл в claude. Идентификатор модели провайдер-специфичен — переносить его между провайдерами нельзя.
- Рекомендуемая правка (рычаг, scope = оркестратор, все репозитории): в `routing/router.py` при формировании попытки на провайдере-замене сбрасывать `request.model` и `request.reasoning` в `None`, чтобы они переразрешились из конфига провайдера-замены (`providers/claude.py:250` уже корректно подставит `config.model`). Минимально — протянуть `next_pid` в `_build_request` (вызов ~`router.py:214`) и при смене провайдера обнулять оба поля. Альтернатива/дополнение: на этапе `resolve_route` запрещать cross-provider fallback, если на узле приколочена `model` (но это режет полезный сценарий «приколотить reasoning, но дать модели плавать»), либо сделать переопределения провайдер-скоупными в схеме (`core/flow/schema.py:56–57, 86–87`) — это крупный рефактор, ниже приоритетом.
- Ожидаемый эффект: cross-provider fallback реально работает; приколоченная на узле модель больше не топит прогон. Конкретно этот прогон был бы спасён: codex всё равно упал бы (см. находку 2), но fallback на `claude-opus-4-8` отработал бы (API был доступен — вернул осмысленный 404).

### 2. codex `--reasoning-effort` не поддержан установленным codex 0.139.0; нет версионного гейта; preflight это не ловит — ВЫСОКО

- Категория: config (целевой) + infra (оркестратор). Серьёзность: высокая. Уверенность: высокая.
- Доказательства: `stages/review/run-000028/1-codex/stderr.log` — `error: unexpected argument '--reasoning-effort' found / Usage: codex exec [OPTIONS] [PROMPT]`, exit 2. `request.json.argv` содержит `… --model gpt-5.5 --reasoning-effort high -`. В исходниках: `providers/codex.py:161–173` безусловно добавляет `--reasoning-effort` (через `_CODEX_EFFORT_MAP`), без какой-либо проверки версии/поддержки; `providers/codex.py:93–94` классифицирует stderr с `unexpected argument` как `unsupported_version`. `worc preflight` гоняет только `codex --version` (executable + auth), а не реальный `codex exec` с боевым argv — поэтому несовместимость флага не видна до середины прогона.
- Корневая причина: адаптер предполагает, что `codex exec` принимает `--reasoning-effort`, а установленный codex 0.139.0 этот флаг на `exec` не принимает (в части версий reasoning задаётся иначе, например `-c model_reasoning_effort=...`). Усугубляется тем, что `review` в целевом флоу приколочен к codex с моделью `gpt-5.5`, которая к тому же не совпадает с моделью codex из конфига (`gpt-5.4`). Это первый реальный вызов codex за весь прогон (всё остальное шло на claude-primary), поэтому проблема всплыла только на `review`.
- Рекомендуемая правка: (a) целевой репозиторий — не приколачивать `review` к codex (вернуть к глобальному primary `claude`) либо привести модель/флаги к возможностям установленного codex; редактируется `debates/.worc/flows/implementation.yaml:101–103`. (b) оркестратор — версионно определять поддержку `--reasoning-effort` (или перейти на `-c model_reasoning_effort=`) в `providers/codex.py:161–173`. (c) оркестратор — расширить `preflight`: делать дешёвый реальный `codex exec` smoke с боевым argv, чтобы ловить такие несовместимости до 12-минутного прогона.
- Ожидаемый эффект: codex-узлы не падают мгновенно на неподдерживаемом флаге; несовместимость CLI ловится на preflight, а не в середине задачи.

### 6. После прогона базовое дерево остаётся «грязным»: файл задачи висит как удалённый на master — ВЫСОКО (подтверждённый баг + регрессия)

Это та самая проблема, на которую отдельно указал оператор: «переключаемся на main — изменений в git быть не должно, а они есть». Разобрано до точного механизма; чинится одной строкой.

- Категория: orchestrator-core (git lifecycle). Серьёзность: средняя по последствиям (дерево грязное, но восстановимо), высокая по важности — это **детерминированный баг, воспроизводится каждый прогон**, когда файл задачи трекается в базовой ветке, и это **регрессия** (см. ниже). Уверенность: высокая.
- Точное наблюдаемое состояние (улики): `git status --porcelain=v2` на `master` → `1 .D N... … tasks/pending/ion-list-full-lines-and-last-divider.md`. Префикс `.D` = в индексе файл не тронут (`.`), в рабочем дереве **удалён** (`D`) — неустейдженное удаление рабочего дерева. `git ls-files --stage` подтверждает: файл по-прежнему в индексе `master` (blob `a5b3cb42`, его руками закоммитил оператор). `git diff` (unstaged) = `38 deletions`. `git reflog`: `master → agent/…` (HEAD@{3}) → 2 коммита (`4496179` код, `8fe026f` audit) → `agent/… → master` (HEAD@{0}).
- Механизм (по шагам, два независимых зазора):
  1. `core/orchestrator.py` `_relocate_task_file` (~1775–1807) переносит файл `tasks/pending/ → tasks/failed/` **обычным перемещением на диске** — `src.replace(dest)` (~1802), не git-aware: на диске `pending` исчез, `failed` появился, в git ничего не застейджено.
  2. Audit-коммит `git_manager.py` `commit_audit` (543–601) собирает pathspec для стейджа только для состояний-**назначений**: `git_manager.py:567–570` — `for state in ("done", "failed")`, затем `git add -A -- <эти пути>` (584). `tasks/pending/<id>.md` в pathspec не входит → его **удаление не стейджится**. Комментарий рядом (572–578) прямо описывает намерение «застейджить и появление, и удаление… `git add -A` стейджит и adds, и deletes», но pathspec неполный — только `done`/`failed`.
  3. `terminal_cleanup` (768–792) перед `git checkout master` зовёт `_unaccounted_dirty_paths()` (794–810), а та пропускает любой путь, для которого `_is_artifact_path()` истинно (471–473: путь в `EXCLUDED_DIRS`, куда входит `tasks/`). Страховка **намеренно игнорирует изменения под `tasks/`** → висящее удаление не считается «unaccounted», cleanup рапортует `safe=true` (подтверждено `publish/terminal-cleanup.json`), и `git checkout master` переносит неустейдженное удаление на базу (master трекает тот же blob — конфликта нет, удаление сохраняется). Итог — «грязный» `master` со статусом `D`.
- Регрессия (важно): ровно этот баг уже чинили. В `docs/backlog/follow_ups.md` строка 36 (2026-06-24, по итогам разбора task-023) помечена **Done**: «`commit_audit` stages task-file deletions on a lifecycle move … so a `failed→done` move of a base-tracked task file no longer leaves a dangling `D`». Но та правка закрыла только сценарий **`failed → done`** (оба состояния уже были в кортеже `("done","failed")`). Сценарий **`pending → failed`** (неуспешный прогон) и **`pending → done`** (успешный прогон по base-трекаемому pending-файлу) не покрыт: исходное состояние `pending` (и `processing`) в кортеж не добавили. Для текущего прогона (pending → failed) фикс — фактически no-op.
- Необходимое условие: файл задачи трекается в базовой ветке. В норме файлы задач коммитятся только на ветке агента и попадают в `master` лишь при мердже PR; здесь оператор закоммитил `tasks/pending/ion-list-…md` в `master` вручную (подтверждено `ls-files`/`reflog`). Но оркестратор обязан оставлять базовое дерево чистым независимо от этого.
- Рекомендуемая правка (рычаг, scope = оркестратор):
  - Основная (одна строка, закрывает первопричину): в `git_manager.py:569` добавить исходные состояния — `for state in ("done", "failed", "pending", "processing")`. Тогда `git add -A -- tasks/pending/<id>* …` застейджит удаление из `pending`, дерево ветки агента после audit-коммита станет чистым, и переключение на базу не принесёт висящего `D`. Инвариант «не подметать чужую задачу» сохраняется — pathspec по-прежнему скоупится по `{task_id}` (docstring 546–547).
  - Защитная (в дополнение, опционально): после `git checkout base` в `terminal_cleanup` явно проверить чистоту базового дерева и восстановить остаточные изменения файла задачи (например `git checkout -- tasks/`), либо не исключать `tasks/` из проверки чистоты на этом шаге. Это страховка, а не замена основной правки.
- Ожидаемый эффект: после любого прогона (успех/провал) `git status` базовой ветки чист; исходный файл задачи на месте; нет риска случайно закоммитить удаление.
