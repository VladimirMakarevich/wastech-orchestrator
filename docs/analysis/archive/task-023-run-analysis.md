## Разбор твоих наблюдений

### 1. Слишком много переходов «тестирование → исправление» — ПОДТВЕРЖДЕНО

7 кругов исправлений — это почти всё «полезное» время прогона. Причина — не задача и не качество кода, а проверки, которые не могли пройти:

- `dotnet test` падал с `error MSB1003: Specify a project or solution file` — команде не передан проект/решение.
- `npm run test:ci` сначала падал из-за отсутствия Chrome (`Cannot start ChromeHeadless ... set CHROME_BIN`), но это агент починил сам к 3-му кругу.

Доказательства: таблица `check_runs` в `state.db` (строки 6,7 … 48,49 — `dotnet` всегда exit 1), логи `checks/006.log`, `checks/007.log`, `checks/005.log`.

### 2. Summary почти пустой — ПОДТВЕРЖДЕНО

Файл `summary.md` содержит «No provider-authored summary was available» и «(no committed changes)», хотя реальный коммит есть (14 файлов, `current.diff` — 33 hunk-а, +33/−325). Здесь две отдельные проблемы:

- Супервайзер не написал финальное summary: в `evaluations` запись `supervisor_final` → `{"summary_written": false}`, а в `result.json` супервайзера `structured_output: null`. То есть слой, который по задумке всегда пишет итог, его не написал.
- Детерминированный «запасной» summary посчитал дифф пустым и написал «(no committed changes)». Скорее всего он смотрит на уже чистое рабочее дерево (после коммита), а не на `base..HEAD`.

Дополнительно: супервайзер дал содержательную заметку только на шаге `planning`, а на всех 7 кругах `testing`/`fixing` его заметки пустые (`"note": ""`). То есть он не заметил, что прогон застрял в одном и том же падении — а это именно то, что он должен ловить.

### 3. Запускались `dotnet build` / `dotnet test`, хотя папка backend не менялась — ПОДТВЕРЖДЕНО

Выбор набора проверок идёт по изменённым путям (`select_check_sets` в `src/wastech_orchestrator/checks/selection.py`), и в нём есть правило «fail-safe в полный прогон»: **если хоть один изменённый путь не попадает ни в один набор с заданными `paths`, запускаются ВСЕ наборы**. У целевого репозитория наборы покрывают только `mobile/**` и `backend/**`, а исключаются из подсчёта лишь `.worc` и `tasks` (`EXCLUDED_DIRS` в `src/wastech_orchestrator/git_manager.py:50`). В корне репозитория есть куча «ничьих» путей: `docs/`, `.github/`, `AGENTS.md`, `CLAUDE.md` и т.д. Достаточно затронуть любой из них — и срабатывает «полный прогон», то есть подтягивается и нерабочий бэкенд-набор.

Дальше цикл сам себя поддерживал: бэкенд-проверка падает → агент лезет в `backend/` чинить (это видно в событиях шага fixing: правки `.csproj`, попытка добавить `global.json`, замена `net10.0` → `net9.0`) → значит `backend/` снова «изменён» → бэкенд-набор снова выбирается → снова падает. Цикл оборвался только когда агент откатил все правки в `backend/`, и рабочее дерево стало снова «только mobile».

Важно: проверка по диффу действительно защищает фронтенд-задачи от бэкенд-проверок, но только если КАЖДЫЙ изменённый путь попадает в какой-то набор. Как только затронут «ничей» путь — защита отключается.

### 4. Файл задачи остался как «удалённый» в git — ПОДТВЕРЖДЕНО, причина найдена

Сейчас на `master`: `git status` показывает статус `D` (удалён в рабочем дереве) для `tasks/failed/task-023-...md`, хотя при этом он есть в дереве коммита `master`.

Что произошло по шагам:

1. Файл `tasks/failed/task-023-...md` оказался **закоммичен в master** вручную — коммит `e3a2b03` («feat: add onboarding link...»), который на самом деле добавил только `.gitignore` (строку `.worc/`) и этот файл задачи, без реализации. Это тот самый «вводящий в заблуждение» коммит, который отметил супервайзер. Автор — твоя git-личность, то есть это ручной коммит, а не оркестратор.
2. На успешной попытке 2 оркестратор перемещает файл задачи по жизненному циклу: `tasks/failed/ → tasks/done/`. Делается это обычным перемещением файла на диске (`src.replace(dest)` в `core/orchestrator.py:1775-1807`, метод `_relocate_task_file`).
3. Audit-коммит (`core/...` через `git_manager.py:566-577`) собирает список файлов задачи и делает `git add -- <только те, что существуют на диске>`. После перемещения файла `tasks/failed/...md` уже нет, поэтому в коммит попадает только **появление** `tasks/done/...md`, а **удаление** `tasks/failed/...md` НЕ стейджится (`git add <путь>` не фиксирует удаление отсутствующего файла). В name-status коммита `dac2ae2` видно только `A tasks/done/...` — удаления нет.
4. Терминальная очистка переключается обратно на `master`. Незафиксированное удаление файла, который трекается в `master` (из `e3a2b03`), переносится на `master` и повисает как удаление со статусом `D`.

Твоя гипотеза («оркестратор закоммитил/запушил, потом переместил/удалил файл, переключился на main, и удаление повисло») верна. Точная причина: audit-коммит фиксирует только появление файла в новой папке и не фиксирует удаление из старой, поэтому при перемещении трекаемого файла базовая ветка остаётся «грязной».

Необходимое условие проблемы — что файл задачи вообще трекается в базовой ветке. В нормальном сценарии файлы задач коммитятся только на ветке агента (audit-коммит на task-ветке), а в `master` попадают лишь при мердже PR. Здесь файл попал в `master` вручную (`e3a2b03`), и слабое место оркестратора превратило это в постоянный «грязный» статус.

### Решение по fail-safe (изменение поведения в коде)

**Решение:** убрать «fail-safe в полный прогон». Сейчас, если хоть один изменённый путь не попадает ни в один набор проверок («ничей» файл), запускаются ВСЕ наборы. Это делает систему непрактичной на реальных монорепо (любая правка в корне `docs/`, `README.md`, `.github/` гоняет весь репозиторий). Новое поведение: «ничей» путь не запускает ничего; работают только наборы, чьи `paths`-маски реально совпали.

**Рычаг:** `src/wastech_orchestrator/checks/selection.py`, функция `select_check_sets`. Удалить блок fail-safe:

```python
    path_bearing = [s for s in sets if s.paths]
    # A changed path claimed by no path-bearing set cannot be attributed to a project → run all.
    for path in paths:
        if not any(_set_matches_path(s, path) for s in path_bearing):
            return tuple(sets)
```

После удаления остаётся обычное объединение совпавших наборов (наборы без `paths` по-прежнему запускаются всегда). Случай `changed_paths is None` (git не подключён, только юнит-тесты) оставляем как «запустить всё» — это не «ничей файл», а «вообще нет данных об изменениях».

**Как поменяется выбор наборов:**

| Что изменилось | Было (fail-safe) | Станет |
| --- | --- | --- |
| `mobile/...` | только `mobile` | только `mobile` (без изменений) |
| `backend/...` | только `backend` | только `backend` (без изменений) |
| `README.md` (ничей путь) | ВСЕ наборы | ничего (или только catch-all без `paths`) |
| `mobile/...` + `README.md` | все наборы | только `mobile` |
| пустой дифф / git=None | ничего / все | ничего / все (без изменений) |

**Риск и как его закрыть.** Fail-safe защищал один реальный случай: коммит меняет только общий корневой файл, влияющий на всю сборку (корневой `package.json`, lock-файл, `Directory.Build.props`, `global.json`, CI-конфиг). После изменения такой файл «ничей» → по нему не запустится ни одна проверка → поломка проедет «зелёной». Поэтому изменение нужно делать в связке с явным покрытием важных путей в `config.yaml` целевого репо:

- завести catch-all набор без `paths` с дешёвыми всегда-нужными проверками (он по дизайну запускается всегда — `paths: () => always`, см. `config/schema.py:188`), и/или
- явно прописать общие корневые файлы в `paths` нужного набора (например, `backend` → `paths: ["backend/**", "Directory.Build.props", "global.json"]`).

Тогда «ничей README» не запускает ничего, а «ничей build-конфиг» всё равно проверяется, потому что оператор объявил его важным.

**Что ещё поправить вместе с кодом:**

- Тест `tests/checks/test_selection.py` — `test_unmatched_path_fails_safe_to_all` переписать под новое поведение (при `["build/codegen.py"]` ожидать только всегда-онный набор, например `["lint"]`; остальные тесты остаются зелёными).
- Докстринг `select_check_sets` (абзац про «Fail-safe to full») и комментарий в `src/wastech_orchestrator/core/flow/nodes/checks.py`.
- Доки с описанием fail-safe: `docs/functional/blocks/B24-check-execution.md`, `docs/operations.md`, `docs/cookbook.md`.

### P1. Не оставлять «грязный» статус в базовой ветке (файл задачи)

**Причина:** наблюдение 4.

1. Главный рычаг — audit-коммит в `src/wastech_orchestrator/git_manager.py:566-577`. Сейчас `git add -- <существующие файлы>` не фиксирует удаление файла, перемещённого из другой папки жизненного цикла. Нужно стейджить и удаление: например, `git add -A -- tasks/done/<id>* tasks/failed/<id>*` (захватывает и появление, и удаление по этим путям), либо явный `git rm` для исходного файла. Тогда перемещение `failed → done` фиксируется на ветке агента как удаление+добавление, и после переключения на базовую ветку рабочее дерево остаётся чистым.
2. Подстраховка — терминальная очистка: после переключения обратно на базовую ветку убедиться, что рабочее дерево чистое (канонический след задачи — на ветке агента/в PR, а не в рабочем дереве базовой ветки); при необходимости восстановить затронутые пути (`git checkout -- tasks/...`).
3. Рекомендация по процессу (не код): не коммитить вручную файлы из `tasks/` в базовую ветку. Оркестратор сам кладёт их в audit-коммит на ветке агента. Коммит `e3a2b03` смешал полезную правку `.gitignore` (`.worc/`) с файлом задачи — из-за этого и появилось трекание в `master`.

**Эффект:** после прогонов `master` остаётся чистым, без повисших удалённых файлов задач.
