## Разбор находок (по убыванию влияния)

### 1. Упавшую задачу нельзя перезапустить штатным `rerun` — ПОДТВЕРЖДЕНО

- **Категория:** infra / процесс. **Серьёзность:** высокая (блокирует сам запуск). **Уверенность:** высокая.
- **Доказательство.** Первый `rerun` (без правок) отказал двумя рефьюзами:
  1. `rerun: task source file is missing (/…/tasks/failed/redesign-…-demo.md); cannot rerun` — `state.db.source_path` указывал в `tasks/failed/`, а файл лежал в `tasks/pending/` (tracked, modified).
  2. `rerun: a prior attempt left a remote branch / open PR (worc/redesign-…-pages); … pass --force-reset-remote`. Кроме того, `worc status` показывал `last_error = git checkout worc/…-pages failed (exit=1): … untracked working tree files would be overwritten by checkout: tasks/failed/redesign-…-demo.md` — это была причина падения **прошлой** попытки (attempt 3): `reset_branch_to_base`/`prepare_branch` упёрлись в untracked-файл задачи в `tasks/failed/`.
- **Корневая причина.** `plan_rerun` берёт `source_path = row.source_path` и фейлит, если по этому конкретному пути файла нет (`core/orchestrator.py:659-661`). Резолва «найти `tasks/{pending,failed,done}/<id>.md` по id» нет — любой ручной/внешний перенос файла между папками жизненного цикла делает задачу неперезапускаемой. Это тот же класс, что и в task-023 (наблюдение 4): взаимодействие «трекание файла задачи ↔ git-операции ветки».
- **Рецидив.** После успеха `state.db.source_path` стал `tasks/done/<id>.md`, а на `master` файл снова в `tasks/pending/` (см. «Побочные эффекты»). Значит следующий `rerun` этого id упрётся в тот же `source file is missing`.
- **Рекомендуемая правка (рычаг).** `core/orchestrator.py:659-661` (`plan_rerun`) — резолвить источник задачи по id среди `tasks/{pending,failed,done}` (а при наличии — по `tasks.slug`), а не доверять единственному сохранённому `source_path`; при множественном совпадении — внятная диагностика. Гард по удалённой ветке (`:684-689`) трогать не нужно — он работает как задумано (защита PR), `--force-reset-remote` штатно его снимает.
- **Зона:** дефолт оркестратора (на все репозитории).
- **Ожидаемый эффект:** упавшая задача переезапускается без ручной правки git; снимается главный барьер сценария «failed → rerun».

### 2. `current.diff` радикально занижает изменение (≈ в 18 раз) — ПОДТВЕРЖДЕНО

- **Категория:** артефакт / достоверность. **Серьёзность:** средняя. **Уверенность:** высокая.
- **Доказательство.** `logs/redesign-…/current.diff` = **67 строк, 2 файла** (`mobile/docs/tasks/TASK-004…md` и удаление `tasks/pending/<id>.md`). Реальное изменение (`git diff --stat master..feat/redesign-…-pages`) = **37 файлов, +322/−245**. То есть весь рефактор контролов (коммиты подзадач 1–5) в `current.diff` отсутствует.
- **Корневая причина.** `write_current_diff` делает `git diff HEAD` — рабочее дерево против HEAD (`git_manager.py:747-757`, строка `:753`). В декомпозированном прогоне (и вообще когда код уже закоммичен к моменту снятия диффа) `HEAD` уже содержит рефактор, и `git diff HEAD` видит лишь «хвост» незакоммиченных правок. Рядом есть корректный `diff_stat` — он диффает `base` против рабочего дерева (`git_manager.py:770-783`), и его докстринг прямо предупреждает, что «committed-only diff (`base...HEAD`)… renders a misleading "(no changes)"». То есть в коде уже знают про эту ловушку, но `current.diff` всё равно собран «ловушечным» способом.
- **Рекомендуемая правка (рычаг).** `git_manager.py:747-757` — собирать `current.diff` как `base..worktree` (или `base...HEAD` для уже закоммиченного), по аналогии с `diff_stat` (`:770-783`).
- **Зона:** дефолт оркестратора.
- **Ожидаемый эффект:** `current.diff` и тело PR отражают реальный объём изменения; обзор/аудит перестают вводить в заблуждение. Финальный summary супервайзера на эту ошибку НЕ попался (он читал реальный контекст), так что это дефект артефакта, а не качества.

### 3. Подзадача 5 отгрузила реальный код, не пройдя ни одной проверки — ПОДТВЕРЖДЕНО

- **Категория:** checks / покрытие. **Серьёзность:** средняя. **Уверенность:** высокая по факту, средняя по точному механизму.
- **Доказательство.** В `check_runs` записи есть только для `subtask_order` 1–4 (по 5 проверок, всего 20, все `passed`). Для подзадач 5 и 6 — НИ ОДНОЙ записи. Узлы `testing` подзадач 5 и 6 в `node_runs` стоят `passed`, но их длительность — **0.14 c и 0.15 c** (против ≈ 45 c у подзадач 1–4); в логе для `subtask=5/6` нет ни одной строки `check started/completed`. При этом подзадача 5 закоммитила реальные изменения (4 файла, `5b14f3f`: `sync-conflict-detail`, `topic-backlog-add-modal`).
- **Корневая причина.** Узел проверок выбирает наборы по `changed_code_paths()` (`core/flow/nodes/checks.py:83`), а `changed_code_paths` читает `git status --porcelain` — **только незакоммиченные** изменения рабочего дерева (`git_manager.py:445-460`). Пустой набор → «run nothing / vacuous pass» (`checks.py:85-87`; докстринг `checks/selection.py`). К моменту запуска `testing` подзадачи 5 её правки уже были в коммите → `git status` чист → проверок не выбралось. Для подзадачи 6 (sweep без изменений) vacuous pass корректен; для подзадачи 5 — это дыра: её код не прошёл ни `lint`, ни `build`, ни `test:ci` на стороне оркестратора (поймает только CI на PR, если настроен).
- **Рекомендуемая правка (рычаг).** Либо база выбора проверок должна учитывать закоммиченное (`base..worktree`, как `diff_stat` в `git_manager.py:770-783`), а не только `git status --porcelain` (`git_manager.py:445`); либо в sub_flow декомпозиции узел `testing` должен гарантированно выполняться ДО per-subtask коммита. Точный порядок «коммит vs testing» по подзадаче 5 из таймстампов однозначно не восстановить (см. «Пробелы в данных») — нужно подтвердить на воспроизведении.
- **Зона:** дефолт оркестратора.
- **Ожидаемый эффект:** ни одна подзадача с реальными правками не уезжает в PR без прогона проверок.

### 4. Хук `rtk` оператора протёк в песочницу агента — ПОДТВЕРЖДЕНО (по summary)

- **Категория:** infra / окружение. **Серьёзность:** средняя. **Уверенность:** средне-высокая (есть прямое свидетельство в summary; сырые events подзадачи 5 не перечитывал).
- **Доказательство.** `summary.md` (раздел «Toolchain friction», подзадача 5): «The `rtk` hook rewrote `npm run lint` into a bare `eslint` call that fails under ESLint 9's flat-config default… it was bypassed with `rtk proxy` to obtain the genuine passing result.» То есть глобальный Claude Code-хук оператора (`~/.claude`, RTK) переписал команду внутри запущенного агента `claude`.
- **Корневая причина.** Спавненный `claude -p …` наследует пользовательские хуки `~/.claude`, если конфиг не изолирован. Собственные проверки оркестратора (узел `checks`) исполняются как argv без shell-хука и потому НЕ пострадали (все 20 — зелёные); пострадал именно агент, когда сам звал `npm run lint`.
- **Рекомендуемая правка (рычаг).** Гарантировать изоляцию `CLAUDE_CONFIG_DIR` для спавненных агентов так, чтобы операторские хуки не подхватывались (`security/isolation.py` + обработка `CLAUDE_CONFIG_DIR` в `config/loader.py`/шаблонах; `CLAUDE_CONFIG_DIR` уже в `security.allowed_environment`). Как минимум — задокументировать запрет на хуки, переписывающие команды проекта.
- **Зона:** дефолт оркестратора (изоляция окружения).
- **Ожидаемый эффект:** агент исполняет реальные команды проекта, не борется с операторским прокси; снимается риск ложных падений/обходов проверок.

### P2. (Опционально) Per-task флаг декомпозиции — переопределение глобального

**Причина / контекст:** сейчас включение декомпозиции — **только глобальное** (`agents.decomposition.enabled`). Проверено: per-task переопределения **нет** — поля `decomposition` нет в `ALLOWED_TASK_KEYS` (`task/model.py:28`), а `reject_unknown_fields: true` отклонит любой новый ключ; гейт `_decomposition_gate_on()` (`core/orchestrator.py:2005-2009`) возвращает ровно `self._config.agents.decomposition.enabled`. Это сознательное решение, и текущая документация это прямо утверждает («Decomposition is **not** a per-task knob» — `docs/worc/decision-guide.md`, `best-practices.md`). Запрос: дать оператору per-task override, когда он видит, что конкретную задачу лучше разбить (или, наоборот, не разбивать), **не меняя саму логику** (флоу-блок `decomposition:` + предложение узла `planning` по-прежнему решают, произойдёт ли реальный сплит).

**Рекомендуемая правка (рычаги).** Зеркалит уже существующий прецедент `prompt_audit` (task-wins над глобальным, без отдельного operator-гейта) и `auto_merge`:

1. Добавить необязательное поле `decomposition: bool | null` в `ALLOWED_TASK_KEYS` (`task/model.py:28`), в модель `NormalizedTask` и парсер (`task/parser.py:241-249`), плюс type-check в `task/validation_gate.py` (как у `prompt_audit`/`auto_merge`).
2. Сделать гейт task-aware: `_decomposition_gate_on(task)` резолвит «значение задачи побеждает, иначе глобальное» — дословно по образцу `_prompt_audit_on` (`core/orchestrator.py:2011-2018`); вызов на `:1453` передаёт `task`.
3. **Логика не меняется:** флаг лишь флипает _гейт_ (разрешена ли декомпозиция для этой задачи), как сегодня делает глобальный флаг. `decomposition: true` → `planning` может предложить сплит даже при выключенном глобальном; `decomposition: false` → один юнит даже при включённом; omit ⇒ глобальный дефолт.
4. Обновить доки, которые сейчас утверждают обратное: `docs/worc/decision-guide.md` (раздел Decomposition), `best-practices.md` (§2), таблицу полей в `docs/worc/README.md`, `docs/task-authoring.md`, `worc-task` SKILL.

**Зона:** дефолт оркестратора (на все репозитории). **Ожидаемый эффект:** оператор задаёт степень дробления точечно для конкретной задачи, не трогая глобальный конфиг и не правя флоу; ядро декомпозиции остаётся как есть.
