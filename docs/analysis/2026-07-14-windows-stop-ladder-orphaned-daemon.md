# Post-mortem: `down`/`--force`/`--force-full` не останавливают watch-демон на Windows

**Задача:** `blog-happy-in-my-misfortunes-2`
**Целевой репозиторий:** `C:\Users\Vladimir Makarevich\Obsidian\WastimeApp`
**Watch-демон:** PID `8956`, `poll_interval` 300s
**Дата инцидента:** 2026-07-14 19:11–20:10 (локально); демон продолжал крутиться и после 20:10
**Платформа:** Windows 10 Pro (`os.name == "nt"`, `_can_signal()` → `False`)
**Анализ:** только чтение консольного транскрипта оператора, `daemon.log` и исходников оркестратора. Правки не вносились.

> Компаньон к [2026-07-14-codex-windows-sandbox-false-success.md](2026-07-14-codex-windows-sandbox-false-success.md): тот разбор объясняет, **почему задача упала** (нода `draft` codex в песочнице), этот — **почему её не удалось остановить**, и почему демон остался жить после того, как задача уже припарковалась.

---

## Вердикт (кратко)

Оператор нажал `down`, затем `down --force`, `down --force-full` несколько раз — и **ни одна команда не остановила демон**. Задача доехала до конца сама (припарковалась в `manual_action_required` в 19:14:45), а watch-демон `8956` остался работать и продолжал сканировать очередь каждые ~5 минут как минимум до 20:10.

Это **не одна ошибка, а три накладывающихся дефекта**, и все — на Windows-специфичном файловом канале остановки (`os.kill` там не достаёт до чужого процесса, поэтому вся остановка держится на двух файлах: `orchestrator.pid` и `orchestrator.stop`):

1. **Дефект A — soft-stop не прерывает активную задачу.** Stop-файл читается только **между тиками** watch-цикла, а тик = целый прогон задачи через весь граф flow. Пока задача идёт по нодам (`supervisor → fixing → length → …`), stop-файл лежит на диске и игнорируется. На Windows нет SIGTERM, поэтому единственный признак завершения для soft-stop — исчезновение PID-файла, которого не будет, пока задача не закончится. Итог: soft-stop на Windows **по дизайну** таймаутит на любой реальной (многоминутной) задаче.

2. **Дефект B — таймаут soft-stop роняет PID-файл и тем самым отпиливает жёсткую ступень.** `--force-full` на Windows умеет `taskkill /F /T`, но ищет демон **по тому же PID-файлу**. Как только soft-stop по таймауту удалил PID-файл, `--force-full` больше не может найти демон и честно отвечает «no running watcher (no PID file)» — хотя демон `8956` жив (его PID даже был напечатан). Лестница остановки перестаёт быть лестницей: дёрнув мягкую ступень, вы лишаетесь жёсткой.

3. **Дефект C — повторный `down` удаляет живой stop-файл.** Когда PID-файла уже нет, `stop_process` уходит в ветку «ничего не записано» и **стирает stop-файл** как «случайный». Но он не случайный — это живой запрос на остановку, который уже отгруженный фикс от 2026-07-14 намеренно оставил, чтобы демон сам вышел на следующем тике. Естественная эскалация оператора («не сработало — нажму ещё раз, посильнее») **своими руками отменяет остановку**. Это и есть причина, по которой демон крутился вечно.

Самое важное: **частичный фикс от 2026-07-14 уже стоял на машине оператора** (текст сообщения «cleared its PID file … taskkill /F /PID 8956» — это ровно его новый вывод), и всё равно инцидент воспроизвёлся. Фикс закрыл задержку опроса и сохранение stop-файла при таймауте, но **не** закрыл дефекты A/B/C — и дефект C прямо перечёркивает то, что фикс сохранил.

## Корневые причины

### Дефект A — soft-stop замечает остановку только между задачами, не между нодами

Watch-цикл проверяет stop-каналы только на границе тика, а `watch_once` за один тик прогоняет **всю** задачу:

- [`watch_loop`](../../src/wastech_orchestrator/cli.py#L1596-L1628): `_stop_requested()` вызывается в начале цикла и во время poll-сна между тиками. Внутри `watch_once` проверок нет.
- [`watch_once`](../../src/wastech_orchestrator/cli.py#L1429-L1474): `resume()` + одна pending-задача. `resume()`/`run_task` гонят задачу через весь граф flow (supervisor/fixing-петли) без единой проверки stop-файла.
- Единственная «между-нодовая» проверка отмены — в роутере: [`router.py#L294`](../../src/wastech_orchestrator/routing/router.py#L294) `is_cancelled` смотрится **только в ветке ошибки провайдера**, перед fallback, чтобы не поднимать запасного агента после stop. В логе оператора **каждый** провайдер завершался `exit_code=0`, поэтому ветка ошибки не срабатывала ни разу — отмена не консультировалась.

На Windows (`_can_signal()` → `False`, [`process_control.py#L49-L59`](../../src/wastech_orchestrator/process_control.py#L49-L59)) SIGTERM недоставляем, поэтому soft-stop идёт по [`_stop_via_pid_file`](../../src/wastech_orchestrator/process_control.py#L641-L676): пишет stop-файл и **ждёт, пока демон сам удалит свой PID-файл**. Но демон удалит PID-файл только на чистом выходе — то есть после того, как задача закончится и цикл заметит stop-файл между тиками. Для задачи длиной в минуты это гарантированно дольше `--timeout` (30s). Вывод: **на Windows soft-stop почти всегда таймаутит на настоящей задаче** и попадает в состояние «PID-файл убрали, демон жив».

### Дефект B — таймаут soft-stop роняет PID-файл, и `--force-full` больше не может эскалировать

При таймауте `_stop_via_pid_file` роняет PID-файл, но оставляет stop-файл ([`process_control.py#L664-L670`](../../src/wastech_orchestrator/process_control.py#L664-L670)) — это верное поведение (фикс от 2026-07-14): «просто занятый» демон сам остановится на следующем тике.

Проблема в том, что **весь `stop_process` ключуется по PID-файлу**. `--force-full` на Windows умеет `taskkill /F /T` через [`_stop_via_tree_kill`](../../src/wastech_orchestrator/process_control.py#L545-L579), и seam для этого проброшен ([`cli.py#L2852`](../../src/wastech_orchestrator/cli.py#L2852), `hard_kill_fn=agent_process.hard_kill_tree`). Но до `_stop_via_tree_kill` дело не доходит: в самом начале [`stop_process`](../../src/wastech_orchestrator/process_control.py#L425-L431) читает PID-запись, и если её нет — сразу возвращает `found=False`. После дефекта B PID-файла нет → `--force-full` уходит в эту раннюю ветку → [`cmd_stop`](../../src/wastech_orchestrator/cli.py#L2891-L2892) печатает «no running watcher (no PID file)».

Итог: **как только мягкая ступень отработала по таймауту, жёсткая ступень мертва** — ровно тогда, когда она нужнее всего. Демон жив, его PID известен (был напечатан), но CLI уже не может на него навестись.

### Дефект C — повторный `down`/`--force-full` удаляет живой stop-файл

Та же ранняя ветка «нет PID-записи» не просто ничего не делает — она **удаляет stop-файл**:

```python
# process_control.py:425-431
record = read_pid_record(path)
if record is None:
    if stop_file is not None:
        stop_file.unlink(missing_ok=True)  # reap a stray sentinel; nothing is recorded
    if children_file is not None:
        clear_children_file(children_file)
    return StopOutcome(found=False, ...)
```

Комментарий называет sentinel «случайным» (stray), но на Windows после дефекта B это **не так**: отсутствие PID-файла не означает «нет демона» — оно означает «предыдущий soft-stop уронил PID-файл, пока демон ещё жив и всё ещё должен нам остановку между тиками». Stop-файл здесь — живой запрос, который фикс от 2026-07-14 намеренно оставил.

В транскрипте это второй `down --force` (~19:12): он удалил stop-файл, который положил первый (таймаутнувший) `down --force`. После этого `_stop_requested()` навсегда `False`, и демон крутится вечно. **Естественная эскалация оператора отменяет собственную остановку.**

## Почему уже отгруженный фикс не помог

В [`docs/backlog/follow_ups.md`](../backlog/follow_ups.md) есть строка от 2026-07-14 про этот же инцидент (`blog-happy-in-my-misfortunes`), помеченная «shipped 2026-07-14». Фикс закрыл:

1. **Задержку опроса** — `watch_loop` теперь во время poll-сна опрашивает stop-каналы кусками по `_STOP_POLL_SECONDS` = 1s ([`cli.py#L1558`](../../src/wastech_orchestrator/cli.py#L1558), [`#L1611-L1627`](../../src/wastech_orchestrator/cli.py#L1611-L1627)), чтобы stop срабатывал за ~1s **между тиками**, а не через `poll_interval` (300s).
2. **Сохранение stop-файла при таймауте** — `_stop_via_pid_file` больше не удаляет stop-файл при таймауте (роняет только PID-файл).
3. **Подсказку** — [`_timed_out_stop_message`](../../src/wastech_orchestrator/cli.py#L2857-L2871) печатает конкретный `taskkill /F /PID <pid>`.

Что оператор реально видел («cleared its PID file … taskkill /F /PID 8956») — это дословно вывод пункта 3, то есть **пропатченная сборка уже стояла**. Почему инцидент всё равно случился:

- **Фикс #1 нерелевантен активной задаче.** Куски по 1s помогают только во время poll-сна **между** тиками. Пока задача 3 минуты шла по нодам, цикл был внутри `watch_once`, а не в poll-сне — там проверок нет (**дефект A остался**).
- **Фикс #2 работал — но дефект C его перечеркнул.** Первый таймаут корректно сохранил stop-файл; второй `down --force` его удалил через ветку «нет PID-записи» (**дефект C**). Фикс #2 и дефект C прямо конфликтуют: #2 рассчитывает, что stop-файл доживёт до следующего тика, а любой повторный stop его стирает.
- **Фикс #3 — только текст.** Он печатает `taskkill`, но не делает `--force-full` рабочим после пропажи PID-файла (**дефект B остался**), и после того, как задача стала терминальной, подсказка исчезает совсем.

## Что почти произошло (и было бы правильным)

Если бы оператор **ничего не делал** после первого таймаута, инцидента бы не было. Первый `down --force` оставил stop-файл на диске (фикс #2). В 19:14:45 задача сама доехала до `manual_action_required`; цикл вернулся к началу `while True`, вызвал `_stop_requested()` → stop-файл на месте → `break` → демон вышел бы чисто, убрал PID-файл, напечатал «watch: stopped».

Ровно этот сценарий сломала эскалация: второй `down --force` удалил stop-файл за ~2 минуты до того, как он бы сработал. **Повторный вызов stop — это то, что предотвратило stop.** Отсюда прямое следствие для приоритетов: дефект C нужно чинить первым.

## Рекомендации (по приоритету)

### P0 — Дефект C: не удалять stop-файл в ветке «нет PID-записи» на Windows

Рычаг: [`stop_process`](../../src/wastech_orchestrator/process_control.py#L425-L431). Когда платформа не умеет пробить живость (`not can_signal`, Windows), отсутствие PID-файла **не** означает «нет демона» — поэтому в этой ветке нельзя трогать stop-файл. На POSIX поведение оставить (там `record is None` действительно означает «демона нет», живость пробивается `os.kill`). Свежий `watch` всё равно чистит устаревший sentinel на старте ([`cli.py#L2746`](../../src/wastech_orchestrator/cli.py#L2746)), так что утечки нет.
Эффект: восстанавливает намерение фикса #2 — демон оператора сам бы вышел в 19:14:45.
Тест: [`tests/test_cli_stop.py`](../../tests/test_cli_stop.py) — в Windows-режиме `stop` при отсутствии PID-файла, но при наличии stop-файла, оставляет stop-файл нетронутым.

### P0/P1 — Дефект B: сохранить возможность эскалации после таймаута

Лестница должна оставаться лестницей. Две совместимые опции:

- **B1 (структурная):** не ронять PID-файл при таймауте soft-stop — держать его, пока завершение не подтверждено, чтобы более поздний `--force-full` мог навестись и сделать `taskkill`. Компромисс: устаревший PID-файл блокирует `up`/`restart` — но это честная, восстановимая блокировка, а не молчаливый сирота.
- **B2 (эскалация для оператора):** реализовать уже отслеживаемый **автоматический `taskkill /F /PID` backstop** (строки в follow_ups от 2026-06-26 и 2026-07-14, помечено «still deferred»): при таймауте soft-stop сам `stop` вызывает `hard_kill_tree(pid)`, а не только печатает команду. Seam уже проброшен ([`cli.py#L2852`](../../src/wastech_orchestrator/cli.py#L2852)) — на soft-timeout-пути он просто не вызывается. Инцидент доказывает, что «только напечатать подсказку» недостаточно: после смерти эскалации оператор не может даже скопировать PID.

Рекомендация: B1 как чистая структурная починка + B2 как дружелюбная к оператору эскалация.

### P1 — Дефект A: кооперативная отмена между нодами

Рычаг: движок flow + уже существующий seam `is_cancelled` (проброшен через [`composition.py#L86`](../../src/wastech_orchestrator/composition.py#L86)/[`#L111`](../../src/wastech_orchestrator/composition.py#L111), консультируется в [`router.py#L294`](../../src/wastech_orchestrator/routing/router.py#L294)). Сегодня `is_cancelled` гасит только fallback при ошибке провайдера; расширить проверку на **границы нод** в движке и парковать задачу восстановимой (`ErrorClass.CANCELLED` → `_park` — хук надёжной остановки). Это отслеживаемый пункт «Clean cooperative per-task cancel» (follow_ups, 2026-06-28).
Эффект: soft `down` прерывается на следующей границе ноды (для этого инцидента — секунды, ноды были по 7–50s) и укладывается в 30s, вообще не доходя до пути «уронить PID-файл».
Ограничение: одну длинную ноду (провайдер с `timeout` 7200s) кооперативная отмена не прервёт — для этого остаётся `--force-full`. Но «прогнать весь остаток flow» превращается в «остановиться на ближайшей границе ноды».

### P2 — Честность сообщений

После починки B (PID-файл сохраняется) сообщение [`cmd_stop`](../../src/wastech_orchestrator/cli.py#L2891-L2892) «no running watcher (no PID file)» снова становится корректным. Пока B не сделан, это сообщение на Windows вводит в заблуждение — демон может быть жив. Правильный ответ — починить B, а не переписывать текст.

Общее замечание: **всё это Windows-специфично.** На POSIX ни один из дефектов не проявляется — soft-stop шлёт SIGTERM и эскалирует до SIGKILL в пределах таймаута ([`_stop_via_signal`](../../src/wastech_orchestrator/process_control.py#L582-L638)), `--force-full` делает group-kill ([`_stop_via_group_kill`](../../src/wastech_orchestrator/process_control.py#L481-L542)), PID-файл присутствует и пробивается. Причина — исключительно в файловом канале остановки на Windows.

## Обходной путь для оператора (сейчас, без правок кода)

1. Не повторять `down`/`--force-full` после первого таймаута — повтор стирает stop-файл (дефект C). Один soft `down` уже положил stop-файл; дать демону дойти до конца текущей задачи, и он выйдет сам на следующем тике.
2. Если нужно остановить немедленно — использовать напечатанную команду прямо из сообщения: `taskkill /F /PID 8956` (или `Stop-Process -Id 8956 -Force`). Восстановление — обычный `resume()` на следующем `up`/`watch`.
3. Найти живой демон, если PID уже неизвестен: `Get-Process python | Where-Object { $_.Path -like '*wastech*' }` или по времени старта; убить через `taskkill /F /T /PID <pid>`.
4. Припаркованную задачу закрыть штатно: `finalize blog-happy-in-my-misfortunes-2 --as failed` (или `rerun … --continue`, чтобы продолжить) — как и советует примечание про парковку ([`cli.py#L1160-L1183`](../../src/wastech_orchestrator/cli.py#L1160-L1183)).
