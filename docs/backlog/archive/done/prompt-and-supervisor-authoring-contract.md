# Prompt & supervisor authoring contract

Status: **implemented** (2026-07-02) Date: 2026-07-01 Owner: Vladimir Makarevich

Implemented on branch `feat/prompt-supervisor-handoff`: **Cluster A** (prompt-authoring contract — flow-aware anti-drift lint, `{?…}` adoption, delivered `prompt-variables.md` reference) in commit `643c4a5`; **Cluster B** (flow-local `supervisor:` block — `role_file` / `finalize_role_file` fallback chains + evidence-gated `emit_follow_ups`) in commit `14791fe`. See [autonomous-run-open-questions.md](autonomous-run-open-questions.md) for the implementation-time decisions.

This ADR refines the requirements for four open [improvements.md](improvements.md) items that all touch one surface — how flow/role authors write prompts and how the supervisor's prompt and output are shaped: task 5 (canonical prompt-variable contract), a new task on more flexible `ALLOWED_PROMPT_VARS` substitution, task 3 (flow-local supervisor/summary prompts with fallback), and task 1 (supervisor tech-debt / refactor signals). It works those requirements through against the current code so each can move to a bounded task; it does not itself specify the implementation. The four split into two clusters: the **prompt-authoring contract** (task 5 + the new substitution task) and the **supervisor prompt/output contract** (task 3 + task 1).

## The problem

The prompt-authoring surface has three rough edges. First, `render_prompt` leaves an unknown `{name}` verbatim by design (so code/JSON braces in a template survive) — but that means a typo like `{plna_path}`, or any variable an author invents that is not in the allowlist, silently ships to the agent as literal placeholder text. Second, the renderer already drops empty allowlisted variables and already has a conditional block `{?name}...{/name}` that keeps its body only when the value is present — but neither behavior is discoverable, so authors write `See the plan at {plan_path}.` and get a dangling `See the plan at .` when the value is empty. Third, `ALLOWED_PROMPT_VARS` is documented in `docs/configuration.md` and `B15-prompt-templates.md` but not presented as a single author-facing reference that says which runner populates each variable and when it may be empty. The common misconception — that an operator "declares" variables in the flow — is false: the Core populates the full allowlisted set for every node ([agent.py:543](../../../../src/wastech_orchestrator/core/flow/nodes/agent.py#L543)); the author only chooses which to reference.

On the supervisor side, task 06 moved every per-node role prompt into its flow's own directory but left `roles/supervisor.md` (and a now-dead `roles/summary.md` that no code reads) in the shared `roles/` tree. So the supervisor is the one prompt whose lens is still a single shared file across all flows, resolved through the global `config.supervisor.role_file` ([config default `roles/supervisor.md`](../../../../src/wastech_orchestrator/install/config_writer.py#L182)), while its observe-vs-finalize emphasis lives as hardcoded code-text in `_step_prompt` / `_finalize_prompt` ([supervisor.py:448](../../../../src/wastech_orchestrator/core/supervisor.py#L448)). A `deep_research` or `security_audit` flow cannot give the supervisor a different lens or a different final-summary emphasis without editing global config. Separately, the supervisor is the only layer that sees a whole run end to end, yet that vantage point yields only prose; there is no stable, operator-facing "what should be improved next" signal, so technical debt and refactor hints stay buried in `summary.md`.

## Constraints

- `render_prompt` is the fixed security core: it substitutes only allowlisted _path/metadata_ variables, never task bodies, diffs, check logs, env, or secrets ([prompts.py](../../../../src/wastech_orchestrator/core/prompts.py)). Nothing here may widen what it injects or let a template weaken argv, the sandbox, the env allowlist, or fallback policy.
- The supervisor invariant holds: advisory, read-only, no routing power, and it must never gain a second LLM turn for this. Task 1 reuses the existing `finalize()` call; task 3 reshapes wording only.
- Best-effort everywhere the supervisor and renderer touch a run: a missing/bad role file, a malformed structured output, or a memory-disabled run must degrade gracefully and never block `summary.md` or publishing. This matches the project rule "only make a config check fatal if there is no safe runtime fallback."
- Memory can be off (an absent or `enabled: false` block; note a fresh `worc install` now ships it on), and the memory subsystem's AC-S4 requires that with memory off the finalize turn behaves exactly as it does today (free-text). Any structured finalize output must respect that.
- Cross-platform path handling stays as-is: variables carry `Path.as_posix()`-style strings; nothing here changes path serialization.

## Alternatives considered

| Option | Why not chosen |
| --- | --- |
| **New substitution task: auto-append a "Context references" section** (Core lists every available path variable; authors stop inlining) | Forces rewriting every packaged role prompt, removes an author's control over where a reference lands, creates two places a reference can appear, and mutates the security-sensitive render surface. Marginal convenience gain, only for brand-new authors. Kept as a future option, not closed. |
| **New substitution task: hybrid** (inline + auto-append for available-but-unreferenced vars) | Two mechanisms doing the same job (KISS violation); an auto-appended var the author deliberately omitted is surprising. Most surface area to document and test. |
| **Task 1: separate `improvements.json` sibling artifact** | A second artifact to reason about, with a taxonomy (`technical_debt` / `refactor_candidates` / `missing_tests` / `scope_concerns`) that overlaps the memory subsystem's `lessons` / `failures` and its fragile-area notion. One artifact set is simpler and works with memory off. |
| **Task 1: prose only in `summary.md`** | Lightest, but leaves the signal unparseable — the original complaint was precisely that debt stays trapped in free-form prose. |
| **Task 3: make only the observe prompt flow-local** | The final-summary emphasis is half the point of the task; leaving it as code-text means `deep_research` and `security_audit` still share one summary lens. |
| **Do nothing** | The unknown-var leak, the undiscoverable `{?...}` pattern, the single shared supervisor lens, and the buried debt signal all persist. |

## Decision

### Cluster A — prompt-authoring contract (task 5 + new substitution task)

Keep `render_prompt` and `ALLOWED_PROMPT_VARS` unchanged. Make the existing behavior explicit and safe instead of adding a new rendering mode:

- Establish `{?name}...{/name}` as the sanctioned pattern for any optional variable, so an author wraps the whole clause (`{?plan_path}Base the work on {plan_path}.{/plan_path}`) rather than inlining a bare `{plan_path}` that can dangle. This is already implemented; the work is documentation and adoption in the packaged prompts.
- Add a **preflight/validate-time lint** that scans each flow's role files for `{name}` and `{?name}` tokens whose name is not in `ALLOWED_PROMPT_VARS`, and warns (naming file + token) that they will render verbatim to the agent. This is a **warning, not a fatal error** — a verbatim render is a safe fallback (code/JSON braces must still pass through), so failing the run would break the safe-renderer contract. This lint directly fixes the only real leak (case 3: unknown/typo vars) and doubles as task 5's requested "low-cost anti-drift guard between docs and `ALLOWED_PROMPT_VARS`."
- Publish one canonical, author-facing prompt-variable reference (task 5) as a new page in the **delivered operator guide** — `packaged/guide/flows/prompt-variables.md`, which `install` already copies into `.worc/guide/` so it sits beside the operator's flows (no new delivery machinery). It documents each variable name, which runner populates it (`agent` / `evaluator` / `supervisor`), when it may be empty, and the `{?name}...{/name}` conditional syntax. The repo's `B15-prompt-templates.md` and `configuration.md` stay as the functional/contributor docs and cross-link to it; the anti-drift lint above guards the packaged source against `ALLOWED_PROMPT_VARS` drift.

Net: minimal, invariant-preserving, and it leaves the auto-append model available for later if authoring proves painful.

### Cluster B — supervisor prompt/output contract (task 3 + task 1)

**Task 3 — flow-local supervisor prompts.** The flow declares its supervisor prompts with **explicit keys** in a `supervisor:` block — `role_file` for the observe lens (overriding the global `config.supervisor.role_file`) and `finalize_role_file` for the final-summary emphasis — mirroring how nodes already declare `role_file`; both paths are validated as flow-dir-contained. The fallback differs per prompt because only the observe prompt has a global counterpart today: **observe** resolves flow `role_file` → `config.supervisor.role_file` → the built-in hardcoded string (three steps), while **finalize** resolves flow `finalize_role_file` → the built-in hardcoded string (two steps; no global finalize prompt is introduced — YAGNI). The observe lens lives in the flow's own `supervisor.md`; the finalize emphasis revives the currently-dead `roles/summary.md` as a flow-owned finalize prompt file. Crucially, only the **wording** moves into files: the structured-output contract (the `memory_delta` schema, and task 1's `follow_ups` schema) stays hardcoded in code, so a flow author can reshape the supervisor's tone and emphasis but can never break the machine contract the orchestrator parses. The flow's `supervisor:` block therefore owns three things: the observe-prompt file, the finalize-prompt file, and the boolean `emit_follow_ups` (task 1, below).

**Task 1 — tech-debt / refactor signals.** This is a **per-flow capability, not a global one.** `follow_ups` is a code concept (technical debt, refactor candidates, extract-a-service), so only code-oriented flows should emit it — a `deep_research` flow or a text-writing flow must never be asked to invent "refactor candidates" for prose it produced. A flow opts in via `supervisor.emit_follow_ups` in its own definition (default `false`); the packaged `implementation` flow sets it, the others do not. This makes task 1 a sub-part of task 3's flow-local supervisor contract — the flow owns its observe lens, its finalize prompt, and whether finalize is structured. When a flow opts in, the existing `finalize()` turn (no extra LLM call) runs with a `{summary, follow_ups}` schema and writes an evidence-gated `follow_ups` array into the always-written `summary.json`, surfaced as a "Technical debt / follow-ups" section in `summary.md`; each record stays minimal and grounded (`title`, `rationale`, `paths`, `evidence`, `severity`, `action_hint`). When a flow does not opt in, finalize stays free-text exactly as today, so the memory subsystem's AC-S4 holds by construction. Memory is orthogonal: when enabled, the same turn additionally feeds `memory_delta` (durable cross-task lessons — a different artifact, consumer, and lifetime from the task-scoped `follow_ups`). No `improvements.json`; missing or malformed structured output leaves today's `summary.md` fallback untouched.

The cost of these choices: we trade the ergonomic automation of an auto-append model for author control and one fixed security core, and we trade a dedicated debt artifact for a single taxonomy that lives beside the summary and the memory delta.

## Open questions

The three design questions raised during refinement (2026-07-01) are resolved and folded into the Decision above: task 1's `follow_ups` is a per-flow `supervisor.emit_follow_ups` opt-in with memory orthogonal to it; task 3's prompts use explicit `supervisor.role_file` / `finalize_role_file` keys with per-prompt fallback; and task 5's reference ships in the delivered operator guide. One implementation-time check remains:

- **Dead `roles/summary.md`.** Confirm nothing outside the supervisor consumes it before repurposing it as the finalize prompt file (a `grep` at implementation time; current scan shows no Python reader).
