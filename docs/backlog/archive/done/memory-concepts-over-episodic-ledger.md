# Memory: durable concepts, not an episodic task ledger

Status: **implemented** (2026-07-11; accepted with all open questions closed, then built on `feat/memory-v2-durable-concepts`) Date: 2026-07-11 Owner: Vladimir Makarevich

A V2 refinement of the shipped [orchestrator memory](../../memory/index.md) subsystem (V1 = [ADR-0001](../../memory/adr.md), phases 01–05, PR #14). It sharpens what memory injects into an agent's context: carry distilled, durable project knowledge (principles, conventions, entity cards, failure remedies) and stop carrying an episodic ledger of orchestrator task runs. The episodic tier stays as internal bookkeeping but is never rendered into a packet, and the durable tier is hardened against refactor-churn (a moved file remaps its card/lesson in place instead of quarantining it) and un-starved (repo-verified knowledge promotes on first sight instead of waiting for orchestrator recurrence), while keeping the path anchor that already neutralizes the far more frequent per-run wording drift.

## The problem

The memory packet that gets injected into agent context (`memory/packet.py`) carries three kinds of low-value or misleading content today.

Ephemeral, rotting pointers reach the agent. The "Recent episodes" section renders raw task ids verbatim — `- task <task_id> — task=done (touched: ...)` (`packet.py:340-352`) — and an episode's only artifact pointer is the repo-relative `.worc/logs/<task-id>` directory (`orchestrator.py:2180-2184`). Tasks and their logs are short-lived and get cleaned up quickly, so these become dead references. The same rot affects `Evidence.ref` values that point at a task id or a commit SHA (in a greenfield repo, task branches are deleted and history is squashed/rebased after merge, so commit-anchored evidence rots too), and the durable `seen_task_ids` / `last_seen_task_ids` provenance lists (`records.py:132-136`, `records.py:154`).

The episodic ledger is a misleading, partial view. The "Recent episodes" section reads like "what has been done in this repo", but the orchestrator only ever sees the tasks it ran itself. The operator frequently does work outside the orchestrator, so this ledger is a strict subset presented as the whole — it confuses more than it helps. And it carries almost no information anyway: `stage_outcomes` is a single terminal token, `{"task": "done"}`, and `task_type` is never populated (`orchestrator.py:2171-2185`) even though the packet ranks episodes by it (`packet.py:171`).

The durable tier — the part the operator actually wants — is fragile and under-fed. Entity cards and lesson scopes are anchored on file paths (`service.py:341`; `Scope.paths`), so an ordinary refactor/rename quarantines the whole card or lesson (`cleanup.py:126-241`, mitigated only by single-candidate basename remap). And promotion out of short-term holding is gated on recurrence across tasks (`promote_min_tasks: 2`, `service.py:303-320`); because the operator works around the orchestrator, the same lesson rarely recurs through it, so genuinely durable knowledge stays stuck in `pending.jsonl`.

## Constraints

Preserve the subsystem's hard invariants from the V1 design ([memory/index.md](../../memory/index.md)):

- **Model-free except the supervisor proposal.** Nothing in `memory/` calls an LLM (`memory/__init__.py:9`); the only LLM touch is the supervisor _proposing_ a candidate delta. Any new capture/promotion rule must stay deterministic on the write path.
- **Advisory only.** Memory never enforces; Core decides. The packet header already says "advisory — verify against the code".
- **No secrets, no raw diffs, no unbounded context** in the store or the packet.
- **Reversibility.** Every write batch snapshots touched tiers first; any re-keying of existing records must go through the same snapshot/restore path.
- **Cross-platform paths.** Any path attribute stays POSIX repo-relative (`Path.as_posix()`).
- **Greenfield, no migration machinery.** There is no deployed store to migrate; a store-format change may be handled by `worc memory clear` on upgrade rather than a migration.

## Alternatives considered

| Option | Why not chosen |
| --- | --- |
| **Do nothing** | Leaves the three problems: dead task/log/commit pointers in-context, a misleading partial "what was done" ledger, and a path-fragile, recurrence-starved durable tier. |
| **Episodes: anonymize instead of hide** — keep an episodic section but strip task id + log pointer and render anonymous "hot path" areas | Still injects a partial, orchestrator-only activity view (the core of complaint #2) and re-introduces a rendered section whose only honest signal (changed-path frequency) is better derived live from git than from an incomplete memory ledger. |
| **Episodes: delete the short-term tier entirely** | Investigation (open question 1, resolved) confirmed the tier becomes write-only for retrieval after de-injection — recurrence counting is backed by `seen_task_ids` on the records, not by episodes. We still keep the tier shell deliberately (see the decision) as raw material for a future V2/V3 (embeddings/graph) consumer; deleting it now would only trade a cheap write for having to re-introduce the tier later. |
| **Durable tier: flexible capture only** (loosen promotion, keep path anchoring, leave cleanup as-is) | Un-starves the tier but leaves an ordinary refactor quarantining the card/lesson — half of complaint #3. The chosen decision adds the missing half (remap the key on a move) without abandoning the path anchor. |
| **Durable tier: anti-rot only** (fix pointers + drop the ledger, don't touch promotion/cleanup) | Fixes the leakage but leaves the durable tier under-fed and refactor-fragile, so the packet stays thin on the project knowledge the operator wants. |
| **Durable tier: re-anchor identity on concepts** (key cards/lessons on name/subject, paths as an attribute) | Survives moves but reintroduces the per-run wording-drift duplication that F30/F44 deliberately keyed on paths to avoid: the supervisor re-derives every card/lesson at each finalize, so a reworded name/subject spawns a near-duplicate on nearly every task, whereas a file move is rare. Path-anchoring makes the frequent event a clean merge; the rare move is handled by remapping the key in cleanup (open question 5). |

## Decision

We split memory's mandate cleanly: **the injected packet carries only durable, distilled project knowledge; the episodic record of orchestrator runs becomes internal-only and is never rendered.** We do this because all three complaints share one root — the episodic/id/pointer layer — while the concept layer the operator wants already exists and only needs to be un-starved and made refactor-robust. The cost is losing the in-context "what recently changed" signal (accepted: it was a misleading partial view) and trusting the deterministic trust-classifier more at capture time (accepted: promotion-on-first-sight is restricted to repo-verified and human/review-trust records; `artifact-backed` keeps its recurrence gate until its validator pass is built).

Concretely, three moves:

1. **Episodic tier → write-only shell, not injected.** Drop the "Recent episodes" section from the packet entirely. Task ids, `.worc/logs/<task-id>` pointers, and commit SHAs never appear in anything an agent reads. Episodes are still written (cheap, deterministic) but the tier is now **write-only for retrieval** — nothing reads an episode's content once the section is gone (recurrence counting is backed by `seen_task_ids` on the long-term/pending records, not by the episode store). We keep the tier shell deliberately as raw material for a future V2/V3 consumer (embeddings/graph), not because anything reads it today; the written rows still drop rotting pointers (see implementation notes) so a future consumer never ingests dead refs.

2. **No ephemeral pointers in the rendered packet.** Whatever is injected cites only durable, resolvable references — repo files, docs, named checks. Task-id / commit-SHA / log-dir refs may persist internally as provenance but are filtered out of `render()`, never shown as a "see …" pointer.

3. **Durable tier → refactor-robust and un-starved (path anchor kept).** Keep the stable path anchor (F30 lesson ids on `scope.paths`; F44 entity cards on `paths[0]`) — it neutralizes the per-run wording drift that would otherwise spawn a duplicate on nearly every finalize — but make an ordinary move non-destructive: the cleanup pass remaps a single-basename move of a card's path or a lesson's `scope.paths` **in place** (rewriting the key and merging into any record already at the new path) instead of quarantining. Path-less "principle" lessons (architecture invariants, conventions) are already first-class (they key on `subject`). Promote repo-verified/human/review knowledge on first sight — add `REPO_OBSERVED` to auto-promote (`HUMAN_CURATED`/`REVIEW_VERIFIED` already do), keep the recurrence gate for `ARTIFACT_BACKED` only (interim stand-in for its unbuilt validator), and never promote `AGENT_INFERRED`/`EXTERNAL_UNTRUSTED` (unchanged). Reframe the supervisor's delta prompt (`supervisor.py:883-897`) to elicit principles/conventions/entity knowledge and to stop asking for task narration or commit-anchored evidence.

## Open questions — all resolved (2026-07-11)

1. **~~Does any internal consumer still read the episode store once it is not injected?~~ Resolved (2026-07-11).** Investigated: after de-injection the only remaining reads are TTL expiry (`cleanup._expire_episodes`, timestamps + id) and two `len()` count displays (`worc memory show`; the `clear`/`tier_counts` confirmation) — none read episode content. Recurrence/promotion is backed entirely by `seen_task_ids` on the long-term/pending records (`service.py:248-311`, `lifecycle.py:88-111`), not by the episode store. **Decision: keep the tier shell** as deliberate raw material for a future V2/V3 consumer (embeddings/graph); it is write-only for retrieval in V2 and that is accepted (over "delete the tier").
2. **~~Commit-SHA evidence: keep internal or forbid at capture?~~ Resolved (2026-07-11): keep internal, never render.** Forbidding at capture would strip evidence the deterministic classifier needs — a lesson whose only pointer is a commit is `artifact-backed` (`lifecycle.py:32,40-58`), so dropping it would leave the lesson evidence-less and quarantined forever (AC-W2). Commit/task/log refs therefore stay in the store as provenance and are removed at render time by an evidence-ref filter: an `Evidence.type` in {`task`,`commit`,`diff`}, or a `ref` shaped like a task id / commit SHA / `.worc/logs/` path, is never shown as a "see …" pointer. `first_seen_commit`/`last_verified_commit` are already non-rendered.
3. **~~Re-key the entity store: `worc memory clear` at upgrade or CleanupJob collapse?~~ Resolved (2026-07-11): moot — there is no entity re-key.** The path anchor is kept (question 5), so `canonical_name` stays path-derived and nothing is re-keyed. Correction to the question's premise: `CleanupJob` has **no** entity duplicate-merge (only a long-term _lesson_ subject-collapse, `cleanup.py:345`), and even that could not bridge an old→new key change — so "let cleanup collapse it" was never viable. The only store-shape delta in V2 is the dropped episode fields (`artifact_paths`/`stage_outcomes`), which the tolerant readers ignore, so no clear or migration is required; `worc memory clear` stays available for an operator who wants a clean slate.
4. **~~Does re-keying entities by name lose the path-overlap ranking?~~ Resolved (2026-07-11): no.** Confirmed in code: `_select_entities` / `_select_long_term` rank by `_path_overlap(row["paths"], …)` / `_path_overlap(scope.paths, …)` — the `paths` **attribute**, not the key (`packet.py:150,160`). Moot for entities under the path-anchor decision, but the confirmation stands: path-scoped ranking is attribute-driven regardless of the key.
5. **~~Anchor identity on concepts (names/subjects) or keep the path anchor?~~ Resolved (2026-07-11): keep the path anchor, fix the churn.** The supervisor re-derives every card/lesson at each finalize, so wording drift is a near-every-run event while a file move is rare. Path-anchoring makes the frequent event a clean no-op merge (same path → same key) and only the rare move needs handling; concept-anchoring would invert that, spawning drift-duplicates on nearly every task (weakly self-healed by the subject-collapse pass). The operator-visible goal — a refactor no longer loses the durable card/lesson — is met by remapping the key on a move (decision move 3), not by abandoning the anchor.

## Implementation notes

Levers, roughly in order of leverage:

- **Packet render** (`memory/packet.py`): remove the episode section from `build()`/`render()` (`_select_episodes`, `packet.py:163-172`; the episode branch of `_render_lines`, `packet.py:302-305`; `_episode_bullet`); add a render-time evidence-ref filter (a durable-only variant of `_first_evidence_ref`, `packet.py:355-361`) that drops task-id / commit-SHA / log-dir refs so no ephemeral pointer is ever shown (question 2).
- **Supervisor prompt** (`core/supervisor.py:883-897`, the `with_delta` branch): reword to ask for durable principles/conventions/entity cards with doc/architecture/file evidence; drop the current "repo files/commits/checks" wording's commit anchoring, and explicitly say not to record which task did what and not to anchor evidence on commit SHAs.
- **Promotion gate** (`memory/lifecycle.py:34-37,88-111`, `_AUTO_PROMOTE` + `should_promote`): add `REPO_OBSERVED` to `_AUTO_PROMOTE` so repo-verified knowledge promotes on first sight (`HUMAN_CURATED`/`REVIEW_VERIFIED` already do); leave `ARTIFACT_BACKED` recurrence-gated until its validator pass exists; `AGENT_INFERRED`/`EXTERNAL_UNTRUSTED` are already excluded from durable trust and never promote. Correction to the original note: the recurrence gate never applied to `AGENT_INFERRED` (it is non-durable outright) — it starves `REPO_OBSERVED`/`ARTIFACT_BACKED`, which is the actual under-feeding.
- **Identity / cleanup** (`memory/cleanup.py`): keep `_derive_id` (F30) and `_ingest_entity`'s `canonical = paths[0]` (F44) — `service.py` keys are unchanged. Extend `_classify_entity`/`_reconcile_entities` (`cleanup.py:126-187`) so a single-basename remap rewrites `canonical_name` to the new path (not just `paths`) and merges into any card already at that path (union `last_seen_task_ids`) rather than leaving two rows. Add the same single-basename remap to `_reconcile_lessons` (`cleanup.py:191-241`, currently quarantine-only): remap `scope.paths`, re-derive `memory_id`, merge into an existing active lesson at the new id, else quarantine only when the path is truly unresolved (0 or >1 candidates). Path-less cards/lessons stay intact (already the case).
- **Episode write** (`core/orchestrator.py:2146-2193`): the tier stays (write-only shell, see decision), so drop the `.worc/logs/<task-id>` `artifact_paths` entry (dead pointer) and the always-`done` `stage_outcomes` from the written episode — even a write-only row should carry no rotting ref a future consumer would ingest.
- **Config** (`config/schema.py:478-514`, `packaged/config.example.yaml:250-268`): no new knobs. `packet_max_episodic` becomes inert once the section is gone; `promote_min_tasks` now governs only `ARTIFACT_BACKED` promotion.
- **Docs** to sync in the same change: the memory hub ([memory/index.md](../../memory/index.md)) and the packaged operator docs (`config.example.yaml`, any role-prompt references to recent-episode memory).
