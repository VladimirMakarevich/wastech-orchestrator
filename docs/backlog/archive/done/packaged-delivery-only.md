# Packaged built-ins are delivery-only — remove every runtime read of the bundled `packaged/` tree

Status: **implemented** (2026-07-11) Date: 2026-07-09 Owner: Vladimir Makarevich

Implemented on `feat/packaged-delivery-only`. `FlowRegistry._find` now resolves only under the operator's `.worc/flows/` — the `_PACKAGED_DIR` constant, the packaged fallback in `_find`, and `_builtin_names()` are gone; a requested `task_type` absent from `.worc/flows/` raises `FlowResolutionError` naming the missing `<task_type>.yaml`, listing the operator's own flow names, and pointing at `worc install`. Role-prompt reads follow automatically (`source_path.parent` is always under `.worc/flows/`). The install/upgrade copy path, `config/upgrade.py`, and the guide handling are untouched — delivery is preserved. Open-question call: shipped the clear missing-flow error (option b), not a hard dependency on `upgrade-flows`; the re-sync gap remains tracked in [follow_ups.md](../../follow_ups.md) (its stakes are now higher — a newly-shipped built-in is unrunnable until delivered). Tests that relied on the packaged fallback now deliver the built-ins into `.worc/flows/` first (`tests/conftest.py::seed_builtin_flows`, called from the task-running harnesses) or point `operator_flows_dir` at the packaged tree (`BUILTIN_FLOWS_DIR`), mirroring real install.

The bundled `src/wastech_orchestrator/packaged/` tree (built-in flows + role prompts, tools, the operator guide, the `config.example.yaml` template) must have exactly one job: **be the source from which files are delivered into the operator's `.worc/`** — at `worc install`, at an upgrade, or via an explicit copy command. Once delivered, the orchestrator must operate **purely from `.worc/`** and never reach back into the installed package at task-execution time. Today one runtime path violates this: flow resolution silently falls back to the built-in flow YAML (and its role prompts) inside the installed package when the operator's `.worc/flows/` has no matching file. This ADR removes that fallback so `.worc/` is the single source of truth for what the orchestrator runs.

## The problem

Flow resolution reads the packaged tree at runtime. `FlowRegistry._find` ([registry.py:153](../../../../src/wastech_orchestrator/core/flow/registry.py#L153)) returns `_PACKAGED_DIR / f"{task_type}.yaml"` ([registry.py:44](../../../../src/wastech_orchestrator/core/flow/registry.py#L44)) whenever `.worc/flows/` lacks the file, and `_builtin_names` ([registry.py:167](../../../../src/wastech_orchestrator/core/flow/registry.py#L167)) globs that packaged dir. This fires at task dispatch ([orchestrator.py:1714](../../../../src/wastech_orchestrator/core/orchestrator.py#L1714)) and — until the companion ADR lands — in preflight ([cli.py:2126](../../../../src/wastech_orchestrator/cli.py#L2126)). Because a resolved packaged flow's `source_path` points into `packaged/flows/`, its node and supervisor role prompts are then also read from the package ([orchestrator.py:1724](../../../../src/wastech_orchestrator/core/orchestrator.py#L1724), [orchestrator.py:2020](../../../../src/wastech_orchestrator/core/orchestrator.py#L2020), via [prompt.py:26](../../../../src/wastech_orchestrator/core/flow/prompt.py#L26)).

The effect is invisible behavior: the orchestrator runs and validates flows the operator cannot see in their repo. This is exactly what produced the confusing `wastech-mdlint` preflight failure — `content_book`/`content_chapter`/`content_translate` were reported as broken even though they were never in the operator's `.worc/flows/`, because the registry read the orchestrator's own bundled copies. `.worc/` should be the whole truth; a packaged fallback makes it only part of the truth.

For scope, this is the **only** genuine runtime violation. Everything else that touches the packaged tree is either legitimate delivery/upgrade or already compliant: `config/upgrade.py` `packaged_template_mapping()` reads `packaged/config.example.yaml` to merge new keys into the operator's config at `worc upgrade-config` ([upgrade.py:76](../../../../src/wastech_orchestrator/config/upgrade.py#L76)) — that is upgrade-time delivery, not task execution; the tool registry has **no** packaged fallback and resolves only `.worc/tools/` ([tools_registry.py](../../../../src/wastech_orchestrator/core/flow/tools_registry.py)); the supervisor's terminal prompt fallback is hardcoded Python strings, not packaged files ([supervisor.py:138](../../../../src/wastech_orchestrator/core/supervisor.py#L138)); and the guide is copy-only, never read at runtime.

## Constraints

This strengthens an implicit invariant rather than adding machinery: the flows, prompts, and config the orchestrator uses are exactly what lives in the operator-owned, operator-visible `.worc/` — the same spirit as "install seeds editable active copies". The core still does not learn CLI syntax; the change is confined to `core/flow/`. Greenfield MVP — no back-compat shim for the removed fallback. Cross-platform is unaffected (`pathlib` only). The hard consequence to respect: correct operation now depends on install/upgrade having delivered every built-in flow into `.worc/flows/`. A fresh `worc install` already copies all of them; an upgrade that ships new built-ins does not yet re-seed them (no `upgrade-flows`), so that re-sync becomes a prerequisite, not a nicety.

## Alternatives considered

| Option | Why rejected |
| --- | --- |
| Do nothing (keep the packaged runtime fallback) | `.worc/` stays only part of the truth; the orchestrator keeps running/validating flows the operator cannot see — the root cause of the mdlint confusion persists. |
| Fix preflight only (the companion validate-flow ADR alone) | Removes the _symptom_ (preflight noise) but leaves the architectural smell: at dispatch the engine still silently loads flows and prompts from the installed package. |
| Drop the built-in flows from the shipped package entirely | Too far — the package must still carry the built-ins to have something to deliver at install/upgrade. Delivery is the one job we are keeping. |
| **Chosen: keep `packaged/` as a delivery-only source; remove every runtime read; `.worc/` is the sole resolution source** | Single source of truth; what the operator sees is exactly what runs. Cost: install/upgrade must deliver completely, and a missing flow becomes an explicit error instead of a silent fallback. |

## Decision

Make `packaged/` delivery-only: remove `_PACKAGED_DIR` from the runtime resolution path so `FlowRegistry` resolves flows (and therefore their role prompts) exclusively from `.worc/flows/`, and a requested flow that is absent there fails with a clear, actionable error instead of silently loading the bundled copy. We do this because the operator's `.worc/` must be the single source of truth for everything the orchestrator runs; the cost is that install and upgrade must deliver every built-in flow into `.worc/flows/` (fresh install already does; the upgrade re-seed is the prerequisite below), and deleting a flow from `.worc/` is now a real removal with no safety net — which is the intended, explicit behavior.

The `packaged/config.example.yaml` read at `worc upgrade-config` and the guide copy at `worc upgrade-docs` are **retained**: both are the delivery/upgrade job this ADR is explicitly preserving (they produce or refresh the operator's own files), not task-time reads. This is a conscious inclusion, recorded so it is not mistaken for an oversight.

## Open questions

Upgrade completeness is now load-bearing: removing the fallback means an operator who upgrades the orchestrator and then requests a newly-shipped built-in flow gets a hard "not found" unless the new flow was delivered into `.worc/flows/`. Does this ADR **depend on** the `upgrade-flows` re-sync being built first (sequencing), or does it ship with a clear error that tells the operator to run `worc install --reconfigure` / the future `upgrade-flows`? (Related rows: the "Single umbrella `upgrade`/`doctor`" and "paths cited in `.worc/flows/`" follow-ups in [follow_ups.md](../../follow_ups.md).)

Exact missing-flow behavior and message: task → `failed` (or a validation-gate reject) with a message naming the missing `.worc/flows/<task_type>.yaml` and the fix. The `_builtin_names()`-based "unknown task_type" hint ([registry.py:91-94](../../../../src/wastech_orchestrator/core/flow/registry.py#L91)) should list the operator's `.worc/flows/` names, not the packaged stems.

Relationship to the companion ADR [flow-validation-cli-command.md](flow-validation-cli-command.md): if this one is accepted, that ADR's "scope validation to `.worc/` only" becomes automatic (there is no packaged layer left to exclude), while its other decisions — remove flow validation from preflight, add `worc validate-flow` — still stand. The two should be reconciled when either is scheduled.

Should `worc upgrade-config`'s read-and-merge of the config template eventually be reframed as a pure file operation too, to keep the "packaged is only ever copied, never parsed" line absolutely strict? Deferred — the merge is what makes config upgrades non-destructive, and it is upgrade-time, not runtime.

## Implementation notes

Center of the change is [core/flow/registry.py](../../../../src/wastech_orchestrator/core/flow/registry.py): drop `_PACKAGED_DIR` from `_find` (resolve only under `_operator_dir`), from `_builtin_names`/`_all_flow_names` (enumerate `.worc/flows/` only), and reword the `resolve` "unknown task_type" error. Role-prompt behavior needs no separate change — once `source_path` is always under `.worc/flows/`, the `flow_dir=source_path.parent` reads in `orchestrator.py`/`supervisor.py` follow automatically.

Verify the built-in flows the orchestrator counts on are guaranteed present in `.worc/`: the default `implementation` flow ([registry.py:39](../../../../src/wastech_orchestrator/core/flow/registry.py#L39)) and the configured `git.merge_flow` (default `merge`). `worc install` copies all packaged flows via the known install path, so fresh installs satisfy this; the upgrade re-seed gap is the prerequisite in Open questions.

Tests that assert the packaged fallback (e.g. `tests/core/test_flow_registry.py` fallback-to-packaged cases, and any dispatch test relying on a built-in flow not present in a fixture `.worc/`) will need to switch to delivering the flow into `.worc/flows/` first — mirroring real install behavior. Do **not** touch the install/upgrade copy path, `config/upgrade.py`, or the guide handling; those are the delivery job being preserved.
