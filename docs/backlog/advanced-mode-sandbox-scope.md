# Advanced mode still sandboxes the shell — what that costs, and whether it should

Status: **инвестигейт закончен — причина найдена, решение владельца записано** Date: 2026-09-03 Owner: Vladimir Makarevich

**Written in Russian**, like the campaign it continues ([full-tool-access/](full-tool-access/README.md)): the decision this document questions is recorded there in Russian, and it is quoted here verbatim rather than paraphrased.

Задача существует потому, что ожидание владельца и поведение продукта расходятся, и расхождение стоило реальных денег на трейле: **«под `strict_isolation: false` у агентов не должно быть никаких ограничений»** — а ОС-песочница Claude при этом остаётся включённой, и одна команда в ней детерминированно умирает.

## Симптом, с которого это началось

На трейле против `wastechlab-mobile-template` (конфиг: `strict_isolation: false`, то есть advanced mode) агент внутри песочницы получал на `npm run build`:

```
exit 134 (SIGABRT)
fatal error: all goroutines are asleep - deadlock!
  github.com/evanw/esbuild/.../ThreadSafeWaitGroup.Wait
  main.runService ... esbuild/cmd/esbuild/service.go:160
```

Check Runner ту же команду на том же дереве выполнял успешно — дважды за ту же задачу, `exit 0`, ~11.5s. Подробности, доказательства и цена — F7 в findings трейла, `e2e-trial-mobile-template/` рядом в этой же папке (назван текстом: ссылка отсюда туда замыкает цикл, который гейт отклоняет — та же причина, по которой fix-record кампании назван текстом в индексе бэклога). Включая эскалацию: агент дважды записал в durable record уверенно ложный вывод «сломан хост оператора», один раз этот вывод дошёл до продукта, и один раз погоня за фантомом привела к удалению каталога в `repo.local_path` — живом чекауте оператора.

## Откуда песочница берётся, если режим включён

Из одной ветки, не закрытой флагом режима. `_resolve_tool_plan` считает `needs_sandbox` по **плану инструментов и возможностям хоста**, а не по `strict_isolation`:

```python
needs_sandbox = False
if "Bash" in tools:
    if capability is SandboxCapability.NATIVE_WINDOWS:
        if strict_isolation:
            ...  # только здесь режим что-то меняет
    elif capability is SandboxCapability.LINUX_MISSING_DEPS and strict_isolation:
        ...
    elif _bash_sandbox_available(capability):
        needs_sandbox = True  # <- флагом режима НЕ закрыто
```

([`claude.py:389-415`](../../src/wastech_orchestrator/providers/claude.py)). А `_host_sandbox_capability` на macOS возвращает `SandboxCapability.MACOS` безусловно — «macOS uses Seatbelt (always available)» ([`claude.py:257-296`](../../src/wastech_orchestrator/providers/claude.py)). Итог: **на macOS и на Linux с `bwrap`+`socat` ОС-песочница включена при обоих значениях `strict_isolation`.** Единственные хосты, где режим действительно отдаёт несендбоксенный шелл, — те, где песочницы нет вовсе: нативная Windows и Linux без зависимостей.

Это не расходится с документацией режима — это в ней записано, просто не там, где оператор стал бы искать. Ам-режим снимает четыре стены (окружение, инструменты, запись, сеть), и ОС-песочница в этот список не входила никогда.

## Что режим уже снял, и что оставил

Стоит держать в голове, насколько мало от песочницы в режиме осталось — потому что это меняет диагноз:

| Ось | В режиме |
| --- | --- |
| Окружение | родительское минус имена из `.worc/.env` |
| Инструменты | полный набор, `--tools` не эмитится вовсе |
| Сеть | `network.allowedDomains: ["*"]` |
| Запись | `filesystem.allowWrite` = **корень тома** воркспейса, а не клон+temp |
| Запись — вырезы | `.git`, git-common-dir, hooks-dir, `tasks/`, `.worc-io/` — deny, вложенный внутрь того же allow |

То есть по файловой системе и по сети режим уже открыт настолько, насколько это вообще возможно: разрешён весь том. Докстринг `allow_write_root` называет этот выбор и его причину прямо — без него «the sandbox permits writes only inside the workspace and the session temp, **which is what makes `dotnet build` fail on `~/.nuget`** rather than on anything to do with `dotnet`» ([`claude.py:753-757`](../../src/wastech_orchestrator/providers/claude.py)).

## Почему песочницу оставили — и это не оплошность

Она держит **механическую половину инварианта публикации**, и в режиме это единственный механизм, который её держит для подпроцессов. Требование самого режима, ТA.1.1: «`.git` неписабелен любым путём… Оба механизма обязательны: ни один не покрывает другой» — ОС-песочница связывает подпроцессы, а `Write`/`Edit`-паттерны связывают встроенные инструменты, которые песочницу не проходят ([requirements-advanced-mode.md](full-tool-access/requirements-advanced-mode.md)). Там же перечислено, что именно теряется без неё: «`HEAD` не уезжает под оркестратором, индекс не переписывается, хуки не подкладываются, гейт опасного диффа не ослепляется, а отчёт о прогоне не подделывается».

Тот же документ фиксирует, что на хосте **без** песочницы эта гарантия уже заменена на advisory-контракт в промпте плюс детект постфактум, и что принятая цена именно такова. Значит вопрос «выключить ли песочницу в режиме» — это не «ослабить ли изоляцию на шаг», а «распространить ли на все хосты то, что сегодня принято только для Windows и Linux-без-зависимостей».

## Противоречие, из-за которого задача и нужна

Внутри самой кампании записаны два несовместимых состояния, и ожидание владельца совпадает с первым:

**Решение владельца (вариант В), [requirements-advanced-mode.md](full-tool-access/requirements-advanced-mode.md):** «режим либо честно ограничивается окружением и инструментами — и тогда он **не** даёт „собрать проект внутри турна“, — либо вбирает Шаги 2, 3 и 4. **Решением владельца выбран второй путь** (вариант В)».

**Текущий статус кампании, [README.md](full-tool-access/README.md):** «Шаг 4 (`unsandboxed_commands`) выведен из очереди и требует отдельного решения… несовместим с полом по построению».

То есть режим должен был вобрать Шаг 4, Шаг 4 из очереди выведен, и «собрать проект внутри турна» — то, что вариант В обещал, — не работает. F7 это ровно тот случай, который вариант В обещал закрыть.

Хуже: **вариант В назвал этот класс отказа заранее.** Его собственный пример — «`dotnet build` падает на стене 3 (кэш в `$HOME` запрещён песочницей), `restore` — на стене 4 (сети нет)». F7 — та же форма на другом тулчейне. Предсказание было записано и осталось нереализованным.

## Гипотеза, которую и надо проверить первым делом: пятая стена

Модель «четырёх стен» может быть неполной, и если так — это главный результат задачи. Стены 3 и 4 (запись, сеть) в режиме **уже открыты**: разрешён весь том, разрешены все домены. Значит падение esbuild не объясняется ни одной из четырёх осей, и ни `extra_writable_paths` (Шаг 2), ни `allowed_domains` (Шаг 3) до него не достают.

Симптом указывает на другой род ограничения: `runService` ждёт на канале, которого никто не закроет, — то есть Node-хост esbuild не смог поднять дочерний процесс или обменяться с ним по пайпу. Это **процессно-IPC-ось seatbelt** (spawn, pipes, mach ports), а не файлы и не сеть. Ни один ключ её не адресует, и ни один документ кампании её не называет.

Если гипотеза верна, из неё следует: для этого класса отказов Шаг 4 — не «один из рычагов», а **единственный существующий**, потому что остальные оси уже открыты и мимо цели.

**Проверено. Гипотеза верна по сути и неверна по механизму** — ось действительно пятая и действительно IPC-ная, но это не spawn, не пайпы и не mach-порты. Что именно — ниже; раздел выше оставлен как есть, потому что он показывает, что искали, а следующий — что нашли.

## Результат: ось найдена, и это System V IPC

Ось не файловая и не сетевая — обе в режиме открыты настежь, и это ничего не меняет. Это **System V IPC**, а точнее одна-единственная операция seatbelt: `ipc-sysv-sem`.

Цепочка целиком:

1. `npm run build` в целевом репозитории — это `ng build --configuration production`.
2. Angular включает свой персистентный дисковый кэш всегда, когда переменная `CI` не выставлена: `cacheEnabled = !isCI` (`@angular/build/src/utils/normalize-cache.js:27-35` в дереве цели).
3. Этот кэш держится на `lmdb-js` (`@angular/build/src/tools/esbuild/lmdb-cache-store.js:11,22`).
4. `lmdb-js` на macOS берёт под блокировку писателя **семафор System V**.
5. Профиль seatbelt, который генерирует Claude Code, разрешает POSIX IPC — `(allow ipc-posix-shm)` и `(allow ipc-posix-sem)`, второе с комментарием «for Python multiprocessing» — и **не разрешает System V IPC вовсе**.
6. `semget` запрещён → LMDB жёстко обрывает процесс → SIGABRT → `npm` перевыбрасывает сигнал на себя → `npm run build` = **exit 134**.
7. Go-паника esbuild, с которой F7 начинался, — **следствие, а не причина**: сервис esbuild теряет своего Node-хозяина посреди запроса и падает по дедлоку. Диагноз «esbuild ломается в песочнице» был неверным, и «процессно-IPC-ось (spawn, pipes, mach ports)» из гипотезы выше — тоже: и spawn, и пайпы, и mach-порты работают.

Подтверждение из crash report самого трейла (`~/Library/Logs/DiagnosticReports/node-2026-09-01-213421.000.ips`, время — минуты до F7): падает поток с именем `npm exec ng build`, стек — `node::Kill` → `uv_kill` → `__kill`. То есть `npm` убивает себя тем же сигналом, каким умер его ребёнок; сам ребёнок — LMDB.

### Доказательства

Матрица снята локально через `sandbox-exec`, **без участия Claude**: профиль восстановлен из строк бинаря `2.1.234`, файловая и сетевая оси в нём открыты настежь — как в режиме.

| профиль                              | `CI`         | `npm run build`       |
| ------------------------------------ | ------------ | --------------------- |
| без песочницы                        | не выставлен | exit 0                |
| `(allow default)`                    | не выставлен | exit 0                |
| claude-like                          | `CI=1`       | exit 0 (2 из 2)       |
| claude-like                          | не выставлен | **exit 134** (2 из 2) |
| claude-like + `(allow ipc-sysv-sem)` | не выставлен | **exit 0**, 9.97 s    |

Примитив — восемь строк, без Angular и без esbuild: `open()` + `put()` + `get()` на `lmdb-js`. Под `(allow default)` — `exit 0` и корректное чтение; под claude-like — **exit 134 молча, без единой строки на stderr**. Перебор кандидатов по одному дал ровно одну операцию, которая лечит: `ipc-sysv-sem`. Не лечат: `ipc-sysv-shm`, `ipc-sysv-msg`, `mach-lookup`/`mach-register`/`mach-bootstrap` без ограничений, `process-info*` + `signal` + `mach-priv-task-port` + `mach-task-name`, `iokit-*`, `file-map-executable`, `job-creation` + `process-exec*`, `system-fsctl`/`system-info`/`system-sched`.

Проверено и на самом продукте, а не только на реконструкции: в живой песочнице Claude, с тем же `claude-sandbox-settings.json`, который сгенерировал узел `fixing` на трейле, `CI=1 npm run build` даёт **exit 0** за 22.7 s. Тот же тулчейн, то же дерево, та же песочница — разница только в том, включён ли LMDB-кэш. Без `CI=1` там же воспроизводится `exit 134`.

### Второй дефект, найденный по дороге (не F7)

Песочница Claude на macOS вставляет в окружение каждой команды `NODE_USE_SYSTEM_CA=1` и полный набор `HTTP(S)_PROXY`/`ALL_PROXY`/`GIT_SSH_COMMAND`/`CLOUDSDK_PROXY_*`, но `mach-lookup` к `com.apple.trustd.agent` разрешён в профиле только под внутренним «weaker network isolation», которого мы не включаем — и включить не можем. Снято в живой песочнице:

- любой Node-процесс, дотянувшийся до TLS, печатает `ERROR: failed to copy trust settings of system certificate-25291` по строке на каждый корневой сертификат и получает **ноль** системных CA;
- `curl` → `200` и `npm ping` → `PONG` (оба читают `*_proxy` из окружения), а `node -e "require('https').get(...)"` → **`ENOTFOUND`**: ни `http`/`https` ядра Node, ни `fetch`/undici прокси-переменные не читают, а прямого выхода и DNS песочница не даёт.

То есть `network.allowedDomains: ["*"]` в режиме означает «сеть есть у того, кто умеет в прокси-переменные», а не «сеть есть». Для Node-инструментов её нет. Это второй, независимый контрпример к «под `strict_isolation: false` никаких ограничений нет», и он тоже не закрывается ни одним нашим ключом.

### Как воспроизвести

Реконструированный профиль и примитив лежат вне репозитория (сессионный scratchpad) — восстанавливаются за десять минут: `strings` по бинарю Claude из `~/.local/share/claude/versions/<version>` даёт профиль целиком (искать `(version 1)` и `(allow process-fork)`), дальше `sandbox-exec -f <profile> npx ng build --configuration production --output-path <tmp>` в дереве цели. Ключ к воспроизведению — **не выставлять `CI`**: с `CI=1` кэш Angular выключен и падения нет.

## Что проверено — по пунктам

1. **Изолировать ось** — сделано, `sandbox-exec` с правилами режима. Падает там же. Ось не файловая и не сетевая.
2. **Сузить до примитива** — сделано. Восемь строк на `lmdb-js`, без Angular и без esbuild.
3. **Лечится ли это без Шага 4** — **нет.** Настроечная поверхность песочницы у Claude Code исчерпывается списком: `sandbox.enabled`, `failIfUnavailable`, `allowUnsandboxedCommands`, `excludedCommands`, `autoAllowBashIfSandboxed`, `filesystem.{allowRead,allowWrite,denyRead,denyWrite,disabled}`, `network.{allowedDomains,deniedDomains,allowAllUnixSockets,allowManagedDomainsOnly,tlsTerminate}`, `credentials.*`, `seccomp.bpfPath`, `workspace`. **Ни один ключ не достаёт до IPC-оси.** Внутренние опции сборщика профиля (`enableWeakerNetworkIsolation`, `allowMachLookup`, `allowUnixSockets`, `allowPty`) оператору не выставляются вовсе — наружу выведена ровно одна из них, как `network.allowAllUnixSockets`. Аналога `allow_write_root`, который вылечил `~/.nuget`, здесь не существует: рычагов ровно два — `sandbox.enabled: false` и `allowUnsandboxedCommands` + `excludedCommands`. Это худший из возможных исходов пункта 3, и он же снимает вопрос.
4. **Масштаб.** Класс — не «esbuild, то есть Vite/Angular/Next», как предполагалось, а «всё, что берёт семафор System V». Сегодня на этой оси сидит `lmdb-js`, а через него — персистентный кэш Angular CLI, то есть **любой Angular/Ionic-билд с настройками по умолчанию** (кэш выключается только под `CI`). Но перечислить класс нельзя, и это и есть вывод о масштабе: профиль вендорский, закрыт для настройки и меняется с версией CLI — мы не знаем и не можем узнать, какой тулчейн сломается следующим. Обходной путь для конкретно этого случая существует и стоит дёшево (`CI=1` в окружении узла выключает LMDB-кэш), но это заплатка на один тулчейн, а не решение оси, и она платит скоростью пересборки.
5. **Свести противоречие** — ниже.

## Решения

**Решение владельца: в advanced mode агент не ограничивается ничем — ОС-песочница в режиме выключается.** Инвестигейт это подтверждает, а не только исполняет: единственная альтернатива, которая физически существует (Шаг 4 в форме списка команд), в этом же документе уже разобрана как небезопасная, потому что тело `npm run build` живёт в `package.json`, а он агенту доступен на запись.

По пунктам, которые задача обязана была вернуть:

- **Значит ли «никаких ограничений» выключенную ОС-песочницу — да.** Чем тогда держится ТA.1.1 («`.git` неписабелен любым путём») на macOS и Linux: тем же, чем уже держится на нативной Windows и на Linux без зависимостей — tool-level denies на весь набор редакторов (`Write`/`Edit`/`MultiEdit`/`NotebookEdit`), которые песочницу и так не проходят, плюс advisory-контракт в промпте, плюс детект постфактум. Это не новая цена, а распространение уже принятой цены на остальные хосты. Механическая половина для подпроцессов отпадает — и отпадает **вслух**: громкой строкой в `worc preflight` и в логе прогона, ровно как сегодня для хостов без песочницы.
- **`unsandboxed_commands` (Шаг 4) закрывается как ненужный.** Он был «единственным существующим рычагом» ровно пока считалось, что песочница остаётся. Она не остаётся — и тогда Шаг 4 не даёт ничего, чего не даёт выключение, а стоит собственной дыры. Противоречие сводится в пользу [README кампании](full-tool-access/README.md): Шаг 4 выведен из очереди окончательно. Переписать надо проигравшую формулировку — вариант В в [requirements-advanced-mode.md](full-tool-access/requirements-advanced-mode.md): режим не «вбирает Шаги 2, 3 и 4», он снимает пятую стену целиком вместе с песочницей.
- **Второй дефект решается тем же действием.** Без песочницы нет ни `NODE_USE_SYSTEM_CA=1` с пустым списком CA, ни прокси-онли-сети: Node-инструменты получают сеть и системные корни хоста. Отдельного ключа он не требует.

Что проверить при реализации, а не сейчас: с `sandbox.enabled: false` ключ `autoAllowBashIfSandboxed` перестаёт что-либо значить, и авто-одобрение `Bash` в headless-прогоне держится только на `--allowedTools`, куда `Bash` в режиме и так попадает. Подтвердить на живом прогоне до смены дефолта.

## Что не двигается, чем бы задача ни кончилась

- **Публикацию оркестратор агенту не делегирует.** Ни один узел не получает мандата на commit/push/PR. Если механическая половина инварианта на каком-то хосте отпадает, она отпадает **вслух** — громкой строкой в `worc preflight` и в логе прогона, как это уже сделано для хостов без песочницы, а не молча.
- **`gh` не попадает в `unsandboxed_commands` ни при каком решении** — он в песочнице работает, и это путь публикации.
- **Конверт безопасности нельзя ослабить через задачу, `extra_args` или узел флоу.** Три слоя проверки остаются на месте. `sandbox.enabled: false` их не трогает и в их список не входит: это ключ в файле настроек, а не флаг полного доступа — он не даёт ни одобрений без спроса, ни отключения хуков, и `--dangerously*`, `--yolo`, `danger-full-access`, `bypassPermissions` остаются запрещёнными абсолютно.
- **Утилита без собственной пробы в песочнице — «не проверена», а не «несовместима».** `gcloud`/`terraform` в ключ не выписываются.

## Пока задача не закрыта
