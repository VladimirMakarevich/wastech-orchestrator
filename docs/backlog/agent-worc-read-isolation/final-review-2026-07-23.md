## ❗ Что ОБЯЗАТЕЛЬНО исправить до старта WRI-006

WRI-006 — это CI-гейт, который прогоняет изоляцию и sealing на трёх ОС. Он **проверяет** гарантии, но **не чинит** логические баги. Если строить гейт поверх сломанной логики, то либо новые тесты сразу «покраснеют», либо, что хуже, гейт закрепит неверное поведение как «эталон». Поэтому до WRI-006 нужно закрыть находки, которые как раз входят в его матрицу проверок.

| Что | Почему это блокер именно для WRI-006 |
| --- | --- |
| **C1** — барьер квиесценции не соблюдается в терминальной обработке | WRI-006 прямо тестирует «выход процесса провайдера с фоновыми/переподхваченными потомками» и «порядок quiescence-перед-манифестом». Гейт нельзя писать поверх пути, который этот порядок нарушает. |
| **C2** — Codex `--full-auto`/`--ask-for-approval` не зарезервированы | WRI-006 проверяет «оба профиля разрешений провайдера» и что `extra_args` не ослабляет изоляцию. Это дешёвый и однозначный фикс security-allowlist — закрыть до гейта. |
| **H1** — устаревший exchange роняет демон в краш-луп | WRI-006 в списке edge-кейсов имеет «interrupted seal/restore», «stale/foreign exchange», «locked/read-only exchange». Их нельзя аккуратно протестировать, пока вместо чистого терминала происходит краш. |
| **H3** — resume обходит проверку WRI-009 | WRI-006 проверяет «паритет fresh/resume». Тихо пропущенная на resume security-проверка — ровно тот паритет-баг, который гейт должен ловить. Фикс дешёвый. |

**Настоятельно рекомендуется до или в рамках WRI-006** (без этого его доказательства будут неполными): **H2** (у Claude нет capability-preflight — гейт про capability-probing), **H4** (канарейка Codex может ложно проходить — гейт опирается на неё как на доказательство), **H5** (принять решение: реализовать проекцию `denied_commands` в Codex или официально задокументировать дескоуп), **H6/H7 и M6** (документация новых гейтов и режимов отказа).

**Можно после (follow-ups):** остальные средние и все низкие. Часть пробелов в тестах (M8) закроется самим WRI-006.

## 🔴 Критические

### C1. Барьер квиесценции WRI-012 не соблюдается при завершении задачи (стык WRI-012 ↔ WRI-007) — проверено лично

**Что не так.** Есть жёсткое правило: пока оркестратор не доказал, что все дочерние процессы агента точно завершились, он не имеет права делать ничего дальше — ни манифест, ни git-команды, ни seal, ни следующую задачу (см. [architecture.md](../../../.agents/rules/architecture.md) строка 59, [README](README.md) строка 58). Это правило нарушается в двух местах одного и того же обработчика завершения:

- Для узлов-оценщиков (read-only, например `review`): в [orchestrator.py:2390](../../../src/wastech_orchestrator/core/orchestrator.py) блок `except EvaluatorInfraError` стоит раньше блока `except NodeInfraError` (строка 2408) и сразу уходит в `_fail(MANUAL)`, не посмотрев на класс ошибки. Из-за этого для read-only узла случай «дерево не доказано тихим» (`CONTAINMENT_UNVERIFIED`) не выставляет флаг `exchange_active_unsafe`. В результате seal выполняется, git checkout при очистке выполняется, и следующая задача не блокируется.
- Для любых узлов: `_fail` в [orchestrator.py:3471-3477](../../../src/wastech_orchestrator/core/orchestrator.py) делает `commit_code` + `commit_audit` + `push`, если у задачи есть ветка, вообще без проверки квиесценции.

**Пример.** Агент-ревьюер запустил фоновый процесс, который завис намертво (например, в состоянии uninterruptible sleep). Оркестратор посылает SIGKILL, но процесс всё ещё числится живым. По правилам оркестратор обязан остановиться, пометить exchange небезопасным и заблокировать следующую задачу. Но на пути `review`-узла он этого не делает: он запечатывает exchange, делает `git commit` и `git push` ветки, и спокойно берёт следующую задачу — как будто всё чисто. Хуже того, запуск следующей задачи перезаписывает служебный файл со списком «детей», и завёсший процесс уже нельзя будет прибить.

**Почему важно.** Это подтверждённое нарушение заявленного жёсткого инварианта, и оно молча пускает следующую задачу после недоказанного дерева процессов. Масштаб ограничен (SIGKILL уже был послан, push идёт в незамёрженную task-ветку без PR, выживший процесс обычно уже не пишет), но правило сформулировано как абсолютное. Кейс не покрыт тестами. Две независимые проверки (по WRI-012 и по стыкам) сошлись на этой находке.

**Как чинить.** Обработчик `EvaluatorInfraError` должен учитывать класс ошибки — `CONTAINMENT_UNVERIFIED` (и, вероятно, `CAPABILITY_UNAVAILABLE`) должен идти тем же fail-closed путём, что и в ветке `NodeInfraError` (выставить `exchange_active_unsafe`, пропустить seal, удержать handle), и лишь потом деградировать в manual. Либо поднять определение класса ошибки выше диспетчеризации по типу исключения. Терминальные `commit/push/cleanup/seal` стоит явно загейтить по доказанной квиесценции. Добавить тест на containment-фейл для evaluator-узла.

### C2. Codex-флаги `--full-auto` / `--ask-for-approval` не зарезервированы в `extra_args` (WRI-003) — проверено лично

**Что не так.** Список запрещённых для операторских `extra_args` Codex-флагов [_RESERVED_CODEX_FLAGS (codex.py:107-135)](../../../src/wastech_orchestrator/providers/codex.py) не содержит `--full-auto`, `-a`/`--ask-for-approval`. Общие проверки `find_forbidden_args`/`find_full_access_args` их тоже не ловят. Валидатор конфига ([validation.py:42](../../../src/wastech_orchestrator/config/validation.py)) и валидатор flow-узла ([validator.py:441/560](../../../src/wastech_orchestrator/core/flow/validator.py)) вызывают только эти две общие функции, но не `_find_reserved_codex_args`. Значит такой флаг проходит обе валидации и в адаптере доходит до командной строки на [codex.py:455](../../../src/wastech_orchestrator/providers/codex.py) (`argv += list(combined_extra)`). Канарейка `extra_args` не воспроизводит, поэтому даже если реальный запуск ослаблен — канарейка «зелёная».

**Пример.** Оператор (или flow-узел) добавил в `extra_args` флаг `--full-auto`. Оркестратор не считает его опасным и передаёт Codex. `--full-auto` включает `--sandbox workspace-write`. По постановке самой WRI-003, если задан `--sandbox`, Codex перестаёт применять наш профиль `default_permissions="worc"` — то есть исчезают запреты на чтение `.worc/.env`, `state.db` и остального приватного. Агент снова видит секреты — ровно та изоляция, ради которой делался весь кластер (пусть и внутри OS-песочницы, а не с полным доступом к хосту).

**Почему важно.** Нарушает инвариант «конверт безопасности нельзя ослабить через task/`extra_args`/flow-узел» и критерий AC6 задачи (агент-ревьюер пометил его FAIL). Оговорка по реальной эксплуатируемости: примет ли Codex `--full-auto` после подкоманды `exec` — без реального CLI не проверено (комментарий в коде на codex.py:395 говорит, что родственный `--ask-for-approval` после `exec` Codex отклоняет с ошибкой). Если отклонит — это громкая ошибка `INVALID_INVOCATION`, а не тихий обход. Но в security-allowlist эти флаги обязаны быть в любом случае.

**Как чинить.** Добавить `--full-auto`, `-a`/`--ask-for-approval` и любые селекторы режима approval/sandbox в `_RESERVED_CODEX_FLAGS` и в gate flow-узла. Опционально — прогонять канарейку с реальными `extra_args`, чтобы ослабляющий флаг ловился.

## 🟠 Высокие

### H1. Устаревший/чужой exchange блокирует запуск через непойманное исключение → задача застревает в RUNNING и краш-луп демона — проверено лично (тройное совпадение)

**Что не так.** Проверка [assert_exchange_current_task_only (orchestrator.py:2273)](../../../src/wastech_orchestrator/core/orchestrator.py) стоит вне `try`. `run_task` (строки 616-625) и `_resume_task` (1746) ловят только `ManualActionRequired`/`PipelineFailed`/`GitCommandError`, а `ExchangeError` — обычный `Exception`, он не пойман. При этом ветка задачи создаётся на строке 2257, то есть **до** этой проверки на 2273.

**Пример.** Прошлая задача не смогла завершить seal (файл заблокирован на Windows, или дерево процессов не доказано тихим), и её каталог `.worc-io/<старая-задача>/` остался. Стартует следующая задача. Оркестратор уже перевёл её в RUNNING и создал ветку, и тут проверка находит чужой каталог и бросает `ExchangeError`. Его никто не ловит — исключение вылетает наружу, задача остаётся в RUNNING с висящей веткой, демон падает. При перезапуске демон снова входит в тот же код и снова падает — и так по кругу, пока оператор вручную не удалит `.worc-io/`.

**Почему важно.** Сама граница держится (провайдер не запускается, утечки между задачами нет), но реализована как грубый краш вместо чистого `manual_action_required`, о котором говорит задача. Это деградация надёжности демона и новый способ «залипнуть» без штатной ремедиации. Находку независимо подтвердили три проверки (WRI-007, регрессии, стыки).

**Как чинить.** Ловить `ExchangeError` из этой проверки и переводить задачу в `manual_action_required` с указанием проблемного каталога (как уже сделано для `ExchangeSealError` рядом, на строке 2288). Идеально — передвинуть проверку до создания ветки/перевода в RUNNING. Тот же путь применить и в resume.

### H2. У Claude нет parser/capability-preflight — дрейф CLI доходит до платного вызова модели

**Что не так.** У Codex есть `_preflight_capability_error` ([codex.py:730](../../../src/wastech_orchestrator/providers/codex.py)), который заранее пробит `--help` и `resume --help` и ловит смену флагов/enum до запуска модели. Класс `ClaudeCodeProvider` ([claude.py:801-891](../../../src/wastech_orchestrator/providers/claude.py)) не переопределяет ни один из этих хуков — его preflight сводится к «бинарь найден» + разбор `--version`.

**Пример.** Новая версия Claude CLI переименовала значение `--permission-mode dontAsk` или изменила смысл `--setting-sources ""`. Оркестратор об этом не знает и запускает модель (это платный вызов). В лучшем случае запуск падает в рантайме по тексту stderr «unknown option» — уже после старта, как non-fallback ошибка. В худшем — флаг всё ещё принимается, но делает не то, и это вообще никак не замечается.

**Почему важно.** Ровно это критерий WRI-002 (строка 55) и README (строка 32) обещали закрыть: «реальный parser/capability preflight, чтобы дрейф enum не доходил до платного вызова». Для Codex сделано, для Claude — нет.

**Как чинить.** Добавить Claude `_preflight_capability_error` по образцу Codex: пробить `claude --help` (и справку по `-p`) на нужные оркестратору флаги и значения `--permission-mode`.

### H3. Resume обходит проверку WRI-009 «lifecycle-файл == замороженный task-packet» — проверено лично

**Что не так.** На [orchestrator.py:2098-2106](../../../src/wastech_orchestrator/core/orchestrator.py) ветка `resume` проверяет и переопубликовывает bundle, но **не** дописывает в `p.instruction_entries`; дописывает только fresh-путь (строки 2116-2134). Поэтому на `rerun --continue` список `instruction_entries` пуст, и `_task_packet_digest` (строка 2078) возвращает `None`. А `commit_audit`, получив `task_packet_digest=None`, пропускает проверку `_assert_lifecycle_matches_packet`.

**Пример.** Задачу поставили на паузу (упал провайдер), а пока она стояла, кто-то переписал её файл `tasks/.../<id>.md`. Оператор делает `rerun --continue`. При финальном audit-коммите оркестратор должен сверить публикуемый lifecycle-файл с байтами замороженного при старте task-packet и, если они разошлись, уйти в manual. Но на resume эта сверка не выполняется — переписанный файл попадает в коммит без проверки. Нужный дайджест при этом лежит в манифесте (его читает `load_instruction_bundle`), он просто не прокидывается обратно.

**Почему важно.** На текущей ветке запрет на запись в `tasks/` — это cluster-exit (WRI-002/003), то есть эта контентная проверка сейчас единственная линия защиты lifecycle-файла, и на resume она выключена. `assert_staged_allowed` проверяет только набор путей, но не содержимое, поэтому не компенсирует.

**Как чинить.** На resume перезаполнять `instruction_entries` из загруженного манифеста (минимум запись `TASK_PACKET_KEY`), чтобы `_task_packet_digest` был не `None` — как на fresh-пути.

### H4. Канарейка Codex не воспроизводит реальный запуск и может ложно проходить (WRI-003)

**Что не так.** Три связанные проблемы: (а) канарейка запускает `codex sandbox -P worc ...`, тогда как реальный запуск — `codex exec ... -c default_permissions="worc" --ignore-user-config ... [extra_args]`. Канарейка выбирает профиль другим способом, **опускает `--ignore-user-config`** (то есть читает пользовательский `config.toml`, который `exec` игнорирует), и не включает `extra_args`. (б) «Запрещено» выводится из «код возврата ≠ 0» без обязательного позитивного контроля. (в) Нет no-model инвентаризации tool-surface (`codex mcp list`, effective config, features), MCP не отключается через `--disable`, а комментарий на codex.py:91 ложно утверждает, что канарейка доказывает пустой MCP-инвентарь.

**Пример.** На минимальном хосте нет `/bin/cat`, который канарейка использует как пробу. Любая проба падает с ненулевым кодом. Канарейка трактует это как «доступ запрещён» и делает вывод «изоляция работает» — хотя на самом деле песочница вообще не проверялась. Проба на чтение приватного файла «ложно проходит», потому что сломанный запуск выглядит как «всё запрещено».

**Почему важно.** WRI-006 опирается на эту канарейку как на доказательство изоляции Codex. Если канарейка может ложно проходить и не воспроизводит реальную комбинацию слоёв конфига, то и гейт WRI-006 поверх неё будет несостоятелен. Также отсутствуют требуемые пробы: запись/чтение repo по профилю, и алиасы через symlink/junction/hard-link (README прямо обещает «canaries include workspace aliases»).

**Как чинить.** Добавить обязательный позитивный контроль (чтение repo-файла, которое **должно** пройти, и проба записи по профилю), добавить пробы алиасов, а случай «песочница не смогла запуститься» трактовать как `CAPABILITY_UNAVAILABLE`, а не как «запрещено». Гнать канарейку тем же набором опций, что и реальный `exec`.

### H5. `security.denied_commands` не проецируется в Codex execpolicy (WRI-003)

**Что не так.** Запрещённые пути (`denied_read_paths`) в профиль проецируются ([codex_profile.py:145](../../../src/wastech_orchestrator/providers/codex.py)), а запрещённые команды (`denied_commands`) в рантайме Codex не применяются вообще. При этом правило #11 ([security.md:26](../../../.agents/rules/security.md)) требует, чтобы оба чёрных списка применялись «перед каждым запуском», а решение в README обещало «denied commands → controlled Codex execpolicy с прямыми/обёрнутыми тестами». Задача это дескоупила.

**Пример.** Оператор занёс в `denied_commands` команду `curl`. Для Claude она блокируется, а Codex-агент может выполнить `curl` внутри своей песочницы — глобальный запрет для него не действует.

**Почему важно.** Правило #11 в его текущей формулировке для Codex-команд не выполняется, и это расходится с обещанием decision-record.

**Как чинить.** Либо реализовать проекцию execpolicy с прямыми и `bash -c`-обёрнутыми тестами, либо явно поправить правило #11 и decision-record, зафиксировав дескоуп (как уже делали для более раннего пробела). Это решение желательно принять до WRI-006.

### H6. Claude workspace-write на Linux теперь жёстко падает на preflight без `bubblewrap`+`socat`

**Что не так.** [claude.py:691](../../../src/wastech_orchestrator/providers/claude.py) → гейт на orchestrator.py:2247 бросает `PipelineFailed` → задача `failed`, если на Linux/WSL2 для workspace-write узла нет `bubblewrap` и `socat` на PATH.

**Пример.** На main Linux-оператор спокойно запускал workspace-write Claude без этих пакетов. После обновления та же задача уходит в `failed`, пока оператор не поставит зависимости.

**Почему важно.** Поведение намеренное и задокументировано (operations.md:198), но это самый явный кейс «работавшая по умолчанию установка теперь заблокирована». WRI-006 будет реально прогонять это на Linux, так что тема на виду.

**Как чинить.** Добавить явный пункт в release-notes/upgrade-гайд, чтобы Linux-операторы ставили зависимости до обновления. (macOS не пробится — только по `platform.system()`; Windows штатно деградирует в режим без Bash.)

### H7. Новые рантайм-гейты Codex без документированных режимов отказа

**Что не так.** Канарейка `codex sandbox` теперь запускается перед каждым `exec`. Офлайн-проверка `isolation_reasons` хост не пробит, поэтому классы отказа `CONFIGURATION_ERROR` и `CAPABILITY_UNAVAILABLE` всплывают только в рантайме, а не в `worc preflight`, и их нет в операторской документации (упомянут только сам факт существования канарейки).

**Пример.** Установка на старом Codex CLI или на хосте без sandbox-helper работала на main. После обновления она падает ещё до вызова модели с сообщением, которое выглядит как баг, и без описанной ремедиации.

**Почему важно.** Оператор не понимает, что делать. WRI-006 добавит host-смоуки, но операторские доки нужно дополнить.

**Как чинить.** Добавить строки troubleshooting в operations.md для двух классов отказа канарейки (по аналогии с уже описанной строкой про Windows-helper) и вывести канарейку в `worc preflight`. (Claude-only оператор `CodexProvider` не создаёт — лишний CLI ему не нужен, это проверено.)

## 🟡 Средние

### M1. `config.yaml`/`.env` не замораживаются и не дайджестятся (WRI-010)

Критерий 4 сформулирован шире реальности. В bundle замораживаются flow-YAML, файлы ролей и исполняемые файлы инструментов, но не `config.yaml`/`.env`. Практика: конфиг грузится один раз ([cli.py:1649](../../../src/wastech_orchestrator/cli.py)) и в памяти неизменяем весь процесс и весь демон, поэтому текущая задача и следующая задача в том же демоне защищены (правка `config.yaml` на диске на них не влияет). Остаточный риск — новый процесс (перезапуск демона / следующий `run`) читает отравленный `config.yaml` без детекции; но это перекрыто запретом записи в `control_home` (WRI-002/003). **Рекомендация:** либо сузить формулировку критерия 4 до «предотвращено запретом записи + неизменяемо в памяти», либо дайджестить конфиг и проверять при старте процесса.

### M2. Регрессия merge-flow: агент разрешения конфликтов остался без repo-инструкций

Подтверждено двумя проверками (WRI-010 и WRI-011). `_run_merge_flow` ([orchestrator.py:2200-2230](../../../src/wastech_orchestrator/core/orchestrator.py)) не вызывает заморозку инструкций, поэтому `repository_instructions_path` пуст; при этом отключение авто-дискавери безусловное (`project_doc_max_bytes=0` у Codex, `--setting-sources ""` у Claude). **Пример:** до WRI-011 merge-агент подхватывал живые `AGENTS.md`/`CLAUDE.md`; теперь он не получает ни живых, ни замороженных инструкций и решает конфликты без соглашений проекта. Ограничено эфемерным merge-flow, есть в follow_ups. **Рекомендация:** заморозить и инжектить merge-специфичную копию инструкций, либо явно зафиксировать решение «merge-агенту они не нужны» в точке вызова.

### M3. Инвентарь repo-инструкций только корневой (WRI-011)

`REPO_INSTRUCTION_NAMES` берёт только корневые `AGENTS.md`/`CLAUDE.md`; вложенные `AGENTS.md` и файлы по `@`-ссылкам (например, здешние `.agents/rules/*`) не замораживаются. Для этого репозитория безвредно (правила читаются по пути по требованию), но ослабляет AC3/AC5 для репозиториев, которые полагаются на вложенные `AGENTS.md` (Codex-дискавери отключён полностью, а замены нет). **Рекомендация:** либо расширить инвентарь на вложенные/`@`-ссылочные файлы, либо описать это ограничение в операторской документации, а не только в backlog-трекере.

### M4. Secret-гейт fail-closed только на известных значениях секретов (WRI-011)

`assert_no_required_secret` ([instruction_bundle.py:107](../../../src/wastech_orchestrator/core/flow/instruction_bundle.py)) сверяет только с известными значениями (env/denied/memory). Секрет, найденный по паттерну, но не по значению, не останавливает запуск — он тихо редактируется в exchange-копию, меняя байты инструкций, которые видит агент. Это ровно кейс «тихо отредактировано в другие инструкции», который AC7 запрещает. Осознанный компромисс (иначе ложные срабатывания на дефисных task-id). **Рекомендация:** либо сузить формулировку AC7 до «известные значения секретов», либо дополнительно падать, когда redaction изменил бы байты обязательного входа.

### M5. Filter refuse-gate применяется не ко всем git-подпроцессам (WRI-009)

`_assert_no_untrusted_filters` вызывается перед commit/branch-операциями, но не перед checkout/pull в `terminal_cleanup` ([git_manager.py:2079](../../../src/wastech_orchestrator/git_manager.py)), `refresh_base` (880) и `reset_branch_to_base` (783). `git checkout`/`pull` запускают smudge-фильтры, а имя фильтра берётся из `.gitattributes`, поэтому `-c`-хардненинг его не отключит — только refuse-gate. Узкое окно: чистое дерево, единственное изменение — `.git/config` (не виден в `git status`) плюс заранее присутствующий `.gitattributes`, выбирающий новый драйвер. Перекрыто детекцией дрейфа fingerprint. **Рекомендация:** вызвать `_assert_no_untrusted_filters` и перед этими тремя checkout/pull для единообразия.

### M6. Устаревшая операторская документация (доковая половина уже сделанных изменений)

Пять мест всё ещё описывают одну строку `.worc/` в gitignore без `.worc-io/` (operations.md:41,496,657; configuration.md:539; cookbook.md:36); `guide/config/reference.md:16` говорит схема «30», а в коде 31; `guide/flows/README.md:152` и `roles.md:46,54` говорят «три» output-слота и не упоминают новый слот `report`; `glossary.md:204` в списке `ErrorClass` есть `containment_unverified`, но нет `capability_unavailable`. **Рекомендация:** обновить — иначе новые гейты выглядят как баги.

### M7. `_seal_terminal_exchange` обещает «Never raises», но голый `OSError` пролетает мимо обработчиков (WRI-007)

Метод ловит только `ExchangeCleanupBlocked` и `(ExchangeError, ExchangeSealError)`, а `mkdir`/`copy2`/`write_text` при переполнении диска (ENOSPC) или проблеме прав бросают голый `OSError`, который derive не от этих классов. **Пример:** на переполненном диске seal падает голым `OSError` уже после того, как терминальный статус и ledger записаны; флаг `exchange_active_unsafe` не выставляется, лога нет — тихо деградирует в краш-путь H1 без сигнала. **Рекомендация:** ловить неожиданный `OSError` как unsafe-teardown (выставить флаг, залогировать точную цель).

### M8. Пробелы интеграционного покрытия

Заглавные вещи проверены только косвенно: нет e2e-теста «`rerun --continue` восстанавливает verified-снапшот» и seal при терминале FAILED (WRI-007); живой `{checks_path}` — главный фикс WRI-001 — не проверяется ни одним assertion (удаление присваивания не сломает ни один тест); wiring sandbox-настроек Claude не тестируется end-to-end, а run-тесты идут с `deny_policy=None`, то есть проверяют неизолированную конфигурацию (WRI-002); нет теста, что tool-узел исполняет именно замороженные байты (WRI-010). **Рекомендация:** часть закроет WRI-006, но точечные тесты стоит добавить вместе с фиксами выше.

### M9. Прочие средние

Схема БД 16→18 молча пересоздаёт существующий `state.db` (согласуется с greenfield-подходом, но стоит одной строкой в upgrade-заметке); `security_audit`-report теперь редактируется перед приватной записью (секрето-подобные литералы маскируются, путь `.worc/security-reports/<id>/report.md` не изменился); латентный fail-open в Claude при `needs_sandbox=True` и `deny_policy=None` (в проде перекрыто composition, но адаптер сам по себе не падает fail-closed).

## 🟢 Низкие

- **WRI-001:** приватная копия слота `plan`/`summary` пишется без редакции (exchange-копия — редактируется; файлы приватны и denied); containment-проверка привязана к корню exchange, а не к каталогу текущей задачи (на практике перекрыто отдельной проверкой current-task-only).
- **WRI-004:** `create_attempt_dir` укоренён в `logs/`, а не в per-task каталоге (при обходе валидатора мог бы попасть в каталог соседней задачи, но остаётся в приватном home); AST-guard на литерал `.worc` ловит только форму деления `/`, а `Path(root, ".worc")`/`joinpath`/f-строку — нет (сейчас таких конструкций нет).
- **WRI-008-смежное:** загрузчик flow молча схлопывает дублирующиеся node-id (лучше падать с `FlowLoadError`).
- **WRI-012:** POSIX tracker-poll 2.0s грубее, чем в тесте (0.05s) — раскрытый остаток; реальное поведение Windows Job Object проверяется только через инъектированный шов (перенесено в WRI-006).
- **WRI-003:** `CODEX_HOME` для deny берётся из родительского окружения, а не из child-allowlist (при нестандартной замене `allowed_environment` — рассинхрон, громкий сбой аутентификации, не тихая утечка); дрейф комментариев (codex.py:91 неверен дважды); фикстуры путей покрывают только Windows drive-letter, без пробелов/не-ASCII/UNC/symlink/junction.
- **WRI-002:** flow-узел с `--permission-mode auto` (эскалация ниже bypass) не флагается на flow-валидации (реальной эскалации нет: `--tools` — жёсткий гейт, `denyRead`/`denyWrite` держат); классификация хоста по наличию бинарей на PATH, а не по реальной способности (WSL1/сломанные namespaces → fail-closed только в рантайме через `failIfUnavailable`).
- **Стыки:** within-stage fallback читает непроверенный exchange-вход до детекции мутации (defense-in-depth: узлы результат не потребляют, вывод fallback отбрасывается + карантин); router сравнивает строгость профилей по config-default, а не по per-request (консервативно, fail-closed; ни один packaged-flow не переопределяет профиль на узле).
- **Регрессии:** два packaged-промпта (`deep_research`/`security_audit` → `repository_analysis.md`) указывают агенту на теперь-запрещённый `.worc/logs/`.

## Стыки между задачами (seams)

| Стык | Статус | Комментарий |
| --- | --- | --- |
| 1. Terminal seal ↔ quiescence | **СЛОМАН** | evaluator-путь обходит барьер (C1) |
| 2. Детекция мутаций ↔ карантин | OK | одна Low по таймингу within-stage fallback |
| 3. Frozen bundles ↔ continue/restore/recovery | OK | дайджесты переверяются, правка на паузе → fail-closed |
| 4. Stale exchange / недоказанный subtree ↔ следующий запуск | ЧАСТИЧНО | блокирует, но через краш (H1) + утечка на evaluator (C1) |
| 5. Supervisor ↔ адаптерная изоляция | OK | proposal после заморозки, только путь-контракт, read-only, через provider.run |
| 6. WRI-009 ↔ WRI-011 (lifecycle digest) | OK на fresh | сломан на resume (H3) |
| 7. happy-path.md ↔ код | ЧАСТИЧНО | доки переоценивают универсальность барьера (следствие C1) |
| 8. Маршрутизация классов ошибок | OK | fallback только для infra; security → manual без fallback; same-or-stricter соблюдается |

Кросс-платформенность (Windows drive/UNC, symlink/junction/reparse, hard-link, NTFS ADS, case-fold, trailing-dot, device-names) в коде покрыта аккуратно через инъектируемые инспекторы и фейки. Реальное нативное поведение помечено DEFERRED (cluster-exit) — это и есть предмет WRI-006.

## Регрессии и даунгрейды

Ни одна существующая возможность не сломана без замены. Намеренные изменения поведения (почти все задокументированы): orchestrator-коммиты больше не запускают хуки целевого репозитория; требуется git ≥ 2.9; legacy `sandbox` Codex мигрируется/отклоняется с внятной ошибкой; `security_audit`-report пишет оркестратор (редактированно); `{checks_path}` теперь публикуется в живом fix-loop (это улучшение). CLI-поверхность, все 8 packaged-flow (`prompt_vars` байт-в-байт), HITL, memory, publish/PR/merge, daemon, rerun/continue/restart, fallback — работают как раньше.

Реальные деградации, требующие внимания: (1) Linux Claude workspace-write теперь требует зависимостей песочницы (H6); (2) merge-агент потерял repo-инструкции (M2); (3) новый режим отказа — краш-луп демона на устаревшем exchange (H1). Плюс устаревшая документация (M6) делает часть новых гейтов похожими на баги.
