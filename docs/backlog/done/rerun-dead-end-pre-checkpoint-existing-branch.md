# Rerun dead-end: a task that fails before its first checkpoint on an operator-owned branch

Status: **implemented** (2026-07-14; Option A only — Option C deferred) Date: 2026-07-13 Owner: Vladimir Makarevich

> **Implemented 2026-07-14 — Option A only (Option C deferred by decision).** `rerun` now treats a pre-checkpoint failure on an operator-owned branch (`existing`/`current`, no recorded checkpoint) as an **in-place restart**: a plain `rerun <id>` re-drives the whole flow from the top on the branch as-is, clearing the per-attempt row state via `reset_task_for_rerun` but never calling `reset_branch_to_base`, and stamping the ledger attempt linkage (`attempt N+1`, `rerun_of`). A `RerunPlan.restart_in_place` flag routes it; the CLI confirmation reads `[restart] on branch '<branch>'` (and `--dry-run` names the `restart` mode). Fresh-from-base stays refused on an operator-owned branch that _did_ produce work (a checkpoint exists → use `--continue`); `new`-mode is unchanged. This covers **all** pre-checkpoint terminal failures on an operator-owned branch (flow resolution, provider outage before the first node, …), answering the third open question. **Option C (pre-slot flow resolution to prevent the dead-end forming) was deliberately not built** — with A in place the dead-end is always recoverable, so C's root-cause prevention was judged not worth the added pre-slot machinery now; it stays available as a follow-up (see [follow_ups.md](../follow_ups.md)). The first two open questions resolved as their leanings: restart-in-place is scoped to `existing`/`current`, and it keys off "no checkpoint" so it is not limited to the flow-resolution trigger.

This is a design record for a `rerun` gap found in a live `wastech-mdlint` run. The operator was serving the queue from `worc shell` (`up`) while editing the flows in another window; between two ticks the daemon claimed the next task (`p7-03-graph-tools`, `branch_mode: existing`) at a moment when `implementation.yaml` was momentarily absent from `.worc/flows/`, so the run failed at flow resolution with _"unknown task_type 'implementation': no flow file implementation.yaml … Run `worc install` …"_. The flow was restored seconds later, but the task can no longer be re-attempted by **either** `rerun` mode: `rerun <id>` (fresh) refuses because the branch is operator-owned, and `rerun <id> --continue` refuses because no flow checkpoint was ever recorded. There is currently no `rerun`-blessed way out of this state; the only working recovery is to re-queue the task file and let it run as if new (`worc run <failed-file>`, or shell `enqueue`+`up`), which sidesteps `rerun` entirely.

## The problem

A run that dies at flow resolution reaches a state neither `rerun` mode was designed for:

1. `run_task` acquires the slot and calls `_register_task` (the `state.db` row is created, status `VALIDATED`) **before** the flow is resolved. Flow resolution happens inside the engine-drive path at [orchestrator.py:1745](../../../src/wastech_orchestrator/core/orchestrator.py#L1745) (`_flow_registry.resolve(p.task.task_type)`), which raises `FlowResolutionError` ([core/flow/registry.py:108](../../../src/wastech_orchestrator/core/flow/registry.py#L108)) when the flow file is missing. The task goes terminal `failed`.
2. Because it failed before any node ran, `save_flow_checkpoint` ([orchestrator.py:1193](../../../src/wastech_orchestrator/core/orchestrator.py#L1193)) was never called — the checkpoint's `current_node` is empty.
3. **Fresh `rerun` refuses.** For `branch_mode` other than `new`, `plan_rerun` refuses on principle: a fresh rerun resets the branch to base, and the branch is operator-owned, so it will not touch it ([orchestrator.py:1029-1039](../../../src/wastech_orchestrator/core/orchestrator.py#L1029-L1039)) — _"a fresh rerun would reset a branch the orchestrator does not own. Use `rerun --continue` … or clean up the branch manually"_.
4. **`--continue` refuses.** With no recorded `current_node`, `plan_rerun` refuses ([orchestrator.py:960-964](../../../src/wastech_orchestrator/core/orchestrator.py#L960-L964)) — _"no recoverable node was recorded for this task; use a fresh `rerun`"_. `--from NODE` cannot rescue it: `--from` is a `--continue`-only control ([orchestrator.py:989-990](../../../src/wastech_orchestrator/core/orchestrator.py#L989-L990)) and its handling is nested under `if continue_mode and current_node:` ([orchestrator.py:993](../../../src/wastech_orchestrator/core/orchestrator.py#L993)), so an empty checkpoint trips the point-4 refusal first.

The two refusals are individually correct (don't reset an operator's branch; don't "resume" a run that has no resume point) but together they leave a legitimate, common failure — a transient environment problem before any real work — with no `rerun` path at all. The sibling ADR [rerun-flow-drift-and-budget-confirm.md](rerun-flow-drift-and-budget-confirm.md) fixed flow-drift for `--continue --from`, but only for tasks that _had_ a checkpoint; the pre-checkpoint case is untouched.

### Why the workaround works (and why it isn't enough)

Re-queuing the file works because a **plain run** in `existing`/`current` mode uses the operator branch as-is — it never does the destructive reset that fresh `rerun` guards against — and `run_task` → `insert_task` upserts the existing `failed` row back to `VALIDATED` and drives the flow from the top ([state_store.py:585-609](../../../src/wastech_orchestrator/state_store.py#L585-L609)). It is safe **specifically** for a pre-checkpoint failure, where there is no per-attempt state (counters, checkpoint, committed work) to leave stale — the upsert's docstring assumes `reset_task_for_rerun` cleared that state first, which the re-queue path skips. But this is undocumented, discovered by trial and error, and produces surprises: shell `enqueue` _copies_ the file, orphaning the original in `tasks/failed/`, and the retry history that `rerun` records in the ledger is lost (the re-queue looks like a first attempt).

## Constraints

- **Only the orchestrator drives state transitions and owns the branch policy** ([.agents/rules/architecture.md](../../../.agents/rules/architecture.md)). A fix must not weaken the "destructive git ops only on a `new`-mode, orchestrator-owned branch" invariant — the reason fresh `rerun` refuses `existing`/`current` in the first place.
- **`state.db` stays the sole authoritative state** ([docs/operations.md](../../../docs/operations.md)); any new resume path must go through the existing store methods (`insert_task`/`reset_task_for_rerun`/`save_flow_checkpoint`), never a hand SQL edit — the same posture the drift ADR held.
- **Greenfield, no migration** ([[greenfield-mvp-no-migration]]): no back-compat machinery needed; pick the cleanest behavior.
- Must behave identically on Windows/macOS/Linux and reuse the existing non-interactive/`--yes` conventions (no new blocking prompt that fights the `worc shell` stdin reader, H1).
- The fix must preserve the ledger's attempt-history linkage that `rerun` provides — the reason to prefer a `rerun`-native path over blessing the re-queue workaround.

## Decision

**Chosen: Option A only** (Option C deferred). The top note records what shipped; the options are kept below for the record.

**Option A (recommended — SHIPPED 2026-07-14): let `rerun` handle the pre-checkpoint case as an in-place restart, no branch reset.** When a terminal task has no recorded checkpoint _and_ runs in `existing`/`current` mode, `rerun <id>` (no `--continue`) should re-drive the flow from the top **on the existing branch** — reusing the branch as-is (exactly what a plain run does), not resetting it to base. This is the natural meaning of "rerun" for a task that never produced work: there is nothing to reset and nothing to resume, so restart it in place. Concretely, `plan_rerun` stops refusing this combination and routes it to a restart-in-place execution (reset the per-attempt row state via `reset_task_for_rerun`, keep the branch), and the CLI confirmation names what actually happens (_"restart on branch '<branch>'"_, not "from base"). Fresh-from-base stays refused for operator-owned branches; only the no-checkpoint restart-in-place is newly allowed.

**Option B: keep `rerun` as-is and bless the re-queue path.** Add a first-class verb (or make `worc run <file>` explicitly the sanctioned recovery), document it in [how-to.md](../../../docs/how-to.md), and — for the shell — move (not copy) the failed file back to `tasks/pending/` so no orphan is left. Cheaper, but loses `rerun`'s ledger attempt-linkage and leaves two conceptually-identical recoveries (`rerun` vs re-queue) the operator has to choose between.

**Option C (DEFERRED): prevent the state entirely (defense in depth, complementary to A).** Resolve the flow **before** claiming the slot / registering the task (move the `resolve` call ahead of `_register_task`, or add it to the pre-slot validation alongside the existing branch-mode IO checks at [orchestrator.py:536](../../../src/wastech_orchestrator/core/orchestrator.py#L536)), so a missing flow quarantines the task to `tasks/rejected/` before it ever gets a terminal `failed` row and a dead-end. This closes the root cause (a task should not be claimed against a flow that isn't there) but does not help tasks already stuck in the dead-end, so it pairs with A rather than replacing it. It also overlaps with the [shell-quit-safety-and-task-staging.md](../shell-quit-safety-and-task-staging.md) "don't pick up a task mid-edit" theme.

Recommendation: **A + C** — A gives stuck tasks a clean, ledger-tracked way out and matches operator intent; C stops the dead-end from being created in the first place. B is the fallback if A is judged to overload `rerun`'s semantics.

## Open questions

- Under Option A, should the pre-checkpoint restart-in-place also apply to `branch_mode: new` (where fresh-from-base already works), or stay scoped to `existing`/`current`? Leaning scoped — `new` already has a working path.
- Should Option C treat a missing flow as a hard `tasks/rejected/` quarantine (fail-closed, consistent with other pre-slot checks) or as a retryable defer (the flow might reappear, as it did here)? A defer is friendlier to the concurrent-edit case but needs a bound so a permanently-missing flow doesn't wait forever.
- Does the same dead-end exist for other pre-checkpoint terminal failures on an operator-owned branch (e.g. a branch-mode IO failure, a provider outage before the first node)? If so, A's restart-in-place should cover all of them, not just flow-resolution.

## Implementation notes

- `core/orchestrator.py`: `plan_rerun` ([orchestrator.py:908](../../../src/wastech_orchestrator/core/orchestrator.py#L908)) is the decision seam — the no-checkpoint + non-`new` branch-mode combination currently produces two refusals (points 3-4 above) and must instead yield a restart-in-place plan. `rerun_task` / a new restart path reuses `reset_task_for_rerun` ([orchestrator.py:1100](../../../src/wastech_orchestrator/core/orchestrator.py#L1100)) to clear per-attempt state without touching the branch, then re-drives via the engine.
- `cli.py`: `cmd_rerun` ([cli.py:1536](../../../src/wastech_orchestrator/cli.py#L1536)) confirmation text needs a third mode label (restart-in-place) distinct from both "from base" (fresh) and "on branch" (continue).
- Option C touches the pre-slot validation block in `run_task` ([orchestrator.py:534-538](../../../src/wastech_orchestrator/core/orchestrator.py#L534-L538)) — add flow resolution there so a missing flow is quarantined before slot acquisition and registration.
- Tests: `tests/core/test_cli_rerun.py` for the new restart-in-place path (existing branch, empty checkpoint → re-drives on the branch); a pre-slot flow-resolution reject test for Option C.
- Docs: [how-to.md](../../../docs/how-to.md) §2 currently recommends fresh/`--continue` for a failed task and is wrong for this case — update it once the behavior lands (or now, if B/interim guidance is chosen).
