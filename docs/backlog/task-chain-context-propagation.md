# Task-chain context propagation

Status: **proposed** Date: 2026-07-01 Owner: Vladimir Makarevich

When the orchestrator runs a sequence of dependent tasks (A→B→C→D) — whether defined by the operator via `depends_on` or generated by a decompose run — each successor agent starts blind: it does not know what predecessor tasks decided, built, or deliberately left out of scope. This document proposes a focused "chain summary" mechanism to propagate that context forward through the dependency chain, improving agent quality and reducing wasted exploration.

## The problem

When task B runs after task A it does not know what A built, what architectural decisions A locked, or what A explicitly deferred. Three concrete failure modes follow: (1) B duplicates work A already completed, (2) B breaks an interface or contract that A established, (3) B spends tokens re-exploring the codebase to understand things A already resolved. All three degrade result quality and increase cost.

## Constraints

- No secrets in any task artifact (`.worc/` paths included) — `security.md` C1.
- Cross-platform paths: `pathlib` + `Path.as_posix()` for any stored/compared path string — `coding-style.md`.
- The core must not know CLI syntax; this mechanism lives in the orchestrator layer, not inside a provider.
- Chain summaries are advisory only — they inform the next agent but do not constrain the Core state machine or the provider.
- This mechanism is distinct from the long-term memory subsystem (`.worc/memory/`). Long-term memory accumulates durable, repo-scoped lessons across many independent runs. Chain summaries propagate transient, chain-scoped context within a single dependency sequence. They must not be stored in the memory tiers.

## Alternatives considered

| Option | Why rejected |
| --- | --- |
| Full git diff + task log injected into prompt | Contextually complete but too noisy. The next agent drowns in implementation details rather than seeing decisions. Token cost is high and the signal-to-noise ratio is low. |
| Rely on long-term memory store | Wrong semantics. Long-term memory is designed for durable lessons that survive across many independent runs, not for immediate task-to-task handoffs within one chain. Mixing them conflates two distinct retention horizons. |
| Do nothing (agent reads git history) | Git shows what changed, not why. The agent has no view into which decisions are locked, which trade-offs were accepted, or what was deliberately left out of scope. |

## Decision

The supervisor generates a focused `chain_summary.md` at its existing `finalize` step for every completed task. The file is stored at `.worc/tasks/<task-id>/chain_summary.md` alongside existing task artifacts. When a dependent task starts, the orchestrator walks the `depends_on` graph, collects `chain_summary.md` files from all predecessors in chronological order (oldest → most recent), and injects them into the planning prompt via a `{predecessor_context}` block — the same pattern as `{memory_path}`.

The summary is generated with a forward-looking framing: "what does the next agent in this chain need to know?" — not a retrospective of what was done. This keeps summaries compact (~100–200 tokens each) and focused on what actually matters to the successor. The format is three fixed sections:

- **New surface area** — files, modules, APIs, config keys the successor can and should use.
- **Locked decisions** — architectural or design choices that must not be revisited. Includes the brief rationale so the successor does not waste time re-litigating them.
- **Open edges** — work deliberately deferred or left to the successor, and anything the successor must not touch.

The cost of the rejected alternatives: the full-diff approach would be contextually richer but produces prompt noise that degrades rather than improves agent focus; the do-nothing approach is cheap but leaves agents blind to the non-obvious decisions that most often cause task failures.

## Scope

**V1 covers:**

- Linear dependency chains (A→B→C→D) — both manually-defined `depends_on` in task YAML and chains produced by `decompose`.
- Per-predecessor files: one `chain_summary.md` per completed task, collected and ordered by the orchestrator.

**Explicitly out of scope for V1:**

- Parallel tasks (no defined ordering — unclear which summary to propagate).
- Diamond-shaped dependencies (B depends on both A and X simultaneously — merging summaries from multiple independent predecessors is a separate design problem).
- Intra-task node summaries (context handoff between `planning` → `implementation` → `review` within one task — different mechanism, different retention horizon).
- Auto-regeneration of a chain summary if a predecessor task is re-run.

## Open questions

- **Soft cap on long chains**: if the chain is 10+ tasks deep, injecting all predecessor summaries could become expensive. Needs a policy (last N, token budget cap, or summarise-the-summaries). Left open for V1 implementation.
- **Missing predecessor summary**: if a predecessor task failed, was manually skipped, or pre-dates this feature, its `chain_summary.md` will not exist. The orchestrator should proceed gracefully (skip the missing entry, log a warning) rather than fail the dependent task.
- **Injection scope**: inject into `planning` prompt only, or also into `implementation`? Planning is the natural point; implementation may not need it if planning produces a good enough brief.

## Implementation notes

Key seams to touch:

- **Supervisor finalize** (`src/wastech_orchestrator/supervisor.py`, the `finalize` method): add a new structured-output block for `chain_summary` on the same LLM turn as the existing memory delta — zero additional LLM calls.
- **Task init / preflight** (engine driver or task runner): walk `task.depends_on`, resolve `.worc/tasks/<dep-id>/chain_summary.md` for each, assemble ordered list, write a combined context file under `logs/<task-id>/predecessor_context.md`.
- **Planning role prompt** (`packaged/flows/.../planning` role prompt): add a `{?predecessor_context}…{/predecessor_context}` conditional block, mirroring the `{?memory_path}` pattern already in place.
- **Storage**: `.worc/tasks/<task-id>/chain_summary.md` — no schema change, no new DB table.
