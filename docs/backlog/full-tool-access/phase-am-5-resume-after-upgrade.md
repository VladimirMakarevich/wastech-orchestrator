# Ам-5, находки живой пробы — операторский resume после апгрейда

Status: **open — две находки, обе с обходом, обе воспроизведены на живом прогоне** Date: 2026-08-24 Owner: Vladimir Makarevich Основание: живая проба Блока А фазы [Ам-5](phase-am-5-ordinary-state-and-codex-home.md) — повтор сценария `journey-18a-journey-recap` на репозитории `wastime-app-content`

Фаза Ам-5 сняла парковку с обычного состояния репозитория. Живая проба, которая эту фазу принимает, до узла не дошла: обе находки ниже сработали **раньше первой строки прогона** — на апгрейде и на команде `rerun --continue`. Обе имеют один и тот же профиль: код фаза-за-фазой делает правильную вещь, а сторож рядом с ней считает обычную операторскую работу нарушением. То есть это ровно тот класс, который Ам-5 и разбирала, просто на два шага раньше по времени — на пути «поставил новую версию и продолжил задачу».

Обе обойдены руками, чтобы проба состоялась; обход записан в каждой находке, потому что он же показывает, насколько мал настоящий объём починки.

## Ам5-1 — версия схемы БД паркует апгрейд, у которого нет ни одного разрушительного изменения

**Что произошло.** После установки сборки с `DB_SCHEMA_VERSION = 25` ([`state_store.py:41`](../../../src/wastech_orchestrator/state_store.py)) любая команда над существующим `state.db` (стоял `24`) отвечает отказом:

```text
error: state.db schema version 24 predates an incompatible (destructive) schema change and
cannot be migrated in place; delete the local state.db or start a fresh workspace
(greenfield — there is no production data to preserve)
```

Отказ ставит ветка `0 < current < DB_SCHEMA_VERSION` в [`_enforce_schema_version`](../../../src/wastech_orchestrator/state_store.py) ([`state_store.py:180-186`](../../../src/wastech_orchestrator/state_store.py)). Она не смотрит, **чем** отличаются две схемы: любая версия ниже текущей объявлена разрушительной по построению.

**Почему это неверно здесь.** Разница между v24 и v25 ровно одна колонка, и она аддитивная и nullable:

```sql
-     push_url_digest TEXT
+     push_url_digest TEXT,
+     base_ref TEXT
```

`_migrate` эту колонку уже умеет добавлять — `base_ref` стоит в его же списке ([`state_store.py:110`](../../../src/wastech_orchestrator/state_store.py)) рядом с `gate_reference_sha` и `push_url_digest`. То есть код, который довёл бы базу до текущей формы, написан и лежит на две функции ниже той, что отказывает его звать.

**Чем это стоило прогону.** «Greenfield — нет продакшн-данных» верно про поставку и неверно про рабочий репозиторий: в `state.db` лежат чекпоинт припаркованной задачи, леджер попыток и вся история узлов. Удалить базу значит потерять именно то, ради чего запускается `rerun --continue` — задачу, которая стоит $14 уже потраченной работы. Единственный предложенный отказом выход уничтожает то, что оператор пытается спасти.

**Обход, применённый руками** (после сверки `_SCHEMA` двух сборок — расхождение действительно одна колонка):

```sh
sqlite3 .worc/state.db "ALTER TABLE tasks ADD COLUMN base_ref TEXT; PRAGMA user_version=25;"
```

Ровно то, что сделал бы `_migrate`. После этого `worc status`, `rerun --dry-run` и сам прогон пошли без единого замечания.

**Что нужно.** Версия должна нести признак «эта ступенька аддитивная», а не считаться разрушительной оптом. Форма — на усмотрение реализации; самая дешёвая: константа последней разрушительной версии (`_LAST_DESTRUCTIVE_SCHEMA_VERSION`), и отказ ставится только при `current <` неё, иначе идёт `_migrate` и штамп. Тогда объявление аддитивного бампа — правка одного числа в том же месте, где правится `DB_SCHEMA_VERSION`, и забыть её нельзя, не забыв сам бамп.

Отрицательное требование: не превращать `_migrate` в общий движок миграций. Разрушительные ступеньки остаются fail-closed, меняется только то, что аддитивная перестаёт выдавать себя за разрушительную.

## Ам5-2 — своя незакоммиченная работа не опознаётся, если её написал `agent`-узел

**Что произошло.** Дерево после парковки держало написанную главу — выход узлов `write` и `polish`. `rerun --continue` отказал:

```text
rerun: the working tree has unaccounted changes
(mobile/wastime-journey-book/18a_journey_recap_time_journey_ru.md); resolve them before rerun
```

Отказ ставит [`orchestrator.py:1209-1213`](../../../src/wastech_orchestrator/core/orchestrator.py) по предикату `resume_tolerates_wip` ([`:1201`](../../../src/wastech_orchestrator/core/orchestrator.py)), а тот — [`_worktree_is_task_output`](../../../src/wastech_orchestrator/core/orchestrator.py) ([`:1123`](../../../src/wastech_orchestrator/core/orchestrator.py)):

```python
return any(
    r.node_kind in ("evaluator", "checks", "publish")
    for r in self._store.get_node_runs(task_id)
)
```

**Почему это неверно.** Предикат отвечает на вопрос «дошла ли задача до стадии, которая работает по произведённому коду» — и берёт ответ по трём видам узлов, ни один из которых не пишет. Пишет `agent`. В прогоне 18A к моменту парковки отработали `brief` (agent), `write` (agent), `prose_lint` (**tool**) и `polish` (agent): глава написана целиком и вычитана, а предикат говорит «дерево чужое».

Это не частный случай флоу. Контентные флоу этого репозитория собраны из `agent` и `tool`: гейты — `check_prose` и `check_journey`, оба `kind: tool`. То есть **ни один прогон такого флоу не может быть продолжен через `--continue`, если он припарковался в фазе письма** — а именно там он и паркуется, потому что там живёт вся работа.

**Второй носитель того же предиката.** `preserve_own_wip` ([`:1958`](../../../src/wastech_orchestrator/core/orchestrator.py) и [`:4529`](../../../src/wastech_orchestrator/core/orchestrator.py)) считается им же. Данные при этом не теряются — `terminal_cleanup` в `new`-режиме на грязном дереве без `preserve_own_wip` не чекаутит базу поверх работы, а честно отдаёт `safe=False` ([`git_manager.py:3236-3243`](../../../src/wastech_orchestrator/git_manager.py)). Но слот остаётся заблокированным, и оператор получает второй отказ там, где фаза Ам-5 обещала предупреждение.

**Обход, применённый руками.** Написанная глава закоммичена оператором на ветку задачи отдельным коммитом, дерево стало чистым, `rerun --continue --from polish` пошёл. Обход рабочий, но он делает ровно то, чего Т5.2 не хотела: работа задачи попадает в PR коммитом оператора, а не коммитом `commit_code`, и в отчётный дифф от `base_ref` она уже не войдёт — `base_ref` встанет на resume поверх неё.

**Что нужно.** Предикат должен опознавать выход пишущего узла. Носитель уже есть и уже читается — `node_runs.node_kind`; добавляется `agent` с непустым `permission_profile: workspace-write` (или просто `agent`, если различать профили не нужно). Тогда «дошла ли задача до стадии, которая пишет» отвечается по тому, что действительно писало, а не по трём видам узлов, которые бывают рядом.

Проверка, которую стоит держать тестом: флоу без единого `evaluator` / `checks` / `publish` узла, припаркованное после пишущего узла, продолжается `--continue` и своё WIP не теряет.

## Чем кончилась проба

После обоих обходов прогон прошёл целиком: `journey-18a-journey-recap` → `done`, PR [#8](https://github.com/VladimirMakarevich/wastime-app-content/pull/8), 19:19 → 20:51, `fix_iterations=5`, дерево после публикации чистое.

**Блок Б доказан живьём.** Шесть попыток Codex, все `succeeded`, ни одного `permission_denied` и ни одного отката на Claude — при том что предыдущие пять прогонов подряд падали на первой же попытке Codex:

| Узел | Модель | Время | Итог |
| --- | --- | --- | --- |
| `polish` | `gpt-5.6-sol` | 411 с | succeeded |
| `rules_critic` ×3 | `gpt-5.6-sol` | 308 / 160 / 160 с | succeeded |
| `rules_fixing` ×2 | `gpt-5.5` | 165 / 153 с | succeeded |

`rules_fixing` важнее остальных: он правит файлы, то есть проходит ровно тем путём `apply_patch` → fs sandbox helper → re-exec бинаря под `sandbox-exec`, который деналь на `$CODEX_HOME` и ломала. Это закрывает вторую живую пробу из DoD фазы на этом хосте.

## Что проба доказала попутно

Обе находки — про путь **до** прогона. Сам сценарий Ам-5 после обходов пошёл штатно: `--continue` усыновил живую контрольную плоскость (`control plane adopted on --continue`, `bundle_digest=2effd5a89bf5`) вместе с правкой флоу, сделанной оператором за полчаса до запуска, — то есть Т5.4 работает на живом хосте, а не только в тестах. Т5.13 тоже видна строкой: `observation cadence narrowed by the flow; the whole-task summary is unaffected` с перечнем отброшенных триггеров.
