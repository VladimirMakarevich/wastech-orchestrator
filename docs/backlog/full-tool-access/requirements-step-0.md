# Шаг 0 (окружение) — требования и критерии приёмки

Status: **accepted** Date: 2026-08-13 Owner: Vladimir Makarevich Основание: [full-tool-access-for-agents.md](full-tool-access-for-agents.md), раздел «Шаг 0 — окружение: три механизма»

Это контракт приёмки, а не пересказ ADR: реализация принимается по критериям ниже. Требования пронумерованы (Т0.x), критерии приёмки — AC под своим требованием, отрицательные требования — Н0.x. Каждое требование помечено фазой, которая его закрывает; порядок фаз и их файлы — в README этой папки.

## Цель шага в наблюдаемых терминах

Утилита, которой нужна **своя** переменная окружения — корень тулчейна, путь кэша, шим версии, — работает и у агента, и у Check Runner-а; появление следующего тулчейна не требует ни правки кода, ни перечисления его имён заранее; сломанный `allowed_environment` виден до запуска, а не в виде «CLI did not succeed».

Чего шаг **не** делает и почему это важно понимать при приёмке: он не добавляет агенту ни одной новой возможности сверх уже разрешённых. `PATH` пробрасывается целиком и сегодня, поэтому утилита, которая просто лежит на `PATH` (`jq`, `fd`, `rg`, `yq`, `sqlite3`), уже видна любому узлу, которому его provider-профиль даёт шелл. Практический выигрыш от назначаемых корней и кэшей получают агентские процессы, Check Runner и сканеры; orchestrator-owned `git`/`gh` получает те же назначения только до своего отдельного scrub. Advanced mode меняет область действия allow-list и записи вне клона; точная оговорка теперь является частью требований ниже, а не подразумевается из старого состояния провайдеров.

## Инварианты, которые Шаг 0 не двигает

- **И-1.** При `strict_isolation: true` агентская политика и при любом значении режима политика orchestrator-owned `git`/`gh` остаются **allow-list по именам**. Advanced mode намеренно передаёт агентским процессам родительское окружение целиком, кроме имён, загруженных из `.worc/.env`; это принятая режимная оговорка, а не свойство Шага 0.
- **И-2.** При strict isolation ни одно секретное **имя**, полученное через шаблон `allowed_environment`, не проходит фильтр; `extra_environment` отвергает секретные имена при любом режиме. Advanced mode может передавать секретно названные переменные из родительского окружения и компенсирует это редакцией; имена из `.worc/.env` всё равно удерживаются. Политика «секретного имени» ровно одна — `is_sensitive_key` ([`redaction.py`](../../../src/wastech_orchestrator/providers/redaction.py)); своего списка масок не заводим.
- **И-3.** `PATH` целиком через конфиг не переопределяется: перезапись `PATH` — это способ подменить любую утилиту. Менять его значение вправе только адаптер через `_augment_child_env` ([`_adapter_base.py:296`](../../../src/wastech_orchestrator/providers/_adapter_base.py)), как Codex делает для своего Windows-хелпера.
- **И-4.** Набор литералов редакции не сужается. Механизм `secret_env_values` собирает значения по правилу «имя секретное **и** его нет в `allowed_environment`» ([`redaction.py:126`](../../../src/wastech_orchestrator/providers/redaction.py)), поэтому любое расширение allow-list потенциально выводит значение из-под вычистки в логах, артефактах и памяти. Шаг 0 обязан оставить этот набор прежним или больше — никогда меньше.
- **И-5.** Отсутствие новых ключей = сегодняшнее поведение **байт в байт**: тот же набор имён, те же значения, тот же порядок.
- **И-6.** Commit / push / PR штатно делает только оркестратор; Шаг 0 этого не касается ни одной строкой. `denied_commands` остаётся сигналом/трением там, где провайдер его поддерживает, но не называется полом: на Codex он не проецируется, а механическая часть публикационного пола описана в [preconditions-floor.md](preconditions-floor.md) и [requirements-advanced-mode.md](requirements-advanced-mode.md).

## Т0.1 — сломанный `allowed_environment` виден до запуска

**Фаза 0.1.** Сегодня проверки нет ни одной: список заменяет дефолт целиком ([`loader.py:573`](../../../src/wastech_orchestrator/config/loader.py)), и оператор, вычеркнувший нужное имя, узнаёт об этом по симптому — на Windows Node-овый `claude.exe` падает с `0xC0000409` до вывода чего-либо, и preflight сообщает «CLI did not succeed».

Проверка разделена по признаку «зависит ли вердикт от хоста», и это разделение — часть требования, а не деталь реализации: конфиг обязан получать один и тот же вердикт на любой машине, а всё, что зависит от ОС хоста, живёт в preflight.

- **Т0.1.1** Конфиг без `PATH` в `security.allowed_environment` — ошибка `validate_config`, host-independent. Без `PATH` strict-mode агентский процесс не находит свой CLI, а orchestrator-owned `git`/`gh` не находит исполняемые файлы при любом режиме.
- **Т0.1.2** На хосте с `platform.system() == "Windows"` конфиг без `SystemRoot` — **FAIL** `worc preflight` и launch-critical отказ `worc run` / `worc watch` / `worc rerun`. Гейт действует в обоих режимах: orchestrator-owned `git`/`gh` всегда остаются на allow-list; при strict isolation дополнительно может молча падать Node-based CLI (`claude.exe` наблюдался с `0xC0000409`). На POSIX то же имя не требуется и не упоминается.
- **Т0.1.3** Документация перестаёт утверждать, что в сгенерированном `config.yaml` лежит кросс-платформенный союз: `install` пишет только дефолт хост-ОС.

**AC0.1.1** `validate_config` на конфиге без `PATH` возвращает issue с именем ключа и подсказкой; тесты настоящего CLI-dispatch подтверждают отказ `worc run` / `worc watch` / `worc rerun`. **AC0.1.2** Чистая функция с подставленной `system="Windows"` даёт FAIL при отсутствии `SystemRoot` и OK при его наличии; тот же конфиг под `system="Linux"` — OK; preflight и task-start используют один гейт. **AC0.1.3** `guide/config/reference.md` и `config.example.yaml` описывают разницу «шаблон (22 имени) против сгенерированного конфига (дефолт хост-ОС)». **AC0.1.4** Живая проба на Windows-хосте остаётся `live-only`: конфиг без `SystemRoot` должен остановиться до запуска CLI; без Windows-хоста кодовая ветка принимается по инъекции платформы, но не объявляется живой host-пробой.

Рассмотрено и отклонено: отдельная проверка на `USER` (macOS резолвит креденшелы через Keychain по `$USER`). Preflight уже фейлит провайдера с `auth=logged_out` и объясняет причину в `reference.md`; вторая проверка того же симптома — дублирование.

## Т0.2 — `security.extra_environment`: значение задаётся, а не наследуется

**Фаза 0.2.** Форвардинг плохо масштабируется на тулчейны: надо знать, что переменная выставлена у оператора, и её значение нигде не зафиксировано, поэтому на другой машине тот же конфиг даёт другое поведение, а забытый `export` молча пропускается ([`env.py:101`](../../../src/wastech_orchestrator/security/env.py)).

- **Т0.2.1 Формат.** `security.extra_environment` — маппинг «строковое имя → строковое значение», по умолчанию пустой. YAML-ключи и значения, которые парсер иначе превратил бы в bool/int/float/null (`on`, `NO`, `1`, `1.10`), отвергаются с подсказкой закавычить исходный текст; уже преобразованное значение в подсказке не повторяется. Имя обязано соответствовать `[A-Za-z_][A-Za-z0-9_]*`; пустая строка как **значение** разрешена. Два имени, различающиеся только регистром, — ошибка валидации.
- **Т0.2.2 Скоуп и единый построитель.** Каждый агентский, check-, scanner- и tool-процесс получает окружение через `build_child_env(SecurityConfig)`. Orchestrator-owned `git`/`gh` получает `build_orchestrator_env(SecurityConfig)` и затем обязательный publication-retargeting scrub; config-aware helper-git пути получают тот же `SecurityConfig`, а install-пробы до появления конфига — явно задокументированный built-in fallback. Нельзя собирать соответствующее окружение вручную из отдельных полей.
- **Т0.2.3 Приоритет и детерминизм.** `extra_environment` применяется **после** форвардинга и перекрывает одноимённое унаследованное значение. На Windows дедупликация и перекрытие регистронезависимы, так что `NPM_CONFIG_CACHE` и `npm_config_cache` не остаются двумя конкурирующими ключами. Порядок результата детерминирован.
- **Т0.2.4 `PATH` запрещён** как ключ `extra_environment` — ошибка валидации (И-3). На Windows имена окружения регистронезависимы, поэтому запрет ловит и `Path`, и `path`.
- **Т0.2.5 Секретные имена запрещены** — по `is_sensitive_key`, ошибка валидации (И-2).
- **Т0.2.6 Значения не проверяются на секретность, и это говорится вслух.** Проверить нечем, а значение оператор пишет сам — оно лежит открытым текстом в `config.yaml`. Гайд обязан сказать прямым текстом: креденшелы в оркестратор не заносятся, ни одним из механизмов Шага 0. **Уточнение факта (2026-08-13):** утверждение ADR «значение видно в конфиге **и в аудите прогона**» неверно — окружение сегодня не пишется ни в один артефакт: в артефакте запроса лежат `argv`, промпт и пути ([`_adapter_base.py:710`](../../../src/wastech_orchestrator/providers/_adapter_base.py)), переменных там нет. **Решение владельца 2026-08-13:** записывать эффективное окружение в артефакт попытки в этой фазе **не** будем — воспроизводимость прогона это бы улучшило, но добавило бы новую поверхность и является отдельной фичей, а не частью Шага 0.
- **Т0.2.7 Совместимость и раздача.** Формат-добавка → `schema_version` +1 (первый уехавший шаг берёт 36); старые конфиги грузятся без ключа; `upgrade-config` подсевает ключ из шаблона; `install` пишет его в свежий конфиг; `config.example.yaml` объясняет его назначение.
- **Т0.2.8 Видимость.** При непустом ключе `worc preflight` печатает одну строку с **именами** заданных переменных и честной областью доставки: agent/check/tool получают назначения, `git`/`gh` — только имена, не снятые его scrub. Значения не печатаются.

**AC0.2.1** Тесты реальных call-site'ов подтверждают единый построитель для agent/check/scanner/tool и config-aware helper-git; комментарии не называют режимное полное окружение allowlisted. **AC0.2.2** Одноимённая переменная побеждает форвард, включая регистровое несовпадение на Windows. **AC0.2.3** `PATH`, секретное/невалидное имя, нестроковый YAML-ключ/значение и пара имён разного регистра дают точный отказ; пустое значение разрешено. **AC0.2.4** Подсказка не повторяет уже испорченное YAML-преобразованием значение. **AC0.2.5** Конфиг без ключа сохраняет обычное strict-окружение и порядок, кроме отдельно принятой защиты env-file pattern intersection. **AC0.2.6** `upgrade-config` по-прежнему подсевает ключ без побочных изменений. **AC0.2.7** Живая проба паритета остаётся `live-only`; кодовый паритет закреплён на реальных adapter/check call-site'ах под обеими политиками.

## Т0.3 — префиксные шаблоны в `allowed_environment`

**Фаза 0.3.** Т0.2 лечит сегодняшний список, но не убирает причину обращений: чтобы пробросить переменную, её имя надо **знать заранее**, а у одного тулчейна имён десяток и они неочевидны (`DOTNET_ROOT`, `DOTNET_CLI_HOME`, `DOTNET_MULTILEVEL_LOOKUP`, `NUGET_HTTP_CACHE_PATH`…). Оператор перечислит три, забудет остальные, и симптом будет не «нет переменной», а «сборка ведёт себя не так, как в терминале». Экономия здесь именно в этом, а не в «правке кода»: добавление обычного имени тоже кода не требует.

- **Т0.3.1 Грамматика.** Элемент списка — либо точное имя, либо префикс с **одной замыкающей** `*` (`DOTNET_*`, `npm_config_*`). Одинокая `*`, `*` в середине и несколько `*` — ошибка валидации. Это по-прежнему allow-list: элемент стал шаблоном, инвариант И-1 не двигается.
- **Т0.3.2 Место раскрытия.** Шаблон раскрывается по родительскому окружению чистой функцией. Strict agent-side и orchestrator-owned `git`/`gh` используют раскрытие как вход политики; advanced agent-side использует список только для диагностики области действия, а не как гейт.
- **Т0.3.3 Фильтр секретов и env-file intersection.** Каждое раскрытое имя проходит `is_sensitive_key`. Кроме того, strict agent-side не получает имя из `.worc/.env`, которое попало в список только через шаблон; точное имя остаётся явным strict-грантом. Advanced agent-side удерживает все имена env-файла, а `extra_environment` остаётся явным способом вернуть несекретное значение.
- **Т0.3.4 Отброшенное видно — и область действия названа.** `worc preflight` и preamble свежего или возобновлённого прогона используют общий formatter. В strict строка относится к `git`/`gh` и agent-side детям с оговоркой env-file intersection; в advanced — только к `git`/`gh`, потому что agent/check/tool получает родительское окружение целиком за вычетом env-файла. Чистое раскрытие логируется на INFO, отбрасывание secret-name — на WARN; отсутствие шаблонов не даёт строки ни на одном уровне.
- **Т0.3.5 Регистр.** На Windows сопоставление, дедупликация и дальнейшее перекрытие назначением регистронезависимы; на POSIX — регистрозависимы. Ветка платформы явная и покрыта тестом на обе стороны.
- **Т0.3.6 Детерминизм.** Раскрытые имена добавляются в стабильном порядке (сортировкой), потому что порядок `os.environ` воспроизводимости не даёт, а результат сравнивается в тестах и печатается в диагностике Т0.3.8.
- **Т0.3.7 Бессмысленный шаблон отвергается.** Шаблон, чей собственный префикс секретен по `is_sensitive_key` (`SECRET_*`, `TOKEN_*` — проверено, оба дают `True`), может раскрыться только в имена, которые фильтр отбросит. Валидатор его отклоняет с текстом, объясняющим механизм: иначе оператор считает переменные проброшенными, а их нет.
- **Т0.3.8 Диагностика ширины.** `worc preflight` печатает, что дал каждый шаблон: `DOTNET_* → 4 имени, NUGET_* → 3 (1 отброшено)`. Шаблон, давший ноль, — почти всегда опечатка (`DOTNET*` вместо `DOTNET_*`) или незапущенный тулчейн, и сегодня это никак не увидеть.
- **Т0.3.9 Совместимость.** Конфиг с шаблоном не понимается прошлой версией оркестратора корректно — она пробросит имя `DOTNET_*` буквально и молча не пробросит ничего. Поэтому расширение грамматики тоже несёт `schema_version` +1.

**AC0.3.1** `DOTNET_*` пробрасывает несекретные совпадения в strict mode. **AC0.3.2** Secret-name drop виден в preflight и свежем прогоне; clean INFO, отсутствие шаблонов и resume покрыты отдельно. **AC0.3.2a** `SECRET_*` — ошибка. **AC0.3.2b** Preflight печатает каждое раскрытие и его effective scope. **AC0.3.3** Одинокая `*` fail-closed и в валидаторе, и в нижнем helper. **AC0.3.4** Windows case-fold покрывает match/dedupe/override. **AC0.3.5** Редакция не сужается. **AC0.3.6** Живая strict-проба остаётся выполненной; advanced-ветка не приписывает ей ложную гарантию. **AC0.3.7** Pattern-only env-file name удерживается в strict, exact name и `extra_environment` проверены как явные способы выдачи.

Рассмотрено и **отклонено**: правило исходного ADR «валидатор отклоняет шаблон, который раскрывается в `PATH`». Форвардинг `PATH` из родителя — ровно то, что делает базовый список сегодня, и опасности не несёт; опасно **присвоение** `PATH`, а оно запрещено Т0.2.4. Правило добавляло бы проверку, которая ничего не защищает. Так же отклонены: **минимальный размер префикса** и потолок на число раскрытых имён (`D*` против `DOTNET_*`) — любой порог был бы выдуман, фильтр секретов работает независимо от ширины шаблона, а Т0.3.8 показывает ширину явно; и **распространение шаблонов на другие списочные ключи** (`denied_read_paths`, `denied_commands`) — у них своя грамматика (глобы путей, префиксы команд), общий синтаксис пришлось бы согласовывать с двумя разными семантиками, и цель об этом не просит.

## Т0.4 — кэши тулчейнов внутрь клона

**Фаза 0.4.** Если через Т0.2 перенаправить `NUGET_PACKAGES`, `CARGO_HOME`, `npm_config_cache` и `GOMODCACHE` внутрь клона, то `dotnet build`, `cargo build` и `npm ci` перестают писать в `$HOME`, и запись за пределами репо (Шаг 2) для них не нужна вовсе. Клон писабелен для `workspace-write` узла, `git clean` оркестратор не запускает, так что кэш переживает задачи.

- **Т0.4.1 Рецепт шипнут.** Гайд и `config.example.yaml` содержат рабочий рецепт перенаправления и его границы. Рекомендуемое имя каталога — `.toolcache/` внутри клона; это соглашение гайда, код на имя не завязан и работает для любого пути внутри клона.
- **Т0.4.2 Служебные пути неперекрываемы — проверка в два уровня.** Значение `extra_environment`, похожее на путь, не может указывать в `.git`, `.worc`, `tasks/`, exchange, env-файл, provider home или конкретный путь, совпавший с `denied_read_paths`; пересечение в любую сторону запрещено для фиксированных корней. Три уточнения:
  - **что считается путём.** Абсолютный или `~`-относительный элемент. Значение-список разбирается по `:` и `;` на любом host, не разрывая Windows drive prefix; несоставное значение дополнительно остаётся collision-кандидатом, но целая строка списка никогда не становится ignore-правилом. Значения без пути (`"1"`, `"C.UTF-8"`) не резолвятся;
  - **лексический уровень — в `validate_config`.** Сравнение путей без обращения к диску; ловит очевидное и даёт один и тот же вердикт на любой машине;
  - **канонизирующий уровень — в `worc preflight` и launch-critical task-start gate.** Он резолвит symlink / junction / reparse и регистр Windows и использует точные метки env-file/provider home. Реальный gitdir/common-dir linked worktree пока не входит в assigned-path protected set; это отдельный явно записанный пробел, а не доказанная гарантия.
- **Т0.4.3 За игнорирование кэша отвечает оркестратор, а не оператор.** Для каждого реального элемента path-list внутри клона оркестратор идемпотентно дописывает одно правило в `.git/info/exclude` и проверяет его через config-aware helper git. Preflight даёт FAIL, если правило не держится; branch preparation повторяет repair, но при неудаче пишет WARNING и продолжает, оставляя последующим diff-гейтам увидеть последствия. Клона нет — SKIP.

  Отклонён вариант «исключать кэш pathspec'ом при стейджинге», как сделано для `.worc/` (`RUNTIME_EXCLUDED_DIRS`): он прячет файлы от коммита, но не от `git status`, поэтому детект дрейфа рабочего дерева всё равно их увидит, и исключение пришлось бы не забыть в каждом месте стейджинга — включая прямой `git add -A` ([`git_manager.py:1727`](../../../src/wastech_orchestrator/git_manager.py)).

- **Т0.4.4 Путь наружу клона — режимно-условное предупреждение.** При strict isolation preflight печатает WARN: такой путь не является разрешённым writable cache root. В advanced mode outside-clone write является заявленной возможностью, поэтому ложного WARN нет.
- **Т0.4.5 Ограничения записаны честно.** Strict-mode `read-only` узел не может писать кэш внутрь клона независимо от наличия шелла; advanced mode может писать наружу. Кэш внутри клона растёт неограниченно, retention `.worc/runs` на него не распространяется.

**AC0.4.1** Фиксированные корни и реальные `denied_read_paths` glob-match'и закрыты; ведущий `**` ловится, `conf/*.yaml` не запрещает соседний `conf/gocache`. **AC0.4.2** Path-list понимает оба разделителя на любом host; non-path не трогает диск. **AC0.4.3** Preflight/run ловит symlink и Windows case alias, точно называет env-file/provider home; linked-worktree actual gitdir остаётся `live-only/open`. **AC0.4.4** В `.git/info/exclude` попадает по одному правилу на элемент, не строка списка; helper git использует caller policy; неудача task-start repair даёт package-log WARNING без остановки. **AC0.4.5** Outside-clone WARN есть только в strict mode. **AC0.4.6** Ранее выполненная macOS-проба остаётся доказательством strict in-clone recipe; Windows UNC/volume behavior не объявляется проверенным живьём.

## Т0.5 — паритет Check Runner-а

Требование сквозное и проверяется в Фазе 0.2, но записано отдельно, потому что это единственный способ провалить Шаг 0 «успешно»: `checks.command_sets` запускаются оркестратором **без песочницы и с полной сетью**, но с тем же `build_child_env` ([`check_runner.py:140`](../../../src/wastech_orchestrator/check_runner.py)). Агент и набор checks обязаны видеть одинаковое окружение — иначе агент собирает проект, а гейт качества падает на «SDK not found» и задача умирает после успешной работы.

**AC0.5.1** Тест сравнивает окружение реального adapter call-site и Check Runner builder при одном конфиге под strict и advanced policy; provider-specific PATH augmentation сравнивается отдельно по вхождению, остальные ключи — на точное равенство.

## Т0.6 — разбор вывода git не зависит от конфига оператора

**Фаза 0.2.** Найдено при подготовке фазы, и это не гипотетика: Git Manager классифицирует результаты **по английским строкам в выводе** — `_TRANSIENT_GIT_STDERR_MARKERS` решают, повторять ли `push` ([`git_manager.py:66`](../../../src/wastech_orchestrator/git_manager.py)), поиск `leftover conflict marker` идёт по выводу `git diff --check` ([`git_manager.py:1731`](../../../src/wastech_orchestrator/git_manager.py)), `_ALREADY_MERGED_MARKERS` — по выводу `gh pr merge` ([`git_manager.py:2077`](../../../src/wastech_orchestrator/git_manager.py)). Git локализован, поэтому `LANG: "ru_RU.UTF-8"` в `extra_environment` (а `LANG` — ровно тот пример, который приводит ADR) превратил бы временный сбой сети в окончательный отказ задачи: маркер просто не совпадёт, и молча.

- **Т0.6.1** Git Manager пиннит `LC_ALL=C` для **своих** процессов — и `git`, и `gh`. Пин ставится поверх окружения и не перекрывается ничем из конфига: место для него уже есть — `_GIT_HARDENING_ENV` ([`git_manager.py:143`](../../../src/wastech_orchestrator/git_manager.py)) применяется как раз после `build_child_env` и уже покрывает оба исполняемых файла.
- **Т0.6.2** Пин не должен ломать не-ASCII. `LC_ALL=C` меняет и классификацию символов, поэтому фаза обязана доказать тестами, что коммит-сообщение и путь с кириллицей проходят как раньше. Если тест покажет регресс — сузить пин до `LC_MESSAGES=C` (сообщения переводятся им, кодировка не трогается) и записать, что на Windows этот вариант проверен отдельно.

**AC0.6.1** При `extra_environment: {LANG: "ru_RU.UTF-8"}` вывод git в процессах Git Manager остаётся английским, и классификация transient-ошибок срабатывает. **AC0.6.2** Коммит с кириллическим сообщением и файл с кириллическим именем проходят весь путь (staging → commit → diff-разбор) без изменений против сегодняшнего поведения.

## Отрицательные требования

- **Н0.1** Никакой инверсии окружения (deny-list по именам переменных) — И-1.
- **Н0.2** Никакой подстановки `{repo}` (и любых других плейсхолдеров) в значениях `extra_environment`: рендеринга в конфиг-слое сегодня нет вообще, плейсхолдеры живут только в промпт-слое, и заводить второй движок ради удобства одного рецепта — цена больше пользы. Оператор пишет абсолютный путь, который и так знает из `repo.local_path`; расхождение с ним ловит Т0.4.2.
- **Н0.3** Доставка `extra_environment` не делается через `_augment_child_env`: по контракту хук меняет только значения уже разрешённых имён и не добавляет новых.
- **Н0.4** Свой список масок секретных имён не заводится — два расходящихся определения «секретного имени» разъедутся при первом же изменении.
- **Н0.5** Шаг 0 не трогает `--tools`, песочницу, сетевую политику, `git_evidence`, `write_guard` и порядок fallback. Любая правка в этих местах означает, что фаза вышла за свой объём.
- **Н0.6** Значения `extra_environment` **не** становятся литералами редакции. Соблазн есть — это защитило бы от секрета, попавшего в значение вопреки гайду, — но путь кэша нужен в логах для диагностики, а короткое значение вроде `"1"` изуродовало бы весь вывод: от этого в коде уже стоит порог `_MIN_DENIED_SECRET_LEN` ([`redaction.py`](../../../src/wastech_orchestrator/providers/redaction.py)).
- **Н0.7** `extra_environment` не умеет **удалять** унаследованную переменную (`NODE_OPTIONS: null` и подобное). Потребности нет, а семантика «удалить» потребовала бы отдельного типа значения — YAGNI.
- **Н0.8** Эффективное окружение не пишется в артефакты попытки. Сегодня его там нет, и Шаг 0 этого не меняет (Т0.2.6).

## Definition of Done шага

Шаг закрыт, когда: все AC выше зелёные; `ruff check .`, `ruff format --check .`, `mypy src`, `lint-imports`, `pytest` зелёные (плюс CI-гейты `interrogate` / `vulture` / `deptry`); документы ветки обновлены тем же изменением — [.agents/rules/](../../../.agents/rules/), [README.md](../../../README.md) и шипнутые операторские доки под `packaged/` (гайд, `config.example.yaml`); `install` и `upgrade-config` дают новые ключи; живые пробы каждой фазы выполнены или явно записаны как «не доказано»; в описании PR оставлена doc-impact строка для производных документов `main` (`configuration.md` — новые ключи, `operations.md` — вывод preflight).
