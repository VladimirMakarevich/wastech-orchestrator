# Фаза Пре-2 — удалённая сторона: отпечаток и восстановление

Status: **реализована 2026-08-19** (`DB_SCHEMA_VERSION` 23; пункты 0–7 целиком). Три уточнения при реализации, каждое ниже отдельным абзацем: конфликтный вариант случая 4 паркует, а не разрешается сам (решение владельца 2026-08-19); `--repo` не добавляется в `detect.py` — там `gh auth status`, у которой такого флага нет (решение владельца 2026-08-19); короткое замыкание идемпотентности push сравнивает теперь записанный SHA, иначе аренда была бы недостижима Date: 2026-08-17 Owner: Vladimir Makarevich Требования: П2 и П3 из [preconditions-floor.md](preconditions-floor.md) `schema_version`: без изменения; **`DB_SCHEMA_VERSION`: +1** (аддитивная колонка под пушнутый SHA — решение по П-В2) Зависимости: **брекет Пре-3**. П2 и П3 сделаны одной фазой намеренно — они делят чтение состояния remote, и П2 без П3 паркует то, что П3 умеет восстановить; но «по каждой попытке» удерживает не эта фаза: кто снимает отпечаток, решил Пре-3 (перекей на «есть ли у попытки шелл»), поэтому откат Пре-3 сузил бы охват П2 до пишущих попыток. Обратная связь тоже сознательная: втягивание идёт merge-коммитом типа `KIND_MERGE_COMMIT` из Пре-3, то есть сдвигает `gate_reference_sha` за содержимое, которого гейт не видел — это ответ на П3.5 (человека не спрашивают повторно про удаления, приехавшие с merge), а не побочный эффект

Отпечаток вокруг попытки сегодня целиком локальный ([`git_manager.py:1134`](../../../src/wastech_orchestrator/git_manager.py)), а вырез `.git` останавливает одну операцию из четырёх: `git push` существующей истории записи в `.git` не требует, `gh pr create` и `gh pr merge` локально не пишут вовсе. Вторая половина проблемы хуже первой: встретив неожиданное состояние remote, оркестратор записывает его как **свой успех** — `push` коротко замыкается и помечает операцию выполненной, не отправив ничего ([`git_manager.py:1859`](../../../src/wastech_orchestrator/git_manager.py)), а `_find_open_pr` подхватывает чужой открытый PR и дописывает в него секцию задачи ([`git_manager.py:2004`](../../../src/wastech_orchestrator/git_manager.py)).

## Что делаем

**0. Аддитивная колонка под пушнутый SHA** (решение владельца по П-В2). Сегодня `publish_operations` для `push` пишет имя ветки и в `fingerprint`, и в `result_ref` — сравнивать не с чем, и без этой колонки не строятся ни правило сравнения из пункта 2, ни различение случаев 3 и 4 из пункта 4. Миграция по существующему образцу (`_migrate` добавляет колонки под `PRAGMA table_info`, [`state_store.py:133`](../../../src/wastech_orchestrator/state_store.py)), `DB_SCHEMA_VERSION` +1 с абзацем истории. Ключ идемпотентности push при этом не меняется — именно поэтому переиспользование `fingerprint` отклонено.

**1. `RemoteState` рядом с `GitControlState`.** Три поля: ссылка ветки задачи по `git ls-remote --heads origin <ветка>`, финальный адрес пуша по `git remote get-url --push origin` (он резолвит `insteadOf`, `pushInsteadOf` и `pushurl`), наличие открытого PR по `gh pr list --head <ветка> --state open`. Снимается тем же брекетом, что и локальный отпечаток, **по каждой попытке**.

**1а. `GitControlState` расширяется на то, чем публикует сам оркестратор** (решение владельца по вопросу 13, ТA.1.7). Добавляются дайджесты содержимого `<клон>/.claude/settings.json`, `<клон>/.mcp.json`, `<клон>/.codex/**` и `~/.gitconfig` — по дайджесту, а не по значениям: они секрето-несущие, и `_diff_config` уже устроен так же. Мотив: на шипнутом дефолте адаптеры **намеренно** загружают проектный конфиг CLI (Claude — `--setting-sources project` со снятым `--strict-mcp-config`, [`claude.py:743-751`](../../../src/wastech_orchestrator/providers/claude.py); Codex — без `--ignore-user-config`, с `trusted` и с возвращённым `hooks`, [`codex.py:391-397`](../../../src/wastech_orchestrator/providers/codex.py)), а `~/.gitconfig` доверен в коде на посылке «агенту он недоступен» ([`git_manager.py:140-142`](../../../src/wastech_orchestrator/git_manager.py)), которую режим отменяет. Через них агент выдаёт себе исполнение кода или уводит наш собственный `push` — и отпечаток `origin` этого не видит по построению.

**1б. `--repo <owner/name>` на каждом вызове `gh`** (там же). Репозиторий сегодня выводится неявно из remote клона, поэтому подменённый `~/.config/gh/hosts.yml` или `url.*.insteadOf` перенацеливает PR молча.

**2. Правило сравнения.** Удалённая ссылка ветки задачи обязана совпадать с записанной нами в `publish_operations` при последнем пуше либо отсутствовать, если мы ещё не пушили. Базовая ветка в сравнение не входит: она законно двигается, когда кто-то смержил свой PR. Расхождение — `NodeManualRequired`, без fallback, как у локального отпечатка.

**Блокирующее уточнение независимого ревью: сравнивать пока не с чем.** `publish_operations` для `push` пишет **имя ветки** и в `fingerprint`, и в `result_ref` ([`git_manager.py:1860`](../../../src/wastech_orchestrator/git_manager.py), `:1868`); SHA не пишется нигде. Носитель заведён пунктом 0 — аддитивная колонка, решение владельца по П-В2. Второе уточнение: подмена `remote.origin.url` / `pushurl` **во время попытки** уже ловится — `_capture_local_config` собирает нефильтрованный `git config --local --worktree --list` ([`git_manager.py:1183-1200`](../../../src/wastech_orchestrator/git_manager.py)), — поэтому новизна пункта 3 только в проверке непосредственно перед пушем, и формулировку стоит сузить до неё.

**3. Адрес пуша перепроверяется безусловно перед `push` и `push_branch_update`.** Это единственное место, где ошибка попадает на настоящую ветку. Разошёлся — отказ, и **URL в сообщении редактируется**: он может нести токен. Дизайн уже написан в [read-only-shell-residues.md](../read-only-shell-residues.md) — около двадцати строк и два теста.

**4. Публикация восстанавливается вместо усыновления.** Четыре случая, различаемые двумя дешёвыми вопросами: `merge-base --is-ancestor` (обёртка `commit_on_branch` уже есть, [`git_manager.py:1058`](../../../src/wastech_orchestrator/git_manager.py)) и наличие нашей записи о пуше.

| Случай | Условие | Действие |
| --- | --- | --- |
| 1 | `remote == local` | не пушим, операцию записываем выполненной |
| 2 | remote — предок локального | обычный `git push` — **здесь сегодня баг** |
| 3 | разошлись, запись есть, аренда сходится | `git push --force-with-lease=<ветка>:<наш последний SHA>` |
| 4 | разошлись, записи нет или аренда не сошлась | `git merge origin/<ветка>` → штатный путь конфликта → коммит → push |

Аренда в третьем случае и есть защита правок оператора: если после нашего пуша он дописал свой коммит, `--force-with-lease` не сойдётся, и случай провалится в четвёртый — правка будет втянута, а не затёрта.

**5. Втягивание переиспользует существующий механизм.** Оркестратор уже умеет втягивать уехавшую базу — `git merge --no-commit --no-edit origin/<база>`, где конфликт является **штатным восстановимым состоянием**, а не отказом ([`git_manager.py:1027-1031`](../../../src/wastech_orchestrator/git_manager.py); рядом `merge_in_progress`, `merge_abort`, `push_branch_update`). Для чужих коммитов та же процедура направляется на `origin/<ветка задачи>`. Rebase не рассматривается: домашняя конвенция — merge.

**Но abort у механизма негерметичен, и фаза обязана это починить, раз переиспользует его на публикации** (находка ревью). `commit_merge_resolution` вызывается при живом `MERGE_HEAD` и может бросить `ManualActionRequired` из `_assert_no_untrusted_filters` ([`git_manager.py:1726`](../../../src/wastech_orchestrator/git_manager.py) → `:1380`) и `assert_staged_allowed` (`:1735` → `:1633`), а обработчик ловит только `(GitCommandError, PipelineFailed)` ([`orchestrator.py:1744-1745`](../../../src/wastech_orchestrator/core/orchestrator.py)) — дерево остаётся в середине merge, вопреки docstring `merge_task`, обещающему abort «on any failure», и вопреки инварианту про возврат репозитория на `base_branch`. В штатном merge-флоу это чинится следующим прогоном; в случае 4 merge происходит **на публикации**, где застрявшее дерево блокирует очистку и следующую задачу.

**6. PR переиспользуется только свой** — записанный в `publish_operations` для этой задачи, а не «любой открытый ветка → база». Проверка идёт **до** вызова `gh pr create`, потому что на существующую пару «голова → база» он отвечает ошибкой.

**7. После втягивания чужого набор checks прогоняется заново** — проверялась комбинация «наши коммиты поверх базы», а публикуется «наши плюс чужие». И **втянутое помечается**: в отчёт и тело PR добавляется строка «втянуто N посторонних коммитов: `<sha>`…», иначе отчётный diff (он считается от базы) перестанет описывать работу этой задачи.

**Решение владельца 2026-08-17 (П-В3): прогонять, при провале парковать.** Ни узел `publish`, ни Git Manager сегодня не знают Check Runner, а ядро вызывает его по графу флоу — поэтому просьбу о повторном прогоне отправляет узел `publish` через ядро, то есть поведение привязано к **kind**, а не к id, и вызов Check Runner остаётся у ядра, которому это по слоям и положено. Провал повторного прогона — `manual_action_required` со втянутым состоянием на диске и без fallback: это не quality-провал нашей работы, а непроверенное сочетание, которое обязан посмотреть человек. Отклонены: объявлять повторный прогон во флоу (новая грамматика ради одного редкого случая плюс обновление всех установленных флоу), парковать случай 4 сразу без прогона, публиковать без прогона.

## Что уточнилось при реализации

**Конфликтный вариант случая 4 паркует.** AC3.3 требовал довести до PR и конфликтный вариант, но разрешает конфликты merge-флоу, которое запускается операторской командой `merge-task` вне пайплайна, а узел `publish` работает уже внутри флоу — автоматическое разрешение потребовало бы реентерации, которой в архитектуре нет. Решение владельца 2026-08-19: конфликт — `merge --abort`, дерево восстановлено, задача паркуется со списком чужих коммитов; человек проводит её через `merge-task`. Чистый merge автоматизирован полностью. Отклонены: просьба узла к ядру прогнать вложенное merge-флоу (новая механика ради редкого случая) и вынос конфликтной ветки в отдельную фазу.

**`--repo` не доходит до `detect.py`.** Пункт 1б говорил «восемь вызовов через `_gh` плюс один прямой в `detect.py:150`», но там `gh auth status` — хостовая проверка авторизации, у которой флага `--repo` нет вовсе (`gh` 2.97.0: только `--active`, `--hostname`, `--show-token`, `--json`), и перенацелить PR она не может. Решение владельца 2026-08-19: оставить как есть. Восемь вызовов через `_gh` пин несут; на тех из них, что адресуют PR полным URL, `gh` берёт репозиторий из URL, так что пин там безвреден, а работает он на `pr create` и `pr list`.

**Якорь пина — `repo.url`.** Выводить `owner/name` из клона нельзя: это ровно та поверхность, которую пункт защищает. Ключ `repo.url` заполняется `worc install` из `origin` и читается в память до старта агента; когда он не называет хостируемый репозиторий (рукописный конфиг), однократно отвечает `origin` клона — первым, кто спрашивает, является отпечаток, снимаемый **до** запуска провайдера. Непарсимый адрес пина не даёт вовсе: неверный пин хуже отсутствующего.

**Короткое замыкание push пришлось уточнить, иначе случай 3 недостижим.** Идемпотентный выход стоял перед всей логикой, поэтому при завершённой записи push таблица П3.1 не выполнялась никогда. Теперь выход срабатывает, когда записанный пушнутый SHA всё ещё является вершиной ветки (или записи о SHA нет — старое поведение по статусу); иначе решает удалённое состояние. Ключ идемпотентности (`task_id`, `kind`, `subtask_order`) не изменился. Побочное следствие записано было неверно и исправлено 2026-08-20. Путь «`rerun` теряет аренду и уходит в случай 4» `plan_rerun` не даёт: свежий `rerun` в режиме `new` при существующей удалённой ветке или записанном PR отказывает, `--force-reset-remote` ветку удаляет, `--continue` записи сохраняет, а в `existing`/`current` отказ приходит при чекпоинте. Достижим другой путь того же класса: `remote_branch_exists` отвечает «нет» и при **недоступном** remote, и тогда пуш втягивает коммиты собственной прошлой попытки. Поэтому в тексте notice и в операторских строках больше не утверждается авторство («commit(s) this orchestrator did not make» → «this run did not record pushing»): случай 4 не может отличить чужой коммит от своего непризнанного.

## Тесты

Ветка задачи, появившаяся на remote во время попытки без нашей записи, паркует задачу **до** checks. Движение базовой ветки не паркует ничего. Подменённый `pushurl` ловится перед пушем, URL в сообщении отредактирован. Открытый PR на ветку задачи, которого нет в наших записях, паркует — **и не переименовывается**: сегодня `_append_reused_pr_body` меняет чужому PR заголовок на «N tasks on `<branch>`» ([`git_manager.py:1964`](../../../src/wastech_orchestrator/git_manager.py), `:1970`) и может урезать чужой текст через `_bound_pr_body` (`:403-432`). Отдельный тест на путь с `branch_name` из файла задачи: имя ветки берётся из задачи дословно ([`git_manager.py:744-753`](../../../src/wastech_orchestrator/git_manager.py)), поэтому короткое замыкание `push` сегодня записывает как свою публикацию любую существующую ветку, а не только «свою прошлую попытку» — эта ветка кода не покрыта ни одним тестом. Подменённый `<клон>/.claude/settings.json`, `.mcp.json`, `<клон>/.codex/config.toml` или `~/.gitconfig` во время попытки паркует задачу, а его содержимое в отпечатке лежит дайджестом, не значением. Каждый вызов `gh` несёт `--repo`; подставленный `GH_REPO` или `url.*.insteadOf` публикацию не перенацеливает. Миграция: база предыдущей версии открывается, колонка под SHA добавляется, существующие записи не теряются. Случай 2 действительно пушит: после нашего пуша добавлен локальный коммит — удалённая ссылка сдвинулась. Случай 3 с чужим коммитом поверх нашего пуша не затирает его, а уходит в случай 4. Случай 4 доводит задачу до PR без вмешательства человека, включая конфликтный вариант. После втягивания checks прогнаны повторно, в теле PR есть строка о втянутых коммитах.

## Живая проба (часть DoD)

На безопасном тестовом remote: пуш ветки «мимо» оркестратора паркует задачу; `rerun` после упавшего прогона доводит задачу до PR через случай 3; чужой коммит поверх нашего пуша уходит в случай 4 и втягивается.

## Риск и откат

Цена пересчитана по замеру против настоящего GitHub (2026-08-20): `ls-remote` — 0,64 с, `gh pr list` — 0,52 с, то есть один снимок ≈ 1,2 с и один вызов API, а брекет снимает отпечаток дважды — ≈ 2,3 с и 2 вызова **на узел**. Первоначальная оценка («0,2 с, секунды суммарно на двадцать узлов») занижена на порядок, и занизила её не эта фаза: на момент оценки бракетились только пишущие попытки, а Ам-3 расширила брекет до любой попытки с шеллом (Пре-1/Пре-3 — до evaluator'а и супервизорской попытки). На флоу из двадцати узлов это ≈ 45 с и 40 вызовов API из пяти тысяч в час — приемлемо, но это уже не «секунды». Если станет дорого, дешёвый шаг — один снимок на узел вместо двух там, где сравнение всё равно идёт против записанного `pushed_sha`. Главный риск не в цене, а в ложных срабатываниях, поэтому правило сравнения намеренно узкое: только ветка задачи, только против собственной записи. Откат раздельный: пункты 1–3 (детект) снимаются независимо от 4–7 (восстановление), но снимать 4–7, оставив 1–3, нельзя — получится парковка там, где раньше был штатный `rerun`.

## Что эта фаза чинит без всякого режима

Три из семи пунктов — дефекты сегодняшнего дня: пуш, записанный выполненным без отправки; чужой PR, дописанный как свой; отсутствие перепроверки адреса пуша. Они окупаются до того, как режим будет включён хоть раз.
