# Фаза Пре-2 — удалённая сторона: отпечаток и восстановление

Status: **ready to implement** Date: 2026-08-17 Owner: Vladimir Makarevich Требования: П2 и П3 из [preconditions-floor.md](preconditions-floor.md) `schema_version`: без изменения Зависимости: нет. П2 и П3 сделаны одной фазой намеренно — они делят чтение состояния remote, и П2 без П3 паркует то, что П3 умеет восстановить

Отпечаток вокруг попытки сегодня целиком локальный ([`git_manager.py:1134`](../../../src/wastech_orchestrator/git_manager.py)), а вырез `.git` останавливает одну операцию из четырёх: `git push` существующей истории записи в `.git` не требует, `gh pr create` и `gh pr merge` локально не пишут вовсе. Вторая половина проблемы хуже первой: встретив неожиданное состояние remote, оркестратор записывает его как **свой успех** — `push` коротко замыкается и помечает операцию выполненной, не отправив ничего ([`git_manager.py:1859`](../../../src/wastech_orchestrator/git_manager.py)), а `_find_open_pr` подхватывает чужой открытый PR и дописывает в него секцию задачи ([`git_manager.py:2004`](../../../src/wastech_orchestrator/git_manager.py)).

## Что делаем

**1. `RemoteState` рядом с `GitControlState`.** Три поля: ссылка ветки задачи по `git ls-remote --heads origin <ветка>`, финальный адрес пуша по `git remote get-url --push origin` (он резолвит `insteadOf`, `pushInsteadOf` и `pushurl`), наличие открытого PR по `gh pr list --head <ветка> --state open`. Снимается тем же брекетом, что и локальный отпечаток, **по каждой попытке**.

**2. Правило сравнения.** Удалённая ссылка ветки задачи обязана совпадать с записанной нами в `publish_operations` при последнем пуше либо отсутствовать, если мы ещё не пушили. Базовая ветка в сравнение не входит: она законно двигается, когда кто-то смержил свой PR. Расхождение — `NodeManualRequired`, без fallback, как у локального отпечатка.

**3. Адрес пуша перепроверяется безусловно перед `push` и `push_branch_update`.** Это единственное место, где ошибка попадает на настоящую ветку. Разошёлся — отказ, и **URL в сообщении редактируется**: он может нести токен. Дизайн уже написан в [read-only-shell-residues.md](../read-only-shell-residues.md) — около двадцати строк и два теста.

**4. Публикация восстанавливается вместо усыновления.** Четыре случая, различаемые двумя дешёвыми вопросами: `merge-base --is-ancestor` (обёртка `commit_on_branch` уже есть, [`git_manager.py:1058`](../../../src/wastech_orchestrator/git_manager.py)) и наличие нашей записи о пуше.

| Случай | Условие | Действие |
| --- | --- | --- |
| 1 | `remote == local` | не пушим, операцию записываем выполненной |
| 2 | remote — предок локального | обычный `git push` — **здесь сегодня баг** |
| 3 | разошлись, запись есть, аренда сходится | `git push --force-with-lease=<ветка>:<наш последний SHA>` |
| 4 | разошлись, записи нет или аренда не сошлась | `git merge origin/<ветка>` → штатный путь конфликта → коммит → push |

Аренда в третьем случае и есть защита правок оператора: если после нашего пуша он дописал свой коммит, `--force-with-lease` не сойдётся, и случай провалится в четвёртый — правка будет втянута, а не затёрта.

**5. Втягивание переиспользует существующий механизм.** Оркестратор уже умеет втягивать уехавшую базу — `git merge --no-commit --no-edit origin/<база>`, где конфликт является **штатным восстановимым состоянием**, а не отказом ([`git_manager.py:1027`](../../../src/wastech_orchestrator/git_manager.py); рядом `merge_in_progress`, `merge_abort`, `push_branch_update`). Для чужих коммитов та же процедура направляется на `origin/<ветка задачи>`. Rebase не рассматривается: домашняя конвенция — merge.

**6. PR переиспользуется только свой** — записанный в `publish_operations` для этой задачи, а не «любой открытый ветка → база». Проверка идёт **до** вызова `gh pr create`, потому что на существующую пару «голова → база» он отвечает ошибкой.

**7. После втягивания чужого набор checks прогоняется заново** — проверялась комбинация «наши коммиты поверх базы», а публикуется «наши плюс чужие». И **втянутое помечается**: в отчёт и тело PR добавляется строка «втянуто N посторонних коммитов: `<sha>`…», иначе отчётный diff (он считается от базы) перестанет описывать работу этой задачи.

## Тесты

Ветка задачи, появившаяся на remote во время попытки без нашей записи, паркует задачу **до** checks. Движение базовой ветки не паркует ничего. Подменённый `pushurl` ловится перед пушем, URL в сообщении отредактирован. Открытый PR на ветку задачи, которого нет в наших записях, паркует. Случай 2 действительно пушит: после нашего пуша добавлен локальный коммит — удалённая ссылка сдвинулась. Случай 3 с чужим коммитом поверх нашего пуша не затирает его, а уходит в случай 4. Случай 4 доводит задачу до PR без вмешательства человека, включая конфликтный вариант. После втягивания checks прогнаны повторно, в теле PR есть строка о втянутых коммитах.

## Живая проба (часть DoD)

На безопасном тестовом remote: пуш ветки «мимо» оркестратора паркует задачу; `rerun` после упавшего прогона доводит задачу до PR через случай 3; чужой коммит поверх нашего пуша уходит в случай 4 и втягивается.

## Риск и откат

`ls-remote` — один round-trip порядка 0.2 секунды, `gh pr list` — один вызов API из пяти тысяч в час; на флоу из двадцати узлов это секунды суммарно. Главный риск не в цене, а в ложных срабатываниях, поэтому правило сравнения намеренно узкое: только ветка задачи, только против собственной записи. Откат раздельный: пункты 1–3 (детект) снимаются независимо от 4–7 (восстановление), но снимать 4–7, оставив 1–3, нельзя — получится парковка там, где раньше был штатный `rerun`.

## Что эта фаза чинит без всякого режима

Три из семи пунктов — дефекты сегодняшнего дня: пуш, записанный выполненным без отправки; чужой PR, дописанный как свой; отсутствие перепроверки адреса пуша. Они окупаются до того, как режим будет включён хоть раз.
