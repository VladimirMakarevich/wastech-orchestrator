# Фаза Ам-2 — окружение целиком, редакция и видимость режима

Status: **ready to implement** Date: 2026-08-17 Owner: Vladimir Makarevich Требования: ТA.2, ТA.6, ТA.7, ТA.9.1, ТA.9.2 из [requirements-advanced-mode.md](requirements-advanced-mode.md) `schema_version`: без изменения (нового ключа нет, меняется смысл существующего) Зависимости: [Ам-1](phase-am-1-drop-full-access.md) — иначе `strict_isolation: false` продолжает отпирать full-access, и режим включается вместе с тем, что его отменяет

Самая крупная фаза режима и первая, после которой `strict_isolation: false` начинает означать «advanced mode». Здесь появляется ось окружения, чинится редакция и строится вся видимость — без неё режим становится молчаливым ослаблением, а это ровно то, чего кампания не делает нигде.

## Что делаем

**1. Полный проброс окружения — на пяти call-site'ах из шести.** Дочернее окружение строится из родительского как есть, без allow-list по именам: агентские процессы ([`_adapter_base.py:351`](../../../src/wastech_orchestrator/providers/_adapter_base.py) и `:485`), Check Runner ([`check_runner.py:140`](../../../src/wastech_orchestrator/check_runner.py)), сканеры и tool-узлы ([`orchestrator.py:2307`](../../../src/wastech_orchestrator/core/orchestrator.py)), Codex-смоук ([`codex.py:713`](../../../src/wastech_orchestrator/providers/codex.py)).

**Git Manager остаётся на сегодняшнем allow-list** ([`git_manager.py:583`](../../../src/wastech_orchestrator/git_manager.py)) — решение владельца по вопросу 8. Ему тулчейн-переменные не нужны, а цена ошибки там — чужой PR: ни один из десяти вызовов `gh` не передаёт `--repo`, поэтому `GH_REPO` из шелла перенацелил бы публикацию, а `GIT_DIR` / `GIT_WORK_TREE` / `GIT_INDEX_FILE` увели бы и команды, и `resolve_control_paths`, из-за чего write-guard защищал бы не тот `.git`.

Паритет агента и набора checks (Т0.5) сохраняется: оба получают одно и то же окружение.

**2. Имена из `.worc/.env` не пробрасываются.** CLI грузит этот файл в `os.environ` на старте ([`env_file.py:35`](../../../src/wastech_orchestrator/env_file.py)), а `InternalDenyPolicy` отдельно запрещает агенту его читать — полный проброс отдал бы содержимое в обход собственного запрета. Набор имён известен точно: `load_env_file` уже сравнивает окружение до и после, `dotenv_values` умеет вернуть ключи без значений. Нужное значение оператор возвращает явно через `extra_environment`.

**3. Нейтрализация для git/gh расширяется.** Пин поверх окружения уже существует и применяется **после** построения ([`git_manager.py:582`](../../../src/wastech_orchestrator/git_manager.py)); к пяти нынешним пинам добавляются вычистки `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_COUNT`, `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_AUTHOR_*`, `GIT_COMMITTER_*`, `GH_REPO`, `GH_HOST`. Это не ослабление цели: без них пол не существует даже при выключенном режиме, если оператор экспортировал такую переменную в своём шелле.

**4. `LC_ALL=C` для процессов Git Manager.** Классификация результатов идёт по английским строкам вывода — `_TRANSIENT_GIT_STDERR_MARKERS` решают, повторять ли `push` ([`git_manager.py:66`](../../../src/wastech_orchestrator/git_manager.py)), `leftover conflict marker` является единственным гейтом против коммита конфликт-маркеров ([`git_manager.py:1731`](../../../src/wastech_orchestrator/git_manager.py)). Пин запланирован Т0.6 в [Фазе 0.2](phase-0-2-extra-environment.md); если к моменту этой фазы он не сделан, он входит сюда как блокирующее.

**5. Седьмая политика окружения приводится к общей.** `memory/derived.py:38` строит окружение из собственного жёстко зашитого кортежа мимо `build_child_env`.

**6. Редакция: правило сбора литералов инвертируется.** «Имя секретное **и** его нет в `allowed_environment`» ([`redaction.py:126`](../../../src/wastech_orchestrator/providers/redaction.py)) при пробросе всего даёт пустое множество — умирает ровно тот слой, который ловит секреты **без узнаваемой формы**, и умирает тогда, когда таких значений в окружении становится максимум. В режиме литералы собираются по `is_sensitive_key` независимо от allow-list. Цена принята и пишется в гайд: значение вроде `TOKEN_PATH=/usr/local/share` начнёт вычищаться из вывода, потому что имя секретно по сегментной проверке.

**7. Видимость — четыре носителя.** Громкая строка preflight по образцу нынешней `read-isolation: OFF (...)` ([`cli.py:2945`](../../../src/wastech_orchestrator/cli.py)): отдельный субъект, `ON`/`OFF` вместо OK/FAIL, ключ-причина в скобках, что перестало действовать и **что продолжает**. Та же строка в лог прогона до создания ветки ([`orchestrator.py:2509`](../../../src/wastech_orchestrator/core/orchestrator.py)). Булево поле в леджере по образцу `auto_merged` ([`ledger.py:47`](../../../src/wastech_orchestrator/ledger.py)). Отметка в `metadata` замороженного бандла ([`control_bundle.py:186`](../../../src/wastech_orchestrator/core/flow/control_bundle.py)) — она есть даже у задачи, не дошедшей до терминального перехода.

В строке preflight обязан быть назван и третий уровень пола: публикация вне нашего `origin` не удерживается ничем (ТA.1). Смягчать формулировку нельзя.

**8. Абзац в промпт-преамбулу.** Механизм уже есть и умеет дописывать усиление при ослабленной read-изоляции ([`security_preamble.py:77`](../../../src/wastech_orchestrator/core/flow/security_preamble.py)); добавляется абзац режима. Правка 55 ролевых промптов отклонена: точка вставки одна, а токены путей собираются из констант layout, поэтому текст не расходится с enforcement.

**9. Компенсации за гейт.** `check_isolation` при включённом режиме запускается, несмотря на `strict_isolation: false` ([`orchestrator.py:2546`](../../../src/wastech_orchestrator/core/orchestrator.py)) — в него переехала хостовая проверка из [Ам-1](phase-am-1-drop-full-access.md). Codex capability smoke перестаёт возвращать `None` при выключенном strict ([`codex.py:711`](../../../src/wastech_orchestrator/providers/codex.py)): именно в режиме, где профиль несёт весь пол, отказ от него недопустим.

## Тесты

Выключенный режим даёт окружение, побайтово равное сегодняшнему (включая порядок). Окружение агента и набора checks равны. Имена из `.worc/.env` не доходят до дочернего процесса. Git Manager получает сегодняшнее окружение байт в байт; подставленные `GIT_DIR` и `GH_REPO` до `git`/`gh` не доходят. Набор литералов редакции при включённом режиме ⊇ набора при выключенном — property-тест, а не рассуждение в ревью (инвариант И-4 Шага 0). Громкая строка preflight покрыта тестом — сегодня ни одна из двух существующих не покрыта. Поле леджера читается у записи предыдущей версии (дефолт). При включённом режиме `check_isolation` и capability smoke запускаются.

## Живая проба (часть DoD)

Реальный прогон с включённым режимом: узел печатает своё окружение, набор checks видит те же значения; в леджере и манифесте бандла стоит отметка; preflight печатает громкую строку с тремя уровнями пола.

## Риск и откат

Самая широкая фаза по радиусу: окружение уходит в пять процессов сразу. Главный риск — «полный проброс» проникает и в Git Manager по недосмотру, поэтому тест на побайтовое равенство его окружения обязателен. Второй риск — инверсия редакции уродует вывод там, где имя секретно, а значение безобидно; порог в восемь символов отсекает короткие, остальное принято. Откат — вернуть allow-list: он остаётся кодом, а не удаляется.
