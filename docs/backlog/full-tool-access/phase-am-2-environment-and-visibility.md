# Фаза Ам-2 — окружение целиком, редакция и видимость режима

Status: **ready to implement** Date: 2026-08-17 Owner: Vladimir Makarevich Требования: ТA.2, ТA.6, ТA.7, ТA.9.1, ТA.9.2 из [requirements-advanced-mode.md](requirements-advanced-mode.md) `schema_version`: без изменения (нового ключа нет, меняется смысл существующего) Зависимости: [Ам-1](phase-am-1-drop-full-access.md) — иначе `strict_isolation: false` продолжает отпирать full-access, и режим включается вместе с тем, что его отменяет; она же вводит WARN-вердикт хостовой проверки, без которого пункт 9 ломает прогон на хосте без песочницы (решение по вопросу 17)

Самая крупная фаза режима и первая, после которой `strict_isolation: false` начинает означать «advanced mode». Здесь появляется ось окружения, чинится редакция и строится вся видимость — без неё режим становится молчаливым ослаблением, а это ровно то, чего кампания не делает нигде.

## Что делаем

**1. Полный проброс окружения — на пяти call-site'ах из шести.** Дочернее окружение строится из родительского как есть, без allow-list по именам: агентские процессы ([`_adapter_base.py:351`](../../../src/wastech_orchestrator/providers/_adapter_base.py) и `:485`), Check Runner ([`check_runner.py:140`](../../../src/wastech_orchestrator/check_runner.py)), сканеры и tool-узлы ([`orchestrator.py:2307`](../../../src/wastech_orchestrator/core/orchestrator.py)), Codex-смоук ([`codex.py:713`](../../../src/wastech_orchestrator/providers/codex.py)).

**Git Manager остаётся на allow-list** ([`git_manager.py:583`](../../../src/wastech_orchestrator/git_manager.py)) — решение владельца по вопросу 8. Ему тулчейн-переменные не нужны, а цена ошибки там — чужой PR: ни один вызов `gh` не передаёт `--repo` (восемь через обёртку плюс один прямой в [`detect.py:150`](../../../src/wastech_orchestrator/install/detect.py)), поэтому `GH_REPO` из шелла перенацелил бы публикацию, а `GIT_DIR` / `GIT_WORK_TREE` / `GIT_INDEX_FILE` увели бы и команды, и `resolve_control_paths`, из-за чего write-guard защищал бы не тот `.git`.

**Формулировку «байт в байт как сегодня» ревью снимает как ловушку.** Сегодняшнее поведение включает полный `env=dict(os.environ)` **внутри** Git Manager — обёртка над `check-ignore` ([`git_manager.py:189`](../../../src/wastech_orchestrator/git_manager.py)), без обоснования в комментарии, в отличие от соседних мест, и именно на неё опирается решение [Фазы 0.4](phase-0-4-toolcache-in-clone.md) про `.git/info/exclude`. Требование звучит как «allow-list **везде** в Git Manager, включая `_git_path_ignored`», а тест на побайтовое равенство пишется против нового ожидания, иначе он законсервирует ровно ту дыру, которую закрывает пункт 3.

Паритет агента и набора checks (Т0.5) сохраняется: оба получают одно и то же окружение.

**2. Имена из `.worc/.env` не пробрасываются.** CLI грузит этот файл в `os.environ` на старте ([`env_file.py:35`](../../../src/wastech_orchestrator/env_file.py)), а `InternalDenyPolicy` отдельно запрещает агенту его читать — полный проброс отдал бы содержимое в обход собственного запрета. Набор имён известен точно: `load_env_file` уже сравнивает окружение до и после, `dotenv_values` умеет вернуть ключи без значений (осторожно: голая строка `KEY` без `=` попадает в `count_env_file` и не попадает в `load_dotenv`, поэтому счётчики двух функций не взаимозаменяемы). Нужное значение оператор возвращает явно через `extra_environment`.

**Обоснование этого пункта сегодня не работает — вопрос 14.** «Запрета читать этот файл», в обход которого шёл бы проброс, на шипнутом дефолте нет: при `read_isolation_off` виды запрета равны `("Write", "Edit")` ([`claude.py:794-795`](../../../src/wastech_orchestrator/providers/claude.py)), а `disable_read_isolation` по умолчанию `True`, то есть инструмент `Read` читает `.worc/.env` уже сейчас. Цена при этом реальная: оператор, держащий `NPM_TOKEN` или прокси в `.worc/.env` — естественном месте, — обязан продублировать значение в `extra_environment`, то есть открытым текстом в `config.yaml`, притом что Т0.2.8 отдельно запрещает печатать значения именно потому, что «они и так лежат в конфиге оператора». В таком виде пункт перемещал бы секреты из gitignored `.env` в конфиг, против [security.md](../../../.agents/rules/security.md). **Решение владельца 2026-08-17 (вопрос 14): закрытие `Read` входит в эту фазу и является для пункта 2 блокирующим.** `internal_deny_kinds` перестаёт зависеть от `read_isolation_off` — приватный набор read-denied всегда; одна строка, функциональности не стоит, и заодно уходит расхождение «`Read` можно, `cat` нельзя», из-за которого один и тот же файл давал два ответа. Порядок внутри фазы: сначала запрет, потом проброс — иначе между правками существует состояние, где `.worc/.env` и читается инструментом, и не пробрасывается, то есть требование стоит, а защищаемого им запрета нет.

**3. Нейтрализация для git/gh расширяется.** Пин поверх окружения уже существует и применяется **после** построения ([`git_manager.py:582`](../../../src/wastech_orchestrator/git_manager.py)); к пяти нынешним пинам добавляются вычистки `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_COUNT`, `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_AUTHOR_*`, `GIT_COMMITTER_*`, `GH_REPO`, `GH_HOST`. Это не ослабление цели: без них пол не существует даже при выключенном режиме, если оператор экспортировал такую переменную в своём шелле.

**4. `LC_ALL=C` для процессов Git Manager.** Классификация результатов идёт по английским строкам вывода — `_TRANSIENT_GIT_STDERR_MARKERS` решают, повторять ли `push` ([`git_manager.py:66`](../../../src/wastech_orchestrator/git_manager.py)), `leftover conflict marker` является единственным гейтом против коммита конфликт-маркеров ([`git_manager.py:1731`](../../../src/wastech_orchestrator/git_manager.py)). Пин запланирован Т0.6 в [Фазе 0.2](phase-0-2-extra-environment.md); если к моменту этой фазы он не сделан, он входит сюда как блокирующее.

**5. Расходящиеся политики окружения приводятся к общей.** Их **шесть плюс четыре**, а не «шесть плюс одна» (уточнение ревью). `memory/derived.py` строит окружение из зашитого кортежа (`_GIT_ENV_KEYS` — `:41`, сборка `:58`) — это допустимо, кортеж уже allow-list. Настоящий риск в трёх остальных, где стоит полный `os.environ`: [`git_manager.py:189`](../../../src/wastech_orchestrator/git_manager.py) (см. пункт 1) и [`detect.py:53`](../../../src/wastech_orchestrator/install/detect.py) / `:152` — `git status` и `gh auth status` с полным окружением, без `-c`-хардненинга, **на каждой команде CLI** (через `resolve_config_path`, [`cli.py:965`](../../../src/wastech_orchestrator/cli.py)). Для `detect.py` проброс объявлен намеренным («an env `GH_TOKEN`/`GITHUB_TOKEN` is honored»), поэтому решение по нему — часть вопроса 13, а не механическая правка.

**6. Редакция: правило сбора литералов инвертируется.** «Имя секретное **и** его нет в `allowed_environment`» ([`redaction.py:126`](../../../src/wastech_orchestrator/providers/redaction.py)) при пробросе всего даёт пустое множество — умирает ровно тот слой, который ловит секреты **без узнаваемой формы**, и умирает тогда, когда таких значений в окружении становится максимум. В режиме литералы собираются по `is_sensitive_key` независимо от allow-list. Цена принята и пишется в гайд: значение вроде `TOKEN_PATH=/usr/local/share` начнёт вычищаться из вывода, потому что имя секретно по сегментной проверке.

**Реальная цена выше, и её надо решить до реализации (вопрос 15).** Пример с `TOKEN_PATH` гипотетический, а живой уже в коде: `"pwd"` входит в `_SENSITIVE_SEGMENTS` ([`redaction.py:104`](../../../src/wastech_orchestrator/providers/redaction.py)), `PWD` не входит в дефолтный allow-list ([`env.py:26-33`](../../../src/wastech_orchestrator/security/env.py)) — значит абсолютный путь репозитория **уже сегодня** собирается литералом и подменяется на `[REDACTED]` в артефактах, тот же класс регресса, что разбирался с другой стороны в [`artifacts.py:250-254`](../../../src/wastech_orchestrator/providers/artifacts.py). Сегодня выход есть — внести `PWD` в `allowed_environment`; инверсия его забирает, и путь прогона исчезает из каждого артефакта. **Решение владельца 2026-08-17 (вопрос 15): явный exempt-список (`PWD`, `OLDPWD`), применяемый в обеих ветках правила** — и в инверсии, и в сегодняшнем «секретное имя и не в allow-list». Это чинит сегодняшний дефект тем же изменением и сохраняет И-4: наборы сравниваются после exempt, поэтому «в режиме ⊇ без режима» остаётся верным. Отклонены: убрать `pwd` из `_SENSITIVE_SEGMENTS` (сужает набор — уходит `DB_PWD`), проверять «похоже на существующий путь» (диск в чистой функции редакции и разное поведение на разных машинах), принять цену (цитаты `file:line` в отчётах и в теле PR стали бы нечитаемыми).

**И property-тест И-4 обязан отдельно пиннить `.worc/.env`.** Пункт 2 убирает эти имена из **дочернего** окружения; если литералы собирать оттуда (естественная реализация), значения выпадут из вычистки, а сравнение «режим вкл ⊇ режим выкл» этого не увидит — просядут оба набора.

**7. Видимость — четыре носителя.** Громкая строка preflight по образцу нынешней `read-isolation: OFF (...)` ([`cli.py:2945`](../../../src/wastech_orchestrator/cli.py)): отдельный субъект, `ON`/`OFF` вместо OK/FAIL, ключ-причина в скобках, что перестало действовать и **что продолжает**. Та же строка в лог прогона до создания ветки ([`orchestrator.py:2509`](../../../src/wastech_orchestrator/core/orchestrator.py)). Булево поле в леджере по образцу `auto_merged` ([`ledger.py:47`](../../../src/wastech_orchestrator/ledger.py)). Отметка в `metadata` замороженного бандла ([`control_bundle.py:186`](../../../src/wastech_orchestrator/core/flow/control_bundle.py)) — она есть даже у задачи, не дошедшей до терминального перехода.

В строке preflight обязан быть назван и третий уровень пола: публикация вне нашего `origin` не удерживается ничем (ТA.1). Смягчать формулировку нельзя. Два уточнения ревью: четвёртый уровень (публикация от имени оркестратора) попадает в ту же строку в той форме, которую задаст решение по вопросу 13; и **до [Ам-4](phase-am-4-write-and-network.md) третий уровень ещё не наступил** — сети у агента нет, — поэтому строка этой фазы говорит про уровни в будущем времени либо появляется целиком в Ам-4. Выбирать надо осознанно: строка, преувеличивающая риск на две фазы вперёд, обесценивается так же, как смягчённая.

**7а. Исполняемые файлы пиннятся абсолютными путями, разрешёнными в preflight** (решение владельца 2026-08-17 по вопросу 13, ТA.1.7 пункт 3). Сегодня `git`, `gh`, CLI провайдеров, `ps` в барьере тишины процесса и `bwrap` в пробе песочницы резолвятся по `PATH` без пиннинга ([`process.py:616-630`](../../../src/wastech_orchestrator/providers/process.py), `:802`), а лончер демона — через `shutil.which("worc")` и спавнится с полным родительским окружением ([`cli_shell.py:139-153`](../../../src/wastech_orchestrator/cli_shell.py), `:240`). При праве писать вне клона это значит, что шим `git` подделывает отпечаток и выполняет публикацию, шим `ps` заставляет лгать барьер тишины, а шим `bwrap` — заявлять песочницу, которой нет. Пути разрешаются один раз, печатаются в preflight и используются дальше как есть; расхождение с ожидаемым — громкая строка. Это идёт в эту фазу, потому что здесь живёт вся видимость и preflight. Что этим **не** закрывается и пишется в гайд: правка кода установленного пакета (пиннинг лончера её не ловит) и подмена, сделанная между прогонами.

**8. Абзац в промпт-преамбулу.** Механизм уже есть и умеет дописывать усиление при ослабленной read-изоляции ([`security_preamble.py:77`](../../../src/wastech_orchestrator/core/flow/security_preamble.py)); добавляется абзац режима. Правка 55 ролевых промптов отклонена: точка вставки одна, а токены путей собираются из констант layout, поэтому текст не расходится с enforcement.

**9. Компенсации за гейт.** `check_isolation` при включённом режиме запускается, несмотря на `strict_isolation: false` ([`orchestrator.py:2547-2552`](../../../src/wastech_orchestrator/core/orchestrator.py)) — в него переехала хостовая проверка из [Ам-1](phase-am-1-drop-full-access.md). Codex capability smoke перестаёт возвращать `None` при выключенном strict ([`codex.py:711`](../../../src/wastech_orchestrator/providers/codex.py)): именно в режиме, где профиль несёт весь пол, отказ от него недопустим.

**Условие корректности здесь — WARN уже введён** (решение по вопросу 17): вердикт `check_isolation` сегодня `raise PipelineFailed`, и включить проверку в режиме, не сделав вердикт громкой строкой, значит запретить `strict_isolation: false` на Linux без `bwrap`/`socat` — конфигурацию, которая сегодня работает. Поэтому WARN живёт в [Ам-1](phase-am-1-drop-full-access.md), а эта фаза только снимает гейт по `strict_isolation`. Плюс таблицу `ISOLATION_CHECKS` нельзя удалить, пока `check_isolation` жив, и у неё есть третий консьюмер — `_can_isolate` в [`router.py:213`](../../../src/wastech_orchestrator/routing/router.py).

## Тесты

Выключенный режим даёт окружение, побайтово равное сегодняшнему (включая порядок). Окружение агента и набора checks равны. Имена из `.worc/.env` не доходят до дочернего процесса. Git Manager получает сегодняшнее окружение байт в байт; подставленные `GIT_DIR` и `GH_REPO` до `git`/`gh` не доходят. Набор литералов редакции при включённом режиме ⊇ набора при выключенном — property-тест, а не рассуждение в ревью (инвариант И-4 Шага 0). Громкая строка preflight покрыта тестом — сегодня ни одна из двух существующих не покрыта. Поле леджера читается у записи предыдущей версии (дефолт). При включённом режиме `check_isolation` и capability smoke запускаются.

## Живая проба (часть DoD)

Реальный прогон с включённым режимом: узел печатает своё окружение, набор checks видит те же значения; в леджере и манифесте бандла стоит отметка; preflight печатает громкую строку с тремя уровнями пола.

## Риск и откат

Самая широкая фаза по радиусу: окружение уходит в пять процессов сразу. Главный риск — «полный проброс» проникает и в Git Manager по недосмотру, поэтому тест на побайтовое равенство его окружения обязателен. Второй риск — инверсия редакции уродует вывод там, где имя секретно, а значение безобидно; порог в восемь символов отсекает короткие, остальное принято. Откат — вернуть allow-list: он остаётся кодом, а не удаляется.
