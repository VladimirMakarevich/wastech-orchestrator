# Заключительная фаза кампании — advanced mode: требования и критерии приёмки

Status: **требования сформированы, фаза НЕ принята — вопрос 1 закрыт, 11 открытых ждут решения владельца** Date: 2026-08-17 Owner: Vladimir Makarevich Основание: [open-question-advanced-mode.md](open-question-advanced-mode.md) — идея и шесть вопросов; этот документ отвечает на них по коду и превращает в контракт Место в очереди: **после** всех фаз Шага 0 `schema_version`: +1 к актуальному на момент старта (сейчас 35, [`schema.py:198`](../../../src/wastech_orchestrator/config/schema.py))

Разбор сплошной, по текущему дереву `dev`: окружение и редакция, поверхность Claude, поверхность Codex, путь публикации целиком, конфиг/preflight/аудит/`.worc`. Всё ниже проверено по коду; там, где вердикт зависит от поведения вендорского CLI, это сказано отдельно и вынесено в живые пробы.

## Главный вывод: пол и «полная свобода» стоят на одной механике

Запрет «коммит / пуш / PR — только оркестратор» **не существует в коде как правило о публикации**. Он собран из побочных эффектов изоляции, и каждый из них — ровно то, что режим «ничего не ограничиваем» снимает.

| Что запрещаем | Claude, macOS / Linux с песочницей | Claude, нативная Windows | Codex |
| --- | --- | --- | --- |
| `git commit` (локальная половина) | `denyWrite` на gitdir / common-dir / hooks-dir в файле песочницы ([`claude.py:604`](../../../src/wastech_orchestrator/providers/claude.py)) — против `Bash` и **любого** подпроцесса; плюс `Write(//gitdir/**)` / `Edit(...)` ([`claude.py:796`](../../../src/wastech_orchestrator/providers/claude.py)) — против встроенных инструментов, которые песочницу **не проходят** ([`claude.py:783`](../../../src/wastech_orchestrator/providers/claude.py)) | файла песочницы нет вовсе ([`claude.py:1114`](../../../src/wastech_orchestrator/providers/claude.py)); сегодня держится тем, что `Bash` выкинут из `--tools` целиком ([`claude.py:248`](../../../src/wastech_orchestrator/providers/claude.py)). Остаются только паттерны инструментов | `filesystem: gitdir = "read"` ([`codex_profile.py:139`](../../../src/wastech_orchestrator/providers/codex_profile.py)) — и **только на `workspace-write`**: `write_guard` резолвится лишь для пишущих попыток ([`agent.py:481`](../../../src/wastech_orchestrator/core/flow/nodes/agent.py)), у `read-only` записи `.git` в профиле нет вообще |
| `git push`, `gh pr create` (удалённая половина) | `network.allowedDomains: []` ([`claude.py:616`](../../../src/wastech_orchestrator/providers/claude.py)) — **единственное**, что не обходится переписыванием команды | ничем | `network = { enabled = false }` **безусловно, на обоих профилях** ([`codex_profile.py:166`](../../../src/wastech_orchestrator/providers/codex_profile.py)) — самый сильный анти-публикационный контроль в кодовой базе |
| то же через второй шелл, обёртку, подпроцесс | паттерны `Bash(git commit:*)` не удерживают: `bash -c`, `/usr/bin/git`, `git -C`, `git --git-dir=`, Makefile, `python -c`, `gh api`, `curl` ([`claude.py:385`](../../../src/wastech_orchestrator/providers/claude.py) — префиксное сравнение нормализованной строки) | — | **паттернов нет вовсе**: `denied_commands` в Codex не проецируется ни строкой (ноль вхождений в `providers/codex*.py`) |
| постфактум | отпечаток git-control-state → park, но **только у `workspace-write` агент-узлов** ([`agent.py:536`](../../../src/wastech_orchestrator/core/flow/nodes/agent.py)); у `read-only` с грантом — только warn ([`agent.py:400`](../../../src/wastech_orchestrator/core/flow/nodes/agent.py)) | то же | то же (механизм провайдеро-нейтральный) |

Из таблицы следуют три вещи, которые определяют форму фазы.

**Первое. Провайдерские full-access режимы несовместимы с полом, а не «широки».** У Codex `sandbox: danger-full-access` — это один `return` ([`codex.py:373`](../../../src/wastech_orchestrator/providers/codex.py)), который выбрасывает профиль целиком: `.git` становится писабельным, `network.enabled = false` не эмитится вовсе, канарейка пропускается (`_extract_profile_arg` возвращает `None`, [`codex.py:672`](../../../src/wastech_orchestrator/providers/codex.py)), preflight-смоук возвращает `None`. После этого на стороне Codex **не остаётся ни одного** механизма против публикации. У Claude `bypassPermissions` мягче — файл песочницы всё ещё пишется, потому что `needs_sandbox` считается по плану инструментов, а не по режиму ([`claude.py:246`](../../../src/wastech_orchestrator/providers/claude.py)), — но действует ли `--disallowedTools` под этим режимом, из нашего кода не следует, и проверить это можно только живой пробой. Вывод для фазы: **advanced mode не может быть надстройкой над `strict_isolation: false`**, потому что тот разблокирует ровно эти два режима. Дверь «полной свободы без пола» уже открыта и никем не запрошена — она называется `strict_isolation: false`.

**Второе. Три оси не независимы, как предполагал вопрос №3 исходного документа.** «Оператору, которому надоело конфигурировать переменные, инструменты открывать не обязательно» — верно. Обратное неверно: ось окружения сама по себе бьёт по полу. `SSH_AUTH_SOCK` отдаёт агенту живой сокет ssh-агента оператора; `GH_TOKEN`/`GITHUB_TOKEN` — готовый токен; при этом `~/.config/gh/hosts.yml`, `~/.gitconfig`, `~/.git-credentials` и `~/.ssh/` **уже сегодня читаемы агентом** — их нет ни в `InternalDenyPolicy` ([`runtime_layout.py:154`](../../../src/wastech_orchestrator/runtime_layout.py)), ни в `denied_read_paths` (там `.env` и `secrets/**`). Единственное, что делает эти креды инертными, — отсутствие сети. Ось инструментов бьёт по полу отдельно: снятие `--tools` создаёт инструменты, которых сегодня не существует, и среди них `EnterWorktree` — новый worktree имеет свой gitdir, которого нет в `write_guard.denied_write_paths` (тот резолвится один раз до попытки, [`agent.py:482`](../../../src/wastech_orchestrator/core/flow/nodes/agent.py)), то есть прямой обход write-guard без всякого шелла.

**Третье. Заявленную цель («включил — ничего не конфигурируешь») ось окружения не закрывает.** Стена 2 — не единственная: `dotnet build` падает на стене 3 (кэш в `$HOME` запрещён песочницей), `restore` — на стене 4 (сети нет). Полный проброс окружения не двигает ни ту, ни другую. Значит либо режим честно ограничивается окружением и инструментами — и тогда он **не** даёт «собрать проект внутри турна», — либо он вбирает Шаги 2, 3 и 4, и тогда с сетью пол перестаёт быть доказуемым (см. пол выше: удалённую половину держит ровно сеть). Это первый и главный вопрос владельцу.

## Пол: определение через свойства, а не через список команд

**ТA.1.** Режим сохраняет инвариант «коммит / пуш / PR делает только оркестратор». Инвариант формулируется как шесть проверяемых свойств; список `denied_commands` остаётся, но классифицируется честно — как трение и телеметрия, а не как граница.

- **ТA.1.1 `.git` неписабелен любым путём.** Gitdir, git-common-dir и hooks-dir write-denied и для подпроцессов (ОС-песочница у Claude, `read`-вердикт в профиле у Codex), и для встроенных инструментов CLI (`Write` / `Edit` / `NotebookEdit` паттерны — песочница их не покрывает, это записано в коде). Оба механизма обязательны: ни один не покрывает другой.
- **ТA.1.2 `write_guard` резолвится для каждой попытки.** Сегодня он `None` у `read-only` ([`agent.py:481`](../../../src/wastech_orchestrator/core/flow/nodes/agent.py)), потому что у такого узла нет инструментов записи. В режиме это перестаёт быть правдой, и без правки `.git` у read-only узла не получает ни одного явного запрета — он держится на широком `read` всего клона, который режим и расширяет. Это то же требование, что и в Шаге 1, и здесь оно тоже является требованием корректности, а не аккуратности.
- **ТA.1.3 `.worc`, `.worc-io` и `tasks/` остаются недосягаемы для записи.** Не «ради изоляции», а потому что через них публикация делается **от имени оркестратора**: `.worc/logs/<id>/summary.md` читается дословно и становится телом PR и закоммиченным аудит-артефактом, причём намеренно **без** проверки дайджеста ([`git_manager.py:1749`](../../../src/wastech_orchestrator/git_manager.py)); `.worc/flows/` и `.worc/tools/` — file-trusted и дают произвольный код с правами оркестратора на следующем прогоне ([`tools_registry.py:5`](../../../src/wastech_orchestrator/core/flow/tools_registry.py)); `.worc/git-null-hooks/` обязан быть пустым, потому что каждая git-команда оркестратора идёт с `-c core.hooksPath=` на него — подложенный туда `pre-commit` исполняется **внутри процесса оркестратора**; `state.db` не имеет ни HMAC, ни внешнего якоря, и запись в него отменяет и карантин обменника, и дайджест замороженного контрольного плана. Иными словами, `.worc` — это не «служебный каталог», это путь публикации.
- **ТA.1.4 Режим не расширяет сеть.** Узел получает ровно ту сеть, которую дал ему флоу. Режим не включает сеть там, где её нет, и не расширяет `allowedDomains`.
- **ТA.1.5 Режим несовместим с провайдерскими full-access режимами.** Конфиг, где режим включён одновременно с `sandbox: danger-full-access` или с full-access селектором в `extra_args` (`find_full_access_args`, [`forbidden_args.py:77`](../../../src/wastech_orchestrator/security/forbidden_args.py)), — ошибка валидации. Абсолютно запрещённые флаги (`--dangerously*`, `--yolo`, `--ignore-rules`) остаются запрещёнными; зарезервированные флаги (`_RESERVED_CLAUDE_FLAGS` / `_RESERVED_CODEX_FLAGS`) остаются зарезервированными — иначе оператор вернёт себе full-access через `extra_args` и обнулит пол, думая, что включил «удобство».
- **ТA.1.6 Процессы самого оркестратора не подчиняются режиму.** Git Manager запускает `git` и `gh` через тот же `build_child_env` ([`git_manager.py:583`](../../../src/wastech_orchestrator/git_manager.py)). Полный проброс отдаёт туда `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_CONFIG_GLOBAL`, `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `GIT_AUTHOR_*` / `GIT_COMMITTER_*` и — отдельно — `GH_REPO` и `GH_HOST`, причём **ни один вызов `gh` не передаёт `--repo`** (десять вызовов, [`git_manager.py:936`](../../../src/wastech_orchestrator/git_manager.py) и далее): переменная из шелла оператора перенацелит PR в другой репозиторий, и ничто этого не заметит.

## ТA.2 — ось окружения

- **ТA.2.1 Проброс целиком, но не отовсюду.** При включённом режиме дочернее окружение строится из родительского **как есть**, без allow-list по именам — для агентских процессов ([`_adapter_base.py:351`](../../../src/wastech_orchestrator/providers/_adapter_base.py) и `:485`), Check Runner-а ([`check_runner.py:140`](../../../src/wastech_orchestrator/check_runner.py)), сканеров и tool-узлов ([`orchestrator.py:2307`](../../../src/wastech_orchestrator/core/orchestrator.py)) и codex-смоука ([`codex.py:713`](../../../src/wastech_orchestrator/providers/codex.py)). Git Manager сохраняет сегодняшнее поведение байт в байт: allow-list плюс `_GIT_HARDENING_ENV`. Обоснование — ТA.1.6: агенту тулчейн-переменные нужны, Git Manager-у нет, а цена ошибки там — чужой PR.
- **ТA.2.2 Паритет агента и checks сохраняется.** Требование Т0.5 не отменяется режимом: окружение агентской попытки и набора checks остаётся одинаковым, иначе агент соберёт проект, а гейт качества упадёт на «SDK not found» после успешной работы.
- **ТA.2.3 Секреты самого оркестратора не пробрасываются.** CLI грузит `<repo>/.worc/.env` в `os.environ` на старте ([`env_file.py:35`](../../../src/wastech_orchestrator/env_file.py)), а `InternalDenyPolicy` отдельно запрещает агенту читать этот файл. Полный проброс отдал бы агенту его содержимое (`TELEGRAM_BOT_TOKEN`, `GH_TOKEN` из шипнутого шаблона `.env.example`, [`cli.py:151`](../../../src/wastech_orchestrator/cli.py)) в обход собственного запрета. Имена, загруженные из `.worc/.env`, исключаются из проброса; список известен точно — `dotenv_values` уже умеет вернуть ключи без значений, и `load_env_file` возвращает счётчик из того же места.
- **ТA.2.4 Нейтрализация для git/gh остаётся и расширяется.** Пин поверх окружения уже существует и применяется **после** построения env ([`git_manager.py:582`](../../../src/wastech_orchestrator/git_manager.py)); к пяти сегодняшним пинам добавляются вычистки `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_COUNT`, `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_AUTHOR_*`, `GIT_COMMITTER_*`, `GH_REPO`, `GH_HOST`. Это не ослабление цели — без этого пол не существует даже при выключенном режиме, если оператор экспортировал такую переменную в своём шелле.
- **ТA.2.5 `LC_ALL=C` обязателен.** Git Manager классифицирует результаты по английским строкам вывода: `_TRANSIENT_GIT_STDERR_MARKERS` решают, повторять ли `push` ([`git_manager.py:66`](../../../src/wastech_orchestrator/git_manager.py)), `leftover conflict marker` — единственный гейт против коммита конфликт-маркеров ([`git_manager.py:1731`](../../../src/wastech_orchestrator/git_manager.py)), `_ALREADY_MERGED_MARKERS` — разбор `gh pr merge`. Локали сегодня нет ни в одном дефолте, поэтому вывод английский случайно. Пин запланирован Т0.6 в Фазе 0.2; если к моменту этой фазы он не сделан, он входит сюда как блокирующее предусловие.
- **ТA.2.6 Седьмая политика окружения приводится к общей.** `memory/derived.py:38` строит окружение из собственного жёстко зашитого кортежа мимо `build_child_env` — при включённом режиме это молча расходящееся поведение.

## ТA.3 — ось инструментов

- **ТA.3.1 Гейт существования снимается, deny-список сужается до пола.** У Claude `--tools` перестаёт быть allow-list-ом (механику и её цену полностью описывает Шаг 1 ADR — здесь она не переписывается). В deny-списке остаётся ровно пол: `Write` / `Edit` / `NotebookEdit` на пути `write_guard` и `InternalDenyPolicy`, плюс `EnterWorktree` (обход write-guard через собственный gitdir), плюс паттерны `denied_commands`. Всё остальное, что Шаг 1 денаит «не для этого сценария» (`Agent`, `Workflow`, `CronCreate`, `SendMessage`, `Artifact`, `PushNotification`, `AskUserQuestion`), — предмет вопроса №11.
- **ТA.3.2 `--disallowedTools` становится единственным носителем изоляции** и обязан попасть в `_REQUIRED_CLAUDE_FLAGS` ([`claude.py:514`](../../../src/wastech_orchestrator/providers/claude.py)), откуда уходит `--tools`. Переименование флага в новой версии CLI обязано ловиться до платного вызова модели.
- **ТA.3.3 На Codex оси инструментов нет.** Профиль состоит ровно из трёх ключей — `extends`, `filesystem`, `network` ([`codex_profile.py:105`](../../../src/wastech_orchestrator/providers/codex_profile.py), закреплено тестом `test_git_evidence_does_not_change_the_codex_profile`), места под перечень команд в нём не существует. Режим на Codex — это только ось записи, и это надо сказать в гайде прямым текстом, а не оставить оператору выводить самому.
- **ТA.3.4 Профиль Codex продолжает эмитироваться всегда.** Без него не запускается канарейка — единственный механизм, который вообще что-то доказывает про изоляцию на этой стороне.

## ТA.4 — ось записи

- **ТA.4.1 Запись расширяется, вырезы пола остаются более специфичными.** Грамматика это позволяет у обоих провайдеров: у Claude — `allowWrite` рядом с `denyWrite` ([`claude.py:572`](../../../src/wastech_orchestrator/providers/claude.py)), у Codex — прямое абсолютное правило в таблице `filesystem`, где более специфичный путь побеждает широкий (проверено живыми пробами, таблица проб в ADR).
- **ТA.4.2 Опираться на приоритет как на границу нельзя.** Унаследованный из `extends` грант способен побить явный `deny`: клон под глобальным `/private/tmp` снимает вырезы целиком (проверено парными контролями). Сегодня это ловит только per-attempt канарейка, и только на приватном наборе; в валидаторе `repo.local_path` не ограничен ничем. Для этой фазы это означает: **вырез `.git` обязан доказываться пробой, а не считаться действующим** (ТA.5.1).
- **ТA.4.3 Сеть — отдельное решение и не входит в режим по умолчанию** (ТA.1.4, вопрос №1).

## ТA.5 — пол доказывается, а не декларируется

- **ТA.5.1 Канарейка получает пробу пола.** Сегодня per-attempt канарейка проверяет приватный набор и обменник ([`codex_canary.py:189`](../../../src/wastech_orchestrator/providers/codex_canary.py)) и **не трогает `.git` ни одной пробой** — то есть главный инвариант проекта сегодня не доказан ничем, ни в этом режиме, ни без него. Добавляется проба «дописать байт в файл внутри gitdir» с ожиданием `denied`, с положительным контролем рядом. Утечка = `CONFIGURATION_ERROR` до вызова модели, как сегодня для приватного набора.
- **ТA.5.2 У Claude пробы такого класса нет вовсе** — там доказательство обеспечивается только тестом на форму `--settings`. Нужна эквивалентная проверка (вопрос №12: чем именно и что делать, если хост не даёт её выполнить).
- **ТA.5.3 На хосте без песочницы пол недоказуем.** Нативная Windows не имеет sandbox-бэкенда ни при каком конфиге; Linux без `bwrap`/`socat` — тоже. Сегодня `strict_isolation: true` закрывает оба случая (шелл снимается / попытка падает `CAPABILITY_UNAVAILABLE`), и в режиме это поведение сохраняется, если режим требует `strict_isolation: true` (вопрос №2). Что печатает preflight в этом случае — вопрос №4.

## ТA.6 — видимость и след в аудите

- **ТA.6.1 Громкая строка preflight.** Форма уже есть и её надо копировать, а не изобретать: `read-isolation: OFF (security.disable_read_isolation=true) — … ; … stay in force` ([`cli.py:2945`](../../../src/wastech_orchestrator/cli.py)) — отдельный субъект, `ON`/`OFF` вместо OK/FAIL, ключ-причина в скобках, что перестало действовать, **и что продолжает действовать**. Рядом живёт `git-evidence: ON (...)` ([`cli.py:2959`](../../../src/wastech_orchestrator/cli.py)). Обе строки сегодня не покрыты ни одним тестом — для режима это не годится.
- **ТA.6.2 Та же строка в лог прогона** до создания ветки, как это сделано для read-изоляции и native memory ([`orchestrator.py:2509`](../../../src/wastech_orchestrator/core/orchestrator.py), комментарий там же: «Never a silent weakening»).
- **ТA.6.3 Отметка в постоянном следе.** Сегодня эффективная security-поза не пишется никуда долговечно: `provider_attempts` и `node_runs` не содержат ни одной security-колонки, в леджере её нет, а единственное место с `permission_profile` и полным `argv` — `request.json` попытки, который при шипнутом `logging.artifacts: standard` **удаляется в конце каждой попытки** ([`artifacts.py:56`](../../../src/wastech_orchestrator/providers/artifacts.py)). Прецедент для нужной формы есть: поле `auto_merged` в леджере ([`ledger.py:47`](../../../src/wastech_orchestrator/ledger.py)) — булев маркер «этот прогон обошёл контроль», с дефолтом, чтобы старые записи читались. Какой носитель выбрать — вопрос №5.
- **ТA.6.4 Промпт-преамбула получает свой абзац.** Провайдеро-нейтральный контракт уже прописывает «never run git commit/push/merge or open a PR» и уже умеет добавлять усиливающий абзац, когда read-изоляция ослаблена ([`security_preamble.py:77`](../../../src/wastech_orchestrator/core/flow/security_preamble.py)). В режиме доля «честности агента» в общей гарантии растёт, поэтому абзац обязателен — при этом он остаётся advisory и так и называется.

## ТA.7 — редакция

- **ТA.7.1 Сбор литералов инвертируется.** Правило «имя секретное **и** его нет в `allowed_environment`» ([`redaction.py:126`](../../../src/wastech_orchestrator/providers/redaction.py)) при пробросе всего даёт пустое множество: не остаётся ни одного «не-allowlisted» имени. Умирает ровно тот слой, который существует для секретов **без узнаваемой формы** (внутренний токен, пароль, 40 hex) — и умирает в тот момент, когда таких значений в окружении становится максимум. В режиме литералы собираются по `is_sensitive_key` **независимо** от allow-list. Структурные слои (`ghp_…`, `sk-…`, `AKIA…`, `Bearer …`, JWT, `ИМЯ=значение`) не трогаются — они и так от allow-list не зависят.
- **ТA.7.2 Цена инверсии называется.** Значение вроде `TOKEN_PATH=/usr/local/share` будет вычищаться из логов и артефактов, потому что имя секретно по сегментной проверке. Порог `_MIN_DENIED_SECRET_LEN = 8` отсекает короткие, остальное — принятая цена, и она пишется в гайд.
- **ТA.7.3 Инвариант И-4 Шага 0 сохраняется в силе:** набор литералов редакции при включённом режиме не меньше, чем без него. Это property-тест, а не рассуждение в ревью.

## Отрицательные требования

- **НA.1** Режим **не** включает и не разблокирует `danger-full-access` и `bypassPermissions` (ТA.1.5). Существующая дверь под `strict_isolation: false` остаётся как есть и этой фазой не трогается.
- **НA.2** Режим **не** снимает абсолютно запрещённые и зарезервированные флаги. Возврат себе `--tools` / `--settings` / `-c` через `extra_args` остаётся ошибкой.
- **НA.3** Режим **не** объявляется в задаче, во флоу-узле или в `extra_args` — только в конфиге оператора, как `disable_read_isolation` и `allow_git_evidence` ([`schema.py:405`](../../../src/wastech_orchestrator/config/schema.py)). Иначе целевой репозиторий, из которого приходит флоу, включает его себе сам.
- **НA.4** Режим **не** отменяет оркестраторные гейты: staged-set allowlist, `assert_index_clean_at_start`, `assert_exchange_never_staged`, дайджест-проверку пакета задачи, идемпотентность `publish_operations`, запрет прямого push в `base_branch`, барьер тишины процесса, `_assert_no_untrusted_filters` и `-c core.hooksPath=` на каждой git-команде оркестратора.
- **НA.5** Режим **не** вводит второго определения «секретного имени»: политика одна — `is_sensitive_key`.
- **НA.6** Режим **не** пишет эффективное окружение в артефакты попытки. Печатаются только имена (как в Т0.2.8), значения — нет.
- **НA.7** Режим **не** является заменой Шагов 2–4. Если решение по вопросу №1 будет «включая запись наружу и сеть», Шаги 2 и 3 не «закрываются автоматически» — их валидация путей и доменная грамматика остаются нужны для конфигураций без режима.

## Предусловия: дефекты, найденные разбором

Разбор нашёл одиннадцать мест, которые сегодня работают не так, как предполагают документы. Четыре первых — блокирующие для режима: без них включать нечего, потому что заявленная единственная гарантия не проверяется и не удерживается.

1. **Пол не доказан ни одной пробой** — канарейка `.git` не трогает (ТA.5.1). **Блокирующее.**
2. **Отпечатка удалённой стороны нет.** `GitControlState` не содержит remote-ссылок ([`git_manager.py:496`](../../../src/wastech_orchestrator/git_manager.py)), поэтому `git push` уже закоммиченной ветки и `gh pr create` агентом **не дают дрейфа вообще** — две из четырёх запрещённых операций не детектируются ничем. **Блокирующее.**
3. **Чужая публикация усыновляется, а не отвергается.** `push` в режиме `new` видит существующую удалённую ветку, коротко замыкается и записывает операцию как выполненную, ничего не отправив ([`git_manager.py:1859`](../../../src/wastech_orchestrator/git_manager.py)); `_find_open_pr` находит любой открытый PR `branch→base`, переиспользует его и дописывает в чужое тело секцию этой задачи ([`git_manager.py:2004`](../../../src/wastech_orchestrator/git_manager.py)). То есть самопубликация агента сегодня превращается в «успех оркестратора». **Блокирующее.**
4. **Самокоммит обнуляет гейт опасного диффа.** `changed_code_entries()` считается относительно `HEAD` ([`git_manager.py:1414`](../../../src/wastech_orchestrator/git_manager.py)); после коммита агента дерево чисто, поэтому удаления, правки манифестов зависимостей и попадания в `protected_paths` проходят мимо HITL, а `commit_code` становится no-op и задача «успешно» завершается чужим непроверенным коммитом. **Блокирующее.**
5. `.worc/git-null-hooks/` обязан быть пустым, и пустоту не проверяет никто.
6. Креды на диске (`~/.config/gh/hosts.yml`, `~/.gitconfig`, `~/.git-credentials`, `~/.ssh/`) читаемы агентом уже сегодня; инертны только из-за отсутствия сети.
7. `gh` вызывается без `--repo` (ТA.1.6).
8. `memory/derived.py` — седьмая, расходящаяся политика окружения (ТA.2.6).
9. Обе громкие строки preflight не покрыты тестами (ТA.6.1).
10. `.worc/logs/<id>/summary.md` становится телом PR и закоммиченным аудит-артефактом без проверки дайджеста (ТA.1.3).
11. `worc stop --force-full` берёт `pgid` из `.worc/orchestrator.children` и делает group-kill **без** проверки `start_time`, в отличие от соседней ветки для PID демона ([`process_control.py:545`](../../../src/wastech_orchestrator/process_control.py)).

Пункты 5–11 в объём фазы не входят, но должны быть заведены отдельно, иначе они потеряются: разбор — единственное место, где они записаны.

## Тесты и живые пробы

Unit и fake-CLI доказывают проводку, живая проба — эффект; правило кампании «проба часть DoD» действует и здесь.

Обязательные тесты: конфиг с режимом и с full-access селектором — ошибка валидации (обе формы, оба провайдера); окружение агента и набора checks равны при включённом режиме; имена из `.worc/.env` не доходят до дочернего процесса; Git Manager получает сегодняшнее окружение байт в байт плюс расширенную нейтрализацию, и подставленные `GIT_DIR` / `GH_REPO` до `git`/`gh` не доходят; набор литералов редакции при включённом режиме ⊇ набора при выключенном (property-тест И-4); профиль Codex при включённом режиме по-прежнему содержит `.git` не-write и `network.enabled = false`; канарейка получает пробу пола и падает `CONFIGURATION_ERROR` на подставленном профиле без выреза; `--disallowedTools` содержит `Write`/`Edit`/`NotebookEdit` на gitdir и `EnterWorktree` при любом наборе прочих ослаблений; выключенный режим даёт argv и окружение, побайтово равные сегодняшним; обе громкие строки preflight покрыты.

Живые пробы, которых не закрыть fake-CLI: действует ли `--disallowedTools` под `bypassPermissions` на актуальном Claude CLI (от этого зависит формулировка ТA.1.5 — «несовместимо» или «бессмысленно»); держится ли вырез `.git` при широком `write` на macOS, Linux и Windows, включая клон под системным temp; работает ли `allowWrite` внутри `denyWrite` у Claude и кто побеждает; проходят ли встроенные `Write`/`Edit` мимо песочницы так, как записано в комментарии кода; и — на безопасном тестовом remote — реальные попытки публикации из турна через `bash -c`, обёртку, абсолютный путь, `git --git-dir`, `git worktree add`, `gh api`, `curl` и ssh.

## Открытые вопросы — нужен инпут владельца

Ни один не решается «по механизму»; каждый меняет либо объём, либо гарантию.

1. **Область режима.** Три варианта, и они дают разный продукт. **(а) Только окружение** — дёшево, пол сохраняется целиком, но «собрать проект внутри турна» не даёт: стены записи и сети остаются. **(б) Окружение + инструменты + запись, сеть не трогаем** — даёт `dotnet build` с кэшем где угодно, пол остаётся enforceable на macOS/Linux (`.git` не писабелен, сети нет), не даёт `restore`. **(в) Плюс сеть** — даёт всё, и пол перестаёт быть доказуемым: удалённую половину держит ровно сеть, а токен лежит на диске и читаем уже сегодня. **Рекомендация: (б).** Вариант (в) — это не «advanced mode», а согласие на то, что публикация держится на честности агента и на детекте, который push и PR не видит.
2. **Гейт режима — `strict_isolation: true`, а не `false`.** Это инверсия рекомендации исходного документа, и вот почему: `strict_isolation: false` — это ровно тот ключ, который разблокирует `danger-full-access` и `bypassPermissions`, то есть единственные два механизма, гарантированно уничтожающие пол. Кроме того он же сегодня отключает preflight-гейт full-access целиком. **Рекомендация: режим требует `strict_isolation: true` и отвергается вместе с любым full-access селектором.** Согласны ли вы на такую инверсию?
3. **Один ключ или три.** Оси не независимы (окружение бьёт по полу через креды, инструменты — через `EnterWorktree`). **Рекомендация: один ключ `security.advanced_mode` с фиксированным составом по решению вопроса №1** — три независимых ключа дают восемь комбинаций, из которых половину нельзя ни доказать пробами, ни описать в гайде одной фразой. Альтернатива, если хочется гранулярности: два ключа — окружение отдельно (оно и правда самостоятельная потребность), всё остальное вместе.
4. **Нативная Windows и Linux без `bwrap`.** Пол там недоказуем в принципе. Варианты: FAIL preflight (режим просто не включается на таком хосте), WARN плюс явная переформулировка гарантии на «детектируется постфактум», или молчаливое сохранение сегодняшнего поведения (шелл снимается / попытка падает). **Рекомендация: FAIL** — режим, чья единственная гарантия на этом хосте не существует, честнее не включать.
5. **Носитель отметки «прогон шёл в advanced mode».** Леджер (одно поле, прецедент `auto_merged`, но только на терминальном переходе), метаданные замороженного контрольного бандла (агенту недоступны, лежат рядом с дайджестом), колонка в `tasks` (переживает resume, запрашиваема), или всё три. Плюс отдельный вопрос: поднимать ли `logging.artifacts` до `full` при включённом режиме, раз `request.json` — единственное место с argv, и на дефолте он удаляется. **Рекомендация: поле в леджере + метаданные бандла; артефакты не трогать, а печатать имена переменных в preflight.**
6. **Инверсия сбора литералов редакции** (ТA.7.1). Стоит десяти строк и заметно смягчает главный эффект режима. Цена — иногда вычищенный путь вроде `TOKEN_PATH`. **Рекомендация: делать.**
7. **Имена из `.worc/.env`** (ТA.2.3): исключать из проброса — или «полная свобода значит полная», и оператор сам отвечает за то, что положил в этот файл? **Рекомендация: исключать** — иначе продукт одной рукой запрещает читать файл, а другой отдаёт его содержимое.
8. **Окружение Git Manager** (ТA.2.1): оставить сегодняшний allow-list или пробрасывать всё и полагаться только на расширенную нейтрализацию? **Рекомендация: allow-list** — Git Manager-у тулчейн-переменные не нужны, а список нейтрализации придётся догонять при каждом изменении git и gh.
9. **`denied_read_paths` (`.env`, `secrets/**`).** Режим их снимает или оставляет? Формально это deny-список, но он же кормит слой редакции, который переживает всё остальное. **Рекомендация: оставить** — снятие ничего не даёт цели и убирает единственный работающий сбор литералов из файлов.
10. **Паттерны `denied_commands`.** Оставить как трение и телеметрию (они не удерживают ничего, но и не мешают) или убрать как создающие ложное чувство границы? **Рекомендация: оставить, но переписать их описание в гайде** — сейчас в коде они названы «tool-level enforcement of that invariant», и это утверждение сильнее правды.
11. **Инструменты «не для этого сценария»** (`Agent`, `Workflow`, `CronCreate`, `RemoteTrigger`, `SendMessage`, `Artifact`, `PushNotification`, `AskUserQuestion`). Пол они не трогают, но стоят денег, переживают таск и создают каналы наружу. Денаить в режиме или отдать? **Рекомендация: отдать всё, кроме `EnterWorktree`** — режим про свободу, а бюджет и каналы наружу — не пол.
12. **Если проба пола не проходит или не может быть выполнена** — падать `CONFIGURATION_ERROR` до вызова модели (как сегодня для приватного набора) или предупреждать и работать? **Рекомендация: падать** — иначе доказательство пола ничем не отличается от его отсутствия.

Отдельно к порядку: если по вопросу №1 будет выбран вариант (в), режим фактически поглощает Шаги 2, 3 и 4, и очередь кампании после Шага 0 надо пересобрать целиком, а не добавлять эту фазу в конец.
