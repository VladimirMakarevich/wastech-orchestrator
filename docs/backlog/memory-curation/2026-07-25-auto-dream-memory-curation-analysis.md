# Анализ идеи: периодический supervisor-проход «auto-dream» по памяти

Дата: 2026-07-25. Метод: read-only анализ кода оркестратора на 2026-07-25 (`src/wastech_orchestrator/{memory,core,config}`, `cli.py`) плюс данные [аудита памяти на WastimeApp](https://github.com/VladimirMakarevich/wastech-orchestrator/blob/main/docs/analysis/2026-07-24-wastimeapp-memory-audit.md) (2026-07-24; `docs/analysis/` живёт только на `main`) и токен-анализа. Ни один прогон в рамках этого анализа не запускался, память не изменялась.

## 0. Что анализируется

Исходная формулировка идеи:

> можно добавить механизм включения supervisor для управления памятью, к примеру каждый 20 запуск оркестратора, или каждый 50ый запуск (задачи), мы перед началом реализации включаем auto-dream который проходится по всей памяти и делает чистку, дополняет, актуализирует, находит проблемы и так далее.

Это не одно решение, а пять независимых. Дальше они разбираются по отдельности, потому что оценки у них разные: часть идеи верна и закрывает признанный в самом репозитории пробел, часть в текущем состоянии кода активно вредна.

| # | Решение внутри идеи | Оценка |
| --- | --- | --- |
| A | Вообще иметь курирующий (не только чистящий) проход по памяти | **Верно.** Пробел реальный и зафиксирован в собственном backlog как headline failure mode |
| B | Делать этот проход моделью (LLM/supervisor), а не детерминированным кодом | **Частично верно.** Верно как _аудитор/предлагающий_; неверно как _редактор памяти_ |
| C | Триггер — каждый N-й запуск оркестратора / каждая N-я задача | **Неверно.** Счётчик не коррелирует с потребностью и не решает наблюдаемую проблему |
| D | Момент запуска — «перед началом реализации», то есть внутри задачи | **Неверно.** Прямо противоречит уже действующей защите стора (`has_active_task`) |
| E | Объём полномочий — «чистит, дополняет, актуализирует, находит проблемы» | **«Находит проблемы» — верно. «Чистит / дополняет / актуализирует» — нет**, пока не закрыты P0 аудита |

## 1. Краткий вердикт

**Идея правильная по направлению и неправильная по форме, порядку и полномочиям.**

Направление верное: она попадает точно в пробел, который V1-план памяти оставил осознанно («Memory curation (phase 04) — V1 scope cuts»): правила §5 про «противоречие дважды» нет, contradiction-ledger не построен, и дословно — _«lessons can still accrete contradiction-rot until a human curates them. Revisit when the steady-state watch-a-queue scenario shows lessons drifting from reality (the ADR's headline failure mode)»_. То есть ADR сам назвал этот сценарий главным способом деградации и оставил в качестве ответа человека-куратора. Идея = «автоматизировать куратора». Вопрос только в том, какие полномочия ему дать и когда.

Форма неверная по четырём проверяемым в коде причинам (§2). Самая жёсткая: **на текущем write path курирующий проход не лечит порчу, а производит её.** Исправленное моделью утверждение по тому же пути получает тот же `memory_id` (`derive_long_term_id`, `service.py:647` — при непустых `scope.paths` subject в ключ не входит), а `_merge_long_term` (`service.py:698`) заменит только `statement` и evidence, оставив старые `subject`/`rationale`/`remedy`. Куратор, пытаясь склеить Frankenstein-запись, сделает ещё одну — и уже с меткой «прошло курирование».

Порядок обязателен: **сначала P0 аудита, потом auto-dream.** До P0 ожидаемый эффект отрицательный, после — примерно тот, что задуман.

Полномочия обязательны: **модель предлагает, детерминированный код решает, применяет человек либо узкий whitelist механически проверяемых операций.** Это не осторожность ради осторожности: в репозитории уже есть ровно этот паттерн дважды — supervisor advisory by construction (`core/supervisor.py:1-21`: «it never reworks, reopens, or routes») и `propose_skill_map` (`supervisor.py:809`: read-only, propose-only, Core сам резолвит токены против реального inventory, битый вывод даёт `{}`). Курирование памяти должно быть третьим применением того же контракта, а не исключением из него.

И одна замена в самой идее, которая, по-моему, важнее всех возражений: **проверять надо не «всю память раз в 20 задач», а то, что записала конкретная задача — сразу после неё** (§4.7). Через 20 задач у куратора строго меньше материала для проверки, чем было в момент записи: artifacts прогона вычищаются, а evidence-refs на task/commit/diff уже помечены в коде как ephemeral (`packet.py`, `_EPHEMERAL_EVIDENCE_TYPES`). Периодический полный sweep нужен, но как второй контур и по health-сигналу, а не как основной механизм.

## 2. Почему в предложенной форме сейчас не даст толка

### 2.1. Курирование не лечит то, что портится на write path — оно это тиражирует

`derive_long_term_id` (`service.py:647`):

```python
basis = _scope_key(paths) or normalize_subject(subject)
digest = content_hash(f"{kind.value}:{basis}".encode())[:12]
```

При непустом `scope.paths` ключ записи = `kind` + отсортированные пути. Subject не участвует. `_ingest_long_term` (`service.py:229`) находит активную запись с этим id и вызывает `_merge_long_term(existing, statement, evidence, now, task_id)` — сигнатура принимает только statement и evidence, поэтому `subject`, `rationale`, `remedy`, `scope` остаются от прошлой мысли.

Что это значит для auto-dream практически, на конкретных данных аудита. Куратор видит `ltm_6cf6a18427e7`: `subject`/`rationale` про word count главы 02, `statement` про повтор clause в bonus-главах, evidence из четырёх разных тем. Он совершенно правильно решает: это две-три разные мысли, надо расщепить и переписать. Он предлагает две чистые записи по тем же путям. Обе получают **один и тот же** `memory_id`, равный существующему. Первая merge-нётся в старую запись, заменив statement; вторая merge-нётся в результат первой, снова заменив statement. На выходе — одна запись, где subject от главы 02, rationale от главы 02, statement от последнего предложения куратора и evidence-объединение из шести источников. Frankenstein-запись стала хуже, а в audit-логе появилось «merged into existing … (same kind+scope.paths)», то есть выглядит как штатная работа.

Вывод: пока P0-1 не закрыт, любой пишущий проход по памяти — усилитель искажения, а не чистильщик. Это не про качество модели; это свойство ключа идентичности.

### 2.2. Курирующая модель становится самым мощным каналом самосертификации trust

`assign_trust` (`lifecycle.py:45`) присваивает уровень доверия по **строковой метке типа** evidence: `file`, `doc`, `code`, `config`, `repo`, `repo_doc` → `repo-observed`. Существование ref не проверяется (проверка `path_exists` есть только для entity-карточек — `assign_entity_trust`, `lifecycle.py:66`). Дальше `repo-observed` входит в `_AUTO_PROMOTE` (`lifecycle.py:40`), поэтому `should_promote` пропускает запись в durable long-term **с первого раза**, без recurrence.

Сложите это. Куратор — модель, которая по определению производит синтезированные утверждения о содержимом стора. Каждое такое утверждение с evidence `type: "file"` мгновенно становится `repo-observed` и durable. Один проход по 71 записи может создать десятки durable-утверждений максимального практического доверия, ни одно из которых никем не проверено. Аудит уже воспроизвёл это в песочнице на одной записи (P0-2, `missing-proof.md`); auto-dream превращает единичный дефект в регулярный массовый процесс. Хуже: у результата будет ореол авторитета («это же куратор проверял»), тогда как проверки в коде нет ни одной.

Рекомендация аудита здесь прямая и её нельзя обойти: _«Синтезированные supervisor claims по умолчанию должны быть `artifact-backed`, пока валидатор не подтвердил связь statement↔artifact»_. Курирующий проход обязан быть первым потребителем этого правила, а не первым его нарушителем.

### 2.3. Он ломает единственную несущую гарантию слоя curation — детерминизм

Docstring `CleanupJob` (`cleanup.py:1-17`) перечисляет инварианты слоя обслуживания памяти: **demote/expire/quarantine/merge only** (нет кодового пути promote вообще), **snapshot first, then bounded**, **quarantine, never silent delete**, **no network, model-free, deterministic** (время инжектируется, модель не вызывается). Именно на этих четырёх строках держится вся аргументация безопасности: что бы ни случилось, обслуживание памяти нельзя «уговорить», оно воспроизводимо и откатываемо.

LLM-проход по стору вносит в этот слой: нон-детерминизм, кодовый путь создания/перезаписи long-term, и запись без task-провенанса. Последнее особенно неприятно на текущем состоянии observability. Аудит зафиксировал: 393 из 398 snapshot'ов сделаны проходами без единой мутации; у 20 cleanup-событий пустой task ID, у 23 пустой rationale; cleanup-событие иногда перечисляет **оставшиеся** ID вместо удалённого; чтения не аудируются вообще. То есть уже сейчас по audit trail нельзя ответить «какая запись исчезла и почему». Добавьте туда модель, которая переписывает формулировки — и различить «куратор поправил» от «данные испортились» станет невозможно даже вручную по snapshot-диффу.

Есть и чисто технический упор: единственный write funnel — `apply_delta` (`service.py:139`) — требует `episode: EpisodeRecord` и при пустом `audit.task_id` берёт `episode.task_id`. Курирующий проход задачей не является. Значит либо синтетический episode (загрязнение short-term и истории задач — аудит уже жалуется на неразличимые эпизоды), либо новый seam. Новый seam — правильный ответ, но это отдельная работа, а не «включим supervisor».

### 2.4. «Перед началом реализации» противоречит уже действующей защите, а счётчик не коррелирует с потребностью

Про момент. `_cmd_memory_compact` и `_cmd_memory_restore` (`cli.py:2424`, `cli.py:2453`) **отказываются работать**, если задача активна: «a task is active — refusing; run when the orchestrator is idle». Idle-hook в `watch_loop` (`cli.py:1673`) дополнительно перепроверяет `has_active_task(config)` перед вызовом cleanup — комментарий там прямо говорит, зачем: чтобы обслуживание никогда не гонялось с задачей и не задерживало pickup. То есть «мутировать стор под живой задачей» в этом коде уже объявлено небезопасным и закрыто в двух местах. Идея предлагает делать это внутри задачи, да ещё и самым тяжёлым видом мутации.

Отдельно — читаемость памяти внутри задачи. Packet собирается **на каждый узел** (`packet.py`, `write_packet`), а retrieval-трейса нет (P1 аудита). Если стор меняется между узлами одной задачи, узлы работают с разными версиями памяти и восстановить, кто что видел, нельзя.

Про счётчик. Три конкретных проблемы:

1. **Семантика не определена и разъезжается.** «20 запусков оркестратора» и «50 задач» — величины из разных миров. По данным аудита: 21 задача за 10 дней; при этом watch-демон перезапускается по причинам, никак не связанным с памятью. «Каждый 20-й запуск» может сработать дважды за день без единого изменения в сторе — или не сработать месяц активной работы. Что считать: старты задач, rerun'ы, resume, упавшие задачи? У упавших задач delta не пишется вообще (`WriteSource.FAILURE` пишет только episode), значит они в счётчик попадать не должны — но именно они его накрутят при цикле fix-retry.
2. **Счётчик негде надёжно держать.** Существующий rate-limit cleanup'а — in-memory (`state: dict[str, float | None]` в `_build_cleanup_hook`, `cli.py:1580`), и это уже зафиксировано как долг: _«the idle hook rate-limits in-memory … so a restarted daemon may run one extra pass sooner»_. Durable-счётчику нужно место — `manifest.json` (`paths.py:122`, там уже есть placeholders и `MEMORY_SCHEMA_VERSION` как migration hook) или `state.db`. Это опять не «включим», а работа.
3. **Частота ≠ потребность.** 20 задач по главам Journey добавляют почти ничего нового: одни и те же kind+scope, всё сливается в существующие записи. Три задачи с переименованием файлов создают почти всю наблюдаемую staleness (аудит: quarantine из-за `blog/**`, `08_live_calculator…` → `08_leftover_calculator…`, `*.md`). Триггерить по числу задач — значит с равной вероятностью запускать дорогой проход впустую и пропускать момент, когда он нужен. Это ровно тот баг, который уже наблюдается в детерминированном виде: 393 из 398 snapshot'ов — работа без работы. С моделью он станет платным.

### 2.5. Масштаб: сегодня «пройтись по всей памяти» дёшево — и именно поэтому польза от «консолидации» мала

Активный стор: **71 запись / 73 495 B** (плюс audit 71 350 B). Это ≈20–30 тыс. tokens — весь стор влезает в один вызов целиком. Стоимость не является возражением (§4.9). Но из того же факта следует и обратное: **сжимать/консолидировать пока нечего.** Проблема не в объёме и не в накопленном шуме от объёма — проблема в качестве записи. Аудит нашёл 3 подтверждённые смешанные записи из 19 активных, 3 near-duplicate пары, 8 из 19 нерешённых relationship-ссылок, 7 stale-записей, читаемых как активные. Всё это — следствия дефектов write path и retrieval, а не эрозии от времени.

Второе следствие масштаба — на будущее: «весь стор за один проход» перестанет работать раньше, чем кажется. Инкрементальность (курировать только изменённое с прошлого прохода) надо заложить в дизайн сразу, иначе на первой тысяче записей механизм придётся переписывать.

## 3. Что в идее правильно — и почему это важнее возражений

Есть класс задач, которые детерминированный код в принципе не решает, а модель решает хорошо. Все они сейчас не покрыты, и идея указывает на них верно.

| Задача | Почему нужна модель | Текущее состояние в коде | Данные аудита |
| --- | --- | --- | --- |
| Семантический дедуп | `_collapse_duplicates` (`cleanup.py:398`) ключуется на `normalize_subject` = lowercase + сжатие пробелов. Перефразировку не ловит в принципе | Дедуп есть только точный, внутри одного tier-файла | 3 near-duplicate пары, задеты 6 из 19 активных записей; `ltm_af257b2e3b95` и `ltm_b8a499659d17` — одно правило |
| Противоречие утверждения текущей реальности репозитория | Требует прочитать файл и оценить, верно ли утверждение сейчас. Кода для этого нет и быть не может | Параметр `should_promote(has_contradiction=…)` (`lifecycle.py:93`) существует, но никогда не вычисляется и не передаётся | Сценарий 5 аудита: новое high-trust утверждение молча перезаписывает старое, conflict не создаётся |
| Entailment evidence («этот файл действительно подтверждает это утверждение?») | Существование пути — детерминированно. Подтверждает ли содержимое statement — нет | Не проверяется ни на write, ни на cleanup | ≥1 подтверждённый пример семантически неверного evidence source (Story Bible policy) |
| Атомарность утверждений (расщепить смешанную запись) | Нужно суждение о том, где границы отдельных мыслей; исходники — в snapshots | Нет | 4 подтверждённые collision-группы |
| Разрешение relationship-ссылок вида «Part9», «Part11» | Канонизация ID детерминированна, но человеческие метки надо интерпретировать | `_ingest_entity` принимает model-generated ID, refs не валидируются | 8 из 19 relationships не резолвятся |

Плюс биологическая метафора в идее работает в пользу правильного вывода, а не предложенного: консолидация памяти происходит **offline, между действиями**, а не перед действием. Это ровно аргумент за idle-gap seam и против «перед началом реализации».

## 4. Как реализовать это эффективно

### 4.1. Принцип

**Модель предлагает — детерминированный код решает — применяет человек или узкий whitelist механически проверяемых операций.**

Формально: курирующий проход не является мутатором стора. Его выход — не записи, а типизированные предложения с evidence. Это перенос уже существующего в репозитории контракта на новую область:

- `Supervisor` advisory by construction (`core/supervisor.py:1-21`): наблюдает, синтезирует, никогда не роутит; блокировка — работа in-flow evaluator'ов.
- `propose_skill_map` (`supervisor.py:809`): read-only, propose-only, Core резолвит токены против реального inventory, любая поломка даёт `{}` и прогон продолжается на operator pins.
- `parse_follow_ups` (`supervisor.py:258`): evidence-gated — запись без непустого `evidence` **отбрасывается**, а не логируется как предупреждение.

Курирование памяти получает тот же контракт. Никаких исключений «ну это же про память, тут надо чинить».

### 4.2. Порядок работ (это условие, не рекомендация)

| Этап | Что | Почему до auto-dream |
| --- | --- | --- |
| Блокирующее | P0-1 claim identity/merge (`derive_long_term_id`, `_merge_long_term`) | Иначе куратор производит Frankenstein-записи (§2.1) |
| Блокирующее | P0-2 evidence validation + запрет self-certification trust | Иначе куратор — массовый канал ложного `repo-observed` (§2.2) |
| Блокирующее | P0-3 typed quarantine reason + запрет stale-retrieval | Иначе куратор курирует стор, часть которого и так читается некорректно |
| Настоятельно до | P1 logical-transition audit + mutation-only snapshots | Иначе правку куратора нельзя отличить от порчи и нельзя откатить (§2.3) |
| Можно параллельно | Детерминированный health-report (§4.11, этап 0) | Это одновременно 60–70% пользы «auto-dream» бесплатно **и** вход для модели потом |

### 4.3. Где живёт и когда запускается

- Новый модуль `memory/curator.py` — **рядом** с `CleanupJob`, не внутри него. Инвариант «cleanup is model-free, deterministic» остаётся неприкосновенным; куратор — отдельный слой с другими правилами.
- Seam запуска: **idle gap watch-loop'а** (уже защищён `has_active_task`, `cli.py:1673`) и явный operator-verb. Внутри задачи — никогда.
- CLI: `worc memory audit` (read-only, печатает отчёт + пишет предложения), `worc memory review` (применение одобренного через audited seam со snapshot). Ложится ровно рядом с существующими `show / validate / compact / restore / clear` (`cli.py:2335`).
- Отдельная route-identity `memory_curator` со своим блоком конфига по образцу `SupervisorConfig` (`config/schema.py:501`): свой `model`, `reasoning`, `role_file`, `permission_profile` форсирован `read-only`. Не переиспользовать per-task supervisor: у него durable lineage-сессия задачи (`__supervisor__`, `supervisor.py:75`), накопившая контекст **этой задачи**; смешивание испортит и синтез задачи, и курирование, и потащит стоимость тёплой сессии.

### 4.4. Триггер: health-сигнал, а не счётчик

Условие запуска — дешёвая детерминированная проверка «есть ли что курировать»:

```
запускать, если ВСЁ верно:
  стор реально изменился с прошлого прохода   (state_hash != last_curated_state_hash)
  И (новых/изменённых long-term записей >= N
      ИЛИ quarantined записей >= M
      ИЛИ median age quarantine > D дней
      ИЛИ детерминированный validate нашёл >= 1 P0-инвариант)
  И прошло >= T часов с прошлого прохода       (нижняя граница частоты)
  И нет активной задачи
```

`last_curated_at` / `last_curated_state_hash` кладутся в `manifest.json` — там уже есть tiers-placeholders и `MEMORY_SCHEMA_VERSION` как migration hook (`paths.py:27,122`). Хеш канонического состояния tiers аудит уже считал (25 уникальных состояний на 398 snapshot'ов) — метод рабочий.

Счётчик задач при этом полезен, но **как верхняя граница, не как причина**: «не чаще одного прохода на N задач». И считать надо задачи, реально писавшие delta (успешные с непустым `memory_delta`), а не все старты. Хранить durable — `manifest.json` или `state.db`, не in-memory.

Это прямо лечит наблюдаемый дефект: 98,7% cleanup-проходов сегодня — работа впустую. Повторять эту схему с платным LLM-проходом нельзя.

### 4.5. Модель полномочий: что можно применять автоматически, что только предлагать

| Операция | Кто применяет | Обоснование |
| --- | --- | --- |
| Пометить запись stale (путь исчез, не резолвится) | Код, автоматически | Полностью детерминированно — это уже `CleanupJob`, модель не нужна |
| Пометить пару записей как conflict-set, исключить обе из packet до разрешения | Код по предложению модели, автоматически | Механически проверяемо, обратимо, fail-closed: исключение из packet ничего не портит |
| Пометить evidence как unsupported (ref не существует / не подтверждает) | Код автоматически для «не существует»; модель предлагает для «не подтверждает» | Существование — код. Entailment — суждение, но следствие (снятие durable trust) обратимо |
| Схлопнуть near-duplicate записи | **Только предложение → ревью человека** | Необратимо теряет формулировку одной из записей |
| Расщепить смешанную запись на атомарные | **Только предложение → ревью человека** | Модель угадывает границы утверждений; ошибка = новая порча |
| Переписать `statement` / `subject` / `rationale` | **Только предложение → ревью человека** | Это и есть «laundering» — самый опасный класс |
| Разрешить relationship-ссылку в canonical ID | Код по предложению, автоматически при exact-match; иначе ревью | При точном совпадении с существующим ID проверяемо детерминированно |
| Создать новую запись, которой в сторе не было | **Запрещено всегда** | Куратор аудирует стор, а не производит знание. Знание производит задача с evidence |
| Присвоить trust уровень | **Запрещено всегда** | `assign_trust` — единственный источник, self-certification исключена по контракту (AC-SF5) |
| Promote в durable | **Запрещено всегда** | Инвариант «cleanup/curation never promotes» (AC-C3) |
| Удалить запись | **Запрещено всегда** | «Quarantine, never silent delete» (Q2) |
| Править файлы репозитория / docs / skills | **Запрещено всегда** | AC-C3 |

Отдельно про trust выхода куратора: любое его предложение, будучи применённым, не может получить уровень выше `artifact-backed`, и `artifact-backed` не входит в `_AUTO_PROMOTE` — то есть не становится durable автоматически. `human-curated` ставится **только** после явного одобрения через `worc memory review`. Это ровно то, чего требует P0-2 аудита.

### 4.6. Контракт выхода

Не мутация стора, а артефакт:

```
.worc/memory/curation/<timestamp>/
  report.md          # человекочитаемо: что найдено, по каким записям, с чем не согласен
  proposals.jsonl    # машинно: по одному предложению на строку
```

Каждое предложение: `op` (из закрытого enum таблицы §4.5), `target_ids`, `rationale`, `evidence` (обязательно непустое — evidence-gated по образцу `parse_follow_ups`), `confidence`, `reversible`, `proposal_hash`. Битое предложение отбрасывается, не роняет проход. Пустой результат — 0 файлов и 0 audit-событий (не повторять историю с no-op snapshot'ами).

Структурированный вывод — через `output_schema`, и здесь есть готовая грабля: `_schema_safe_reasoning` (`supervisor.py:199`) капит reasoning до `high` для schema-turn'ов, потому что на `xhigh`/`max` провайдер тратит ход на размышление и не отдаёт валидный tool call (`error_max_structured_output_retries`). Курирующий проход — тяжёлый по рассуждению и обязательно structured, так что он попадёт в этот случай первым. Либо капить так же, либо разделить на два хода: free-text анализ, затем компактный structured-ход по его результату.

### 4.6.1. Операторский цикл: что конкретно значит «применяет человек»

| Шаг | Кто | Что происходит | Изменения в сторе |
| --- | --- | --- | --- |
| 1 | Куратор (модель) | `worc memory audit` — читает стор + репозиторий, пишет `curation/<ts>/{report.md, proposals.jsonl}` | **ноль** |
| 2 | Код | Механически проверяемые операции (путь исчез, evidence-ref не существует, conflict-маркировка) применяет сам | да, автоматически |
| 3 | Человек | `worc memory review` — по каждому _судящему_ предложению: принять / отклонить / отложить | нет |
| 4 | Код | Одобренное применяет через audited seam: snapshot → атомарная запись → одно логическое audit-событие. Откат — `worc memory restore` | да, по одобрению |
| 5 | Код | Отклонённое пишет в ledger по `proposal_hash` — второй раз не предложит | нет |

Человек видит **не все находки, а только суждения**. «Файл `08_live_calculator…` исчез» — это код. «Эти две записи говорят одно и то же разными словами, схлопнуть?» — это суждение, и цена ошибки необратима: схлопывание теряет формулировку одной из записей навсегда.

Три формы одобрения, любая: интерактивно (`worc memory review` спрашивает по одному — `_confirm` / `_confirm_yes`, `cli.py:1742`/`1751`, уже умеют `--non-interactive`); пакетно (`--accept-class stale-evidence --reject-class rewrite-statement`); файлом (удалить лишние строки из `proposals.jsonl` вручную и `worc memory review --from <file>`). Канал не обязан быть терминалом: transport-agnostic `Notifier` + HITL approval round-trip (`core/hitl.py`) и `auto_mode.confirm_next_task` уже дают подтверждение в Telegram.

Объём работы на текущих данных: 19 активных long-term, 17 в quarantine, 13 entity. Первый проход после P0-миграции — разовая уборка накопленного, реалистично 5–15 предложений, из них судящих единицы. Дальше почти ноль: стор меняется мало (21 задача дала 71 запись), ledger отклонений гасит повторы, health-триггер не запускает проход на неизменённом сторе.

Человек в контуре — не постоянная повинность, а способ получить `proposal precision`, не заплатив за ошибки. После 2–3 проходов с посчитанной precision конкретные классы операций поднимаются в автоприменение (§4.11, этап 3).

### 4.7. Главная замена в идее: инкрементальная верификация вместо «раз в 20 задач»

Это, на мой взгляд, самое полезное изменение исходной мысли.

Проблема памяти — не накопленный шум от объёма (§2.5). Проблема — **неверифицированная запись в момент записи**. Через 20 задач у куратора строго меньше материала для проверки:

- artifacts прогона (`.worc/logs/<task-id>/`) вычищаются;
- evidence на `task` / `commit` / `diff` в коде уже помечены как гниющие — `_EPHEMERAL_EVIDENCE_TYPES` в `packet.py`, и роль-промпт finalize прямо просит не якорить evidence на SHA/task id;
- diff и touched paths той задачи больше не восстановимы дешёво.

Поэтому предлагаю двухконтурную схему:

**Контур 1 (основной) — post-task verification.** После задачи, записавшей delta, в idle gap запускается узкий проход: проверить **только те записи, которые эта задача создала или изменила**. Вход: 1–5 записей, их evidence-refs, диф задачи, её артефакты. Вопрос модели один и проверяемый: подтверждает ли указанный evidence указанное утверждение, и не противоречит ли оно активной записи. Выход: `supported` / `unsupported` / `contradicts:<id>` + предложение. Это дёшево (единицы тысяч tokens), точно (контекст ещё жив) и попадает в первопричину, а не в симптом.

**Контур 2 (второй) — periodic full sweep.** По health-сигналу (§4.4), не по счётчику: семантический дедуп по всему стору, атомарность, relationship-integrity, «что устарело относительно текущего репозитория». Это и есть «auto-dream» из идеи — но как редкая ревизия, а не как основной механизм гигиены.

Исходная идея — это только контур 2, причём с триггером, который не связан с потребностью. Контур 1 даёт больше пользы за меньшие деньги.

### 4.8. Идемпотентность и сходимость

Обязательное требование, иначе механизм превратится в шум: **отклонённое предложение не должно предлагаться снова.** Нужен ledger отклонений, ключуемый на `proposal_hash` = content-hash от (op, target_ids, нормализованный предлагаемый текст). Дедуп именно против «всех когда-либо виденных», а не против «применённых» — иначе каждый проход будет заново приносить то, что оператор уже отклонил, и оператор перестанет читать отчёты. Ровно так же должно вести себя `worc memory audit` при повторном запуске без изменений стора: тот же вход → тот же вывод, и никакой мутации.

### 4.9. Стоимость: не является возражением, но стоит считать правильно

Реальные измерения из токен-анализа прогона `blog-review-happy-in-my-misfortunes-4`:

- одна advisory-observation supervisor'а после детерминированного `length` — **44 107 input tokens** ради 175 output;
- семь advisory-вызовов за задачу — **480 293 Claude input tokens**, 70,3% всего Claude input прогона;
- один узел `context` + следующая observation — **80 430 Claude input tokens** и **$0.1670**.

Курирующий проход: весь стор ≈73 KB ≈ 20–30 тыс. tokens входа; с чтением файлов репозитория для верификации — по моей оценке 100–300 тыс. input за проход, то есть ориентировочно $0.2–0.6. Это **меньше, чем supervisor тратит на advisory-наблюдения внутри одной задачи**. Раз в 20–50 задач — статистически незаметно.

Но считать надо не стоимость прохода, а стоимость его ошибки. Одна ложная durable-запись входит в packet каждого подходящего узла каждой будущей задачи. Стоимость шума мультиплицируется вниз по всем последующим прогонам, стоимость прохода — нет. Поэтому экономика говорит: проход делать можно хоть часто, но писать он не должен.

### 4.10. Метрики и acceptance

Переиспользовать метрики аудита, добавив специфичные для куратора:

- **proposal precision** = принято оператором / предложено (главная метрика этапа 1; ниже ~0,6 механизм не заслуживает автоприменения ничего);
- false-quarantine rate (сколько верных записей куратор предложил изолировать);
- сходимость: доля повторно предложенного из ранее отклонённого (целевое — 0);
- влияние на packet: stale-in-packet 7 → 0, mixed-record 3/19 → 0, semantic duplicate rate < 5%, unresolved relationships 8/19 → 0.

Инвариантные тесты, без которых не мерджить:

1. куратор не может создать запись, которой не было в сторе;
2. выход куратора никогда не получает `repo-observed` / `human-curated` без явного одобрения;
3. проход при активной задаче отказывается (симметрично `compact`/`restore`);
4. no-op проход пишет 0 файлов и 0 audit-событий;
5. отклонённое предложение не появляется во втором проходе;
6. проход над стором с одной malformed-строкой не теряет остальные записи;
7. применение одобренного предложения даёт ровно одно логическое audit-событие с точными added/updated/removed ID и один snapshot.

### 4.11. Этапность

| Этап | Содержание | Модель | Ценность |
| --- | --- | --- | --- |
| 0 | Дожать детерминированный `worc memory validate` (`cli.py:2392`) до полноценного health-отчёта: duplicate rate, stale, unsupported evidence, unresolved refs, quarantine age, growth per task; exit non-zero на P0-инвариантах | Нет | 60–70% пользы «auto-dream» бесплатно и воспроизводимо; служит входом для модели дальше |
| 1 | `worc memory audit` — read-only куратор, только отчёт + предложения, ноль записей. Прогнать 2–3 раза, вручную оценить proposal precision | Да, read-only | Проверка гипотезы без риска |
| 2 | `worc memory review` — применение одобренного через audited seam со snapshot и логическим audit-событием | Нет (применяет код) | Замыкает цикл, человек остаётся в контуре |
| 3 | Автоприменение узкого whitelist из §4.5 — только если этап 1 показал precision и ноль false-quarantine | Да, ограниченно | Снижает ручную нагрузку |
| 4 | Post-task инкрементальная верификация (контур 1, §4.7) | Да, узко | Бьёт в первопричину, а не в симптом |
| — | Свободная перезапись `statement` моделью без ревью | — | **Не делать никогда** |

Обратите внимание на порядок 0 → 1: этап 0 бесплатный, детерминированный и, по данным аудита, закрывает большинство находок (stale, duplicates, unresolved refs, unsupported evidence существования — всё это вычисляется кодом). Если после этапа 0 останется мало работы для модели — это хороший результат, а не провал идеи.

## 5. Прямые ответы на поставленные вопросы

| Вопрос | Ответ |
| --- | --- |
| Насколько идея правильная? | По направлению — правильная и попадает в признанный в репозитории headline failure mode. По форме (LLM редактирует память, триггер по счётчику, момент внутри задачи) — неправильная во всех трёх частях |
| Насколько корректная? | Некорректна технически в текущем коде: пишущий курирующий проход производит Frankenstein-записи (§2.1) и массово создаёт ложный `repo-observed` (§2.2), а «перед началом реализации» противоречит защите `has_active_task`, уже реализованной в двух местах (§2.4) |
| Будет ли смысл/толк? | **Сейчас — отрицательный.** До закрытия P0 аудита проход ухудшит стор и сделает форензику невозможной. **После P0 и в форме propose-only — да**, потому что закрывает пять классов задач, недоступных детерминированному коду (§3) |
| Если нет, то почему? | Четыре причины: ключ идентичности сливает разные утверждения; trust самосертифицируется строковой меткой; слой обслуживания держится на детерминизме и его нельзя ломать раньше, чем починен audit trail; триггер и момент выбраны против уже существующих защит |
| Если да, то как наиболее эффективно? | Propose-only куратор рядом с `CleanupJob` (не внутри), запуск в idle gap по health-сигналу (не по счётчику), закрытый enum операций с явным разделением «код применяет / человек одобряет / запрещено», выход в `curation/*/proposals.jsonl` с evidence-gate, ledger отклонений для сходимости, отдельная route-identity и конфиг. Плюс главная замена: сначала инкрементальная post-task верификация, полный sweep — вторым контуром (§4.7) |

## 6. Риски и как они закрываются

| Риск | Как проявится | Закрывается |
| --- | --- | --- |
| Laundering: модель придаёт испорченным данным опрятный вид | Frankenstein-записи превращаются в одно уверенное утверждение, следы теряются | Propose-only + ревью человека на все переписывающие операции (§4.5); P0-1 до запуска |
| Куратор как канал poisoning | Синтезированные утверждения получают `repo-observed` и durable с первого раза | Выход куратора ≤ `artifact-backed`, `assign_trust` остаётся единственным источником, promote запрещён |
| Потеря форензики | Нельзя отличить правку куратора от порчи, нельзя откатить | P1 аудита (logical-transition audit, mutation-only snapshots) до этапа 2; отдельный `AuditActor` для куратора (`audit.py:40` сейчас знает только finalizer/cleanup/operator) |
| Шум предложений и эрозия доверия оператора | Каждый проход приносит то же, что уже отклонили; отчёты перестают читать | Ledger отклонений по `proposal_hash` (§4.8) |
| Работа впустую | Повтор истории «393 из 398 snapshot'ов без мутации», но платно | Health-сигнал вместо счётчика, no-op = 0 файлов и 0 событий (§4.4) |
| Гонка с задачей | Узлы одной задачи видят разные версии памяти, восстановить нельзя | Только idle gap + `has_active_task`; никогда внутри задачи |
| Рост стора обгоняет «весь стор за проход» | На первой тысяче записей механизм придётся переписывать | Инкрементальность заложить сразу (курировать изменённое с `last_curated_state_hash`) |

## 7. Ограничения анализа

1. Read-only анализ кода на 2026-07-25 и данных аудита от 2026-07-24. Ни один прогон не запускался, память не изменялась, предложенный механизм не прототипировался.
2. Оценки стоимости курирующего прохода (100–300 тыс. input tokens, $0.2–0.6) — экстраполяция от измеренных цифр **другого** прогона (`blog-review-happy-in-my-misfortunes-4`, флоу `blog_article_revise`). Это порядок величины, не измерение.
3. `proposal precision` не измерена — её измерение и есть содержание этапа 1. Все утверждения о полезности модельного курирования до этого замера остаются гипотезой; проверяемая часть анализа — только про вред пишущего варианта на текущем коде.

5. Анализ не рассматривает V2/V3/V4 память (SQLite+FTS, embeddings, entity graph) — они заблокированы измеренным recall-lift'ом, и курирующий проход этот гейт не отменяет.
