Their `## Coverage` sections are what the deliverable's own coverage claim must be built from: a subsystem the analysis enumerated and skipped is reported as unexamined, never as clean. Under this flow's `repository_document` output policy, `{repo}/docs/research/{task_id}/` is the **only** writable path; any write outside it fails validation. Produce exactly these two files there, and write nothing anywhere else:

- `{repo}/docs/research/{task_id}/report.md` — the answer in prose. Open with a short summary of the question and the headline conclusion, then the findings, the recommended approach and its trade-offs, and an **Open questions** section for anything left unresolved or unverified.

  For a **plan-vs-implementation audit**, structure the body by whatever unit the project's own plan uses (phase, milestone, epic), findings ordered by severity within each unit, and give each finding: what is wrong or thin, the `path:line` evidence, the plan clause it violates, why it matters, and a concrete remediation pointing at where it should be closed. Keep a dedicated **Cross-unit gaps** section for earlier work left partial pending a later unit and never revisited. Use the project's own vocabulary consistently if it maintains a glossary.

- `{repo}/docs/research/{task_id}/sources.json` — the citation manifest: `{"sources": [ ... ]}`, one entry per claim that cites the repository. Each entry is `{"id": "...", "claim": "...", "path": "<repo-relative file>", "line": <1-based int, optional>, "snippet": "<exact text expected at that location, optional>"}`. For an external reference use `{"id": "...", "claim": "...", "url": "..."}` instead of `path`. For a plan-vs-implementation finding, cite both the code location _and_ the plan clause it's measured against — a claim that "the code diverges from the plan" needs a citation to each side.

Where a claim can be **checked** rather than cited, check it: you have a shell, so a crash, a wrong exit code, a regular expression that misbehaves on real input, or a test that does not cover what it claims can be settled with one command — the project's own test suite, its command-line entry point, or a one-liner (`node -e`, `python -c`) rather than a file, since anything written in the report directory ships in the pull request. Say in the report which findings were reproduced and which rest on reading alone; a finding you confirmed by running it is worth stating as confirmed, and one you could not is not. Never weaken, stub, or "fix" anything to make a reproduction work.

Every repository citation must point at a real file whose snippet is actually present — a citation to something that does not exist will be rejected. Two things the deterministic check now grades that are easy to get wrong: the `line` must be the line the `snippet` is genuinely on (a real quote on the wrong line is reported as a mis-attribution, not accepted), and an entry with **no** `snippet` cannot be verified at all — it is recorded as unchecked, so quote the text whenever you cite a location. If a verification round flags a citation as broken or mis-attributed, correct it to the real location, or drop the claim and record it under **Open questions** as unverified; do not invent sources, and do not overstate a suspected issue as a confirmed one. Do not modify any source file. Return the typed structured result required by the output schema.
