# `security` and `validation` — the guardrail blocks

**You are an operator (or an agent helping one) configuring wastech-orchestrator.** This page documents the two blocks that decide what an agent may reach: `security` (environment allowlist, isolation, read-deny paths, denied commands, the dangerous-diff approval threshold, protected paths) and `validation` (the hardening gate every task file passes before a branch exists).

For the fields not on this page see [reference.md](reference.md), which also carries the cross-field rules that apply across blocks; for the how-to walkthrough see [README.md](README.md) and for safe defaults [best-practices.md](best-practices.md).

## `security` — the guardrail block

| `security.strict_isolation` | bool | dataclass/loader `true` / **install writes `false`** | — | `false` **is the advanced mode** described below, and it is the posture a fresh install writes into your `config.yaml`. `true` is the fail-closed sandbox, and it is still what a config that OMITS the key gets. Fail-closed sandbox: preflight (and the run) fail when a provider's configured isolation cannot be enabled — at **either** value of this key, because what is checked is whether the provider's configuration is legal, and `false` is the setting where the generated profile carries the whole local floor. The declaration and this switch are both required: a flow can express the need but cannot grant itself the capability, and turning this on hands a shell only to the nodes that asked, never to every read-only node in the run — on the shipped default. ### How the isolation claim is actually proved

Two of these fields — `strict_isolation` and `disable_read_isolation` — describe a policy. Whether the operating system honors it on *your* host is a separate question, and the orchestrator answers it with probes rather than with claims.

- **Before every Codex attempt** — an agent node, an evaluator and the supervisor's own read-only turn alike, since all three get a shell there — the adapter re-runs the exact permission profile it is about to launch under `codex sandbox` (no model, no network) and checks that the private control home is unreadable, that the exchange is read-only, that the CLI binary itself **executes** under the profile (`codex --version` inside the sandbox — the same re-exec shape `apply_patch`'s fs sandbox helper uses, and the one capability every read probe misses; a refusal there fails the attempt as a configuration error, never as a host gap, because the capability provably exists and only the profile can be taking it away), and that a write into each Git-control root — the gitdir, the shared common dir of a linked worktree, the hooks dir and the `tasks/` tree — is refused. A write that lands is a security violation: the attempt fails before the model is called, and the file the probe created is removed. A probe that cannot run at all is reported as a host capability gap, never as a pass.
- One asymmetry worth knowing: when a declared Git-control root has **no directory on disk** (a repository with no `tasks/` tree, say), `worc preflight`'s battery reports the whole fixture as `NOT DEMONSTRATED`, while a real attempt logs a warning naming that root and runs the remaining probes. That is deliberate — an attempt must not be refused because a directory it never needed is absent — but it does mean the warning is the only place that root's deny is ever discussed, so read it as "this one was not proved", not as "this one held".
- One thing that battery does **not** prove, said plainly: whether a hook declared in your own `$CODEX_HOME` could execute during an attempt. Two measures stand against it — every Codex launch carries `--ignore-user-config`, and the clone's own config layer is marked untrusted — but no free probe reaches the question, because `codex sandbox` runs one command and no agent turn, so no hook event ever fires in it. Proving it needs a billed `codex exec` turn against a planted hook, and until someone runs that, treat the two measures as the reason to believe it rather than as a demonstration. Note also that on the shipped default the `hooks` feature itself is left enabled (read-isolation off means native discovery stays on), so the flag is not doing that work.
- **`worc preflight`** additionally runs the same battery against a throwaway fixture, so you learn before a run that this host cannot enforce the profile. It also prints one `<provider>-binary:` line per configured provider — the launch path, the real file behind it after following symlinks, and whether that file lies inside the provider's config home. Purely informational, never a failure: the standalone-package layout (Codex keeps its binary inside `$CODEX_HOME`) is the one fact that explains why the same build behaves differently on two hosts, and learning it should not require reading a failed attempt's stderr.
- **`worc preflight --paid-isolation-probe`** adds the one probe that cannot be free. Claude builds its sandbox inside its own session and offers no way to run a command under it without the model, so the only honest test is to let an agent try: one real (billed) call per supporting provider asks it to write into the two Git directories, the control home, and one allowed path inside the workspace. The verdict is read from the filesystem afterwards, never from what the model said it did. Because it costs money it is never implied — no run, and no plain `worc preflight`, spends it. It leaves its evidence behind: `.worc/preflight/claude-paid-isolation-probe.json` records the per-path verdicts and the model's own last message (redacted), which is the only way to tell "the sandbox refused" from "the model never tried" when the verdict is `NOT DEMONSTRATED`.

One rule is shared by all of them and worth knowing before you read a report: **"nothing was written" is not a pass.** If not even the allowed control file appears, the probe cannot tell an enforced sandbox from a model that never attempted the write, so it reports `NOT DEMONSTRATED` — a warning when another provider can cover the work, a preflight failure when none can. A proven leak is always fatal.

### `strict_isolation: false` — the advanced mode, and the floor under it

There is one door, not a matrix: `strict_isolation: false` **is** the advanced mode. It means "full freedom for the agent under your responsibility, except the floor", and it is worth reading what each half of that sentence buys.

What it relaxes. Read-isolation is forced off, and the parent environment is forwarded **whole** to every process run on the agent's behalf — the agent CLIs, the check commands, the dependency scanners, the tool nodes — so `allowed_environment` is not consulted for any of them. Two things it still withholds: the names your `.worc/.env` defines (the agent is denied reading that file, so forwarding its contents would route around the deny — name one in `extra_environment` to get it back), and anything `extra_environment` assigns, which still wins on top. The orchestrator's own `git` and `gh` keep the allowlist: the mode widens what the *agent* may do, and those processes are not the agent — a `GH_REPO` from your shell would otherwise retarget a pull request, and `GIT_DIR` would move both the commands and the paths the write-guard protects.

Beyond the environment it opens three more axes, and all three are worth reading before you switch the key. **Tools:** no allowlist reaches the agent CLI, so every built-in tool exists and every node has a shell — read-only ones included. **Write:** the agent writes anywhere the sandbox reaches rather than only inside the clone, which is what makes `dotnet build` find `~/.nuget` and `npm ci` find `~/.npm` with no cache redirection on your part — and, said plainly, includes a directory on `PATH`, which is the right to replace an executable that later runs *outside* the sandbox, this orchestrator's own `git`/`gh` among them. One limit on that width: the grant is anchored at the workspace path's own volume, so a second drive (Windows `D:`) stays unwritable. And one width that has to be said out loud, because it is the opposite of what a reader expects: the agent CLIs' own config homes (`~/.claude` / `$CLAUDE_CONFIG_DIR`, `$CODEX_HOME`) are protected by NOTHING in this mode — not write-denied, not read-denied, at every value of every key, and there is no setting that restores a deny. Credentials live there (`$CODEX_HOME/auth.json` is a file on disk; Claude's token on macOS sits in the Keychain, elsewhere in files), and so does configuration the CLIs load on their own next start — hooks in `~/.claude/settings.json`, MCP server commands in `$CODEX_HOME/config.toml` — so an agent that writes there has planted code that runs outside any sandbox later, and an agent that reads there can exfiltrate a token over the network this mode grants. That is an accepted cost of the mode, of the same nature as floor levels 3 and 4 below, and it is deliberate: a whole-home deny protects a directory where the need is per-file, and it breaks the CLI outright — the standalone Codex package keeps the `codex` binary itself inside `$CODEX_HOME`, and denying that home stops its own `apply_patch` sandbox helper from executing, so no patch lands at all. What holds instead: the orchestrator's own private set (`.worc`, the resolved env-file, the frozen `runs/` tree) stays denied on both providers, name-based redaction still scrubs secrets from logs and artifacts, and the publication mandate is unchanged. **Network:** every node is online whatever its flow granted, and that is three surfaces rather than one boundary — the sandboxed shell, the CLI's own `WebFetch`/`WebSearch` (which do not pass through that sandbox), and Codex's `web_search` (which runs on its backend, outside the permission profile). There is no domain filtering and none is planned: an allowlist that has to pass `github.com` for ordinary dependencies holds nothing, and on Codex a domain list is not enforced at all without an experimental feature that ships disabled.

What it does not do. It unlocks no provider full-access mode — those are forbidden at every value of the key. It skips no proof: the config-legality check and the per-provider capability probes run at either setting, because in this mode the generated permission profile is the whole local floor, which makes it the last configuration to excuse from demonstrating it.

**The floor, in four levels.** `worc preflight` and the run log announce the mode in **one line**, and that line points here rather than reciting all four levels into every report and every run log — which is how a loud line stops being read. Levels 3 and 4 are the ones worth deciding about before you keep the key.

1. **The integrity of the task's own state is held mechanically.** The clone's `.git` and the private `.worc` stay unwritable — wherever this host can enforce a sandbox at all. Where it cannot (native Windows; Linux/WSL2 without `bubblewrap`+`socat`), preflight says so on its own line, and then this level is not held either. One qualifier belongs here, because the write grant above is volume-wide: what keeps these paths out of it is the carve-out being the *more specific* rule. Codex re-proves exactly that before every attempt, under its own sandbox and without a model — a write into the gitdir, the common dir, the hooks dir and `tasks/` has to be refused or the attempt fails before the model is called. Claude offers no such probe, so there this level rests on the tool-level write denies — the full editor set (`Write`, `Edit`, `MultiEdit`, `NotebookEdit`), which never passes through the sandbox and holds regardless. A `denyWrite` nested inside an `allowWrite` is a **first-class construction of the vendor's own** — its settings compiler carries the carve-outs as `denyWithinAllow` and applies them inside the allowed set — but that is read out of the pinned binary, **not proven on this host**, so it is still recorded as an open live probe rather than assumed. One environment variable changes the answer outright: with `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` set, that CLI filters a volume-wide `allowWrite` out of the settings file by name, so the write grant quietly does not apply — in this mode your shell's environment reaches the agent whole, so `worc preflight` warns when it finds that variable set. You can settle it on your own host if you want to: `worc preflight --paid-isolation-probe` with the mode on launches under exactly that settings file, so its verdict is an answer about your machine rather than about the documentation. It asks for two attempts on each path — the file-writing tool *and* a shell command — because only the shell one tests the nesting, and its verdict says which of the two it actually got: a pass where the model never reached for a shell is stated as resting on the tool denies, not as the answer. Read the per-path rows in `<private home>/preflight/claude-paid-isolation-probe.json` for the same thing in detail. It costs one model call, which is why nothing implies it. The same set is wider than the two names suggest — the resolved env-file and the frozen `runs/` tree are write-denied by name too — and it is also narrower in one place worth naming: the agent CLIs' own config homes (`~/.claude`, `$CODEX_HOME`) are NOT in it, held by nothing at this level; what that costs and why it is accepted is stated in the write axis above.
2. **Publication to your origin is not held, and is not detected either.** A branch that appears or moves on `origin`, and a pull request that appears on the task head, are ordinary working state: neither parks a run, and neither is checked against the orchestrator's own records. What happens instead is recovery — a diverged remote is merged in locally, the checks re-run over the combination, and only then does anything go out; an open pull request on that head is appended to and adopted. Only a merge conflict or failing checks over the adopted combination stop the run. One consequence worth knowing before you share a branch: a pull request **you** opened on the task branch is retitled and appended to like any other.
3. **Publication anywhere else is held by nothing**, and it is reachable today: the agent has the network. Credentials are picked up automatically and are not withheld — `gh` reads its own `hosts.yml`, `git` over HTTPS reads your `credential.helper`, over SSH your key — so a repository assembled outside the clone and pushed to any address is neither prevented nor noticed. Nothing is planned to hold this. What is asked instead is stated in the prompt every node receives: no commit, push, merge, tag or pull request, to this repository's remote or any other address, by any route.
4. **Publication as the orchestrator is reported by detection, not held by it.** The agent does not publish and does not touch `.git` — it replaces what the orchestrator publishes *with*. Three measures answer it: your user git config and the clone's own agent-CLI config are fingerprinted around the attempt, every `gh` call names its repository outright, and the executables the orchestrator launches (`git`, `gh`, the agent CLIs, `ps`, the daemon launcher) are resolved once at startup and used as those paths for the rest of the process — so a program planted on `PATH` while the agent works does not change what the orchestrator runs.

   Say the word **reported** literally, because this is the level where it costs the most. Drift never stops the run, on any node class: a planted hook, a rewritten `pushurl` and a swapped binary on `PATH` are a loud warning and a ⚠️ trace, and then the run keeps going — which means the orchestrator's own next git command executes in that clone. The reason is that the fingerprint reads "the state moved", never whose hand moved it, and in practice what it catches is an operator committing a neighbouring file in their own repository — parking there costs a finished node's work for nothing. **What that asks of you:** the drift warning is a stop-the-run signal, not a note. If you did not do it yourself, stop the run and discard the clone before anything is committed or pushed.

Two things that last measure does **not** cover, and cannot: a substitution made **between** runs (each run resolves fresh, so a stand-in already in place is simply what gets pinned), and an edit to the **installed package's own code** — pinning the launcher answers "which `worc`", never "whose `git_manager.py`". If the machine's `PATH` directories or the installed package are writable by something you do not control, this mode is not the place to start.

**Redaction widens to compensate.** With the name gate gone, a secret-named environment variable is scrubbed from logs and artifacts by its **name** alone, without the allowlist excusing any — that is the layer that catches a secret with no recognizable shape, and it would collect nothing here otherwise. The accepted cost: a secret-named variable holding something harmless can appear as `[REDACTED]` in output. `PWD` and `OLDPWD` are exempt by name, because they match on the `pwd` segment while holding a path, and scrubbing them turned every `file:line` citation into `[REDACTED]/src/foo.py:42`.

**Where the run's posture is recorded.** Two places, dividing the timeline rather than backing each other up: the frozen control bundle's `manifest.json` records the mode the task **started** in (written before the first node runs, so it is there even for a task that never reached a terminal transition), and the completed ledger's record carries `advanced_mode` for a task that **finished**. A successful run sweeps its own `runs/` subtree, so the bundle is gone exactly when the ledger record exists. There is deliberately no marker in the pull request: from a merged PR detached from the machine you cannot tell which mode produced it — only `.worc/logs/completed.jsonl` on the host that ran it can answer that.

### What the per-attempt fingerprint watches

Around every provider attempt the orchestrator fingerprints the Git control surfaces and compares them afterwards. A change is **reported and never parks the task** — see level 4 above for what that costs and what it asks of you. Three parts of the fingerprint are worth knowing because they are not inside the clone's `.git`:

- **The remote side — only where a push would go.** Denying the agent write access to `.git` stops only one publishing operation out of four, so the fingerprint reads one remote fact: the URL a push actually resolves to (`remote get-url --push`, kept as a digest since it can carry a token). A rewritten `insteadOf`/`pushurl` would otherwise send the branch, with this orchestrator's credentials, somewhere you did not choose. What is deliberately **not** read: what `origin` holds for the task branch, and whether that branch has an open pull request. Reading them would mean treating a branch or PR the orchestrator has no record of as someone else's, and that does not hold — a recreated `state.db` has no records at all while the branch and its PR are still yours — while publishing recovers from a diverged remote properly anyway (it merges the foreign commits in locally, re-runs the checks over the combination, and only then pushes). So a branch appearing or moving on `origin`, and a pull request appearing on its head, are ordinary working state. The **base** branch is not watched either: it moves legitimately whenever someone merges their own PR.
- **The agent's own CLI configuration.** The shipped defaults load the clone's `.claude/settings.json`, `.mcp.json` and `.codex/` on purpose — that is how hooks and MCP servers reach the agent — and the orchestrator's own git commands read your user git config (`~/.gitconfig`, `~/.config/git/config`). Each hands out code execution or redirects a push, so all of them are fingerprinted. They are kept as content digests, never values: these files carry tokens and key paths, and a drift report names the file, never what is in it. Editing one mid-run is reported like every other aspect — which for the clone's own `.codex/` is usually you, since the shipped defaults load it on purpose.
- **Where `gh` points.** Every `gh` call carries `--repo`, pinned from `repo.url` (or, when that names no hosted repository, from the clone's `origin` read once before any agent runs). Without it `gh` infers the repository from the clone, which is exactly the surface being watched. When neither can be parsed into `owner/name` — an ssh alias, a `file://` URL, a local path — there is no pin at all, on any call, including the probe that decides which pull request this task appends to; `worc preflight`'s `gh-repo-pin` line says so out loud rather than letting the guarantee switch off quietly.

A push additionally re-reads its destination immediately before sending — the one moment an error reaches a real branch — and refuses when it changed.

### What the dangerous-diff gate measures from

`trust_level` decides *which* diffs raise the approval gate; this is *what* the diff is measured against. The reference point is the last commit the orchestrator itself made for the task — or, until it has made one, the task's base. It is deliberately not `HEAD`: a commit made inside the task would then leave nothing for the gate to see, and the one question you are asked before publishing would go quiet exactly when something unusual happened. So if an agent commits its own work mid-run, its content still reaches the gate and you are still asked.

**Where you are asked** is three places, and the third is the one that makes the promise hold for every flow: at a writing node after its edit, at that node's `hitl` round-trip on the way back, and once more immediately before the publishing commit. The last one exists because any node with a shell can commit — a `tool`, an `evaluator`, a read-only agent attempt, and in this mode that is every node — and none of them parks over it, so a flow that ends with one (or has no writing node at all, like `security_audit`) would otherwise reach publication with content nobody had been asked about. Because drift never parks the run, this measurement is not a second line of defence behind it: it **is** the thing that holds a commit made inside a run, whoever made it. A denial there is a stop, not a retry: the agent is gone by then, so nothing is committed or pushed and the task parks for you. An approval you already gave earlier in the same task for the same change is not requested twice.

Two consequences worth expecting:

- In a decomposed task, deletions you approved on the first subtask are not put to you again on the second — the reference moves with each subtask commit — while the run's reported diff and the pull-request body still describe the whole task.
- If the state being published contains commits the orchestrator did not make, it says so in the log **and in the pull-request body**, and records the adopted commit rather than reporting a commit it never performed. The same happens per subtask in a decomposed run. The change itself has passed the gate; the commit message and authorship are whoever made them.

A node that asks you a question mid-run (`hitl`) and also writes goes through this gate like any other writing node. If you have such a node in a flow, expect an approval request where earlier there was none: asking a question was never meant to be a way past the gate.

## `validation` — input hardening gate

Rejects a malformed task **before** any branch or agent runs.

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `validation.max_task_bytes` | int | `262144` | Reject a task file larger than this. |
| `validation.max_task_lines` | int | `5000` | Reject a task file with more lines. |
| `validation.max_line_bytes` | int | `8192` | Reject any single line longer than this. |
| `validation.max_control_ratio` | float | `0.01` | Reject if control/binary chars exceed this fraction (0.01 = 1%). |
| `validation.quarantine_folder` | string | `"./.worc/tasks/rejected"` | Where rejected task files are moved. A relative path is resolved against `repo.local_path`, not the working directory, so it lands in the same place wherever `worc` was launched from. |

Two things this block does **not** control, because they are not the operator's to relax (the keys that pretended to be were removed in config v35 — `upgrade-config` strips them): the required front matter (`id`, a non-blank `title`, and a non-empty `Description` section) and the deny on an unrecognized front-matter key. Both are hard-coded in the task gate. `id` becomes a branch fragment, a run directory, and a state-store key, so dropping it would break identity rather than loosen a policy.
